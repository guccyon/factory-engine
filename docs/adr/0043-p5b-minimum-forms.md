# ADR 0043: P5b（Operate）の各項目を Gen1 の最小の形で 1 本ずつ通す

- 状態: 案（2026-11-08。範囲はオーナーがカードで「最小の形で全項目を 1 本ずつ」を選択し、届かない分は Gen1.5 に持ち越してよい。決めどころ O1〜O9 の中身はオーナーの承認待ち）
- 関係: ADR 0012（出荷）、ADR 0013・0023（Learn ループ・学習の体系。合成の利用者）、ADR 0024（知見と委員会）、ADR 0028（QA と実行環境。P5 の 2 段）、ADR 0030（窓口。順番 4 の回答役）、ADR 0032（報告の出し分け）、`definitions/roadmap.yaml` の P5b、`definitions/quality_policy.yaml`

## 文脈

2026-11-08 オーナー: P4 と P5 を今週中に完了まで持っていき、Gen2 の準備を始めたい。

P5b の 9 項目は、方向は ADR 0023・0028・0030 で決まっているが、Gen1 で「何をもって 1 本通したとするか」の形が決まっていない。項目ごとに ADR を切ると承認の往復が 9 回になり今週に収まらない。そこでこの ADR で 9 項目の最小の形をまとめて決め、承認のあとは項目ごとに実装して自動マージする（承認済み ADR の実装）。

前提:

- rally は development の段階で本番を立てない（ADR 0012 の追記）。本番が要る項目（Incident、KPI、SLI）は staging と合成の利用者で代える
- Gen1 は精度よりカバレッジ。各項目は「回路が端から端までつながり、1 本通った記録が events に残る」までで済とする。精度と運用の厚みは Gen2
- ラインはワーカー 1 で止まっていることがある。P5b の仕事は窓口の枠・supervisor の定期の仕事・QA の枠で動き、ラインのワーカーを奪わない形を優先する

## 決定（案）

### O1. Answer ライン（`answer_line`）

ADR 0030 の順番 4 をそのまま作る。窓口の問い合わせを回答役（`answer`）が受け、立場（計画・工場長。ADR 0030 の W4）を選び、根拠（参照した記録の id）つきで答える。曖昧なら問い返しを 1 回まで挟む（clarify と同じ形）。読むだけで工場を変える操作は持たない。

- 済の条件: 窓口の MCP から実際の問い（例「今週の P4 の残りは」「#xxx はなぜ止まっている」）を 1 本流し、問い返し → 根拠つきの回答 → `desk.answered` が残る
- 動く枠: 窓口（`desk`）。ラインが止まっていても答える

### O2. Report ライン（`report_line`）

既存の開発状況レポート（`report.product`、ADR 0032）に週次の Routine を足す。週に 1 回、製品の KPI（Gen1 は合成の利用者と staging の行動ログから出す、O4）を集計し、前週や予測から外れた値を「異常」として Opportunity（窓口の相談と同じ下書きの型）に起こし、受信トレイに出す。起票はしない（人かプランナーが拾う）。

- 済の条件: 週次の集計が 1 回出て、異常 1 件が Opportunity の下書きになった
- KPI は仮置きで 3 つ（予約の完了率、動画の添削の返却までの時間、月額契約の継続）。値は運用パラメータとして工場が調整してよい

### O3. KPI の予測誤差を教師信号に（`kpi_error_signal`）

チケットが閉じるとき、プランナーが Requirements の `success_definition` に「どの KPI がどれだけ動くと見込むか」を 1 行書く（任意）。週次の Report が実測と突き合わせて誤差を `kpi.forecast_scored` に残し、Learn の教師信号（テーマ 1）の 1 種として束ねる。

- 済の条件: 見込みを書いたチケット 1 件について、誤差が `kpi.forecast_scored` に残り、`learn.retrospected` の束に入った
- 合成の利用者の値なので誤差の中身には意味がない。回路の確認に限る

### O4. 合成の利用者のループ（`synthetic_users_loop`）

ADR 0023 の決めどころ 3。QA 役の探索（P5a の `nightly_explore`）の道具を流用し、ユーザーストーリーに沿って合成の利用者が staging を一定量歩き、行動ログ（`specs/analytics/events.yaml` の名前）と応答時間を残す。わざと仕込んだ詰まり（遅い API 1 本、見つけにくい入口 1 つ）を見つけ、改善の提案（Opportunity）まで出る 1 周を確かめる。

- 済の条件: 仕込みの 2 つのうち 1 つ以上が提案になった（テーマ 1・2 のどちらか）
- 仕込みは staging だけに、環境変数で入れる（製品のコードに入れない）

### O5. 障害の重要度とエラーバジェット（`severity_budget`）

- `quality_policy.yaml` に S2〜S4 の条件とエラーバジェット（期間と S ごとの許容件数）の欄を足し、rally の値を建設者が仮置きする（`provisional: true`。緩める変更は人の承認のまま）
- Incident（ADR 0028 の決定 5）を events に足す。Gen1 は staging で起きたものを対象にする
- S1 は QA 役がラインを差し止める（ADR 0028 の方針）。差し止めは新しい `line.held_by_qa` で、解除は人。ラインの一時停止とは別の札にする
- 済の条件: 演習で S1 を 1 回起こし（staging に個人情報が見える画面を仕込む）、QA 役が Incident を S1 で残してラインを差し止め、人が解除した

### O6. 定期便（`release_train`）

出荷（ADR 0012）を「マージのたびに staging」から「便」に変える。Gen1 は 1 日 1 便（時刻は運用パラメータ、既定 JST 18:00）で、その時点のマージ済みの変更を 1 つの Release にまとめ、人の承認は便ごとに 1 回（受信トレイ）。S1 の修正だけは緊急便として待たずに出す。

- 済の条件: `release.train` が 3 便（緊急便 1 を含めるのが望ましい）
- staging への出し方は今のまま。便は「承認の単位」と「Release のまとめ方」だけを変える

### O7. PR ごとの使い捨て環境（`ephemeral_env`）

触れる環境（P5a の `touchable_env`）の仕組みを PR の単位に広げる。Mac の docker で compose のプロジェクト名を PR ごとに分け（`rally-pr-<番号>`）、合成シードを入れ、QA 役か人が触ったあと、PR が閉じたら壊す。同時に立てるのは 2 つまで（運用パラメータ）。

- 済の条件: PR 1 本で立つ → 触る（QA の Verdict か人のアクセス）→ PR が閉じて壊れる、が events に残る（`env.ephemeral_up` / `env.ephemeral_down`）

### O8. 日中の並走と TestFlight（`preview_distribution`）

ADR 0028 の決定 6 のとおり、配布は出荷側のアダプタ。署名と提出はオーナーの Mac のキーチェーンで、Mac ランナーに「署名つきのビルドとアップロード」の道具を、attended のときだけ足す（人が Mac の前にいる合図でだけ通る）。鍵は工場に預けない。

- 済の条件: TestFlight に 1 本配った（オーナーの操作は Mac での承認 1 回）
- これはオーナーの手が要る唯一の項目。日時を合わせて 1 回で済ませる

### O9. 品質の Learn（`quality_learn`）

Defect（P5a の `defect_metrics`）と Incident（O5）を入力に、週 1 回、発見工程の分布と出やすい場所を集計し、

- QA の重点（どのストーリーを厚く流すか）とシナリオの追加を自動で行う（QA 役の入力の更新。工程は変えない）
- 基準の変更（`quality_policy.yaml` の値）は案として委員会（ADR 0024）に出すだけ

- 済の条件: 1 周回り、シナリオが 1 本自動で足され、基準の変更案が委員会に 1 件出た

## 順番

1. この ADR の承認
2. 前提の P5a（`nightly_explore`・`defect_metrics`・`scenario_time`）を先に。O4・O9 はこれを使う
3. ラインを使わないもの（O1 Answer、O2 Report、O5 の欄と演習、O6 便）から並行に。各項目は別スレッドで実装し、自動マージ
4. O3・O4・O7・O9。O8 はオーナーと日時を合わせて 1 回

### 持ち越し（2026-11-08 オーナー）

今週はできるところまで進め、残りは Gen2 の前に置く Gen1.5 に持ち越してよい。今週は順番 3（O1・O2・O5・O6）を先に済ませ、順番 4 は手が届いた分だけ。持ち越した項目は roadmap の P5b に todo のまま残し、Gen1.5 の計画で拾う。

Gen1.5 は既存プロダクト（運用中・backend / mobile / IaC の複数リポジトリ）を工場に載せるオンボーディングを作る段（2026-11-08 オーナー。Gen2 のパイロットの前提）。O6 定期便・O7 使い捨て環境・O8 TestFlight は今の形だとリポジトリ 1 つの rally を前提にしており、複数リポジトリで作り直しになりやすい。そこでこの 3 つは今週は回路の確認に留め（便・環境・配布の単位を Release の束として持てる形にだけしておく）、本番の形は Gen1.5 のオンボーディングの設計に合わせて決める。O1・O2・O5 はリポジトリの数に依らないので今週そのまま作る。

## 承認が要る点（変わる線）

- O5: QA 役にラインを差し止める裁量を実際に持たせる（ADR 0028 で方針は承認済み、実装の形はここで）
- O6: 出荷の承認の単位が「Release ごと」から「便ごと」に変わる
- O8: 外の機械（オーナーの Mac）で署名つきの操作をジョブから呼ぶ

## 選ばなかった案

- 項目ごとに ADR を切る: 承認の往復が 9 回になり、今週に収まらない
- P5b を Gen2 に回す: Gen2 の設計の入力（Operate の回路の手触り）がないまま設計することになる
- 本番を立てて Incident・KPI を本物で取る: rally は development で本番を動かさない（ADR 0012 の追記）。合成の利用者で回路を先に作る（ADR 0023 の決めどころ 3）

## 結果

- P5b の 9 項目は、すべて「回路が 1 本通った」までで済になる。精度・量・本番の信号は Gen2 の範囲として残る
- オーナーの手が要るのは、この ADR の承認、O5 の S1 の解除、O8 の TestFlight の 1 回
