# ADR 0035: 工場の前段に GitHub ログインを置く（パイロットの一時の囲い）

- 状態: 承認（2026-11-05 オーナー。決定「まずは前段に proxy を置く方式。後で個別のエンドポイントに認証を入れるので取り外しやすく」。OAuth は Gen2 が始まってから仕様を考える）
- 関係: ADR 0009（操業コンソール。決定 4 の閉じた網）、ADR 0030（事業部の窓口。決定 5 の認証と順番 5 のリモートの MCP と OAuth）、ADR 0034（決定 3 の Claude の入口、決定 7 の答えた人の確認、順番 6 のコンソールのログイン）、ADR 0031（更新役）、factory-engine#178（悪用の防ぎ）

## 文脈

パイロット（2026 年 12 月から）では、工場を Mac ではなくクラウド（EC2）に置く。今の工場は Mac の中で開く前提で、操業コンソールにはログインがなく、窓口（ADR 0030）は依頼者ごとのトークンを持つが `127.0.0.1` でしか待たない。

オーナーの整理（2026-11-05）:

- パイロットで工場に触れるのは 2 名。工場を運用し健康を見る人と、工場にアプリの作成を指示する事業パートナー。導入先の企業の人は工場にアクセスしない
- そのため、コンソールのログインの実装はぎりぎりまで遅らせられる。ただしクラウドに置く以上、IP 制限などで不特定多数を遮ることは要る
- パートナーは主に AI 越し（手元の Claude から窓口の MCP）で頼む。誰が頼んだかを記録できれば足りる
- Basic 認証は避け、GitHub のアカウントの OAuth で絞る。Tailscale などの私設ネットワークは将来の候補（今は設定が増える）
- 後で個別のエンドポイントに認証を入れるので、前段は取り外しやすくする

## 決定

### 1. 前段は compose に重ねる別のファイル。工場のコードは変えない

- `orchestrator/compose.edge.yaml` に、前段の 2 つのサービス（`edge` = Caddy、`oauth2-proxy`）と、前段から見える名前を足す環境変数の上書き（コンソール・窓口の開いてよいホスト名、プロトタイプの公開の URL、通知のリンク）だけを置く。`compose.yaml`・`console.py`・`desk_api.py` は変えない
- 使うかどうかは `.env` の `COMPOSE_FILE=compose.yaml:compose.edge.yaml` で決める。更新役（ADR 0031）の `docker compose up -d` も同じ `.env` を読むので、更新で前段が落ちない
- 外すときは `COMPOSE_FILE` から抜いて `up -d --remove-orphans`。Mac の工場はこのファイルを使わない

### 2. 入口は 3 つのホスト名。ブラウザの入口だけにログインを置く

| ホスト | 上流 | 確かめ方 |
|---|---|---|
| `console.<EDGE_DOMAIN>` | 操業コンソール | GitHub のログイン（oauth2-proxy。Caddy の `forward_auth` で要求ごとに確かめる） |
| `proto.<EDGE_DOMAIN>` | 動くプロトタイプの配り口（別オリジン、ADR 0026） | 同じログイン（Cookie を親のドメインで共有） |
| `desk.<EDGE_DOMAIN>` | 事業部の窓口の API | ログインは通さない。窓口のトークン（Bearer）を今どおり `desk_api.py` が確かめる |

- 窓口をログインの外に置くのは、AI 越しの口がブラウザの Cookie を持てないため。窓口は初めからトークンで守られている（ADR 0030 の決定 5）
- 通す GitHub のアカウントは `.env` の `EDGE_GITHUB_USERS` で渡す。リポジトリにアカウント名を書かない
- GitHub に求める権限は `user:email` だけ

### 3. HTTPS は Caddy が取る。IP 制限はクラウドのファイアウォールが先

- Caddy が Let's Encrypt の証明書を取り、更新する（HTTP-01。80 番は確かめの応答と HTTPS への転送だけを返す）。ロードバランサー（ALB と ACM）で TLS を終える形も `EDGE_SCHEME=http` で選べる
- 不特定多数を遮るのは EC2 のセキュリティグループ（443 は通す人の送信元だけ）。Caddy の `EDGE_ALLOW_CIDRS` は同じ制限の二重目（設定の誤りで開いても通さない）
- 前段は、利用者から来た `X-Auth-Request-*` を捨て、ログインを確かめた後だけ oauth2-proxy の値（`X-Auth-Request-User` = GitHub の login）を上流に付ける

### 4. AI 越しの口は 1 人 1 本の窓口のトークン。誰が頼んだかは窓口の記録に残る

- 窓口のトークン（`factoryctl desk token create`）を人ごとに 1 本出し、共用しない。運用主は `operator`、アプリの作成を指示する人は対象の製品を付けた `requester`
- 窓口の events（`desk.opened`・`desk.request_confirmed`・`desk.priority_changed` などの `by`、`desk.message` の `author`）にトークンの名前が残る。これで「誰が頼んだか」を追える。新しい仕組みは足さない
- 手元の窓口の MCP（stdio、ADR 0030 の順番 3）は `FACTORY_DESK_URL=https://desk.<EDGE_DOMAIN>` に向けるだけで使える

### 5. ADR 0034 との合わせ方

- **答えた人の確認（ADR 0034 決定 7）**: 写しの表に載せる身元は、パイロットでは「窓口のトークンの名前」と「前段の GitHub の login」の 2 つ。どちらも同じ人に写す（Blueprint の人の一覧）。コンソールからの答えは、コンソールがヘッダーを読むまで今どおり `by: console`
- **Claude の入口（ADR 0034 決定 3・順番 2）**: `inbox_list`・`inbox_read`・`inbox_answer` は窓口の API と MCP に足す予定なので、この前段の `desk.<EDGE_DOMAIN>` とトークンのまま届く。前段に手を入れずに足せる
- **リモートの MCP と OAuth（ADR 0030 順番 5、ADR 0034 決定 3 の「パイロットの前に OAuth に移す」）**: パイロットはトークンのままにし、OAuth は Gen2 が始まってから仕様を考える（オーナー 2026-11-05。2 名で、どちらも手元の Claude から stdio で繋ぐため）。ADR 0034 の「パイロットの前に」はこれで置き換える。OAuth に移すときの案は、MCP の認可サーバーの身元の確かめに同じ GitHub の OAuth App（か、事業主の Google Workspace・Microsoft のアカウント）を使い、身元はこの前段と同じ GitHub の login にする。人の手を介さないエージェント用にトークンは残す
- **コンソールのログイン（ADR 0034 順番 6、Gen2）**: コンソールが自分でログインを持ったら、oauth2-proxy を外し、Caddy は TLS と IP 制限だけにする（前段が付ける `X-Auth-Request-User` を読む中間の段を挟んでもよい）

## 決めどころ（オーナーの承認が要る）

| # | 問い | 推奨 |
|---|---|---|
| E1 | 前段の形 | compose に重ねる別ファイル（Caddy ＋ oauth2-proxy）。工場のコードは変えない |
| E2 | 通す人 | GitHub のアカウントの許可リスト（`.env`）。組織・チームでは絞らない（パイロットは 2 名） |
| E3 | 窓口の扱い | ログインの外。1 人 1 本の窓口のトークンで、誰が頼んだかは窓口の記録 |
| E4 | HTTPS | Caddy の Let's Encrypt（80 番を開ける）。ALB は選べるようにするだけ |
| E5 | IP 制限 | セキュリティグループが主、Caddy の許可リストが二重目 |
| E6 | Cookie | `SameSite=None; Secure`、期限 24 時間。プロトタイプの CSS・画像のため |

## 選ばなかった案

- **Basic 認証**: 多要素がなく、総当たりされやすく、合言葉を共有しがちで、誰の操作かを区別しにくい。GitHub の OAuth でも手間はほぼ同じ
- **Tailscale などの私設ネットワークに 2 名だけ入れる**: 工場をインターネットに出さずに済み、将来は良い候補。ただし利用者の端末ごとの設定が増える（オーナー 2026-11-05）
- **コンソールにログインを実装する**: 正しい終着点だが、パイロットの 2 名には早い。ADR 0034 の順番 6 で入れる
- **窓口も oauth2-proxy の後ろに置く**: AI のクライアントはブラウザのログインを通れない。窓口はすでにトークンで守られている
- **プロトタイプをログインなしで出す**: 製品の未公開の画面がオブジェクトの番号を当てるだけで見える。同じログインに入れる

## 結果

- 工場を EC2 に置いても、2 名だけがコンソールに入れ、AI 越しの依頼は人ごとに記録される
- 前段の外し方は `COMPOSE_FILE` から 1 行抜くだけ
- 新しい外の依存が 2 つ増える（Caddy、oauth2-proxy。どちらも版を固定）。証明書の更新は Caddy に任せる
- 許可リストから外した人も、Cookie の期限（24 時間）までは入れる。すぐ締め出すときは Cookie の鍵を作り直す
- GitHub の webhook（8787）とランナーの窓口（8794）は前段に入れない。EC2 ではポーリングで PR を見張り、Mac ランナーを EC2 の工場に繋ぐのは別に決める
- 触れる環境（ADR 0028 の touchable_env、`SHIP_TOUCH_*`）の画面はこの前段を通らない。EC2 で使うときはセキュリティグループで同じ送信元に絞り、前段に載せるかは別に決める
