# ADR 0056: 「QA だけ」のチケットを、プランナーの計画どおりに流す（道 verify）

- 状態: 提案
- 関係: ADR 0028（QA 役）、ADR 0037（道）、ADR 0038（ワークフローの宣言。決定 3 の飛ばせないステップ、2026-11-10 の追記「複数の役を通るタスクは必ずプランナーを通す」）、ADR 0049（出荷の QA の関門）、ADR 0054（版ごとのチケットとシナリオごとのジョブ）、ADR 0055（QA の時刻／スパイクのレーン）

## 文脈

オーナーの求め（2026-11-14）: 出荷のレーンを動かすチケットを作り、本文に「デプロイ（本番）以降の処理は行わない」と書けば、プランナーが QA 以外の手順（実装・CI・マージなど）を飛ばす計画を書き、指示役はその計画どおりに振り分ける。版を出すのを待たずに、確かめたいことだけを QA に流せる。事業部として人に提供するなら、この形の依頼をチケットで受けられないといけない。

今の工場では、これが通らない。

| 障害 | 中身 |
|---|---|
| 1. 計画の qa が QA のジョブにつながっていない | プランナーは Plan の workflow に qa の手順を書けるが、記録されるだけ。QA のジョブを積む入口は、版を staging に出したときの関門（ADR 0049）・夜の探索・合成の利用者・人の `factoryctl qa run` の 4 つで、チケットから積む入口がない |
| 2. 実装のない計画を組めない | プランナーの経路（steps の役）が空なら「経路が組めなかった」（empty_steps）で人に回る。道 ticket のひな形は 実装 → CI → 検査 → judge → マージ → QA → 出荷 → Learn の 1 本で、CI・マージ・Learn は飛ばせない（ADR 0038 の決定 3）。実装を飛ばすと、マージする PR がないまま止まる |

## 決定

### 1. 道に verify（QA だけ）を足す

ADR 0037 の道に `verify` を足す。コードを変えず、いまある製品を確かめて結果を返す道。

| 道 | ひな形のステップ | 上限の既定 |
|---|---|---|
| `verify` | stage → qa → respond → learn | QA のジョブごとの上限（ADR 0054 の決定 5）と、チケットの上限（ジョブの上限の合計 × 係数） |

- `stage`（新しいステップ、kind: handoff）: QA の前に、マージ済みでまだ版にしていない変更を staging に出す（`factoryctl env up` と同じ。版を切って staging に配備する）。出す変更がなければ何もしない
- `qa`: `scope` に流すストーリーの id を書く（空なら全ストーリー）。厚みは ADR 0038 の決定 2 の表のまま。探索（推論）は `deep` のときだけ足す（チャーター 1 つ）
- `respond`: 結果をチケットにコメントで返して閉じる
- `learn`: 信号の記録。飛ばせない（ADR 0038 の決定 3 のまま）
- 実装・CI・検査・judge・マージ・出荷は**ひな形にない**。飛ばすのではなく、この道にはもともとない

ADR 0038 の決定 3 の「CI とマージは飛ばせない」は変えない。あれは「コードを変えるなら必ず通す」の約束で、コードを変えない道には当てる対象がない。道 ticket で実装を飛ばしてマージだけ残す形にすると、マージするものがないチケットが止まる（今の障害 2）ので、道を分ける。

### 2. プランナーが道 verify を選ぶ条件

- チケットの本文が、コードを変えずに確かめることだけを求めているとき（「QA だけ」「確かめるだけ」「本番には出さない」「デプロイ以降は行わない」など）。決まった言い回しに反応するのではなく、本文の求めから読む
- 確かめたいことが、どのストーリーか（または、どの機能か）まで読めること。読めなければ `ask` で起票者に問う（ストーリーの一覧から選べる形で）
- 確かめた結果、直しが要ると分かったら、それは QA の起票（`factory:qa-defect`）が別のチケットにする。verify のチケットの中で直さない
- 決定論の守り（guards）: 道 verify なのに経路に役（デザイナー・実装役）があれば、人に回す（`verify_with_roles`）。道 verify では経路が空でよい（empty_steps に当てない）

### 3. 指示役が計画どおりに QA を積む

プランナーが道 verify で `ready` と判定したら、dispatcher はチケットに `factory:qa-ticket` を付ける。指示役（supervisor）は周回ごとに、このラベルのチケットを次の順で進める。判断は持たず、計画を読んで数えるだけ（ADR 0004）。

1. **stage**: `run: true` で、マージ済みで版にしていない変更があれば、版を切って staging に出す。出した版には今までどおり出荷の関門（ADR 0049）が開き、全ストーリーが流れる。このチケットは**その関門の結果を使う**（同じ版を 2 回流さない）。チケットに版の QA のチケット（`QA: <版>`）へのリンクを書き、関門の報告が出たら、`scope` のストーリーの結果を抜き出して返す
2. **qa**（stage で新しい版を出さなかったとき）: いま staging にある版に対して、このチケットを入れ物にした関門を開く。ADR 0054 の形のまま、`scope` のストーリー 1 本につき 1 ジョブ（判定）、`deep` なら探索 1 ジョブを、このチケットに単位（jobs.unit）を付けて積む。時刻をまたぐストーリーは、ほかが終わってから 1 本ずつ（ADR 0055 の決定 3）。確かめられなかった単位は 1 回だけ積み直す
3. **respond**: 結果がそろうか、開いてから `gate.hours` で、報告（ストーリーごとの結果、見つけた不具合と起票した Issue、確かめられなかったもの）をチケットにコメントし、チケットを閉じる。窓口から来た依頼なら、窓口の返し方（ADR 0037 の done.task）で依頼者にも返す
4. **learn**: `plan.outcome` に、宣言（scope・厚み・上限）と実績（流した本数・費用・結果）を残す

チケットの関門は、版の関門とは別のもの（記録の鍵は `qa_gate:ticket:<repo>#<番号>`）。

- 承認とつながない: 受信トレイの「本番待ち」に出さない。prod へは何もしない（オーナーの「デプロイ以降の処理は行わない」）
- 途中で staging の版が替わっても、置き換え（superseded）にしない。報告に「流した間に版が替わった」と書く
- 009_job_unit.sql の前の DB では、`scope` の全ストーリーを 1 ジョブで流す（今の固定 Issue の形）

### 4. 費用と上限

- ジョブごとの上限は ADR 0054 の決定 5 のまま（判定 40 ターン・$3、探索 80 ターン・$5）
- チケットの上限は「積むジョブの上限の合計 × `ticket_cap_factor`」を工場が決定論で決める。プランナーは caps でそれより低くできる（天井は ADR 0038 の `ticket.cost_usd` の天井 $30）
- 上限に当たったら、残りを積まず、そろった分で報告する。人への停止は開かない（ADR 0054 と同じ。結果が返らないほうが困る）
- 1 日の合計は予算の枠（ADR 0029）で抑える

### 5. 見せ方

- プランナーの着手のコメントに「経路: QA だけ（実装はしません）」と、流すストーリー・探索の有無・stage の有無・上限を書く
- `factoryctl plan show` と操業コンソールのチケットの一覧で、道 verify のチケットを見分けられるようにする

## 決めどころ

| # | 問い | 推奨 |
|---|---|---|
| V1 | 実装のない計画をどう通すか | 道 verify を足す（決定 1）。道 ticket の「CI・マージは飛ばせない」は変えない |
| V2 | QA の前に最新を staging に出すか | stage を持つ。プランナーが本文から決める（既定は出す）。出した版は版の関門の結果を使い、同じ版を 2 回流さない（決定 3 の 1） |
| V3 | 本番との関係 | 承認・本番には一切つなげない。結果をチケットに返して閉じる |
| V4 | 探索を流すか | `deep` のときだけ。既定は判定（ストーリーどおり）だけ |

## 順番

1. この PR: 本 ADR（提案）
2. 承認後の実装 1: `definitions/workflow.yaml` の道 verify とステップ stage、`core-gates/plan.py` のプロンプトと守り（verify_with_roles、道 verify の空の経路）、dispatcher の `planner.act` の道 verify（`factory:qa-ticket`）
3. 実装 2: `qa_gate.py` のチケットの関門（stage・単位を積む・報告して閉じる）と supervisor の周回。テスト
4. 済の条件: rally に「QA だけ」のチケットを 1 件立て、プランナーが道 verify で計画し、QA のジョブがそのチケットに積まれ、報告が付いてチケットが閉じる。実装・マージのジョブが 1 つも動かない

DB の変更はない（ADR 0054 の 009_job_unit.sql を使う。当たっていなければ 1 ジョブの形で動く）。

## 選ばなかった案

- **道 ticket で、実装がなければ CI とマージを飛ばしてよいことにする**: 同じことはできるが、「コードを変えるなら CI とマージは必ず」という安全の約束に例外の条件が入る。条件の判定を誤ると、コードの変更が CI を通らずに流れうる。道を分ければ、約束はそのままで済む
- **窓口の決まった操作に「QA を流す」を足す**: 軽いが、プランナーを通らない。何を流すか・どこまで厚くするか・上限を、計画として残せない（ADR 0038 の 11-10 の追記に反する）
- **プランナーを通さない入口のラベル（`factory:qa-request`）**: 同上
- **チケットの QA も版の関門として開き、承認につなぐ**: 「本番には出さない」という依頼の趣旨に合わない。版の関門は定期便と緊急便のもののまま

## 結果

- 「この機能を今の staging で確かめて」という依頼を、チケット 1 枚で受けられる。実装やマージの手順は動かない
- 計画の qa の手順が、初めて実際の QA のジョブにつながる。道 ticket の qa（マージ後にチケットごとに流す）を入れるときも、同じ配線（チケットの関門）を使える
- 道が 1 つ増える。プランナーのプロンプトと評価セット（ADR 0036 の 4b）に、verify を選ぶべき件・選んではいけない件を足す
