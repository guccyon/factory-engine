# ADR 0057: 本番を立てた製品を運用する最小の形（見張り・自動の戻し・出す前の DB の控え）

- 状態: 承認（2026-11-14 オーナーがカードで「推奨どおり進める」を選択。rally の段階を launch に上げるのも同じ判断）
- 関係: ADR 0012（出荷と Rollback。段階の追記）、ADR 0028 の決定 4（製品の段階）、ADR 0043 の O5（障害の重要度とエラーバジェット）、ADR 0049（QA の関門）、ADR 0053（メジャー不具合の自律修正）

## 文脈

オーナー（2026-11-14）: 「rally の本番環境も動かして、開発からリリースまで一気通貫で不自然なく動かせるよう磨いてほしい。運用周りにまで踏み込めるなら踏み込んでほしい」。

いまの工場は、本番（prod）を「承認ボタンで起動する」ところまでしか持っていない。製品の段階（ADR 0012 の追記）を development から launch に上げると本番が立つが、立てた後のことが抜けている。

1. **本番が落ちても誰も気づかない**。起動を確かめるのは出した瞬間だけ（`verify`）。Docker の再起動・端末の眠り・コンテナの異常で本番が止まっても、Incident も停止も開かない。Incident は QA 役が staging で見つけたものだけ（incident.py の冒頭「Gen1 は本番を立てないので staging を本番の代わりにする」）
2. **本番への出荷が途中で失敗すると、本番が壊れたまま残る**。`docker compose up` は新しい版のコンテナに入れ替えてから確かめるので、確かめで落ちると本番は「動かない新しい版」のまま。停止は開くが、戻すのは人が「前の版に戻す」を押すまで待つ
3. **本番の DB の控えがない**。DB は前進だけで、戻せることは expand/contract が支える（ADR 0012 の 6）。それでもマイグレーションの誤りや、contract の後で前の版に戻せないときに、出す前の状態に戻す手段がない

## 決定

本番を立てる段階（launch・operating）の製品にだけ効く。development の製品は何も変わらない。

1. **本番の見張り**（shipper の常駐に足す）。本番に版が出ている製品について、`PROD_WATCH_SEC`（既定 60 秒）ごとに、出したときと同じ確かめ方（ship.yaml の `verify`）で本番に版を聞く。
   - 答えない・違う版を答えるのが `PROD_WATCH_FAILS`（既定 3）回続いたら「止まっている」とし、まず 1 回だけ**自分で立て直す**（いまの版で `docker compose up -d --wait`）。`prod.self_healed` を残す
   - 立て直しても答えなければ、**Incident（S2、detected_by: prod_watch、env: prod）と停止（factory-bug）を開く**。S1 にしない（止まった原因の多くは端末や Docker で、製品の不具合と決まっていない。S1 にするとラインの差し止めが人の解除待ちになる）
   - 答えるようになったら Incident と停止を閉じる。止まった・戻ったの境目だけを `prod.down` / `prod.up` に残す（周回ごとには書かない）。止まっていた時間はこの 2 つから出す
2. **本番への出荷が失敗したら、自動で前の版に戻す**。承認で本番に出す途中（起動・確かめ）で落ち、前の版があり、contract で戻せない版でなければ、shipper がそのまま前の版に戻して確かめる（`release.rolled_back` に `auto: true`）。失敗は従来どおり `release.ship_failed` と停止に残し、Incident（S2）も開く。前の版がない（最初の本番）・戻せないときは従来どおり停止だけ
3. **本番に出す前に DB の控えを取る**。製品の ship.yaml の `backup`（環境・部品・コマンド。コマンドの標準出力を控えにする）に本番が入っていれば、本番に出す直前に控えを取り、shipper の作業場（`/ship/backups/<製品>/<環境>/`）に置く。残すのは直近 `backup.keep`（既定 10）個。`release.backed_up` に場所と大きさを残す。本番がまだ動いていない（最初の本番）ときは取らない。控えから戻すのは人の手（手順は runbook）で、工場は戻さない（データを上書きするので）
4. **本番待ちの受信トレイに、DB の contract を添える**。前の本番の版からこの版までに当たる contract のマイグレーションがあれば、「この版を出すと X より前には戻せない」を detail に足す。承認者が戻せなくなることを知ってから押せるように

## 選ばなかった案

- **本番の見張りを外の監視サービスに置く**: Gen1 の本番は端末の中（127.0.0.1）だけで開くので外から見えない。置き場所が EC2 などに移るとき（ADR 0012 の 1）に、環境の定義と一緒に見直す
- **止まったら S1 にする**: 原因が製品と決まっていないのに、ラインの差し止め（人の解除待ち）になる。製品の不具合とわかったら、QA・委員会が S1 に上げる（ADR 0053）
- **DB も自動で控えから戻す**: 控えを取ったあとに入ったデータを失う。戻すかは人が決める

## 結果

- 本番が止まったら数分のうちに工場が気づき、まず自分で立て直し、だめなら Incident と停止で人と建設者に知らせる。止まっていた時間がエラーバジェット（O5）と日報に乗る
- 本番への出荷の失敗で本番が壊れたまま残らない
- 本番の DB に、出すたびの控えが残る
- オーナーの手が要るのは、この ADR の承認と、製品の段階を launch に上げる PR の承認（rally は 2026-11-14 オーナーの依頼「本番環境も動かして」による）

## 実装

1 PR（factory-engine）: `prod_watch.py`（見張り）、`ship.py`（自動の戻し・控え）、`inbox.py`（contract を添える）、definitions/events.yaml、テスト。DB のスキーマは変えない（events に足すだけ）。
製品の側（rally）: `.factory-config/ship.yaml` に `backup`、`.factory-config/manifest.yaml` の `product_stage` を launch に。

## 追記（2026-11-14）: 本番待ちの版で便を止めない場合

rally を launch に上げると、staging の版が本番待ちの間は定期便も緊急便も次の版を切らない（`ship.busy`）。次の 2 つで便が止まったままになるので直した（ADR 0049・0053 の意図どおりにするだけで、承認の仕組みは変えない）。

- **見送った版**: 承認者が QA の関門の報告を見て「見送る」（`qa.gate_blocked`）と、その版は本番に出ないのに staging に残り、本番待ちのまま次の便も止まっていた。「修正は次の便で」（ADR 0049）が出せない。見送った版は本番待ちに数えない
- **緊急便**: S1 の修正（ADR 0053）が、本番待ちの版の承認を待っていた。緊急便は本番待ちを追い越して staging に出す（処理中の依頼だけ待つ）。追い越された版は本番待ちから外れ、受信トレイにはいまの staging の版だけが出る
