# ADR 0031: 工場の入れ替えを、建設者の依頼とプランナーとの時刻の合意で自律的に行う

- 状態: 提案
- 関係: ADR 0004（DB の expand → 移行 → contract）、ADR 0005（番人と停止の記録）、ADR 0009（操業コンソール）、ADR 0012（出荷）、ADR 0020（入れ替えで仕掛かりを壊さない）、ADR 0029（ラインの流量の宣言）、ADR 0030（事業部の窓口）

## 文脈

工場（factory-engine）の変更は、建設者が PR にして main に入れ、工場を動かしているマシンに入れ替えて初めて効く。今の入れ替えは人の手順になっている。

```
建設者: 入れ替えたい版が main に入った
  → ラインの一時停止（factoryctl drain --wait）
  → 運用主に合図し、運用主か運用主のマシンの上のセッションが git pull・docker compose build・up -d
  → 確かめて factoryctl resume
```

困りごと:

- **人が引き金になっている**: 合図を待つ間、入れ替えたい版は効かない。夜や運用主の留守の間にマージした修正は、翌朝まで反映されない。反映を忘れた版が積み残る（どの PR がマシンに反映済みかを、建設者が覚えておく必要がある）
- **いつ入れ替えてよいかを、誰も知らずに決めている**: 実行中のジョブ、出荷の列車（ADR 0012）、日次レポートの時刻、流している大事なチケットを見て決めるべきだが、今は建設者が様子を見て、運用主が都合で決めている
- **戻し方が決まっていない**: 上げ直した版が壊れていたときの戻し方（前の版に戻す、DB の変更をどうするか）が手順にない。失敗したまま再開すると、壊れた工場でジョブを回す
- **DB の変更を含む版**: `postgres/init/` の SQL は新しい DB を作るときにしか流れず、既存の DB には運用主が手で流している

オーナーの方針（2026-11-05）: 工場の入れ替えは自律的にできた方がよい。工場そのものの入れ替えなので、ラインの指示役などではなく、工場の建設者が実行の引き金を引くのが自然。建設者はプランナーとタイミングを示し合わせ、任意のタイミングで工場を入れ替える。

あわせて守る線:

- 工場（指示役）は工場自体を変えない（2026-11-05 オーナー）。入れ替えるのは建設者が依頼した、main に入った版だけ。工場が自分で版を選んだり、自分のコードを書き換えたりはしない
- 戻しにくいもの（データが消える DB の変更、秘密情報、マシンそのものの再起動）は人に回す

## 決定

### 1. 役割を 3 つに分ける

| 役 | 何をするか | しないこと |
|---|---|---|
| 建設者（引き金） | 入れ替えの依頼を出す: どの版に、何を含む変更か、いつまでに、急ぎか。提案された時刻を受けるか、取り消す | 工場のマシンで直接コマンドを打たない |
| プランナー（時刻の相手） | 工場の今の姿を見て、入れ替えの時刻を提案する。理由（何を待つか、何を避けるか）を添える | 版の中身を判断しない。入れ替えるかどうかを決めない |
| 入れ替え役（`swapper`、実行） | 合意した時刻に、事前の確かめ → 必要なら一時停止 → 入れ替え → 確かめ → 再開、を行う。失敗したら前の版に戻す | 依頼のない版に入れ替えない。人に回す条件に当たったら進めない |

入れ替え役は常駐させず、入れ替えのたびに起動する使い捨てのコンテナ（`docker run --rm factory-swapper:<sha> swap <依頼の id>`）にする。Docker のソケットと、工場のリポジトリの作業ツリー（同じ絶対パスでマウントし、`docker compose` の相対パスがそのまま効くようにする）を持つ。
- 起動するのは dispatcher。依頼を拾い、合意した時刻になったら起動する。dispatcher の子プロセスにしないのは、入れ替えで dispatcher 自身を作り直すときに一緒に止まらないようにするため（別のコンテナなら、デーモンが dispatcher と切り離して動かす）
- 常駐しないので、ソケットを持つプロセスが待機中に増えない。compose のサービスでもないので、入れ替え役が自分を作り直す問題が起きない（次の入れ替えでは、そのとき作った新しい版のイメージで起動する）
- 同時に 1 つだけ動く（コンテナの名前 `factory-swap-<id>` と、制御プレーンのロック）。動いている間に dispatcher が上げ直っても、入れ替え役は最後まで続け、結果を制御プレーンに書く
- マシンの上の常駐（launchd など）にしないのは、パイロットで工場を外のマシン（EC2 など）に移しても、同じ形で動かすため

### 2. 依頼は窓口に出す。クラウドの建設者は GitHub の Issue を郵便受けにする

- 正本は窓口の API（ADR 0030）に足す入れ替えの依頼: `POST /desk/swaps`（依頼）、`GET /desk/swaps/<id>`（提案と進み具合）、`POST /desk/swaps/<id>/confirm`・`/cancel`
- 窓口のトークンの役割に `builder` を足す。`builder` にできるのは入れ替えの依頼・確認・取り消しと、その状態を見ることだけ。チケットの優先度や相談は触らない
- 建設者はクラウドのセッションで動き、工場のマシンの中（`127.0.0.1`）の窓口には届かない。そこで Gen1 は、factory-engine の Issue に `factory:swap` を付けたものを依頼の郵便受けにする。dispatcher がいつもの周回で拾い、窓口と同じ関数で依頼にする。提案・進み具合・結果は同じ Issue のコメントに返す
  - 拾うのは、ラベルを付けたのが決めた人（`SWAP_REQUESTERS`。既定は建設者の GitHub アカウント）のものだけ。リポジトリは公開なので、ほかの人の Issue やラベルは無視する
  - 本文は決まった形（下の依頼の項目）だけを読み、自由な文はデータとして記録するだけで、シェルにもプロンプトにも渡さない
  - 窓口を外に開いたら（パイロット、ADR 0030 の 5）、建設者も窓口の API・MCP を直接使い、Issue の郵便受けはやめられる
- 依頼の項目:

| 項目 | 例 | 意味 |
|---|---|---|
| `target` | `main` か コミット | 入れ替える版。`main` は取り込む時点の main の先頭。コミットは main に入っているものに限る |
| `kind` | `code` / `control_plane` / `db` | 変更の種類の自己申告。入れ替え役が差分から判定し直し、重い方を採る（決定 5） |
| `deadline` | `2026-11-05T18:00+09:00` | これより前に入れ替えたい。空なら「急がない（次の 24 時間のどこか）」 |
| `urgency` | `normal` / `urgent` | `urgent` は実行中のジョブの終わりを待たず、つなぎ直し（ADR 0020）を当てにしてすぐ入れ替える（`code` のときだけ） |
| `auto_confirm` | `true` | 提案が `deadline` の内なら、建設者の確認を待たずに受ける（既定 `true`） |

### 3. 時刻はプランナーが提案し、建設者が受ける（示し合わせ）

```
建設者: 依頼（版・種類・期限・急ぎ）
  → プランナー: 提案（開始の時刻、一時停止の要否、見込みの止まる時間、理由）
  → 建設者: 受ける（auto_confirm なら期限の内で自動）/ 別の時刻を返す / 取り消す
  → 入れ替え役: 時刻に実行。始める前までは取り消せる
  → 結果を建設者に返す（Issue のコメントと events）
```

- 提案はプランナーの決定論の関数で出す（LLM のジョブにしない）。材料は制御プレーンにあるものだけ:
  - 実行中のジョブと、その役ごとのふだんの所要時間（jobs の実績の中央値）から見た終わりの見込み
  - 出荷の依頼の処理中か、出荷の列車（`RELEASE_TRAIN_HOUR`）の前後
  - 日次レポート（`DAILY_REPORT_HOUR`）と朝の報告の時刻
  - 委員会のジョブ、流量の宣言（ADR 0029）、ラインの一時停止の有無、工場のモード（attended / unattended）
  - 優先度の高いチケット（p0・p1）が今どの工程にあるか
- 決まり（仮置き。数値は `definitions/swap.yaml` に置く）:
  - `code`: 一時停止しない。出荷の処理中と、日次レポート・出荷の列車の前後 15 分を避けた、いちばん早い時刻
  - `control_plane`・`db`: 一時停止が要る。実行中のジョブが終わる見込みの時刻から一時停止を始め、待ちが最短になる時刻。attended の時間帯に限る（戻せなかったときに人が近くにいるように）。期限までに空きがなければ、期限の時刻に一時停止を始める（新しく取り出さず、実行中は最長 `JOB_TIMEOUT_SEC` まで待つ）
  - p0 のチケットのジョブが動いている間は、`urgent` でも一時停止を伴う入れ替えを始めない
- 提案の理由は人が読める文にする（例: 「#912 の実装が 14:20 ごろ終わる見込み。17:00 の出荷の列車より前に済ませる」）。提案と理由は events に残す（後で、見込みと実際の差を Learn の材料にする）
- 入れ替えの依頼は同時に 1 件。待っている依頼の後に新しい依頼が来たら、新しい版が古い版を含む（main の上で後）なら 1 件にまとめ、時刻は早い方の合意を引き継ぐ

### 4. 入れ替えの手順

入れ替え役が行う。どの段も events に残し、Issue のコメントに要点を返す。

1. **事前の確かめ（一時停止の前。ラインは止めない）**
   - `git fetch` し、`target` が `origin/main` に入っていることを確かめる
   - 今の版と `target` の差分から変更の種類を判定し直す（決定 5）。人に回す条件（決定 7）に当たれば、ここで止めて人に回す
   - 新しい版のイメージを、版のコミットを付けた名前（`factory-dispatcher:<sha>` など）で作る。作り終えるまで、今の工場はそのまま動く
   - `docker compose config` が今の `.env` で通ることを確かめる（新しい版が求める環境変数の抜けを、止める前に見つける）
   - 新しいイメージの中で、dispatcher のテストを流す
2. **一時停止（`control_plane`・`db` のときだけ）**: `factoryctl drain --reason "入れ替え <sha>" --wait`。入れてよくなるのを待つ（ADR 0020 の決定 3）
3. **DB の変更（`db` のときだけ）**: 先に DB をまるごと書き出し（`pg_dump`。オブジェクトストアの `swaps/<id>/` に置く）、差分に含まれる `postgres/init/` の SQL を順に流す
4. **入れ替え**: 作業ツリーを `target` に進め（`git merge --ff-only`）、`ENGINE_VERSION` に版のコミットを入れて `docker compose up -d`（入れ替え役自身を除く）
5. **確かめ**: 決めた時間（仮置き 5 分）の内に、次がすべてそろえば成功
   - 各サービスのコンテナが動き、ヘルスチェックが通る
   - dispatcher と supervisor の周回の印（events）が新しい版で出る
   - 操業コンソールの `GET /api/state` と窓口が応える
   - 実行中だったジョブがつなぎ直されている（`job.reattached`。`code` のとき）
6. **再開**: 一時停止したときは `factoryctl resume`。結果（版、止まっていた時間、つなぎ直したジョブ）を返す
7. **入れ替え役自身**: 入れ替え役は使い捨てで compose のサービスではないので、自分を作り直す手順は要らない。差分が入れ替え役のコードに及ぶときは、手順 1 で作った新しい版のイメージが次の入れ替えから使われる。今回の入れ替えは、起動した時点の版の入れ替え役が最後まで行う

入れ替え役が「コンテナの中から」できるのは、Docker のソケット越しに Docker のデーモン（コンテナの外）に頼める操作まで: イメージを作る、ほかのコンテナを止める・作り直す。dispatcher がワーカーのコンテナを起動し、shipper が製品の環境を上げ下げしているのと同じ仕組み。Docker のデーモンそのもの・Docker Desktop・OS の再起動は、頼む相手ごと止まるのでコンテナの中からはできず、人に回す（決定 7）。ワーカー（タスクを実行するコンテナ）にはソケットを渡さない（今どおり）

### 5. 変更の種類は差分で判定し、重い方を採る

| 種類 | 差分の例 | 一時停止 | 戻し方 |
|---|---|---|---|
| `code` | `orchestrator/dispatcher/`・`worker/`・`core-gates/`・`definitions/`・`health/` の変更、ワーカーのイメージの作り直し | 要らない（ADR 0020 のつなぎ直し） | 前の版のイメージで上げ直す（作り直さない） |
| `control_plane` | `compose.yaml` のサービスの足し引き・ポート・ボリューム、postgres・オブジェクトストアのイメージの版 | 要る | 前の版の作業ツリーとイメージで上げ直す |
| `db` | `postgres/init/` の追加・変更 | 要る | 下の「DB の変更の扱い」 |

- 判定の決まりは `definitions/swap.yaml` に置き、建設者の自己申告より軽くは判定しない

### 6. 失敗したら前の版に戻す

- 事前の確かめで失敗: 何も変えずに終わる。一時停止もしていない。依頼は `failed` にして理由を返す
- 確かめ（手順 5）で失敗: 前の版（作業ツリーのコミットと、前の版の名前のイメージ）に戻して上げ直し、もう一度確かめる
  - 戻した版が通れば、一時停止を解いて再開し、依頼は `rolled_back` にする（壊れているのは新しい版だけで、前の版のままラインは回る）
  - 戻した版も通らなければ、一時停止のまま人に回す（停止 `swap:`、分類 human）。壊れた工場では流さない
- 同じ版の入れ替えが 1 回戻ったら、建設者が新しい版（直したもの）を出すまで、その版では自動で入れ替えない
- 前の版のイメージは、次に成功した入れ替えまで消さない

### 7. 人に回す条件

入れ替え役は次のどれかに当たったら進めず、建設者と運用主に知らせる（受信トレイと停止の記録）。

- DB の変更が expand に当たらない（列・表の削除や改名、型の変更、データの書き換え。ADR 0004 の contract は人の承認）
- 新しい版が、今の `.env` にない環境変数を必須にしている（秘密情報は人が入れる）
- 差分に秘密情報・権限（Docker のソケットのマウント、トークンの渡し方、ポートの開き方を外に広げる変更）が含まれる
- マシンそのもの（Docker・OS）の再起動が要る
- 戻した版も確かめに通らない（決定 6）
- 期限までに入れ替えてよい状態にならない（実行中のジョブが打ち切りの時刻を超えても終わらない、など）

### 8. DB の変更の扱い

- `postgres/init/` の SQL は冪等に書く（`create ... if not exists`、`add column if not exists`）。今の決まりのまま
- SQL の先頭に種類の印を書く: `-- factory:migration expand` / `-- factory:migration contract`。印がないものは contract とみなす（人に回す）
- 自動で流すのは expand だけ。expand は前の版のコードからも使える形なので、コードを戻すときに DB は戻さない
- 書き出し（`pg_dump`）は戻しの最後の手段として残す。戻す（書き戻す）のは人の判断で、自動ではしない

### 9. 記録と見せ方

- events: `swap.requested` / `swap.proposed` / `swap.confirmed` / `swap.cancelled` / `swap.started` / `swap.preflight_failed` / `swap.drained` / `swap.applied` / `swap.verified` / `swap.rolled_back` / `swap.escalated` / `swap.completed`。版（前と後）、種類（申告と判定）、提案と実際の時刻、止まっていた時間を残す
- 操業コンソールに、次の入れ替えの予定と直近の結果、今の版（`ENGINE_VERSION`）を出す
- 建設日報に、その日の入れ替え（版、止まっていた時間、戻した回数）を出す。「どの PR がマシンに反映済みか」はここと `ENGINE_VERSION` で分かるようにする

## 決めどころ（オーナーの承認が要る）

| # | 問い | 推奨 |
|---|---|---|
| S1 | 引き金と実行の分け方 | 建設者が依頼して時刻を受ける。実行は dispatcher が入れ替えのたびに起動する使い捨ての入れ替え役。建設者はマシンで直接コマンドを打たない |
| S2 | クラウドの建設者からの届け方 | 正本は窓口の API。Gen1 は factory-engine の Issue の `factory:swap` を郵便受けにし、決めた人のラベルだけ拾う。窓口を外に開いたら API を直接使う |
| S3 | 時刻の決め方 | プランナーの決定論の関数が提案し、期限の内なら自動で受ける（`auto_confirm`）。LLM のジョブにしない |
| S4 | 一時停止を伴う入れ替えの時間帯 | attended の時間帯だけ。`code` だけの入れ替えはいつでも（夜も） |
| S5 | DB の変更 | 先頭の印が expand のものだけ自動で流し、事前に書き出す。contract と印のないものは人 |
| S6 | 失敗したとき | 前の版に自動で戻して再開。戻しても通らなければ一時停止のまま人へ |

## 順番

1. 入れ替え役（使い捨てのコンテナ）と手順（決定 4・6）。まず `factoryctl swap run <sha>` で、建設者か運用主が手で 1 回通す（時刻の合意なし）
2. 依頼の記録と、Issue の郵便受け（決定 2）。窓口のトークンに `builder` の役割
3. プランナーの時刻の提案（決定 3）と `definitions/swap.yaml`
4. DB の変更の印と自動の expand（決定 8）。既存の `001`〜`005` に印を付ける
5. コンソールと建設日報への表示（決定 9）

## 選ばなかった案

- **建設者が運用主のマシンの上のセッション（Remote Control など）を使って自分でコマンドを打つ**: 今の手順を建設者に移すだけで、マシンへのつなぎ込みに人の承認が要り、自律にならない。戻し方も人の手順のまま
- **main に入ったら工場が自分で入れ替える**: 早いが、工場（指示役）が自分の版を選ぶことになり、「工場は工場自体を変えない」の線を越える。いつ・どれを入れるかの引き金は建設者が持つ
- **ラインの指示役（supervisor）が入れ替える**: supervisor は工場の中の判断なしの周回で、自分が入れ替えの対象でもある。入れ替えの最中に自分を止められない
- **時刻の合意をプランナーの LLM のジョブにする**: 材料がすべて制御プレーンの数字で、決まりで出せる。ジョブにすると、ラインを止めているときに答えられず、費用もかかる。見込みと実際の差が溜まって決まりで足りなくなったら考える
- **工場のマシンの上の常駐（launchd）で実行する**: Mac に縛られ、パイロットで外のマシンに移すときに作り直しになる
- **入れ替えのたびに一時停止する**: `code` だけの入れ替えはつなぎ直し（ADR 0020）で足り、止める必要がない

## 結果

- 建設者が main に入れた版を、運用主の手なしで、ラインの都合に合わせた時刻に反映できる。夜にマージした修正も、`code` なら夜のうちに効く
- 「どの版がマシンに反映済みか」が記録で分かり、建設者が覚えておく必要がなくなる
- 入れ替え役は Docker のソケットと作業ツリーを持つ強いコンテナになる（動くのは入れ替えの間だけ）。依頼を拾う相手を決めた人に限ること、依頼の本文をデータとして扱うことが守りの前提
- 前の版のイメージを 1 つ残すぶん、ディスクを使う
- 環境変数: `SWAP_REQUESTERS`。定義: `definitions/swap.yaml`。イベント: `swap.*`。停止の分類に `swap:` を足す
