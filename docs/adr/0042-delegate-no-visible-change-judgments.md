# ADR 0042: 利用者への振る舞いが変わらない実装の判断を judge に任せる

- 状態: 提案（2026-11-08。決めどころ J1〜J4 はオーナーの判断待ち）
- 関係: ADR 0006（仮決めと出口の judge）、ADR 0025 の E4 と 2026-11-01・11-02 の改訂（見た目の要素レベルの自己承認。本 ADR は同じ考え方を内部実装に広げる）、ADR 0034（受信トレイで答える）、`definitions/judgments.yaml`、`core-gates/judge.py`・`severity.md`、`orchestrator/dispatcher/judgment.py`

## 文脈

2026-11-08、受信トレイに rally #1111（入室前チェック）の判断が 1 件回ってきた。問いは「開始 5 分前」の 5 分という値をどこに置くか。

- 今の案: 値の正本は用語集の `prejoin_check` に置き、コードでは各アプリが定数を 1 つずつ持つ
- 他の案: サーバーに寄せて、アプリは API から受け取る

どちらを選んでも、生徒・コーチ・本部に見える振る舞い（5 分前から開ける、開始時刻まで入室を押せない）は同じ。オーナーは「今の案のまま」と答え、あわせて次のように書いた。

> 事業主的にはぶっちゃけどっちでもいい。実装に関わる部分でユーザーへの振る舞いの変化ってないよね？自律的に判断して欲しい項目かも。

事業主が判断できる・したい軸は、利用者に何が起きるか。どれを選んでも利用者に同じに見える実装の選び方は、人に回しても判断の材料がなく、待ち時間だけが増える（その間 PR はマージで止まる）。

### いま人に回っている理由

内部実装（`implementation`）は、見た目（`aesthetic`）のような条件付きの委任の対象ではなく、judge がもともと自分で決めてよい類型になっている。それでも人に回るのは、judge の読む物差しのせい。

- `core-gates/severity.md` の姿勢: 「利用者の利益になると言い切れる根拠が渡したものの中にないときは、決めずに人に回す」
- `core-gates/judge.py` のプロンプト: 「利用者の利益・不利益を言い切る根拠が渡したものにないときは escalate」

利用者への振る舞いが変わらない選択では、利益・不利益の根拠はそもそも存在しない。judge はこれを「根拠がない」と読み、人に回している。

## 決定（案）

1. **judge が 2 つの印を書く**（仮決めの各件、類型を問わず）
   - `user_visible`: `none`（どの案を選んでも、利用者・API の利用者に見える振る舞いが同じ）/ `changes`（どれかの案で変わる）
   - `reversible`: `true`（後で選び直すのに、データの移行・公開した契約の互換の維持・利用者への知らせが要らない）/ `false`
   - 迷ったら `changes`・`false` にする。書いていないものも同じに扱う
2. **内部実装で振る舞いが変わらず選び直せるものは judge が決める**
   - 類型が `implementation`、`user_visible=none`、`reversible=true` の仮決めは、adopt でも replace でも judge が決め、人に回さない
   - 物差しは利用者の利益・不利益ではなく、正本（ADR・SSOT・既存のコード）との整合、前例、保守のしやすさ、変更の小ささ。拠ったものを `precedent` に書く
   - 確信度の下限は 0.5（見た目の要素レベルと同じ）。これを下回るものは今までどおり人へ
3. **工場の機械的な守り**（`judgment.delegated_verdict`）
   - 上の 3 条件を満たし、確信度 0.5 以上で、judge が escalate にしたうえで推奨（`recommend`）を書いているときは、工場が推奨を採る（escalate を adopt / replace に替え、`forced_delegation` を記録する）
   - 逆に、`user_visible` が `none` でない・`reversible` が `true` でない・`precedent` が空の implementation を judge が決めたときは、今までどおり judge の裁きを通す（本 ADR は人に回すものを減らすだけで、増やさない）
4. **今までどおり人に回すもの**
   - 権限・秘密情報・決済・破壊的スキーマに関わるもの（`always_human_approve`）
   - 類型が `implementation` 以外のもの（画面・文言・エラー処理・API やイベントの形・データ・スコープ）。振る舞いや契約に効くので
   - `user_visible=changes`、または `reversible=false` のもの（例: 公開した API の項目名、DB の形）
5. **記録と後からの確かめ**
   - judge が決めた判断も Judgment（`stage=judged`）に `user_visible`・`reversible`・`precedent` を含めて残す。人の採点（一致率）で後から確かめ、外れが続けば下限を上げるか、委任をやめる
   - `severity.md` と judge のプロンプトの「根拠がなければ人へ」に、「利用者への振る舞いが変わらない選択は、利益・不利益の根拠を要しない」を添える

## 決めどころ

| # | 問い | 推奨 | 他の案 |
|---|---|---|---|
| J1 | 委任する類型 | `implementation` だけ | 検査の指摘（`inspection`）のうち、直しても直さなくても利用者に見えないものも含める |
| J2 | 確信度の下限 | 0.5（要素レベルの見た目と同じ） | 0.7（慎重に始めて、一致率を見て下げる） |
| J3 | judge が escalate にしても、条件を満たせば工場が推奨を採る（決定 3） | 入れる | 入れない（プロンプトの変更だけで様子を見る） |
| J4 | judge が自分で決めた分の見せ方 | 記録に残すだけ（コンソールの判断の記録で見られる） | 朝の報告に「工場が決めた実装の判断」として件数と一覧を出す |

## 効果の見込み

直近 2 週間で `factory:needs-judgment` が付いた rally の PR は 21 本。その仮決めのうち類型が `implementation` のものは次のとおり（PR の本文の「仮決め」から。人に回ったかどうかの内訳は制御プレーンの記録で確かめる）。

| PR | 問い | 利用者に見える差 |
|---|---|---|
| rally #1111 | 「5 分」の定数を置く場所 | なし（人に回った。オーナーの答えは今の案） |
| rally #1095 | `check.mjs --events` の見張りに TAP を求めるか | なし（工場の検査の内部） |
| rally #995 | `bundling_status` の文の書き換え | なし（正本の中の注記） |
| rally #931 | PR 本文の見出しの正をどこに置くか | なし（開発の道具） |

人に回った判断の正確な内訳（類型ごとの件数と、本 ADR の条件で自律になる件数）は、制御プレーンの `artifacts`（`type='Judgment'`, `stage='judged'`, `verdict='escalate'`）から数えて、承認の前に本 ADR に書き足す。

## 結果

- 人に回るのは、利用者への振る舞いか、後で戻しにくいことに関わる判断だけになる。オーナーが答える判断が、事業主として判断できるものに揃う
- 内部実装の選び方が judge の物差し（正本との整合・前例・保守のしやすさ）で決まる。外れたときは、振る舞いが変わらないので、後のチケットで直せる
- `user_visible` の読み違い（実は振る舞いが変わるのに `none` と書く）が新しい外れ方になる。人の採点で類型ごとの一致率を見て、外れが続けば委任を狭める
