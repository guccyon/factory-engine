# ADR 0039: 単発の依頼のループ（受付から提出・受け取りまでと、型を育てる外側のループ）

- 状態: 提案（2026-11-06。決めどころ L1 は決まり、L2〜L7 はオーナーの承認待ち）
- 関係: ADR 0013・0023・0024・0027（Learn ループ・学びの体系・知見と委員会・工程の信号）、ADR 0030（事業部の窓口。会話・トークン・窓口の枠）、ADR 0032（通知。`done.task`）、ADR 0034（どこからでも答える。正本は 1 つ）、ADR 0036（プランナーの評価セット）、ADR 0037（単発の依頼の道・確認の段・成果物の扱い）、ADR 0038（プランナーのワークフローと上限の宣言）、`orchestrator/dispatcher/desk.py`・`desk_line.py`

## 文脈

ADR 0037 で、単発の依頼にいくつかの道（`ticket`・`direct_line`・`operate`・`quick`・`analysis`）があること、確認の段、報告書の書き方、成果物は提出の後に廃棄してよいことを決めた。ADR 0038は、プランナーが道ごとのひな形からステップ・厚み・上限を宣言し、指示役が守らせる形を出している（道のひな形は ADR 0038の決定 6）。

残っているのは、依頼 1 件が「受け付けられてから終わるまで」のループと、そのループの結果から道と型を育てるループである。オーナー（2026-11-06）: 単発の依頼のためのループの設計をしっかりやりたい。型は今完全には定義できず、Gen2 のパイロットで届く実際の要求から、追加の実装でケイパビリティを得ながら更新していく。

今の窓口の会話（`desk_conversations`）は、変更の依頼のために作った状態しか持たない。

| 今の状態 | 意味 | 単発の依頼で足りないもの |
|---|---|---|
| `open` | 依頼者が書いた。相談役に回す | ― |
| `waiting_requester` | 問いの返事待ち | ― |
| `drafted` → `confirmed` | タスクのまとまりの下書き → 確認して起票 | 起票で会話が終わる。実行・提出・受け取りの状態がない |
| `answered` | 問い合わせに答えた | 答えが役に立ったか、続きがあるかを受け取らない |
| `closed` | 閉じた | 誰が・なぜ閉じたか（受け取った・断った・放置）の区別がない |

また、依頼の入口は窓口（MCP・API）と GitHub の Issue の 2 つに分かれていて、Issue から来た依頼には会話がない。どちらから来たかで、返し方も記録も変わってしまう。

## 決定

### 1. 依頼 1 件の正本は窓口の会話 1 つ。入口はいくつあってもよい

- 窓口（MCP・API）から来た依頼は今どおり会話になる
- GitHub の Issue から来た単発の依頼（プランナーが `ticket` 以外の道を選んだもの）も、会話を 1 つ作って Issue と結ぶ（`desk_conversations.source_ref` に Issue の URL）。Issue のコメントは会話の写しで、返事は Issue のコメントからでも窓口からでも受ける（ADR 0034 と同じ「入口は多く、正本は 1 つ」）
- Slack からの新しい依頼（通知への返信ではない、新しい頼みごと）は Gen2 以降の入口として、同じく会話にする
- `ticket` の道（チケット化）は、今どおり起票した時点で会話から製品のライン（Issue → PR）に渡し、会話は `handed_off` で終える。単発の依頼のループが持つのは、それ以外の道

### 2. ループは 5 つのステップで回す。ステップごとに責務を分ける

```
受付 → 振り分け → 確認 → 実行 → 提出（受取確認まで）
 (1)     (2)       (3)    (4)    (5)
           │         │      │      ├─ 受け取った → 閉じる
           │         │      │      ├─ 続き      → (2) へ（同じ会話）
           │         │      │      ├─ 違う      → (2) へ（振り分けのやり直し）
           │         │      │      └─ 返事なし  → 期限で受け取った扱いで閉じる
           │         │      └─ 上限に当たった → 途中までを (5) で出す
           │         └─ 断られた・期限切れ → 閉じる
           └─ どの道にも乗らない → 断る（理由と代わりの案）→ 閉じる
```

| ステップ | 責務（何を決め、何を決めないか） | 会話の状態 | 誰が |
|---|---|---|---|
| 1. 受付 | 依頼を会話にし、受け付けたことと次に起きることをすぐ返す。中身は読まない | `open` | dispatcher（決定論） |
| 2. 振り分け | どの道で扱うか（ADR 0037）と、そのワークフロー（ステップ・厚み・上限。ADR 0038）、確認の段、見込み（費用・時間）を決める。通常のラインの着手判定と同じ責務。依頼者に問うのは、道か確認の段が決まらないときだけ（着手判定の `ask` と同じ。往復の上限も同じ）。**依頼の中身の解釈と、作業の進め方は決めない**（実行役の責務） | `waiting_requester` / `routed` | プランナー（窓口の相談役） |
| 3. 確認 | 確認の段（ADR 0037 の 4）が要るものだけ、振り分けの結果を依頼者に見せて 1 回確かめる。`read` の段は飛ばす | `awaiting_confirm` | 依頼者（受信トレイの件。ADR 0034 のどの入口からも） |
| 4. 実行 | 依頼の中身を解釈し、作業の進め方を自分で決めて行う（決定 2a）。長くかかるものは途中の様子を会話に書く | `running` | 実行役（`operate` は dispatcher、`quick`・`analysis` はエージェントのジョブ） |
| 5. 提出 | 届けて、受取確認を取るまで（決定 5）。成果物を置き場に置き、会話と依頼の来た口にリンクと所見の要約を書き、`done.task` で知らせる（事業主の宛先には工場の内部の情報を載せない）。届いたかを確かめ、送れなければ決まった回数やり直して運用主に回す。依頼者の答え（受け取った・続き・違う）を記録して次へ進め、返事がなければ期限で閉じる | `delivered` → `accepted` / `closed` | dispatcher（答えるのは依頼者） |

- 受け取りを別のステップにしない（オーナー 2026-11-07「通知モジュールが通知と既読確認を内包するように、提出も受取確認を内包する」）。受け取りは工場のステップではなく依頼者の答えなので、提出の中に受取確認として持つ
- 精緻化と見立てを分けない（オーナー 2026-11-07）。振り分けで問うのは「どの道か」を決めるのに要ることだけで、依頼の中身を細かく詰めるのは実行役の仕事にする。通常のラインでも、プランナーは経路を決め、タスクの解釈は実装役が行う。それと同じ線を引く
- 状態は今の `open`・`waiting_requester`・`closed` に、`routed`・`awaiting_confirm`・`running`・`delivered`・`accepted`・`handed_off` を足す。閉じるときは理由（`accepted`・`expired`・`declined`・`withdrawn`・`handed_off`）を持つ
- 状態を変えるのは dispatcher だけ（今どおり）。プランナーと実行役は結果を返し、dispatcher が状態を進める
- 振り分けの結果（道・やること・成果物の形・見込み・確認の段）は、確認を飛ばすときも必ず会話に書く。依頼者が「何をしようとしたか」を後から読めるように、また振り分けの外れを数えるため

### 2a. 実行役が依頼を解釈し、進め方を自分で決める。進め方は Learn で改善する

作業の細かい進め方は、工場の定義で逐一決めない（オーナー 2026-11-07「実行役となるエージェントが正しく解釈し、細かい単純作業なら小さなモデルのサブエージェントで実行する。その作業のプロセス自体もレトロスペクティブで自律的に改善されてほしい」）。

- 実行役（`quick`・`analysis` のエージェント）は、依頼の言葉と振り分けの結果を読み、何を求められているかを自分で解釈してから取りかかる。解釈が割れて成果物が大きく変わるときだけ、実行の途中で依頼者に 1 回問える（問いの往復の上限は振り分けと合わせて数える）。解釈は成果物の冒頭に「こう受け取った」と書く（違ったときに依頼者がすぐ気づけるように）
- 実行役は、作業を自分で分け、細かい単純作業（データの整形、決まった集計の繰り返し、表の書き出しなど）は小さなモデル（Sonnet・Haiku の段）のサブエージェントに任せてよい。どこを分けてどの段のモデルに任せるかは実行役が決める。上限（ADR 0038 のターン・費用）は実行役とサブエージェントの合計で数える
- 実行役は、進め方の記録（どう解釈したか、どう分けたか、どの段のモデルに何を任せたか、どこでやり直したか）を成果物と一緒に返す。セッションの記録は後片付け（ADR 0021）が保存する
- 進め方の改善は Learn のレトロスペクティブに任せる（決定 7 の `desk_execution`）。進め方の記録・費用・やり直し・「違う」を束ねて事例型の分析役に回し、改善は知見として委員会（ADR 0024）を通って実行役の入力に入る。実行役のプロンプトやスキルを変えるのは、承認の線（`role_line_engine`、人）のまま
- `operate` は決定論の操作なので解釈しない。引数の決め方は振り分けが行い、dispatcher が宣言と照らして検査する（ADR 0037 の決定 3）

### 3. すぐ返す。最初の返事と提出の目安を持つ

単発の依頼は、オンデマンドで即時の対応を求める（ADR 0037 の決定 1）。待たせる時間を道ごとに目安として持ち、守れたかを数える（仮置き。運用パラメータとして工場が調整してよい）。

| | 最初の返事（受付） | 振り分け | 提出 |
|---|---|---|---|
| すべて | 1 分以内（決定論。受け付けた・次に起きること・振り分けの目安の時刻） | ― | ― |
| `direct_line` | ― | 5 分 | 優先度を変えた時点（ラインに入ったことを返す） |
| `operate` | ― | 5 分 | 確認から 5 分 |
| `quick` | ― | 5 分 | 15 分 |
| `analysis` | ― | 15 分 | 振り分けで示した時刻（目安 2 時間） |

- 単発の依頼のジョブは窓口の枠（ADR 0030 の決定 6）で動き、ラインの一時停止中も動く。枠の中の順は「先に受けた順」で、`direct_line` と `operate` の振り分けは軽いので先に回す
- 目安を超えそうなとき（`analysis` の実行が振り分けで示した時刻を過ぎるなど）は、超える前に会話に「今どこまで・あとどれくらい」を書く。黙って遅れない
- 夜間や枠が埋まっているときに受けた依頼は、受付の返事で「いつ頃振り分けを返せるか」を言う

### 4. どの依頼も、提出か断りのどちらかで終わる

- 振り分けでどの道にも乗らない依頼（操作の一覧にない、データ源がない、本番のデータが要る、など）は、断る。断りには理由と、代わりの案（できる範囲の別の道、チケット化して工場に足す提案、人に回す）を必ず付ける。黙って閉じない
- 上限（ADR 0038の決定 4）に当たったら、決まったところまでを提出し、残りと次の選択肢（続ける・`analysis` に切り替える・やめる）を添える。止めて黙らない
- プランナーが振り分けを決められない（確信が低い・問いを使い切った）ときは、運用主の受信トレイに回す（今の `planner-human` と同じ）。依頼者には「人に確認している」と返す
- 依頼者が会話を閉じたら（取り下げ）、動いているジョブを止める（`cancel_requested`）。止める前に出ていた結果は残す

### 5. 提出は受取確認を内包する。続きは同じ会話で受ける

- 提出は、届けて終わりではなく、依頼者の受取確認を取るまでを責務にする（通知と既読確認の関係と同じ）。依頼者は 3 つで答えられる（ADR 0034 の `answer.type: choose`）: **受け取った**（終わる）、**続き**（同じ会話で、提出した成果物を前提に追加を頼む。例「この数を地域別にも」）、**違う**（頼んだことと違う。理由の一言を要る）
- 続きは同じ会話の中で振り分け（2）から回し、前の成果物を実行役に渡す（廃棄の猶予の間。ADR 0037 の D6）。続きの回数に上限を置き（仮置き 5 回）、超えたら新しい会話にしてもらう
- 違うは振り分け（2）からやり直す。外れとして数える（決定 7。振り分けの外れか、実行役の解釈の外れかは事例型の分析役が見る）
- 返事がなければ、提出から 3 日（仮置き）で受け取った扱いで閉じ、成果物の廃棄の猶予を始める
- 「これを毎週」「これを画面にして」のように、繰り返し・仕組みを求める続きは、チケット化の道（定期レポートや機能を足す）に渡す。会話は `handed_off` で終え、起票したチケットを会話に結ぶ

### 6. 依頼者に見えるものを揃える

どの入口から見ても、依頼者は同じものを読める（会話の `view`）。

- 今のステップと、次に何が起きるか、いつ頃か
- 振り分けの結果（道・やること・成果物の形・見込み・確認の段）と、実行役の解釈（「こう受け取った」）
- 途中の様子（長いもの）
- 成果物と所見、受け取りの選択肢
- 断りの理由と代わりの案

依頼者の手元の Claude は、MCP の「会話を読む」でこれを読み、依頼者に伝える。窓口の MCP の道具は今のまま（開く・返事をする・読む・確認する・状態を見る・一覧）で、受け取りは「返事をする」か受信トレイの件への答えで受ける（道具を増やさない）。

### 7. 外側のループ: 既存の Learn ループに載せる。単発の依頼ならではの学びだけを足す

外側のループの仕組みを別に作らない（オーナー 2026-11-06「既存の Learn 側の仕組みに寄せていくことはできないのか。単発作業ならではの学びもあるので、単純に同じものとはいかないと思うが」）。Learn ループ（ADR 0013・0023・0027）がすでに持つ部品をそのまま使う。

| Learn の部品 | 今の形 | 単発の依頼で使うところ |
|---|---|---|
| 一次記録 | events・artifacts | 会話の events（決定 8）と、閉じたときの記録（下の表） |
| 教師信号（`learning.yaml` の `teacher_signals`） | 検査の指摘の採用・仮決めの差し替え・衝突の解消など | 単発の依頼の信号を足す（下の表）。数えるのは決定論 |
| 束ね方（Retrospective。`learn.py`・`process_learn.py`） | `rubric:<id>`・`process:<信号>:<鍵>` で束ねる | `desk:<信号>:<鍵>` で束ねる。鍵は道・断りの理由・依頼の主題 |
| 事例型の分析役（`case.py`） | 差し戻し・停止・工程の束を、観点ごとになぜなぜで掘る | 閾値を超えた `desk:` の束と、「違う」と言われた依頼 1 件を出来事に足す |
| 知見と委員会（ADR 0024） | 知見の候補を委員会に回し、通ればプランナーなどの入力に入れる | 「この種の依頼は `operate` で済む」「この依頼者は所見を先に読む」などの知見 |
| 承認の線（`learning_taxonomy.yaml` の `approval`） | 作用先ごとに自動か人か | そのまま。Engine（道・操作・データ源を足す）は `role_line_engine` で人、製品の改善チケットは自動 |
| 効き目（`factoryctl report learning`） | 改善の前後で束の件数と費用を比べる。学習器に自分を採点させない | 同じ。束の件数と、最初の返事・提出までの時間、受け取りの率を前後で比べる |

会話 1 件ごとに、閉じたときに記録する（`desk.closed` の中身。束ねる材料）:

| 記録 | 中身 |
|---|---|
| 道 | 振り分けで選んだ道、確認の段、やり直しの有無 |
| 時間 | 最初の返事・振り分け・提出までの時間と、目安を守れたか |
| 費用 | 道ごと・ステップごとの費用（ADR 0038の台帳） |
| 往復 | 振り分けと実行の問いの回数、続きの回数 |
| 進め方 | 実行役の解釈、作業の分け方、サブエージェントに任せた作業とモデルの段、やり直し（決定 2a） |
| 結末 | 受け取った・続き・違う・期限・断り・取り下げ・人へ |
| 断りの理由 | 操作がない・データ源がない・本番のデータが要る・規模が大きすぎる、など（決まった語） |
| 主題 | 依頼の主題の語（工場の稼働・利用状況・品質・売り上げなど。ADR 0037 の決定 7 の表の行。決まった語からプランナーが選ぶ） |

足す教師信号（`learning.yaml`）と、学びの体系（ADR 0023）のどのテーマに入るか:

| 信号 | 数えるもの | テーマ | 学び方の型 |
|---|---|---|---|
| `desk_misroute` | 「違う」・振り分けのやり直し | 7 判断の精度（プランナーの道の選び方） | 反復型・校正型（評価セットの正解に足す） |
| `desk_cap_hit` | 上限に当たった依頼 | 6 工程の進め方 | 反復型（ADR 0038の `process:cap_hit` と同じ束ね方） |
| `desk_late` | 待たせる時間の目安を超えた | 6 工程の進め方 | 傾向型 |
| `desk_declined` | 断った依頼（理由つき） | 新しいテーマ 9（下） | 傾向型 |
| `desk_repeat` | 同じ主題・同じデータ源の依頼が、期間を替えて繰り返された | 新しいテーマ 9 | 傾向型 |
| `desk_execution` | 実行役の進め方の記録・費用・やり直し・解釈の外れ（決定 2a） | 6 工程の進め方・4 役割間の言葉と伝達 | 事例型（セッションの記録をなぜなぜで掘る） |
| `desk_trimmed` | 依頼者が報告書の項目を省いた・所見の書き方を直した | 8 人の意図と好み | 校正型（依頼者・事業主ごとの好みの知見） |

単発の依頼ならではの学びは 2 つある。今の Learn のテーマにないので、学びの体系に 1 つ足す:

- **テーマ 9「求められるケイパビリティ」（`demand`、外向き）**: 事業主が事業部に何を求めているか。断りの理由と繰り返す依頼を、主題・系統（開発・マーケティング・CS）ごとに傾向として見る。出力は「足すべき道・操作・データ源」と「定期レポートに昇格させる候補」。作用先は、Engine に足すもの（`role_line_engine`、人の承認。建設者に回す）と、製品に定期レポートや画面を足す改善チケット（`improvement_ticket`、自動）。チケットの仕事の学び（テーマ 4〜7）は「頼まれたことを上手くやる」ためのもので、これは「何を頼まれているか」を学ぶ
- **依頼者ごとの好み**（テーマ 8 の中）: 単発の報告は依頼者ごとに読み方が違う（どの項目を省いたか、所見をどの順で読みたいか）。好みの知見は依頼者・事業主の単位で持ち、その依頼者の次の報告の入力にだけ入れる（ほかの依頼者に混ぜない）

閾値（仮置き。`learning.yaml` に持ち、運用パラメータとして工場が調整してよい）: `desk_declined` は同じ理由が 2 件以上、`desk_repeat` は同じ主題が期間を替えて 3 回、`desk_misroute` は 3 件以上で事例型の分析役に回す。束と候補は週 1 回、委員会の週次の報告と日報に出す（今の Learn の出し方のまま）。

### 8. 記録

events に足す: `desk.routed`（振り分け。道・ワークフローの宣言・見込み・確認の段）、`desk.confirm_requested` / `desk.confirmed_run`、`desk.progress`（途中の様子）、`desk.delivered`（成果物の参照・所見の要約）、`desk.received`（受け取り。受け取った・続き・違うと一言）、`desk.declined`（断りの理由と代わりの案）、`desk.handed_off`（起票したチケット）、`desk.closed`（理由と決定 7 の記録）。今の `desk.opened`・`desk.message`・`desk.request_confirmed`・`desk.tickets_created`・`desk.answered` はそのまま出す。

## 決めどころ（オーナーの承認が要る）

| # | 問い | 推奨 |
|---|---|---|
| L1 | 依頼の正本 | 決まり（2026-11-06 オーナー「GitHub Issue に作った intake の課題を、単発のループのラインに乗せるという意味なら良い」）。窓口の会話 1 つ。Issue から来た依頼（`factory:request` の intake、`factory:plan`）でプランナーがチケット化以外の道を選んだものは、会話を作って Issue と結び、単発のループに乗せる。チケット化の道は起票で会話から製品のラインに渡す（決定 1） |

| L3 | 待たせる時間 | 道ごとに最初の返事・振り分け・提出の目安を持ち、守れたかを数える。超えそうなら先に言う（決定 3。値は仮置き） |
| L4 | 終わり方 | すべての依頼が提出か断りで終わる。断りには理由と代わりの案、上限に当たったら途中までを出す（決定 4） |
| L5 | 提出の受取確認 | 受け取った・続き・違うの 3 つ。続きは同じ会話で 5 回まで、返事がなければ 3 日で受け取った扱い。繰り返しを求める続きはチケット化へ（決定 5） |

## 順番

1. 会話の状態と閉じる理由の拡張、events（決定 2・8）。Issue から来た単発の依頼を会話に結ぶ（決定 1）
2. 受付の即時の返事と振り分けの記録。`operate` の `report.send` で、受付 → 振り分け → 確認 → 実行 → 提出 → 受け取りを 1 本通す（ADR 0037 の順番 1・2 と一緒に）
3. 待たせる時間の目安と途中の様子、断りと上限の扱い（決定 3・4）
4. 受け取りと続き（決定 5）、依頼者に見えるものの揃え（決定 6）
5. 外側のループ（決定 7）: `learning.yaml` に信号、`learning_taxonomy.yaml` にテーマ 9、Retrospective に `desk:` の束、`case.py` の出来事に足す。届いた依頼が溜まってから

## 選ばなかった案

- **単発の依頼もチケット（Issue）を正本にする**: チケットは PR とマージで終わる形で、受け取り・続き・断りを持たない。顧客の担当者は GitHub を使うとは限らない（ADR 0030）。Issue は入口の 1 つに残す
- **提出で終わりにする（受け取りを待たない）**: 届いたか、役に立ったか、続きがあるかが分からず、外側のループに材料が入らない。返事がなければ期限で閉じるので、依頼者の手間は増えない
- **断らずに何でもチケット化する**: 今の形。依頼者が欲しかったのは答えで、PR ではない。断りの理由を記録しないと、工場に足すべきケイパビリティも見えない
- **振り分けを LLM が毎回ふりかえって型を更新する**: 学習器に自分を採点させない（ADR 0013 の 8）。外側のループの集計は決定論にし、型を足すのは建設者の PR にする
- **単発の依頼のための外側のループを別に作る**（この案の最初の版）: 束ね方・分析役・委員会・効き目の測り方が 2 つになり、同じ真因（例: プランナーの振り分けの癖）がチケットと単発の依頼で別々に扱われる。Learn ループに載せ、単発の依頼ならではの学びだけをテーマと信号として足す

## 結果

- どの入口から来た単発の依頼も、同じ 5 ステップのループで回り、必ず提出か断りで終わる。依頼者はどこから見ても今のステップと次に起きることを読める
- 待たせる時間・費用・結末が依頼ごとに記録され、目安を守れたかが数えられる
- 断りの理由と繰り返す依頼が、Learn ループのテーマ 9 として、ケイパビリティを足す改善と定期レポート・操作への昇格の候補になる。ADR 0037 の「型は運用で更新する」が、今の Learn の部品で回る
- 会話の状態と記録が増える。窓口の API と MCP の道具は増やさない
