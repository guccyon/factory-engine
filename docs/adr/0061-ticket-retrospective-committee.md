# ADR 0061: 知見の委員会をチケットのレトロにする

- 状態: 提案（2026-11-16）
- 関係: ADR 0024（知見の蓄積と委員会。本 ADR が委員会の開き方と構成を置き換える）、ADR 0023（学習の体系・事例型の分析役）、ADR 0013（Learn ループ）、ADR 0027（工程の信号）、ADR 0040（知見の作用先）、`definitions/knowledge.yaml`、`orchestrator/dispatcher/committee.py`、`core-gates/committee_review.py`、`core-gates/committee_weekly.py`

## 文脈

ADR 0024 の委員会は、**知見の PR 1 本ごと**に開かれる。事例の分析（差し戻し・長い停止を 1 件ずつ掘ったもの）から知見の Issue が起票され、その PR を 4 つの観点の役（整合・根拠・担保・反対）が投票で審査する。製品ごとに 1 件ずつ直列に流れ、ほかに週 1 回の定例（置き場の棚卸し）がある。

2026-11-16 オーナーの指摘: これは意図と違う。委員会は、工場で対応した**チケットに対するレトロスペクティブ**として開いてほしい。

- 毎チケットでは多すぎるので、10 件・20 件ごとのように**消化したチケットの件数で区切る**。スクラムの 1 スプリントにあたる。工場の開発では、時間で区切るより消化した件数で区切るほうが、議論の量がちょうど良くなる
- 件数が多すぎると知見の抽象度が高くなりすぎ、少なすぎると局所的な知見しか得られない。ちょうど良い件数は回しながら見極める（工場が自動で調整してよい）
- 議題は「どのチケットの対応を振り返るか」。生産の中で起きた問題、どうすればもっと効率よく作れるか、品質を高められるか、プロダクトのドメインから得られた気づきなどを議論し、**普遍的な知見を抽出**する（これは取っ掛かりの例で、観点はこれに限らない）
- 2026-11-16 オーナーの追記: ほかにも、計画の時点でのジョブへの分割の単位は正しかったか、着手の順は適切だったか、予期しない問題が起きたときに再発防止に取り組んだか、などがある。運用が始まったら障害も委員会の入力になり、事故調査委員会の内容も踏まえて開発体制を改善したい
- 知見はレビューを経て、最終的に**事業部全体に展開**される Learn ループにする
- 委員会は、**そのチケットに関わったロールのエージェントと、事業部のリーダー**で構成する。議事録には、どの立場からの意見かを明記する
- 操業コンソールの議事録には、対象のチケット・得られた知見・判断した結果を載せる

仕様の側でも、05_specs の見回り体制（10 の 4.5「学習・改善は節目で動かす」）が、振り返りと委員会の定例を日時から節目（終わったタスクが N 件たまった）に移す方向をすでに出していた。本 ADR はそれを委員会の形として具体にする。

今の作りで意図と合わないところ:

| 今 | 意図 |
|---|---|
| 1 件の出来事（差し戻し・停止）が 1 本の知見になる。委員会はその知見を審査するだけ | 何件かのチケットをまとめて振り返り、そこから知見を抽出する。委員会そのものが抽出の場 |
| 委員会の役は観点で分けた 4 役。チケットに関わった役は入らない | チケットに関わったロール（実装・検査・judge・QA・デザイナーなど）が自分の立場で話す。まとめるのは事業部のリーダー |
| 開く単位は PR と週。チケットとは結びつかない | 消化したチケット N 件ごと（スプリント） |
| 議事録は票の一覧。対象のチケットが出ない | 対象のチケット・立場ごとの意見・得られた知見・判断の結果 |
| 生産の失敗（差し戻し・停止）だけが入力 | 問題・効率・品質・ドメインの気づき・計画と分割・着手の順・再発防止など、観点は決め打ちしない。うまくいったチケットも振り返る。運用後は障害と事故調査委員会の記録も入力 |

## 決定

### 1. 委員会は「振り返り（レトロ）」として、消化したチケット N 件ごとに開く

- 単位は**製品ごとのスプリント**。工場が対応を終えたチケットが N 件たまったら、その N 件を 1 回の振り返りの議題にする
- 「対応を終えたチケット」は、ラインで工場が対応した Issue のうち、PR がマージされた・PR なしで閉じた（重複・対応不要など）・人が閉じたもの。工場の内部の Issue（知見・担保・改善の Issue、窓口の単発の仕事）は数えない。数え方は決定論（events の `pr.merged`・`ticket.closed_with_source` など）
- **N の初期値は 12**、調整の範囲は 8〜24（オーナーの例の 10〜20 を中に含む）。どのチケットも 1 回だけ、どこかのスプリントに入る（`retro.sprint_closed` に対象の一覧を残す）
- 時間の下限も置く。N 件たまらなくても、最後のスプリントを閉じてから 14 日たち、3 件以上たまっていれば閉じる（チケットの少ない製品で振り返りが止まらないように）

### 2. N は工場が自動で調整する

振り返りのあとに、決定論で 2 つの数を測り、次のスプリントの N を ±2 ずつ動かす（範囲 8〜24）。調整の記録は events の `retro.size_adjusted` に、理由と数を付けて残す。

| 測るもの | 多すぎる（抽象的すぎる）合図 → N を下げる | 少なすぎる（局所的すぎる）合図 → N を上げる |
|---|---|---|
| 知見 1 件あたりの根拠のチケット数（中央値） | — | 1 件（ほとんどの知見が 1 チケットの話） |
| 議題のチケットのうち、どれかの知見の根拠になった割合 | 30% 未満（大半のチケットに触れずに終わる） | — |
| レビューの差し戻しの理由 | 「範囲が広すぎる・根拠がたどれない」が多い | — |
| 知見が 0 件 | 2 回続いたら N を上げる | — |

- 閾値は仮置き。調整の決まりを変えるのは定義の PR（学ぶ側が自分で動かさない。ADR 0013 の 8）
- 調整は工場に任せる（2026-11-16 オーナー「自動で調整してよい」）。推移は建設日報とコンソールの振り返りのページに出す

### 3. 議題はチケットの一覧と、チケットごとの材料

議題は決定論で組み立てる。委員はこれを読んでから話す。

- 対象のチケットの一覧（番号・題・ライン・入口・結果）
- チケットごとの材料（制御プレーンの記録から）: リードタイムと工程ごとの時間、差し戻しと検査の指摘、judge の判断、仮決め、停止、QA の結果、費用、プランの外れ（`plan.outcome`）、そのチケットについての事例の分析（`case.analyzed`。あれば）、渡した知見（`knowledge.used`）
- スプリント全体の材料: 工程の信号の束（ADR 0027）、計画の記録（チケットからジョブへの分け方・着手の順・依存とその見込みと実際）、前回の振り返りで決めた打ち手が効いたか（効き目の確認）、期限切れ・矛盾の候補など置き場の棚卸しの事実（今の週 1 の定例の決定論の部分）
- **運用の材料**（製品が本番で動き始めたら）: スプリントの期間に起きた製品の障害（S1〜S4、ADR 0053 の重大な不具合の自律修正を含む）と、その対応のチケット。障害の原因になった変更のチケットが過去のスプリントにあれば、それも参照として添える
- **事故調査委員会の材料**（ADR 0046）: スプリントの期間に記録・更新された事故記録（FIR）と台帳の兆しのうち、この製品の工場に関わるもの。事故調査委員会は「お金の損」を横断で見る、振り返りは「開発体制」を見る、という分担で、事故の再発防止を開発のやり方（分割・順番・検査・担保）に落とすのは振り返りの仕事にする。FIR はラインのワーカーには渡さない決まり（ADR 0046）のままで、振り返りの委員は読んでよい

事例の分析（ADR 0023）は残すが、**単独で知見の Issue にしない**。その出来事のチケットが入るスプリントの振り返りの材料にする（今の `knowledge_issue_step` は止める）。

### 4. 委員会の構成: チケットに関わったロールと、事業部のリーダー

- **ロールの委員**: 議題のチケットのジョブに出てきたロール（例: プランナー・実装・検査・judge・QA・デザイナー・デザイン検査・窓口）。ロールごとに 1 体のエージェントで、そのロールの指示と、そのロールが担った工程の記録だけを中心に読み、**そのロールの立場から**話す（「実装の立場では、仕様のこの書き方で 2 回迷った」）。出てくるロールが多いときは、関わったチケットの数の多い順に 6 つまで（仮置き）
- **事業部のリーダー**（議長）: 全体を読み、ロールの意見を突き合わせ、普遍的な知見を抽出し、扱いを判断する。どのロールの意見を採ったか・採らなかったかを理由とともに残す
- 呼び名は仮。「事業部のリーダー」「振り返り」「スプリント」は用語集（05_specs/04_glossary.yaml）の未決の語に入れ、決まったら置き換える
- 委員はロールの**立場**で話すが、実際にそのチケットを作業したセッションを続けるのではない（記録を読んで、そのロールの指示を持った別のエージェントとして話す）

### 5. 議論の観点は決め打ちしない（取っ掛かりの例を持つ）

観点を固定の 4 つに絞らない。下は委員に渡す**取っ掛かりの例**で、委員は議題の材料から、ほかの観点を自分で立ててよい。リーダーは、どの観点から出た知見かを議事録に残す。よく使われる観点・知見の出ない観点は振り返りのたびに数え、例の一覧の見直しは定義の PR で行う（観点の一覧は `definitions/knowledge.yaml` の `retro.prompts` に置き、工場が自分で動かさない）。

| 取っ掛かり | 問いの例 |
|---|---|
| 生産の問題 | どこで詰まったか・差し戻されたか・止まったか。なぜか（複数のチケットに共通するか） |
| 効率 | どうすれば、もっと少ない手戻り・時間・費用で作れたか |
| 品質 | どうすれば、検査や QA で見つかる前に防げたか。見逃したものはないか |
| ドメインの気づき | このプロダクトのドメインについて、作業の中で分かったこと（言葉・利用者・業務のルール） |
| 計画と分割 | チケットからジョブへの分割の単位は正しかったか（大きすぎ・小さすぎ・誤った振り分け） |
| 着手の順 | 着手の順は適切だったか。依存や衝突の見込みは当たったか |
| 再発防止 | 予期しない問題が起きたとき、その場の対処で終わらずに再発防止に取り組んだか。前の振り返りの打ち手は効いたか |
| 運用と障害 | 本番の障害・重大な不具合は、どのチケットのどの工程で入り、どこで防げたか |
| 事故（お金の損） | 事故調査委員会の記録に出た損の兆しを、開発のやり方のどこで減らせるか |

うまくいったチケットも振り返る（再現したい良いやり方も知見になる）。

### 6. 流れ: 振り返り → 抽出 → レビュー → 展開 → 効き目の確認（Learn ループ）

1. **意見を出す**: ロールの委員が、議題を読んで、取っ掛かりの例（決定 5）を手がかりに意見を出す（並列。立場とチケットの番号を必ず付ける）
2. **抽出する**: リーダーが意見を突き合わせ、知見の候補を出す。候補ごとに、根拠のチケット・どのロールの意見から来たか・普遍性（何件のチケットで起きたか）を付ける。1 件のチケットだけに根拠がある候補は hypothesis、独立した 2 件以上で起きていれば confirmed の候補にする（ADR 0024 の確かさの基準のまま）
3. **知見の変更セットにする**: 1 回の振り返りで出た知見を、影響を受ける既存の知見の扱い（直す・置き換える・廃止）と一緒に、**1 本の変更セットの PR** にする（ADR 0024 の決定 4 のまま）。スプリントに 1 本なので、今の「1 件ずつ直列に流す」と番号の付け直しの仕組みはほぼ要らなくなる（残しておく）
4. **レビュー**: 変更セットの PR を、今の 4 観点（整合・根拠・担保・反対）のレビューにかける。今の委員会の 4 役は「知見のレビュー」として残す。振り返りに出た委員はレビューに入らない（書いた側に自分を採点させない、ADR 0024 の決定 5 のまま）。議決の集め方・可決でマージ・割れたら人へも今のまま
5. **展開する**: マージで知見が active になる。作用先は知見の `acts_on` と scope（ADR 0040）のとおり
   - `context`: その業務・ロールのエージェントに渡す（confirmed 以上。今の選び手のまま）
   - `engine`・`process`: Engine の改善 Issue、役割への指示・ラインの設定の変更の提案として人に回す（ADR 0023 の承認の線のまま）
   - **ドメインの気づき**は、生産の知見ではなく製品の知識なので、製品リポジトリ（specs/ など）の変更の Issue にする。製品の仕様を変えるかは事業主の判断（05_specs Q9・Q15、ADR 0044）
6. **効き目の確認**: 次の振り返りの議題に「前回の打ち手が効いたか」を入れる（同じ問題が再発したか、渡した知見に従った作業が差し戻されたか）

### 7. 議事録とコンソール

- 議事録の正本は制御プレーンの artifacts（型 `RetroMinutes`）と events（`retro.held`）。git の置き場には、変更セットの PR の本文と議決（`committee/D-NNNN.yaml`）に、振り返りの番号と要約だけを書く（意見の全文には作業の記録の抜粋が入るので、個人情報の検出を通したものだけ）
- 議事録に載せるもの:
  - 振り返りの番号・製品・スプリントの範囲（最初と最後のチケット、件数、その回の N）
  - **対象のチケット**の一覧（リンク・題・結果・リードタイム・差し戻しの数）
  - 出席した委員（ロールとリーダー）
  - **立場ごとの意見**（「実装: …」「QA: …」の形。チケットの番号付き）
  - **得られた知見**（K の id・主張・確かさ・根拠のチケット・どの立場から来たか）と、採らなかった候補と理由
  - **判断の結果**（レビューの議決、マージ・人へ・差し戻し）と、**展開先**（どのロール・業務に渡るか、起票した Issue）
  - 費用、次の N とその理由
- 操業コンソールの委員会のページ（`/committees`）に「振り返り」を足し、上の項目を出す。今の「知見の審査」は振り返りの子（レビュー）として同じ議事録の中に出す

### 8. 週 1 の定例はやめ、振り返りに畳む

置き場の棚卸し（期限切れ・矛盾の候補・確かさを上げる候補・置き場の構造）は、振り返りの最後の議題にする。チケットの流れていない製品では棚卸しも急がない。14 日の時間の下限（決定 1）で、まったく止まることはない。

### 9. 費用と枠

- 1 回の振り返りの上限は $10（仮置き。ロールの委員 6 体＋リーダー 1 体）。見回りの費用の集計（05_specs/10）に足す
- ジョブは委員会と知見の専用の枠（`GOVERNANCE_PARALLEL`。ADR 0024 の 2026-11-04 の追記）で動く。ラインが止まっていても動く

### 10. 承認の線は変えない

委員会の可決で工場がマージしてよいのは今と同じく知見の PR だけ。新しい用語・業務ルールの定義、役割への指示・ラインの設定・Engine、Blueprint、製品の仕様は、議事録を添えて人に回す。

## 今あるものとの関係

| 今のもの | これから |
|---|---|
| `knowledge_issue_step`（事例の分析 → 知見の Issue） | 止める。事例の分析は振り返りの材料 |
| `enqueue_committee`・`committee_review.py`（4 役の審査） | 「知見のレビュー」として残す。審査の対象は振り返りの変更セットの PR |
| `committee.queue`・`committee.turn`（1 件ずつ直列） | 残す（振り返りの PR が人の判断待ちの間に次の振り返りが閉じたとき用） |
| `committee_weekly_step`・`committee_weekly.py`（週 1 の定例） | やめる。決定論の棚卸しは振り返りの議題に、議長の見直しはリーダーに移す |
| `case_review_step`（事例の分析） | 残す。対象の選び方はそのまま |
| `/committees` の「審査」「定例」 | 「振り返り」を足す。過去の記録はそのまま読める |

## 段取り

1. 本 ADR と仕様（05_specs の Learn ループの仕様・見回り体制・用語集・オンボーディング）の更新。オーナーの承認
2. 定義: `definitions/knowledge.yaml` に `retro`（N の初期値と範囲、調整の決まり、時間の下限、委員の上限、費用の上限、観点）を足す。`agents.yaml` に `retro.role`・`retro.lead` の工程
3. スプリントを閉じる（supervisor の `retro_step`: 対象のチケットを数え、N に届いたら議題を組み、ジョブ `retro` を積む）
4. 振り返りのワーカー（`core-gates/retro.py`: ロールの委員を並列に呼び、リーダーが抽出し、知見の変更セットの Issue を起票する材料と議事録を返す）。dispatcher が議事録を記録し、変更セットの Issue を起票する
5. レビューの対象を振り返りの PR に替え、`knowledge_issue_step` と週 1 の定例を止める
6. N の自動調整（`retro.size_adjusted`）と効き目の確認の材料
7. コンソールの振り返りの議事録

3〜7 は Engine のプロセスの変更なので、本 ADR の承認のあとに PR を分けて出す。ワーカーのプロンプトを足す 4 はオーナーに見せてからマージする。

## 選ばなかった案

- **時間で区切る（週 1・2 週ごと）**: 工場の生産の量は日によって大きく変わるので、議論の量がばらつく（オーナーの指摘）
- **毎チケットで振り返る**: 回数が多すぎ、局所的な知見しか出ない
- **今の 4 役を委員のまま、議題だけチケットにする**: 作業した立場の意見が入らず、どの立場からの意見かが残らない
- **振り返りの委員がそのまま知見を可決する**: 書いた側に自分を採点させることになる。レビューは別の役で行う
- **N を固定する**: 製品の段階やチケットの大きさで、ちょうど良い件数は変わる
