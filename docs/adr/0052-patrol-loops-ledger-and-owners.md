# ADR 0052: 見回りを外ループに限り、台帳を工場が読む定義にし、持ち主と業務の id（govern.watch・govern.budget・learn.signals）を決める

- 状態: 承認（2026-11-12 オーナー「推奨で」。事業部の仕様 05_specs/10 の判断ポイント P2・P3・P8・P9。P5・P6 は P2 の承認に乗せる）
- 関係: ADR 0050（見回りの見回り・実施の記録・GitHub に直接聞く 4 つの寄せ。Gen1 の実装はこちら）、ADR 0005（停止と番人）、ADR 0029（予算の枠）、ADR 0038（チケットごとの上限）、ADR 0040（業務のツリーと知見の作用先）、ADR 0046（事故の見回り）、#308
- 検討の記録: 事業部の仕様の置き場（05_specs）の 10（工場の見回り体制、1.2）と 07（オンボーディング）

## 文脈

工場の中で定期に「何かを見ている」ものは 21 個あり、時刻と頻度が 6 か所に散らばり、見回りが動いたかを誰も見ていなかった。さらに、前の工程の出来事を待って進む処理（内ループ）と、時刻・期限で起こす処理（外ループ）が同じ 60 秒の周回に混ざっていて、「見回り」が何を指すか紛れていた。

Gen1 で入れる範囲（見回りの見回り、実施の記録と費用・可用性、GitHub に直接聞く 4 つの寄せ、小さな時刻のずれ 2 つ）は **ADR 0050** で決めて実装している。この ADR は、その土台になる **考え方と構造** を決める。実装は Gen1 では ADR 0050 の小さな表と、ここで足す業務の id まで。それ以外は Gen1.5 以降。

## 決定

### 1. 内ループと外ループを分ける（P8）

- **内ループ**（進行）: レーンの中で前の工程の出来事を待って次に進める処理。見回りではない。出来事（events）を合図に動く形に寄せる。持ち主はそのレーン
- **外ループ**（見回り）: 時刻か時間切れをきっかけに、レーンにタスクを入れる・止まりに気づく処理。型は **日時** か **期限** の 2 つ。「逃したときの扱い」（既定は、起きたときに 1 回取り戻す）を必須にする
- 予算の枠・チケットごとの上限・エラーバジェットは、投入や記録の直前・直後の **その場の確認** で、どちらのループでもない
- 工場が手元の Mac や社内のネットワークで動いていて Webhook を受けにくい間は、イベント駆動にできるものでも無理にしない。**小さなポーリングが見た結果を出来事として events に記録し、処理は出来事を読んで動く**（ADR 0015 がお手本、ADR 0050 の決定 2）。Webhook が使えるようになったら入口を差し替えるか併用する（dedupe_key で二重にならない）
- 全面的なイベント駆動（events を通知やキューで配る仕組み）は Gen2 の進行役の設計に入れる

### 2. 見回りの台帳は工場が読む定義にする（P2）

- `definitions/patrols.yaml` を置く。仕様の対応表にとどめず、**工場が読む定義** にする。理由: 見回りはこれからも増える／項目ごとに有効・無効を切り替えられる（事業化後にプランごとに機能を付け外しする余地）／追跡のための記録が要る
- 1 行に、**見回りの id**・区分（生産プロセス・プロダクト品質・学習・改善・インシデント）・見るもの・型（日時か期限）・頻度と時刻・逃したときの扱い・トークンの有無・1 回と週の上限・出口・持ち主（領域とケイパビリティの id）・根拠の ADR・見直しの日
- 台帳に載せるのは外ループだけ。定期レポートと定期便は見るためのものではないので見回りに数えないが、台帳には載せる
- **台帳にない定期処理は足さない**。新しい見回りは、まず既存の見回りの観点に足せないかを確かめ、足せないときだけ台帳に行を足す（その判断を ADR か Issue に書く）。90 日ごとに、出口に何も出していない見回りを止める候補にする
- 見回りの id は ADR 0050 の `patrol_watch.py` の表の id をそのまま引き継ぐ
- **時期**: Gen1 では作らない。Gen1 の代わりは ADR 0050 の小さな表（`dispatcher/patrol_watch.py`）。台帳は Gen1.5 で、最初は宣言だけ（今の設定はそのまま）にして、時刻と頻度の置き場を各定義と環境変数から 1 つずつ台帳に移す
- **P5・P6 を台帳に乗せる**（Gen1.5）: 費用の外れ値の集計は 1 か所に寄せ、閾値も 1 つの定義にして、建設状況の日報・工程の信号・事故の見回りが同じ集計を読む（P5）。可用性は、ラインが動いていた割合・停止に気づくまでの時間・人が起こした割合の 3 つを測って線を引くだけにし、線の値は運用パラメータとして工場が調整する。割ったら止める、はしない（P6）

### 3. 見回りの見回り（P3）

ADR 0050 の決定 1 のとおり（番人に足す。決定論、LLM なし、$0。停止 `patrol:<id>`）。この ADR では決めを足さない。#308 の一部を受け持つ。

### 4. 持ち主を 1 つに決め、業務のツリーに 3 つの id を足す（P9）

- 見回りごとに持ち主を 1 つ決める。閾値や頻度を変えるのは持ち主
- 領域の持ち分: **Govern** は工場そのものの流れ・費用・守り、**Learn** は作り方の材料、**Ops** は製品の実行環境と製品の障害（B1・B2・D3）、**Biz** は製品の使われ方（B3）。**Dev は内ループだけを持ち、見回りは持たない**。内ループの持ち主はレーン
- **工場の可用性（ラインが流れているか）は Govern が持つ**。Ops は製品の実行環境と障害を持つ。工場の止まりと製品の障害を混ぜない
- `definitions/work.yaml` に 3 つの id を足す（`core-gates/knowledge_check.py` と `orchestrator/dispatcher/requester_prefs.py` の写しも同じ変更で直す）

| id | 中身 | 持つもの |
|---|---|---|
| `govern.watch` | 工場の流れと見回りを監視する | 停止の番人、投入待ちのタスクの残り、受信トレイの知らせ直し、見回りの見回り |
| `govern.budget` | 予算の枠とチケットごとの上限を守らせる | ADR 0029・ADR 0038 |
| `learn.signals` | 教師信号から振り返る | 振り返り、ルールの移り変わり、品質の Learn |

どれも決定論で LLM を使わず、エージェントの役（`from_agent_steps`）には対応づけない。次の世代の工場では、監視役というロールとして `govern.watch` をドメインモデルに定義する（ここでは id を置くだけ）。

### 5. オンボーディングへの影響

ケイパビリティを足すので準備度を確かめた。事業主から新しく提供してもらうものは **増えない**。`govern.watch` が止まりを知らせる宛先は既存の項目「通知の宛先と承認者」（`p-notify`）が受け持ち、`govern.budget` は工場の予算の枠、`learn.signals` は工場の記録だけを使う。事業部の仕様 07 に、この確かめた結果を書く。

## 入れないもの（Gen1.5 以降。05_specs/10 に未来の仕様として残す）

- 台帳そのもの、時刻と頻度の置き場の一本化、費用の集計の一本化（P5）、可用性の目標の線（P6）
- 節目による学習・改善の起動（節目の型: リリース・ロードマップのマイルストーン・件数。節目が来ないときの期限を対応づけに持たせ、過ぎたら監視の対象にする）。リリースが本格化する Gen2 で要る
- トークンの有効期限・パッケージのサポート期限などの期限の判定
- 停止への一次対応（Gen2）
- 内ループ全体のイベント駆動（Gen2 の進行役）

## 影響

- 業務のツリーのノードが 3 つ増える。知見の作用先（`scope.work`）に使える
- この変更で動きは変わらない（定義の追加だけ）。台帳と実施の記録の実装は ADR 0050 と Gen1.5 の順番に従う
- 事業部の仕様 10 の版と判断ポイントを「決定済み」にし、07 に準備度の確かめを足す
