# ADR 0055: スパイクのレーンを Gen1 にプロトタイプで置く（方針が決まっていないチケットは、着手判定でスパイクへ回す）

- 状態: 承認（2026-11-13 オーナー。プロトタイプの水準で構築し、Gen1.5 の参考にする）
- 関係: ADR 0025（上流の工程とデザインの線）、ADR 0026（着手判定）、ADR 0038（ワークフローの宣言）、ADR 0053（メジャー不具合）、
  事業部の仕様の置き場（05_specs）の 01（工場のアーキテクチャ。3 つのレーン、計画の 2 段、2026-11-08 の決定）

## 文脈

ADR 0053 の改訂（#409）で、メジャー不具合の直し方を「プランナーが決める」とした。オーナーの指摘（2026-11-13）:

- プランナーはワークフローをどう組むかと、今着手してよいかを決める役で、直し方（方針）は別の担当が決める
- 方針が明確でないことは、着手できないことと同じ
- 調査の役をプランナーの手前に置くと、それを飛ばすかを誰も判断できない。飛ばすかの判断はプランナー（振り分け）が持つ
- 方針を明確にする流れは、上流工程の流れとほとんど同じ

仕様（01 の 11-08 の決定）は、Dev にスパイクのレーン（要件・ドメイン・画面・システム設計を決め、成果物は 1 本の設計書。役はプロダクトデザイナー・ドメインモデラー・System Architect で、要る役だけ呼ぶ）とビルドのレーンを置き、振り分け（DoR とどのレーンに回すか）とレーンの計画を分けている。Gen1 にはスパイクのレーンがなく、デザイナー役を同じ経路の前段に並べる「複合」の形だけがある。System Architect にあたる役もない。

## 決定

### 1. 着手判定に「スパイクへ」を足す

プランナーの判定（ready・ask・escalate・split）に `spike` を足す。方針（原因・直し方・どの層をどう変えるか）が本文から決まらず、起票者に問えば決まるものでもないとき、着手できないとしてスパイクのレーンに回す。プランナーは方針を決めない。スパイクで決めることを問い（`spike.questions`）として渡す。

- 原因と直し方が本文から明らかなら ready（スパイクを飛ばす）。飛ばすかを決めるのはプランナー
- ラベルは `factory:spike`。チケットの記録は Plan（decision: spike）と `plan.decided`
- 同じチケットでスパイクを通すのは 1 回まで（運用パラメータ `spike.max_rounds`）。設計書があるのにまた spike と答えたら人へ（guard `spike_exhausted`）

### 2. スパイクのレーン（プロトタイプ）

- 進行: dispatcher が `factory:spike` の Issue を `spike` のジョブに積む。ワーカーは `worker/spike.sh` → `core-gates/spike.py`。製品のリポジトリと Issue を読むだけで、何も書かない（作用は dispatcher が結果を見て行う）
- 役: Gen1 のプロトタイプは System Architect（`architect`）の 1 役だけ。原因の特定（コードと証拠）、同じ原因の開いている不具合の束ね、直すか revert か作り直すか、どの層をどう変えるか、体験や仕様が変わるかを決める。開いている QA の不具合の一覧（`defects.md`）はこの役が読む
- 成果物: 設計書（DesignDoc）。Gen1 は Issue のコメント（印 `<!-- factory:designdoc -->`）と artifacts の `DesignDoc` に残す。製品のリポジトリに置く形（仕様の決定）は Gen1.5 で
- 役の並びはスパイクのプランナーが決めるのが仕様の形だが、プロトタイプは 1 役なので持たない。プロダクトデザイナー・ドメインモデラーをスパイクに移すのは Gen1.5 で

### 3. スパイクの出口

- 体験や仕様が変わる方針（`experience_change`）か、確信度が低い（0.6 未満）ときは、人の判断へ（`factory:spike-human`、受信トレイ）。体験や仕様の判断は Biz の側の仕事。人は確かめてラベルを `factory:plan` に替える
- そうでなければ `factory:plan` に戻し、プランナーがもう一度着手判定をする。プランナーは設計書の方針に従って経路と見積もりを組み、方針は決め直さない
- 束ねた Issue には「#N の方針でまとめて直す」とコメントし、`factory:bundled` を付けて単独では流さない（流れている最中のものには触らない）

### 4. ADR 0053 の改訂を差し替える

メジャー不具合の Issue は今までどおり `factory:plan`・p0 で着手判定に入る。直し方はプランナーではなく、方針が要るとプランナーが判断したときにスパイクで決める。プランナーに渡していた `defects.md` はスパイクに移す（プランナーには、同じ原因らしい不具合があればスパイクへ回す材料として件数と題だけ残す）。

## 順番

1. この PR: 本 ADR、プランナーの `spike`、`spike` のジョブ（spike.sh・spike.py・dispatcher の後処理）、ADR 0053 の差し替え
2. 実際の不具合 1 件で通す（着手判定 → スパイク → 設計書 → 着手判定 → ビルド）
3. Gen1.5: 振り分けとレーンの計画の役を分ける、スパイクのプランナーと複数の役（プロダクトデザイナー・ドメインモデラー）、設計書を製品のリポジトリに置く

## 選ばなかった案

- 調査役をプランナーの手前に置く: 飛ばすかの判断ができない（オーナー）
- 調査役をビルドの経路の役に足す（ui_design と同じ並び）: ビルドの見積もりと切り方は方針が決まってから組むもので、方針の前に経路を組むことになる
- 事故の調査の委員会を使う: 合議で重く、即時に直す方針と合わない。直した後の振り返りに向く

## 結果

- 方針が決まっていないチケットがビルドのレーンに入らなくなる。プランナーは経路と時期だけを決める
- スパイクのジョブが 1 本増える（tier-large、読むだけ）。プロトタイプの費用と効き目は、通した件で見る
- Gen1.5 の設計の材料として、着手判定の `spike` の率、設計書の確信度、出口で人に回った率を記録に残す
