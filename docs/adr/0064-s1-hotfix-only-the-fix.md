# ADR 0064: S1 の緊急便は、本番の版に直しだけを足して出す（原因が明らかな直後の不具合は revert）

- 状態: 承認（2026-11-16 オーナー、#546。方針：「main を丸ごと載せることで二次被害のリスクがある。S1 は cherry-pick をしてでも、その問題だけを直せると良い。リリース直後の問題でどの PR か明確に分かる場合は revert で対応。一旦は a で良い」）
- 関係: ADR 0053（メジャー不具合の即時修正と再リリース。決定 3 の緊急便と決定 4 の revert をこの ADR で具体にする）、ADR 0043 の O6（定期便と緊急便）、ADR 0049・0060（出荷の QA の関門）、ADR 0062（QA が差し止めを解く）、ADR 0063（流出の振り返り。この ADR はその最初の打ち手）、ADR 0012（出荷・contract のマイグレーション）

## 文脈

S1 の緊急便は、その時点の main をまるごと載せ、staging に出たあと supervisor が本番まで承認する（ADR 0053 の決定 3 と 2026-11-14 の追記）。直しを急ぐための決まりだが、まだ QA の関門を通っていないほかの変更も一緒に本番に出る。

2026-11-16 の rally 0.53.0 で、これが二次被害になった。なりすまし（rally#1785）の直しを出した緊急便に、同じ日にマージされた別の直し（PR #1768）が乗り、それが新しい S1（rally#1798。無料の体験予約のキャンセルで今月の通話回数が減る）を本番に持ち込んだ。QA の関門は本番に出たあとの staging で見つけた。

S2 については 2026-11-14 の追記で、本番は QA の関門と承認者を待つ形にした。S1 は急ぐので自動の承認を残したが、載る中身を絞っていなかった。

## 決定

### 1. S1 の緊急便は「直しだけの便」にする

- 土台は**いま本番に出ている版のコミット**（その Release の `release.built` の `commit`）。そこから製品リポに `hotfix/<本番の版>` のブランチを切る
- その上に、**S1 の直しの PR のコミットだけ**を cherry-pick する（squash マージの 1 コミット。同じ Incident で束ねた直しが複数あれば、マージの順にすべて）
- 版は本番の版の patch を 1 つ上げる（例: 0.52.0 → 0.52.1）。Release の `prs` は直しの PR だけ。main のほかの変更は Release に入らず、次の定期便で QA の関門を通って出る
- 出し方は今の緊急便と同じ: staging に出したあと supervisor が本番を承認する（QA の関門の報告は待たない。`release.approved` の `qa_skipped` に理由を残す）。関門は staging の配備で今までどおり開き、結果は記録に残る
- 便の記録（`release.train`）に `mode: hotfix`、土台の版とコミット、cherry-pick したコミットを残す
- staging はいったん直しだけの版になる。次の定期便で main の版に戻る（main には直しがすでに入っている）。staging の DB が main の版の expand まで進んでいても、expand は古い版と両立する決まり（ADR 0012）なので戻さない

### 2. cherry-pick がぶつかったとき

- 直しが、本番の版にまだない変更の上に書かれていて、cherry-pick がぶつかったら、工場は自分で解かない（S1 の直しを、確かめていない形に書き換えることになる）
- そのときは **main をまるごと載せる便**に切り替えるが、**本番の自動の承認はしない**。載るほかの変更が QA の関門を通るのを待ち、承認者（事業主・事業主代理）の判断で本番に出す（S2 の緊急便と同じ扱い）
- 切り替えたことは、受信トレイに承認者宛てのお知らせとして出す（「直しだけでは出せなかったので、関門の確認を待って出す」）

### 3. 直後の不具合で原因の PR が明らかなら revert

本番に出た直後の版で見つかった S1 で、原因の PR がはっきり分かるときは、直しを待たずにその PR を戻す（ADR 0053 の決定 4 を具体にする）。

- 「直後」: 見つけた不具合が、いま本番に出ている最新の版で入ったもの（原因の PR がその版の Release の `prs` にある）
- 「原因の PR が明らか」: プランナーかスパイク（ADR 0055）が、Defect の Issue に原因の PR を書き、根拠（再現とその PR の差分の関係）を添えたもの。推測だけのものは対象にしない
- 戻せる条件（ADR 0053 の決定 4 のまま）: 原因の PR より後にマージされた PR が、その PR の変えたファイルに触れていない。contract のマイグレーションを含まない
- 戻し方: 製品リポの main に revert の PR を出し（製品のマージ基準で入れる）、同じ revert のコミットを決定 1 の直しだけの便で本番の版に載せて出す
- 戻した PR のチケットは開き直し、直してから次の便で出す
- 条件に合わなければ、決定 1（直して直しだけを出す）で扱う

### 4. 変えないもの

- S1 の差し止めと、その解除（ADR 0062。QA が本番で確かめて解く）
- S2 の緊急便（staging までは急ぎ、本番は関門と承認者を待つ）
- 定期便の中身と承認
- 本番を立てない段階（development）の製品は、緊急便で staging に出すまで（直しだけの便にはしない）

## 段取り

1. 本 ADR のオーナーの承認
2. `train.py`・`ship.py`: 直しだけの便（土台の版のコミット、`hotfix/` ブランチ、cherry-pick、patch の版）。ぶつかったときの切り替えとお知らせ
3. `major_defect.py`: S1 の緊急便を直しだけの便で出す。自動の承認は直しだけの便に限る
4. revert（決定 3）: 条件の判定、revert の PR、直しだけの便
5. 試験: ぶつからない・ぶつかる・revert の 3 つの経路

2〜5 は出荷の決まりの変更なので、PR はオーナーに見せてからマージする。

## 選ばなかった案

- **main をまるごと載せ、関門を通っていない変更があれば本番の自動の承認をやめる**（案 b）: 安全だが、S1 の直しが関門と人の判断を待つ。ぶつかったときの逃げ道としてだけ使う（決定 2）
- **今のまま**（案 c）: 二次被害が 2026-11-16 に実際に起きた
- **ぶつかったら工場が解いて出す**: S1 の直しを、どこでも確かめていない形に書き換えて本番に出すことになる

## 結果

- S1 の緊急便で本番に出る変更は、直し（または戻し）だけになる。ほかの変更は必ず QA の関門と承認者を通る
- 本番の版と main がしばらくずれる（hotfix のブランチ）。次の定期便で揃う
- 見る数: 直しだけの便の数、ぶつかって切り替えた数、revert した数、緊急便のあとに見つかった S1（二次被害）の数。流出の振り返り（ADR 0063）が効き目を数える
