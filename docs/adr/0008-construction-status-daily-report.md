# ADR 0008: 建設状況の日次レポート

- 状態: 承認（2026-10-27 Tetsuro。「レポートはプロダクト品質や工場の精度に影響しないのでマージしてよい」。見る場所は claude.ai のページ、毎朝 6:00 JST）
- 関係: 憲章 07 節（ロードマップと Exit 条件）、ADR 0002（欠損を隠さない）、ADR 0004（supervisor）、ADR 0005（工場状況 Issue）、`definitions/roadmap.yaml`

## 文脈

工場の建設がどこまで来たかは、建設者が聞いたときに手元の Claude が見積もって答えていた（2026-10-27 の「全体の約 2 割」）。
見積もりは聞くたびに根拠が変わり、トークンも使う。建設者は毎朝、前日分と累計をグラフで見たい。予算が少ないので、日次の生成にトークンをなるべく使わない。
Gen2 以降のメタファクトリーでも、工場ごとの建設状況の見える化は要る。個別工場の機能ではなく Engine（メタファクトリー）側の機能として育てる。

## 決定

1. **進捗は表から機械的に出す**。憲章 07 節の各フェーズを「測れる項目」に分けた `definitions/roadmap.yaml` を正本にする。項目は done / todo / 割合（manual）か、取得元から測る数値（GitHub、建設作業フォルダ、制御プレーン）。フェーズは項目の平均、全体はフェーズを期間の目安（週）で重み付けした平均
2. **集計は LLM を使わない**。`health/daily/status_report.py` は標準ライブラリと PyYAML（と、あれば psycopg）だけ。日ごとの系列（マージした PR を工場と建設者で分けたもの、ジョブの成否、費用、停止の件数と時間、検査の件数）は毎回取得元から作り直し、状態を持たない
3. **govern の経路に置く**。進捗と健康は学習器に採点させない（憲章 06 節）。learn の出力は入力にしない
4. **集計は Mac、描画はクラウド**。ジョブ・停止・費用は Mac の制御プレーンにしかないので、集計は supervisor が JST の 5 時（`DAILY_REPORT_HOUR`）を過ぎて今日の `report.daily` がなければ 1 回走らせる。結果は固定 Issue（`factory:construction`、factory-engine）の本文に書き、末尾にスナップショットの JSON を埋める。日次の文章はコメントで足す
5. **毎朝 6:00 JST に claude.ai のページを更新する**。クラウドの予約（トリガー）が `health/daily/render_html.py` で Issue のスナップショットをテンプレート `page.html` に差し込み、同じ URL に公開し直す。LLM が書くのは公開の手続きだけで、中身は決定的
6. **推移は events に残す**。毎回のスナップショットを `report.daily`（dedupe は JST の日付）に記録し、全体の進捗の折れ線はそこから描く
7. **「前日」は JST の 0〜24 時**。累計は建設の初日（2026-10-25）から前日まで
8. **測れなかった項目は「不明」と出し、0 で数える**。前回の値で埋めない（欠損を隠さない）

## Gen1 限定: 自動マージできなかった PR と出入り（2026-10-27 追加）

Tetsuro の依頼で、工場の PR のうち自動マージされなかったものを観点ごとに数え、日ごとの出入り（入: 工場が出した PR、出: 自動マージ・人のマージ・閉じた）と並べてページに出す。目的は自動マージの基準づくりの知見を溜めることと、出入りのレポート。Gen1 の特別対応で、メタファクトリーの機能（建設状況の見える化）には含めない。

- 観点は supervisor の最新の `supervisor.merge_decided` から機械的に決める: 表（manifest の autonomy）が承認を求めた変更種別 ＞ 表は auto だが工場の権限（phase_grants）で止めた ＞ 判定まで来なかった（CI・衝突・途中終了）。人が閉じたものは「人が閉じた」も付ける
- 「表が auto で人がそのままマージした件数」を併記する。自動マージを解放する根拠（manifest の release_conditions）
- 実装は `status_report.py` の `merge_gate()` とページの「Gen1 限定」の欄。Gen2 に持っていかないときは両方を消す

## 選ばなかった案

- **手元の Claude が毎日見積もって書く**: 根拠が毎回変わり、トークンを使う
- **ページを Claude に毎回書かせる**: 見た目が日ごとに揺れ、トークンも多い。テンプレートを PR で磨く方が、メタファクトリーの機能として育てやすい
- **GitHub Actions の cron で出す**: ジョブ・停止・費用が Mac の制御プレーンにあり、Actions から届かない
- **新しい常駐サービスにする**: 1 日 1 回の処理に常駐は要らない。supervisor の周回に載せれば heartbeat で生死も見える

## 結果

- 建設者は毎朝ページを開けば、全体とフェーズの割合、前日と累計の指標、Exit 条件ごとの実測、頼まれていることを見られる。Issue は GitHub の通知と元データを兼ねる
- Mac が寝ていた日は集計が出ず、6 時のページは前回のまま（日付で分かる）
- 項目の完了は `roadmap.yaml` の manual を書き換える PR で反映する。自動で測れる項目を増やすほど、書き換えの手間と見積もりの揺れが減る
- 重み（期間の目安）、項目の分け方、指標の選び方は仮置き。Gen2 で Blueprint ごとの roadmap を持つときに、この表の形を Engine の型にする
