# ADR 0008: 建設状況の日次レポート

- 状態: 提案（2026-10-27。supervisor に日次のタイマーを足すのは工場の構成に触れるので、Tetsuro の了承を得てからマージする）
- 関係: 憲章 07 節（ロードマップと Exit 条件）、ADR 0002（欠損を隠さない）、ADR 0004（supervisor）、ADR 0005（工場状況 Issue）、`definitions/roadmap.yaml`

## 文脈

工場の建設がどこまで来たかは、建設者が聞いたときに手元の Claude が見積もって答えていた（2026-10-27 の「全体の約 2 割」）。
見積もりは聞くたびに根拠が変わり、トークンも使う。建設者は毎日見たい。予算が少ないので、日次の生成にトークンを使いたくない。

## 決定

1. **進捗は表から機械的に出す**。憲章 07 節の各フェーズを「測れる項目」に分けた `definitions/roadmap.yaml` を正本にする。項目は done / todo / 割合（manual）か、取得元から測る数値（GitHub、建設作業フォルダ、制御プレーン）。フェーズは項目の平均、全体はフェーズを期間の目安（週）で重み付けした平均
2. **LLM を使わない**。`health/daily/status_report.py` は標準ライブラリと PyYAML（と、あれば psycopg）だけで、日次のトークンは 0
3. **govern の経路に置く**。進捗と健康は学習器に採点させない（憲章 06 節）。learn の出力は入力にしない
4. **見る場所は GitHub の固定 Issue**（ラベル `factory:construction`、factory-engine）。本文を毎回ダッシュボードに書き換え、日次レポートはコメントで足す。工場状況 Issue（`factory:status`）は停止の通知用なので分ける。スマホの GitHub アプリで通知付きで見られる
5. **推移は events に残す**。毎回のスナップショットを `report.daily`（dedupe は JST の日付）に記録し、直近 14 日を折れ線にする。表を足さない
6. **supervisor が 1 日 1 回走らせる**。JST の `DAILY_REPORT_HOUR`（既定 7 時）を過ぎて今日の `report.daily` がなければ起動する。常駐処理は増やさない。Mac が寝ていた日は起きたときに出る
7. **測れなかった項目は「不明」と出し、0 で数える**。前回の値で埋めない（欠損を隠さない）

## 選ばなかった案

- **手元の Claude が毎日見積もって書く**: 根拠が毎回変わり、トークンを使う
- **claude.ai のページを毎朝クラウドのセッションで更新する**: 見た目は良いが 1 日数万トークン。必要になったら同じスナップショットから描く形で足せる
- **GitHub Actions の cron で出す**: ジョブ・停止・費用が Mac の制御プレーンにあり、Actions から届かない
- **新しい常駐サービスにする**: 1 日 1 回の処理に常駐は要らない。supervisor の周回に載せれば heartbeat で生死も見える

## 結果

- 建設者は Issue を開けば、全体とフェーズの割合、Exit 条件ごとの実測、頼まれていること、前日の動きを見られる
- 項目の完了は `roadmap.yaml` の manual を書き換える PR で反映する。自動で測れる項目を増やすほど、書き換えの手間と見積もりの揺れが減る
- 重み（期間の目安）と項目の分け方は仮置き。実測の推移を見ながら直す
