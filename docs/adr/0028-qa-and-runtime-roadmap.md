# ADR 0028: QA と実行環境のケイパビリティと、P5 の 2 段への分割

- 状態: 承認（2026-11-04 オーナー。P5 を 2 段に分ける案をカードで選択。アーキテクチャに触れる点は本文で承認、実装は各 PR）
- 関係: ADR 0012（出荷）、ADR 0019（内部品質）、ADR 0023（学習の体系）、ADR 0024（知見と委員会）、ADR 0025（上流の工程）、factory-engine #160（SHIP_PROD_HOLD。製品の段階ができるまでのつなぎ。段階に置き換えた: ADR 0012 の追記 2026-11-05）、ADR 0049（決定 2 の「ship の手前で動作確認」を出荷のレーンに配線する。2026-11-11 提案）
- 検討の記録: 50_build-work/strategy/qa-and-runtime-2026-11-04.md（発散）、strategy/qa-model/、strategy/capability-model/、strategy/roadmap-qa-runtime/（図）、capability-model-knowledge-2026-11-04.md（知見）

## 文脈

2026-11-04 のデモの準備で、工場に「アプリを立ち上げ、データを入れ、利用者の流れを通して確かめる」工程がないことが露呈した。作業機に Xcode と Flutter がなく iOS シミュレーターで生徒アプリを動かせない、シードが staging にしかない、月額契約がバックエンドのメモリにしかない、コーチのチャットで一覧が更新されない（rally #895。単体テストは API をモックにしているので拾えない）。どれも ship まで誰も気づかなかった。

今の工場が確かめているのは、CI の単体テスト、画面のキャプチャの前後比較、検査役と judge による「読んで判断」まで。ケイパビリティ台帳にも実行環境と QA の群がない。人のレビューでも、報告と実際に動かして見るものの乖離が大きいことが分かった。

オーナーの方針（2026-11-04）:

- QA という役を新設し、実装のラインとは切り離して ship の手前で動作確認する。機能要件のカバレッジだけの E2E にはしない（E2E は QA のケイパビリティの 1 つ）
- QA の定義は「プロダクトの利用者（エンドユーザー、カスタマーサポート、運営担当）にとって使いやすいシステムであるかの品質を担保する」。システムの運用（監視・ログ・戻し）は QA の外
- 保証の対象は機能の正しさより「利用者の流れ」。そのためにタスクの時点でユーザーストーリーが要る
- 言葉と文脈、データの持続（シナリオベース）、端末（サポート対象を定義し、対象は保証）、脆弱性診断（リリースフローに必ず。シフトレフトと水際の両方）、アクセシビリティ（Blueprint でレベルを定義し、設計の時点から）も QA の観点
- 障害の重要度は事業のフェーズとドメインで変わる。エラーバジェットを決め、超えない限り無視する基準が要る。個人情報の漏洩のような欠陥はどの機能開発より優先し、QA の判断で指示役とプランナーに対してラインを差し止める裁量を持つ。リリース判断は五月雨にしない
- 実行環境は「ステージ × プラットフォーム」で考える。顧客は B2C が多くモバイルが要る。iOS は Mac でしか動かないので、Mac 側の常駐クライアント（ランナー）が最初の現実解。夜間は無人でシミュレーターの探索テスト、日中は人が並走して署名と TestFlight。鍵は工場に預けない
- 今日のデモで Claude Code 越しに iPhone シミュレーターを動かしつつサーバ側の Claude と変則的にシナリオを流した。これを 1 つの指示役が分断されずに両者に指示できる環境にしたい
- 製品の段階（development / launch / operating）を工場が持ち、段階で出荷先を決める（リリース管理）。rally は development で、本番は動かさない
- Gen1 は精度よりカバレッジ。予算は絞る

## 決定

### 1. P5 を 2 段に分ける

`definitions/roadmap.yaml` の P5「Operate」を、P5a「触れる環境と QA の 1 本」（6 週）と P5b「Operate」（6 週）に分ける。P5a は P4 に依存しないもの（Mac ランナー、触れる環境）から着手し、P4 の残りと並行でよい。ユーザーストーリーの型は P4 の `typed_upstream` と同じ PR で足す。

P5a の項目: `mac_runner`、`one_orchestrator`、`touchable_env`、`user_story`、`qa_verdict`、`scenario_time`、`nightly_explore`、`defect_metrics`、`quality_policy`、`product_stage`、`ci_diagnose`。順番は ① Mac ランナーと触れる環境 → ② ユーザーストーリー 3 本と QA 役の最初の Verdict → ③ 夜間の探索、Defect の型と指標、Blueprint の欄、CI の診断。

P5b は既存の 4 項目に `severity_budget`、`release_train`、`ephemeral_env`、`preview_distribution`、`quality_learn` を足す。P6 は変えない。

### 2. QA 役と Verdict を足す

- QA 役（`agents.yaml`）を新設する。入力は Release 候補、ユーザーストーリー、シナリオ、Blueprint の品質方針とサポート対象、環境。出力は Verdict、Defect、品質レポート、人への印
- Verdict は judge と同じ判断の型（決定・確信度・根拠。`judgments.yaml`）で記録し、判断の記録（ADR の B7・C3）と人判断との比較に乗せる。見た目（aesthetic、ADR 0025 の E4）と言葉の温度は判定せず、印として人に出す
- Gen1 は QA 役 1 つが観点を切り替える。診断役と障害対応役は P5b で分ける（役の分割の案は検討の記録）

### 3. Mac ランナーを工場の機械として足す

- 工場の外の機械をジョブから呼ぶ最初の例。Mac 上の常駐プロセス（MCP サーバー: シミュレーターの起動・インストール・画面の取得・操作・ログの回収）を、QA ワーカーのツールとして渡す。対話は要らないので Remote Control ではない
- Gen1 は工場自体が Mac にいるので、dispatcher から直接呼ぶ最短の形でもよい。クラウド化しても iOS だけ Mac に残せる形にする
- 夜間（unattended）は署名なしの debug ビルドで探索。日中（attended）は署名・TestFlight・ストア提出を人の Mac のキーチェーンで通す。人の不在時は便を飛ばすだけで止まらない

### 4. Blueprint に品質方針と製品の段階の欄を足す

- 品質方針: アクセシビリティのレベル、扱うデータの種類、サポート対象の表（OS 版 × 端末 × ブラウザ × 支援設定）、言葉の指針、S1（止める）の条件。値は Gen1 では建設者が代理で仮置き
- 製品の段階: development / launch / operating。段階で出荷先と承認が決まる（development は production を立てない）。切り替えは人。#160 の `SHIP_PROD_HOLD` はこれができるまでのつなぎ
- 欄の型は `definitions/quality_policy.yaml` と `definitions/product_stages.yaml`（2026-11-05）。製品側は `.factory-config/quality_policy.yaml` と manifest の `product_stage`

### 5. Defect と Incident を events の型に足す

- Defect: どの Release、どの変更、どこで見つけた（上流 / PR / CI / QA / 診断 / 本番）、原因の工程、観点、再現手順。来歴（ADR の C6）と同じく全属性 optional で、紐付け率を併記
- Incident: 本番で利用者に影響が出たもの。Stoppage（工場の止まり）とは別の型で同じ events に載せる。重要度（S1〜S4）とエラーバジェットの照合は P5b
- 品質の指標（流出防止率、変更量あたりの欠陥、出やすい場所、発見工程の分布）は Govern が集計する。QA 自身には採点させない

### 6. 配布は出荷側のアダプタ

preview の配布（TestFlight、Play 内部テスト）、署名、ストア審査は実行環境ではなく、出荷（ADR 0012 の「出し先は環境の定義を差し替える」）の配布方式のアダプタとして置く。実行環境は「工場が動かして確かめる場所」に絞る。

## 順番

1. この PR: roadmap.yaml と本 ADR。Mac の正本（台帳の G 群・H 群、積み残し 15、憲章 07 節）は同時に直す
2. 着手はラインの再開の指示の後。P5a-① から

## 追記（2026-11-05）: ユーザーストーリーの型と最初の 3 本を先に入れる

決定 1 の「ユーザーストーリーの型は P4 の `typed_upstream` と同じ PR で足す」を変える（オーナーがカードで選択）。`typed_upstream` を待つと、P5a-② の QA 役の最初の Verdict も止まるため。

- 先に入れるもの: 型（`definitions/user_story.yaml`、`artifacts.yaml` の `UserStory`）と、rally の `specs/stories/` の 3 本（コーチが新しい相談に返事する、生徒が月額契約して翌日も残っている、CS が「予約が消えた」の経緯を追う）。製品の側でストーリーが正本の id だけを使っているかを検査する
- 後に残すもの: プランナーの出力にストーリー（増やす・変える・守る）を加えることは、従来どおり `typed_upstream` で
- 既存機能に遡って書いたストーリーは「あるべき流れ」で書き、今の実装が満たしていないところは `known_gaps` に書く。QA 役の最初の Verdict の材料にする

## 選ばなかった案

- P5 の項目に足すだけ: フェーズが分かれないと日報の進捗が粗くなり、触れる環境の着手が P4 の後に見える
- P4 と P5 の間に新フェーズ: P4 の後に直列になり、触れる環境が遅くなる
- Flutter Web で iOS を代用し続ける: push 通知、カメラ、IAP など B2C で肝心なものが確かめられない
- クラウドの Mac（EC2 Mac）: 費用が高く、Gen1 の予算に合わない。商用化で選択肢に戻す

## 結果

- 工場のモデルは Business / Dev / Ops の 3 領域と横断（Govern、Learn）で整理し、ケイパビリティは工程・資源・性質の 3 種類で表す（検討の記録。Gen2 の工場建設で改めて検討）
- QA の責務が大きいので、役の分割（品質方針役 / QA 役 / 診断役 / 障害対応役 / Govern / 品質の Learn）は P5b で決める。Gen1 は型と裁量だけ分けておく
