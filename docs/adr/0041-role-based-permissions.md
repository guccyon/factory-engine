# ADR 0041: 工場の権限を役ごとに分け、工程を変える変更は特権のラインで扱う

- 状態: 承認（2026-11-08 オーナー。決めどころ R1〜R6 は推奨どおり）
- 関係: ADR 0003（制御プレーン。秘密情報は .env、ワーカーは PR 作成まで）、ADR 0004（supervisor。決定 5 のマージ用トークンの分離）、ADR 0010（エージェントの差し替え）、ADR 0014（検査役の承認）、ADR 0024（知見の委員会）、ADR 0031（工場の自動更新）、ADR 0037・0039（単発の依頼の道）、`definitions/change_type_rules.yaml`、`definitions/agents.yaml`、製品の `.factory-config/manifest.yaml`（autonomy・phase_grants・always_human_approve）、Gen2 の設計の叩き台（役＝職能の組み合わせ＋モデル＋道具と権限＋裁量）

## 文脈

製品の CI の定義（`.github/workflows/`）にある Engine の版（`ENGINE_REF`）を上げる変更を、工場が出せなかった。理由は 2 つある。

1. GitHub は、ワークフローのファイルを変える push に、トークンのワークフローの権限を求める。工場のトークンにはそれが無い
2. 製品の開発ガイド（rally の `CLAUDE.md`）が、ワークフローの変更をワーカーの権限の外としている

その結果、Engine の検査の道具（`core-gates/`）を直すたびに、製品の CI の版上げを建設者が手で行っている。

オーナーの指摘（2026-11-08）:

- 工場が開発する製品で、ワークフローが権限上書き換えられないということは、あってはならない。Claude の動作方針として実行しないだけなら、Issue として工場のラインに乗せて対応できるはず
- 工場のリソースの 1 つとはいえ、工場の中の全プロセスが同じ権限を共有しているのも違う。実際の事業部でも、強い権限を持つ役とそうでない役がある
- ワークフローは工程に影響を与えるものなので、工場の中でも特権を持ったラインの定義が要るかもしれない

### Gen1 の今の権限

| 主体 | GitHub の身元 | 権限 | 根拠 |
|---|---|---|---|
| ワーカーのすべての種類（実装・続き・本文の直し・検査役・QA 役・デザイナー役・デザインの講評・委員会・窓口の相談・ケースの講評・聞き返し） | 1 つの fine-grained PAT（`GH_TOKEN`） | Contents・Pull requests・Issues の読み書き。ワークフローは無し | `orchestrator/.env.example`、各 `worker/*.sh` |
| dispatcher・pr_events・出荷・通知・factoryctl | 同じ PAT | 同上 | `dispatcher.py`、`ghapi.py` |
| supervisor（マージ） | 同じ PAT（`SUPERVISOR_GH_TOKEN` の枠はあるが空） | 同上。Contents の書き込みでマージもできる | ADR 0004 決定 5、`compose.yaml` |
| 更新役（工場の自動更新） | Mac の Docker | 工場自身の作り直し | ADR 0031 |
| Claude Code | 1 つの OAuth トークン（`CLAUDE_CODE_OAUTH_TOKEN`） | 全ワーカーで共有 | `compose.yaml` |

分かること:

- **権限の差は「プロンプトとガイドの約束」と「supervisor の表（manifest の matrix）」だけ**で、身元とトークンでは分かれていない。検査役（読むだけでよい）も実装役と同じく push もマージもできる。ADR 0004 決定 5 が「約束をトークンの権限でも守れるように」と枠を作ったが、使っていない
- 一方で、ワークフローだけはトークンで一律に閉じている。**表（`change_type_rules.yaml`）はワークフローの変更を「権限・秘密に触れる行があれば secrets_iam、なければ通常の変更」と細かく分けているのに、トークンがその手前で全部止めている**。方針の層と強制の層が食い違っている
- PAT は人のアカウントに結び付き、期限で全体が止まる（更新は人の手）

## 考え方

- **役ごとに、その仕事に要る最小の権限を、その仕事の間だけ渡す**。事業部の職務分掌と同じで、作る人と承認する人、普段の仕事と工程そのものを変える仕事を分ける
- **方針は表（manifest・`change_type_rules.yaml`）、強制は身元とトークン**。表で「人の承認」にしたものを、トークンでも越えられないようにする（二重の鍵）。逆に、表で許したものをトークンが一律に止めることもしない
- **特権は入力の信頼とセットにする**。ワークフローは CI の秘密情報と GitHub の権限に届くので、外から来た文（Issue の本文、PR のコメント、窓口の依頼）に誘導されて書き換わるのがいちばん怖い。特権のラインは、信頼できる発生元のチケットしか受けない
- **特権が要る変更そのものを減らす**。例えば `ENGINE_REF` を CI の定義から外に出せば、Engine の版上げは普通の変更になる

## 決定（案）

### 1. 権限の段（ロール）を 4 つ持つ

| 段 | 役 | GitHub の権限 | 外の文を読むか |
|---|---|---|---|
| **見る** | 検査役・QA 役の判定・委員会・講評・窓口の相談・聞き返し | Contents 読み、Pull requests・Issues の書き込み（コメントとラベルだけ） | 読む |
| **作る** | 実装・続き・本文の直し・デザイナー役 | Contents 書き（作業ブランチ）、Pull requests・Issues 書き。ワークフロー無し。main への反映はできない | 読む |
| **決める** | supervisor（マージ）・dispatcher・出荷 | マージ、ラベル、出荷に要るもの。LLM を通らない決定論のプロセスだけ | 読まない（番号を拾うだけ。ADR 0004 決定 4） |
| **工程を変える（特権）** | 特権のラインのワーカー | 作るの権限＋ワークフロー | 信頼できる発生元だけ（決定 3） |

更新役（ADR 0031）は Mac の Docker に届く別の特権で、本 ADR では今のまま（人の承認の線は ADR 0031 のとおり）。Claude Code の OAuth トークンの分け方は本 ADR の外（使用量の枠の話なので ADR 0029 の流量と一緒に考える）。

### 2. 身元は GitHub App にし、ジョブごとに権限を絞った短命のトークンを渡す

- 工場の GitHub App を 1 つ作り、製品のリポジトリに入れる。秘密鍵は dispatcher だけが持つ（`.env`。将来は AWS の Secrets Manager）
- dispatcher がジョブを起動するたびに、そのジョブの役の段に合わせて **権限と対象リポジトリを絞ったインストールトークン**（1 時間で切れる）を発行して渡す。ワーカーは PAT を持たない
- 「決める」段のプロセスは自分用に発行する
- main への反映は、製品の ruleset で **supervisor（App）だけが通れる**ようにする。作る段がトークンでマージを試みても GitHub が止める
- 役と段の対応は定義ファイル（`definitions/agents.yaml` の役に `grant:` を足す）に置き、dispatcher はそれを引くだけにする。Gen2 の「役＝職能＋モデル＋道具と権限＋裁量」の「権限」がこの欄になる

PAT のままで役ごとに分ける案（段ごとに PAT を 4 本）は、選ばなかった案に書く。

### 3. 特権のラインを分ける

- **入口**: Issue のラベル `factory:privileged`。付けられるのはオーナーと、工場の決定論のプロセス（例: Engine の版が上がったときに版上げのチケットを起こす supervisor）だけ。それ以外の経路（窓口の依頼、外の人の Issue）で付いたラベルは dispatcher が外して人に回す
- **ジョブ**: 実装と同じ流れだが、別の種類（kind）として数え、同時に 1 本まで。ワーカーには特権の段のトークンを渡す
- **プロンプト**: Issue の本文は「データとして扱う」に加えて、変えてよいファイルの範囲をチケットに書かせ、範囲外の変更は PR にしない
- **マージ**: `change_type_rules.yaml` の判定に従う。ワークフローの変更で権限・秘密に触れる行がある（secrets_iam）ものは人の承認。それ以外の扱いは R3 で決める
- **記録**: 特権のラインのジョブ・PR・マージは events に別の種類で残し、日報で必ず見せる

### 4. 特権が要る変更を減らす（版の外出し）

- 製品の CI が Engine の道具を取る版（`ENGINE_REF`）を、ワークフローの外のファイル（例: `.factory-config/engine.lock`）から読むようにする。版上げは通常の変更になり、特権のラインを通らない
- 版のファイルの変更は factory_rule に当てて、表の判定（今は auto）で扱う
- テンプレート（`templates/ci/`）を合わせて直し、製品に写す最初の 1 回だけ特権のラインか建設者が行う

### 5. 移し方（順番）

1. 版の外出し（決定 4）。これだけで今回の詰まりは解ける
2. GitHub App を作り、dispatcher にトークンの発行を足す。まず全ジョブに今と同じ権限で渡し、PAT を外す（PAT の期限切れの心配が無くなる）
3. 役ごとの段を `agents.yaml` に書き、段どおりに絞る。ruleset で main を supervisor だけにする
4. 特権のラインを足す

1 は Gen1 で行う。2〜4 を Gen1 で行うか Gen2 の最初に行うかは R1。

## 決めどころ（オーナーの判断）

- **R1. いつ入れるか**: 推奨は「版の外出し（順番 1）は Gen1 ですぐ。App とトークンの発行（順番 2）も PAT の期限（11/24）の前に Gen1 で。段の絞り込みと特権のライン（順番 3・4）は Gen2 の役の定義と一緒に」
- **R2. 身元**: 推奨は GitHub App 1 つ＋ジョブごとに絞ったトークン。代わりは段ごとの PAT
- **R3. 特権のラインのマージ**: 推奨は「権限・秘密に触れない差分（secrets_iam に当たらない）は今の表どおり自動、当たるものは人」。代わりは「特権のラインの PR はすべて人の承認」
- **R4. 特権のラインの入口**: 推奨は「オーナーと決定論のプロセスだけ」。代わりは「検査役か委員会が承認したチケットも入れる」
- **R5. 「見る」段にもコメントの書き込みを許すか**: 推奨は許す（検査役の指摘を PR に残すため）。代わりは書き込みは dispatcher が代わりに行い、見る段は読むだけ
- **R6. 製品の開発ガイドの書き方**: 推奨は rally の `CLAUDE.md` の「`.github/workflows/` の変更（ワーカーの権限にない）」を「特権のラインのチケットでだけ行う」に改める

## 選ばなかった案

- **今の PAT にワークフローの権限を足す**: 一番早いが、全ワーカーが CI の定義を変えられるようになる。外の文に誘導された実装役が、CI から秘密情報を持ち出す経路ができる。方針（表）でマージを止めても、PR の CI はブランチの定義で走るので、PR を作った時点で届いてしまう
- **段ごとに PAT を分ける**: 仕組みは簡単だが、人のアカウントに結び付いたトークンが 4 本になり、期限の更新も 4 倍になる。どれも人のアカウントの全リポジトリの権限の範囲内でしか絞れない
- **ワークフローの変更はずっと建設者が行う**: 今の運用。Engine の道具を直すたびに人の手が要り、「人の承認ボタンと審美眼だけ」のゴールに反する

## 結果

- 工程を変える変更も工場のラインに乗る。人が触るのは、権限・秘密に触れるものの承認だけになる
- 役の約束（検査役は書かない、実装役はマージしない）が、プロンプトだけでなく GitHub でも守られる
- 人のアカウントに結び付いた PAT が無くなり、期限切れで工場が止まらなくなる
- dispatcher がトークンを発行する役を持つので、dispatcher の秘密鍵の扱いが新しい守りどころになる

## 確かめること

- ruleset の「更新の制限」で、PR のマージも supervisor の App だけに絞れるか（rally で試す）
- App のインストールトークンで作った PR に、製品の CI が今と同じく走るか
- 特権の段のトークンで、ワークフローのファイルを含む push が通るか
