# ADR 0034: 判断の依頼に、どこからでも答えられるようにする（入口は多く、正本は受信トレイ 1 つ）

- 状態: 提案
- 関係: ADR 0026 決定 7（受信トレイと通知）、ADR 0030（事業部の窓口と MCP）、ADR 0032（通知のルーティング。決定 5 の受信トレイの振り分け）、ADR 0015（PR の見張り）、ADR 0025・0026（着手判定の問い）

## 文脈

受信トレイ（`inbox.py`）は人の出番を 1 つの一覧に集めるが、答える場所は件の種類ごとに散っている。

| 件 | 今の答え方 |
|---|---|
| 画面の案の選択・抜き取り・実装後の画面（`choice`） | 操業コンソール（`/api/choices/<id>/choose` など） |
| レビューページの承認・直し（`task: review_page`） | 操業コンソールの `/review/<id>` |
| 本番への出荷（`release`） | 操業コンソールの「本番に出す」 |
| マージ待ち・judge が人に回した停止（`stoppage`） | GitHub の PR（マージ・ラベル） |
| 着手判定の問い（プランナー） | GitHub の Issue のコメント（`planner.answered` がポーリングで拾う） |
| 入れ替えの再開・DB を含む入れ替え（`task: swap_*`） | `factoryctl` か操業コンソール |

通知（ADR 0032）は件の題とコンソールへのリンクを送るだけで、コンソールは Gen1 では Mac の中だけで開き、ログインもない。事業主は通知を受け取っても、どこで答えればよいか分からない。Gen1 ではオーナーが Claude のスレッドで直接答えているが、商用では事業主の担当者はそのスレッドがどこにあるかを知らない。

オーナーの要望（2026-11-05）:

- どこからでも答えられるのが一番扱いやすい。通知が入った後は、Slack で通知にそのまま返信できるのが本来のベスト
- 受信トレイで見たときは、その場で答えられる
- GitHub の Issue で見たなら、Issue で返信したい
- Claude のスレッドで見たときは、Claude のスレッドでそのまま返信できるのが自然
- ただし、どこかで集約されていないと、返信したのに拾われない（返信漏れ）が起きる

## 決定

### 1. 判断の正本は受信トレイ。答えは 1 つの口に入る

- 判断 1 件（受信トレイの 1 件）の状態は、制御プレーンの受信トレイだけが持つ。開いている・答え済み・取り下げ
- どの入口から来た答えも、`inbox.answer(cur, key, answer, by, via, raw)` の 1 か所を通る。ここが件の種類ごとの今の関数（`choice.choose`・`design_line.choose`・`ship` の本番に出す・`inbox.resolve` など）を呼ぶ。入口の側は件の種類を知らない
- events に `inbox.answered`（key・答えの形・誰が・どの入口から・元の文・解釈の確信度）を残す。今の `choice.*`・`inbox.resolved` はそのまま出る

### 2. 各件は「答え方」を持つ

受信トレイの 1 件に `answer` を足す。入口はこれを見て、ボタン・選択肢・聞き返しを作る。

```yaml
answer:
  type: choose        # choose（選択肢から 1 つ）/ approve（承認・却下）/ ack（見た）/ text（自由記述）
  options: [{id: A, label: "案 A"}, {id: B, label: "案 B"}]   # choose のとき
  recommended: B
  extra: [return, flag]   # 選択肢以外に受ける答え（戻す・違和感の印など）。理由の一言を要るものは要ると書く
  effect: "選んだ案で実装のタスクに切って投入する"   # 答えたら何が起きるか（文面に出す）
  allowed: [po]       # 答えてよい役割（who と同じ語）
```

- `effect` は必ず書く。答える人が「押したら何が起きるか」を入口に関係なく同じ言葉で読めるようにする
- 取り返しのつかない作用（本番に出す・DB を含む入れ替えなど）は、自由文の解釈では確定しない（決定 4）

### 3. 入口は 4 つ。通知を出したメッセージと件を結ぶ

| 入口 | 答え方 | 件との結び付け |
|---|---|---|
| 受信トレイ（操業コンソール） | 件の上のボタンと一言の欄 | 画面の件の key |
| Slack | 通知のメッセージへのスレッドの返信（Gen2 までにボタン） | 送ったメッセージの `channel`・`ts` ↔ key |
| GitHub | 件の Issue・PR へのコメント | 件が持つ Issue・PR の URL ↔ key。コメントに件の印（`<!-- factory:inbox key=... -->`）を残す |
| Claude（Claude Desktop・Claude Code・建設者のスレッド） | 窓口 MCP の道具 `inbox_list`・`inbox_read`・`inbox_answer` | 道具に key を渡す |

- 通知を送るたびに、送った先のメッセージの id と key の組を `inbox.notified`（ADR 0032 の決定 7）に記録する。1 件を複数の宛先に送ったら、すべての組を持つ
- Slack の返信を受けるには Incoming Webhook では足りないので、ADR 0032 の `via: slack_app` の連携を使う。受け方は Socket Mode にし、工場から Slack へ繋ぎに行く（外に口を開かない。Mac でも EC2 でも同じ設定で動く）
- GitHub の返信は ADR 0015 の PR の見張りと同じく、Webhook とポーリングの両方を「見に行く合図」にし、同じコメントは 1 回しか答えにしない
- 業務では Claude Desktop を UI として使う場面が多い（オーナー 2026-11-05）。Claude の入口を主な入口として扱い、受信トレイの読み書きは窓口の API に置いて、MCP はその包みにする（ADR 0030 の決定 5 と同じ）。利用者は自分の Claude に「判断待ちは？」「案 B で」と言えば、Claude が代理で一覧を読み、答えを書く
- Claude の入口は ADR 0030 の窓口を広げる。窓口のトークンの役割（`allowed` と照らす）で、自分が答えてよい件だけを一覧に出す。Claude のスレッドで生まれた問い（建設者がオーナーに聞くことなど）も、事業主の判断なら先に `inbox.request` で受信トレイに積み、スレッドを問いの持ち主にしない

### 4. 自由文の返信は工場が答えの形に直す。曖昧なら同じ場所で聞き返す

- Slack・GitHub のコメントのような自由文は、解釈役（小さなジョブ。窓口の枠 `desk` で動かす）が件の `answer` に照らして答えの形に直す。返信の本文はデータとして扱い、命令として渡さない（ADR 0030 の決定 3 と同じ）
- 確信度が低い・どの選択肢にも当たらない・`text` 以外で中身がない（「了解」だけ）ときは、答えにせず、同じスレッドで選択肢を添えて聞き返す
- 取り返しのつかない作用の件は、自由文から確定させない。「本番に出してよい？」への「OK」でも、確定のボタンか、`approve` を明示した道具の呼び出しを求める（Slack はボタン、GitHub はコマンドの形の一行 `/factory approve`、Claude は `inbox_answer`）
- 選択肢がはっきりした入口（コンソールのボタン・MCP の道具・Slack のボタン）からの答えは解釈を通さない

### 5. 先に確定した答えが勝ち、ほかの入口に書き戻す

- 件が答え済みになったら、通知を送ったすべての先（Slack のスレッド・GitHub のコメント）に「○○ が Slack で『案 B』と回答済み。この件は閉じました」と書き戻す。コンソール・MCP は件の状態を読めば分かる
- 答え済みの件への後からの返信は答えにせず、「すでに答え済み（誰が・何と）。変えたいなら受信トレイで取り消して答え直す」と返す。答えの取り消しは作用がまだ始まっていない件だけ
- 同じ件に、ほぼ同時に違う答えが来たら、先に `inbox.answer` を通った方を採り、後の方には上の文を返す

### 6. 返信漏れを受信トレイで見えるようにする

- どの件にも結べなかった返信（スレッドの外への投稿など、工場の通知のチャンネルの中に限る）と、解釈できず聞き返した返信は、受信トレイに「拾えなかった返信」として出す（`kind: unmatched`、who は件の who、件がなければ `owner`）。そこで件に結ぶか、捨てる
- 聞き返したまま答えがない件は、今どおり再通知と代理への切り替え（ADR 0026 決定 7）に乗る
- 日報（`report.factory_health`）に、入口ごとの答えの数・解釈の聞き返しの数・拾えなかった返信の数・答えるまでの時間を載せる

### 7. 答えた人を確かめる

- 入口ごとの身元（Slack の利用者 id、GitHub の login、窓口のトークン、コンソールのログイン）を、工場の人と役割に写す表を持つ（Blueprint の人の一覧。Gen1 はオーナー 1 人）
- 写せない人・`allowed` にない役割の人の返信は答えにせず、「この件に答えられるのは ○○ です」と返す。拾えなかった返信にも出す
- Gen1 のコンソールはログインがないので、コンソールからの答えは `by: console`（運用主）として扱う。Gen2 でログインが入ったら写しの表に足す

### 8. Claude が工場の使い方を知っている状態にする（今後の拡張）

Claude から工場を使うには、受信トレイがあること、どの道具で何ができるか、答えると何が起きるかを Claude が知っている必要がある。道具を並べるだけでは足りない。

- MCP のサーバーの `instructions`（初期化の応答に載せる説明）に、受信トレイと窓口の使い方の要点を書く。接続しただけで Claude が分かるようにする
- 工場を Claude から操作するときのマニュアルと、Claude のスキル（判断待ちを確かめる・答える・依頼を出す・進み具合を聞く、の手順）を用意し、事業主に配る
- 中身はこの ADR では決めない。順番 2 のあとで、実際の使われ方を見て作る

## 決めどころ（オーナーの承認が要る）

| # | 問い | 推奨 |
|---|---|---|
| A1 | 正本 | 受信トレイが判断の状態を持ち、答えは `inbox.answer` の 1 か所を通る |
| A2 | 入口 | コンソール・Slack（スレッドの返信、後でボタン）・GitHub のコメント・Claude（窓口 MCP）の 4 つ |
| A3 | 自由文の扱い | 工場の解釈役が答えの形に直す。曖昧なら聞き返す。取り返しのつかない作用は自由文で確定させない |
| A4 | 二重・漏れ | 先に確定した答えが勝ち、ほかの入口に書き戻す。結べなかった返信は受信トレイに出す |
| A5 | Slack の受け方 | ADR 0032 の Slack アプリの連携を Socket Mode で使う。Gen1 の試行の Incoming Webhook は通知だけ |
| A7 | Claude の扱い | 主な入口とする。API に受信トレイの読み書きを置き、MCP はその包み。使い方の説明（MCP の instructions・マニュアル・スキル）は今後の拡張 |
| A6 | 答えた人の確認 | 入口の身元を役割に写す表（Blueprint の人の一覧）。写せない人の返信は答えにしない |

## 順番

1. 正本: 各件の `answer`、`inbox.answer`、`inbox.answered`、答え済みの件を閉じる。コンソールのボタンをこの口に寄せる（挙動は今と同じ）
2. Claude の入口: 窓口 API と MCP に `inbox_list`・`inbox_read`・`inbox_answer`（ADR 0030 の順番 3 の stdio の MCP に足す）。通知の文面に key と「Claude に『受信トレイの ○○ に答えて』と言う」を入れる
3. GitHub の入口: 件の Issue・PR のコメントを拾う（着手判定の問いの `planner.answered` をこの口に寄せる）。解釈役と聞き返し、書き戻し
4. 拾えなかった返信と、日報の数
5. Slack の入口: Slack アプリの連携と Socket Mode、スレッドの返信を拾う。その後ボタン（Block Kit）
6. Gen2: コンソールのログインと身元の写し
7. 今後の拡張: MCP の instructions、Claude から工場を操作するマニュアルとスキル（決定 8）

## 選ばなかった案

- **答える場所を 1 つ（受信トレイかコンソール）に決め、通知はそこへのリンクだけにする**: 集約は簡単だが、通知を見た場所から離れないと答えられない。事業主の担当者はコンソールも GitHub も使うとは限らない（オーナー）
- **入口ごとに件の状態を持つ（Slack のスレッドで答えたら Slack の側で閉じる）**: 入口が増えるほど状態が割れ、返信漏れと二重回答が起きる。正本は 1 つにする
- **自由文を解釈せず、決まった書式（`/factory choose B`）だけを受ける**: 確実だが、普段の言葉で返信できない。取り返しのつかない作用の件だけ明示を求める
- **Slack の返信を Events API（HTTP の受け口）で受ける**: 工場に外から届く口が要る。Socket Mode なら工場から繋ぎに行くだけで済む。商用で受け口が要るようになったら足す

## 結果

- 通知を見た場所でそのまま答えられ、どこで答えても受信トレイで 1 つにまとまる。答え済みはほかの入口にも伝わる
- Claude のスレッドで判断を聞く運用（Gen1 のオーナー）も、事業主の担当者が Claude Desktop から答える運用も、同じ窓口の道具で回る
- 自由文の解釈という新しい失敗のしかた（読み違い）が増える。取り返しのつかない作用は明示を求め、聞き返しの数と答えの取り消しの数を測る
- Slack アプリの credential が要る（ADR 0032 の連携。秘密の置き場は `.env`、将来 AWS Secrets Manager）
