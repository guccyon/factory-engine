# ADR 0033: ランナーのペアリングと、複数の Mac を並べた束へのディスパッチ

- 状態: 提案（2026-11-05。オーナーの承認待ち）
- 関係: ADR 0028（決定 3: Mac ランナー。工場から 127.0.0.1 の MCP へ繋ぐ形を、この ADR の決定 2 で置き換える）、ADR 0009（操業コンソール）、orchestrator/macrunner/SCOPE.md・PROTOCOL.md

## 文脈

P5a の Mac ランナー（#185・#193・#196）は、工場と同じ Mac に 1 台を置き、127.0.0.1 で待ち受け、トークン 1 本で工場から呼ぶ形で動いた。オーナーの方針（2026-11-05）:

- 範囲はこれ以上絞らない。任意のコマンドと Mac 本体の操作ができない線を守る（SCOPE.md）。絞りすぎると、エンジニアでない事業主が設定でハマる
- 工場からランナーに送れるメッセージを整理し、そこで絞れるようにする。利用者が別の利用者の Mac のランナーに任意のコマンドを実行させたり、情報を取ったりする穴を作らない
- ランナーと工場の間は、Bluetooth のペアリングのように、設定のときに両方で承認する
- 1 つの工場を、事業主の社内の複数の従業員（社長・経理・CS など）で共有する
- リリース前のアプリを人が触るのは TestFlight などの実機だけ。ランナーは開発の関心ごとで、シミュレーターでネイティブアプリの E2E を確かめるときに、ローカルの Mac を何台か並べ、テストケースごとに並列で流すために使う。Mac ごとにランナーを立てて工場に登録し、QA がそれらにディスパッチする

## 決定

### 1. ランナーは工場の機械で、ペアリングで登録する

- ランナーは事業主の工場の持ち物（従業員個人のものではない）。登録と外すのは、工場を建てる・操業する役（開発の担当）だけができる操作にする（操業コンソールのログインが入るときに役で分ける。それまでは今のコンソールの操作と同じ扱い）
- ペアリング: Mac で `macrunner.sh install` → ランナーが工場に接続の依頼を送り、ターミナルに 6 桁の番号を出す → 操業コンソールに同じ番号の依頼が出る → 人が番号を見比べ、コンソールで「許可」、Mac で「y」→ そのランナー専用の鍵ができ、両側に保存する
- 番号は両側の乱数から作る。依頼は 10 分で切れる。許可されるまで、ランナーはどの道具も受けず、工場もそのランナーを使わない
- 外すと鍵を捨てる。外した Mac・持ち出された Mac は、ペアリングし直すまで工場と話せない
- 工場側の鍵は制御プレーンの DB に置き、dispatcher だけが読む。`.env` への写しと上げ直しは要らなくなる
- 標準ライブラリだけで動かすため、公開鍵ではなく共有の鍵（HMAC）にする

### 2. ランナーから仕事を取りに行く（ランナーは待ち受けない）

- 複数の Mac を並べるので、工場からランナーへ繋ぎに行く形をやめる。ランナーは工場へ取りに行き（長いポーリング）、工場が積んだ道具の呼び出しを受け取って、結果を返す。今の 1 分ごとの連絡と同じ向き
- Mac に待ち受けのポートを開けないので、事業主の LAN やファイアウォールの設定でハマらない。外から Mac に届く経路もなくなる
- 工場とランナーの間で通るのは、PROTOCOL.md の一覧だけ（道具の呼び出しとその結果、連絡、外す依頼）。道具の一覧はテストで固定し、足すときはこの ADR の改訂として承認を通す
- 安全の判定は Mac 側に置く。許したアプリ・URL・ビルドしてよいリポジトリは Mac の設定で、工場はそれを広げるメッセージを持たない
- 工場にランナー専用の窓口を置く（操業コンソールとは別のポート）。ランナーはそこへ繋ぐ
- 通信は TLS にする（社内 LAN を画面の中身が流れる）。工場が自分用の証明書を作り、ペアリングのときに Mac 側に覚えさせる（証明書の購入と設定は要らない）。工場と同じ Mac のランナーも同じ形にする
- ランナー本体の更新は工場から押し込まない（押し込むと「工場から Mac のコードを書き換える」経路ができる）。コンソールに版のずれを出し、更新は Mac 側で行う

### 3. QA はランナーの束にディスパッチする

- 工場は、ペアリング済みで動いているランナーを束（プール）として持つ。ランナーごとに同時に動かせる端末の数（既定 1）を宣言する
- ランナーは連絡に、ランナー・Xcode・iOS のシミュレーター・Flutter の版を含める。シナリオが求める版に合わないランナーには振らない
- QA の 1 本のシナリオ（テストケース）は、束のうち空いているランナーの 1 台に割り当てる。複数のケースは複数のランナーで並列に流れる。割り当ては dispatcher が決め、ランナーは選べない
- ワーカー（QA のジョブ）にはランナーの鍵を渡さない。dispatcher がジョブごとに中継（MCP の口）を立て、ジョブの間だけ、割り当てたランナーへ、そのジョブに許した道具だけを通す。呼んだ道具は工場の events に残す
- ランナーが途中で落ちたケースは、別のランナーで最初からやり直す（ケースはランナーに状態を残さない前提で書く。端末は割り当てのたびに初期化する）

### 4. 事業主の手間

- Mac ごとに Xcode・Flutter・idb が要る。`macrunner.sh install` が足りないものを平易な言葉で案内し、入れる手順を 1 行ずつ出す
- 夜間に回すなら、各 Mac にスリープの抑止（ADR 0011 の 7 の keep-awake）も入れる。install が一緒に入れる

## 順番

1. この ADR と PROTOCOL.md（この PR）
2. ペアリングと、取りに行く形（ランナー 0.3.0・コンソール・dispatcher）。今の 1 台は 1 回ペアリングし直す
3. 操業コンソールのログインと役（ランナーの許可・外すを開発の担当だけに）。工場全体に関わるので別のタスク
4. ジョブごとの中継と束への割り当て（P5a の one_orchestrator）。最初は 1 台の束で 1 本のシナリオを通す
5. 2 台目の Mac で並列と、落ちたときのやり直し（nightly_explore の前）

## 選ばなかった案

- 工場からランナーへ繋ぎに行く形のまま、ランナーを LAN に開く: Mac ごとにポートとファイアウォールの設定が要り、外から Mac に届く経路が増える
- 公開鍵（mTLS）でランナーも証明書を持つ: 強いが、標準の Python の標準ライブラリだけでは扱いにくい。工場の証明書をペアリングで覚えさせる TLS と、ペアリングの共有の鍵で足りる
- ランナーを従業員ごとの持ち物にする: 工場は事業主の 1 つの持ち物で、ランナーはその機械。従業員ごとに分けると割り当てと権限が複雑になる

## 結果

- 工場とランナーの間の認証と、2 台目以降の土台ができる。偽のランナーの登録・なりすまし・持ち出された Mac からの接続を止める
- 閉じないもの: 操業コンソールのログインと役（同じ LAN の人が工場側の「許可」を押せる。Mac 側の y がないと完了しない）。利用者を増やす前に要る
