# ADR 0049: 出荷のレーンに QA の関門を入れる（staging の後に判定と探索を並行し、両方の結果を添えて承認へ）

- 状態: 承認（2026-11-11 オーナー。合否は関門で決めず、検証の報告を添えて承認に出し、ブロッカーにするかは承認者が決める形に直して承認）
- 関係: ADR 0012（出荷）、ADR 0028（QA 役。決定 2 の「ship の手前で動作確認」の配線がこの ADR）、ADR 0029（予算の枠）、ADR 0034（受信トレイ）、ADR 0043（O5 の重要度、O6 の定期便）、ADR 0046（事故の台帳）
- 検討の記録: 事業部の仕様の置き場（05_specs）の 10（見回り体制の整理）の G7 と P10(1)

## 文脈

ADR 0028 は「QA 役を新設し、実装のラインとは切り離して ship の手前で動作確認する」と決めた。実装は次のところで止まっている。

- 定期便（`train.py`、毎日 17 時 JST）は Release を切って staging に出したところで終わる
- ストーリーどおりの判定（`qa_line.enqueue`、mode: verdict）は人が `factoryctl qa run` で流したときだけ動く
- 推論による探索的テスト（mode: explore）は、出荷と切り離された夜間の探索（`nightly_explore_step`、毎晩 1〜5 時）だけ

そのため「出荷の前に、決定論の E2E と推論の探索を通す」という意図が実装に入っておらず、夜間の探索がその代わりに見えていた（見回り体制の整理の G7）。

オーナーの方針（2026-11-11）:

- 出荷のレーンの流れを「… → staging に配備 → 判定（E2E）と探索（推論）を並行 → 両方の結果を待つ → リリースの承認 → リリース」にする
- 承認には検証の結果の報告を添える。リリースのブロッカーになりそうなものが見つかったかを示し、それをブロッカーにするかは承認者が判断する（2026-11-11 オーナー、この ADR の承認時）
- 並行にするのは時間の効率のため。順番に意味はない
- レーンの外の探索（マイルストーンと事業主の依頼で起こす。見回り体制の整理の P10(2)）は別に決める。この ADR では扱わない

## 決定

### 1. 関門を起こす契機

staging への配備が成功した（`release.deployed`、env=staging、ok）ら、その Release に対して QA の関門を 1 回開く。定期便・緊急便・手の出荷のどれで出た版でも同じ。

- 起こすのは supervisor（今の定期便と同じく条件を見るだけで、判断は持たない）。`qa.gate_opened {release_id, repo, jobs: {verdict, explore}}`
- 同じ Release に関門は 1 回だけ（dedupe）。シードの入れ直し・再起動・Rollback では開かない
- 関門が開いている間に次の版が staging に出たら、古い関門は `superseded` で閉じ、新しい版で開き直す（承認の対象は staging にいまある版だけ。`ship.request_approve` と同じ考え）

### 2. 判定と探索を同時に積む

関門を開くとき、同じ Release を入力にした QA のジョブを 2 つ同時に積む。

| ジョブ | 入力の mode | 中身 | 決定論か |
|---|---|---|---|
| 判定 | verdict | `specs/stories/` の全ストーリーを手順どおりに流す（E2E） | 手順は決定論。歩の判定は QA 役 |
| 探索 | explore | チャーター 1 つに沿って利用者として寄り道し、ストーリーに書いていない食い違いを探す | 推論 |

- 今は 1 つの固定 Issue（`factory:qa`）に動けるジョブが 1 つだけ（`jobs_one_active_per_issue`）なので、探索は別の固定 Issue（ラベル `factory:qa-explore`、題「QA の探索（毎回更新）」）に積む。夜間の探索もこちらに移す。DB の索引は変えない
- 探索のチャーターは、その製品で最後に使ったものの次（夜間の探索と同じ 5 種を回す）。関門の探索の入力には `gate: true` を足し、記録 `qa.explore` の `unattended` は偽（roadmap の nightly_explore の夜の数には数えない）
- iOS のシミュレーターは Mac ランナーに 1 台なので、判定が iOS を使い、探索は Web 版で歩く（Gen1）
- 「並行」は同時に積むところまで。実際に同時に走るかはワーカーの空き次第（いまのラインの宣言はワーカー 1）。待ちが長いときは流量の宣言で調整する（運用パラメータ）
- 予算の枠を使い切っていれば次の枠を待つ（夜間の探索と同じ）。ラインの一時停止中も関門は流す（出荷は一時停止と別に動くので、関門だけ止まると承認が出なくなる）

### 3. 結果のまとめ（ブロッカーの候補）

関門は合否を決めない。2 つのジョブの結果を 1 つの報告にまとめ、リリースのブロッカーになりそうなものがあるかを示す。ブロッカーにするかは承認者が決める（オーナー 2026-11-11）。

| ジョブ | ブロッカーの候補として挙げるもの | 参考として載せるもの |
|---|---|---|
| 判定 | known_gap でない Defect のある hold | known_gap だけの hold、blocked（何が足りなかったか） |
| 探索 | s1・s2 の、known_gap でない見つけたもの | s3・s4 の見つけたもの（起票はする） |

- 両方の結果がそろったら `qa.gate_decided {release_id, candidates: n, verdict: {...}, explore: {...}, report}` を 1 件残す。`candidates` はブロッカーの候補の数で、合否ではない
- 確かめられなかったジョブ（blocked だけ・失敗・結果なし）は 1 回だけ積み直す。それでもだめなら、そのことを報告に書いて承認に出す
- 関門を開いてから 6 時間（運用パラメータ）で結果がそろわなければ、そろった分だけで報告を作って承認に出す（そろわなかったジョブを書く）
- Defect と Incident の起票は今の `qa_line.act`・`record_explore` のまま（S1 はラインの差し止めまで、ADR 0043 の O5。差し止めは関門とは別に動く）

### 4. 承認とのつなぎ

- 本番を立てる段階（launch・operating）の製品: 受信トレイの「本番待ち」（`inbox._release_item`）は、その版の関門の報告ができてから出す。項目に報告を添える: ブロッカーの候補（件数と 1 件ずつの題・重要度・Issue）、参考の項目、判定と探索の要約、2 つのジョブへのリンク
- 承認者は報告を見て、候補をブロッカーにする（受信トレイの「見送る」。どの候補をブロッカーにしたかを選ぶ。修正が次の便で出るのを待つ）か、承知で本番に出すかを決める。承認の記録（`release.approved`）に、そのとき見た報告（`qa_gate` の id と候補の数）を残す
- 報告ができる前に人が承認したいとき（`factoryctl release approve`・`release train-approve`）は `--skip-qa --reason ..` を付ける（`release.approved` に `qa_skipped` と理由を残す）。関門は承認を置き換えず、承認に出す前に結果をそろえる工程になる
- 本番を立てない段階（development。rally がいま）の製品: 承認はもともと出ない。報告は記録し、コンソールの出荷の画面と日報に出すだけにする

### 5. 見せ方

- コンソールの出荷の画面に、staging の版ごとに関門の状態（判定中・探索中・報告済み、ブロッカーの候補の数）と、2 つのジョブへのリンク
- 建設日報と操業レポートに「出荷の QA（昨日）」の行（関門の数、ブロッカーの候補の数、承認者がブロッカーにした数、判定と探索それぞれにかかった時間）

## 順番

1. この PR: 本 ADR（提案）と ADR 0028 の関係の欄
2. 承認後の実装 1: 探索の固定 Issue を分ける（`factory:qa-explore`）。夜間の探索をこちらに移す
3. 実装 2: 関門を開く（supervisor）・2 つのジョブを積む・結果を集めて報告と `qa.gate_decided` を残す（`dispatcher/qa_gate.py`）。`factoryctl qa gate show <repo>`
4. 実装 3: 承認とのつなぎ（受信トレイの報告・`release approve`・`train-approve` の `--skip-qa`）とコンソール・日報の表示
5. 済の条件: rally の定期便 1 便で、staging の配備の後に判定と探索の 2 つのジョブが積まれ、`qa.gate_decided` が 1 件残る

## 選ばなかった案

- 関門で合否を決め、不合格なら承認に出さない（この ADR の最初の案）: QA 役の重要度の付け方がまだ確かでなく、ブロッカーかは事業の事情でも変わる。承認者が報告を見て決める（オーナー）

- 判定の後に探索（直列）: 時間がかかるだけで、順番に意味がない（オーナー）
- 1 つのジョブで判定と探索の両方をする: ジョブの上限（ターン数）を食い合い、片方の失敗でもう片方の結果も失う。記録の型（Verdict と探索）も分かれている
- 一意索引をゆるめて同じ固定 Issue に 2 つ積む: DB の変更になり、ほかの固定 Issue の二重積みの防ぎも弱くなる
- 夜間の探索を出荷の関門の代わりにする: 出荷の版と探索した版がずれる。承認の前に結果がそろわない

## 結果

- 定期便で出た版は、承認の前に必ず判定と探索を通る。人が承認を押す時点で QA の報告とブロッカーの候補が見えている
- 候補を自動でブロッカーにしないので、重要度の付け方が甘くても出荷は止まらない。代わりに承認者がブロッカーにした数を記録し、QA 役の重要度の当たり具合（候補と人の判断の比較）を見る
- QA のジョブが便ごとに 2 本増える（rally は 1 日 1 便）。費用は日報の行で見て、多ければ探索のターン数を絞る
- 夜間の探索は残るが、出荷の探索と目的が重なる。毎晩をやめてマイルストーンと事業主の依頼で起こすか（見回り体制の整理の P10(2)）は別に決める
