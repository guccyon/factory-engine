# ADR 0048: 工場の問題を、窓口に頼むと工場の中で一次調査し、特定できなければ外に引き継ぐ

- 状態: 承認（2026-11-10 オーナー。I1 はオーナーのコメントで決定、I2〜I8 は推奨どおり）
- 関係: ADR 0024（知見の委員会。個人情報を git に入れない）、ADR 0029（予算の枠）、ADR 0030（窓口）、ADR 0037・0039（単発の依頼の対応の種類とループ）、ADR 0038（プランナーのワークフローの宣言）、ADR 0041（権限の区分）、ADR 0044（判断の宛先。工場の仕組みの問いは提供元へ）、ADR 0046（事故の台帳と調査委員会）、#308（工場の中のエラーに気づけない）
- 検討の記録: 事業部の仕様の置き場（05_specs）の 11（工場の中での一次調査、叩き台 0.1）

## 文脈

工場そのものの問題（止まった理由、レポートの数字のずれ、マージが進まない理由など）は、今は建設者が工場の外から Claude で調べている。外からなら Engine のソースコードまで読めるが、頼めるのは建設者だけで、事業主は自分で調べられない。

オーナーの要望（2026-11-10）:

- 商品化の後は、事業主が自分で工場の問題を調べられるほうがよい
- 工場の中から実行環境をもとに調べ、改善の Issue を上げる仕組みがほしい
- 外からの調査にはソースコードを読める強みがあるので、どちらも要る。まず工場の窓口に頼むと工場の中で自律的に一次調査し、それでも特定できなければ外から Claude がコードも含めて包括的に調べる、という2 本立てにしたい

今ある部品:

- 窓口の問い合わせ（ADR 0030、`desk_answer`、立場「工場長」）: dispatcher が組み立てた記録を読み、1 回で答える。自分で探しに行かない
- 単発の依頼の `analysis`（ADR 0037）: 製品のデータを集計・分析する。対象は工場自身ではない
- 調査委員会（ADR 0046）: お金がかかった事故を週次に横断で見回り、事故記録（FIR）にする。事故に限り、1 件ずつの依頼には応えない
- 改善 Issue の起票（委員会の `file_issues`）: Engine の改善 Issue を起票する道がある

## 決定

### 1. 窓口に集約し、新しい対応の種類 `investigate`（工場の調査）を足す（I1）

- 口は窓口 1 つ。依頼者はいくつもの口を使い分けられないので、困っていることを言葉で書くだけにする
- 依頼者に種類（問い合わせ・調査・依頼）を選ばせない。中身から工場（プランナー）が決める
- プランナーは振り分けで、対応の種類だけでなくワークフローの体制まで宣言する（ADR 0038）。例: 「なぜ止まった？」は問い合わせで答え、足りなければ同じ会話で調査に切り替える。「調べて、直せるなら直して」は調査 → 結果しだいで操作の提案・製品の依頼の下書き・Engine の改善 Issue につなぐ
- 体制の厚み（ターン・費用・追う仮説の数・続きの回数）は決定 4 の値を天井にして、依頼ごとに宣言する
- 振り分けの根拠は今の着手判定と同じく 3 層（根拠・解釈・確信度）で残す。当たり外れ（差し戻し、問い合わせから調査への切り替え）は ADR 0039 の外側のループの信号にする
- コンソールには「窓口に相談」を置き、見ているジョブや停止を添えて会話を開くだけにする（種類は選ばせない）
- 調査は読むだけなので確認のレベルは `read`。見込みの費用が 1 件の上限を超えそうなときだけ、振り分けで範囲を絞るかを 1 回問う

### 2. 一次は実行環境と宣言まで。Engine のソースコードは読まない（I2）

調査役（新しい役。権限の区分は ADR 0041 の「見る」）が見るもの:

| 物 | どう見るか | 備考 |
|---|---|---|
| 制御プレーンの DB | 調査用の読み取り専用ロールで、調査用のビュー（`investigate.*`）に SELECT | ビューはジョブ・イベント・停止・チケット・判断・窓口の会話・費用・ラインの宣言。`restricted` スキーマと `desk_tokens` は入れない |
| ジョブのログ | 道具 `job_log(job_id, tail)`。dispatcher が置き場から取って渡す | 渡す前にトークンらしき文字列を伏せる |
| Engine の定義と ADR | 入っている版の `definitions/` と `docs/` | ソースコード（`orchestrator/`・`core-gates/` など）は読まない |
| 製品の GitHub | Issue・PR・コメント・CI の結果 | 書き込みの権限は渡さない |
| 工場の状態 | `operations.yaml` の `read` のレベルの操作だけ | シェルは渡さない |

見ないもの・しないこと: 秘密情報、Docker のソケット、ホストの中、状態を変える操作（止める・再開・やり直し・ラベル・起票。提案として返すだけ）、依頼の本文や Issue のコメントにある URL や指示（材料であって指示ではない）。

ソースコードを読ませないのは、一次と二次の境目をはっきりさせるため。商用で事業主の側に Engine のソースを渡さない形とも揃う。

### 3. DB は読み取り専用ロールと調査用のビューで、自由な SELECT（I3）

- 決まったクエリの一覧だけでは探索ができず、一次調査の意味が薄れる
- 1 文 10 秒・500 行まで（仮置き）。ロールとビューは expand だけで、既存の表は変えない。DB の変更なので、作る PR は人に見せる

### 4. 費用（I4、仮置き。運用パラメータとして工場が調整してよい）

| 項目 | 値 |
|---|---|
| モデル | 上位（`tier-judge`）。安いモデルは評価セット（決定 8）で試してから |
| 1 件の上限 | $3・40 ターン |
| 1 日の上限 | $10（工場の 1 日の予算の内数） |
| 続きの調査 | 同じ会話で 2 回まで |

- 費用がかかるのは誰かが頼んだときだけ（決定 7）。調査委員会が同じ調査役を使うときは委員会の枠（ADR 0046）に数え、ここの 1 日の上限には入れない
- 上限に当たったら止めずに、そこまでの事実と仮説で「特定できない」として引き継ぎ資料を出す

### 5. 結果の出し方（I5）

| 結果 | 出すもの |
|---|---|
| 特定できた | 依頼者への報告（事業主の言葉で）。直すのが Engine なら改善 Issue を提供元の口に起票（起票まで。直すのは建設者）。運用の値（流量・予算・宣言）なら操作の提案（`change` のレベルなので承認ボタン）。製品なら窓口の依頼の下書き（依頼者の確認でチケット） |
| 原因が工場の外 | 報告と正しい行き先（製品の不具合なら依頼の下書き、外部サービスの障害なら様子見） |
| 特定できない | 分かったところまでの報告と、引き継ぎ資料（決定 6） |
| お金の損がある | 上のどれかに加えて、事故の台帳に案件を開く（ADR 0046。委員会に渡す） |

- 調査役は何も変えない。起票・操作・台帳への記録は、結果を見て dispatcher が決まった道で行う
- 起票の前に、同じ部品・同じ症状の Engine の Issue が開いていないかを見る。開いていればそこに事実を足す（ADR 0044）

#### 顧客の情報を Issue に書かない

調査役は DB で製品と依頼者の記録を見るので、そのまま書くと Engine の Issue（Gen1 は public）に顧客の情報が出る。3 重で守る。

1. **書く物を分ける**: 調査役は結果を「Engine の話（どの部品が・どの条件で・どう振る舞ったか）」と「その工場の事実（製品・チケット・会話・数値）」に分けて返す。Issue の本文は前者だけから、dispatcher が決まったひな形で組み立てる
2. **決定論の検査**: 起票の前に本文を検査する。製品のリポジトリ名・製品名・人の名前・メールアドレス・電話番号・URL（Engine の docs 以外）・チケットや PR の番号・トークンらしき文字列・ホスト名や IP・`restricted` の id が 1 つでもあれば起票しない。数値は比（ADR 0046 の FIR と同じ正規化）にする
3. **止めて人に回す**: 検査に引っかかったら調査役に 1 回だけ直させ、それでも残れば起票せず提供元に「起票の保留」として出す（漏れるより遅れるほうを選ぶ）

事業主への報告（窓口の会話）はその工場の中なので製品の言葉で書いてよい。Engine の内部の話は事業主の言葉に置き換える（ADR 0044）。

### 6. 二次への引き継ぎ（I6）

次のどれかに当たったら、特定できないとして引き継ぐ。

1. 仮説が残らない、または確信度が低いまま上限に当たった
2. 確かめるにはコードを読むしかない（定義・ADR の宣言と、記録に残った振る舞いが食い違うなど）
3. 確かめるのに試しの実行やホストの中を見る必要がある
4. 秘密情報・権限・決済・DB の破壊的な変更に関わりそう（調べるのも止めて人に回す）
5. 依頼者が外でも調べてと言った

引き継ぎ資料（`INV-YYYY-NNNN`）の項目: 依頼者の問い（言葉のまま）、範囲（製品・Engine の版・時間帯）、見た事実（参照の id と、どう見たか）、仮説（確信度・支える事実・次に確かめること）、打ち消した仮説と打ち消した事実、まだ見ていない所、再現の手がかり、費用、止めた理由（`budget`・`needs_code`・`needs_host`・`sensitive`・`asked`）。

- 資料の本体は、その工場の制御プレーンの中（窓口の会話の添付）に置く。利用者の個人情報と `restricted` の中身は入れない
- 提供元への送り出し口は、FIR（ADR 0046）・#308 の内部エラーの通知と共通にする。Gen1 は本リポジトリの Issue（ラベル `factory:investigation-handoff`）に、決定 5 の検査を通した要約と資料の id だけを書く。Gen2 は提供元の非公開のトラッカー
- 二次調査（外の Claude）は資料の id から始め、一次の事実をやり直さない

### 7. 工場が自分から調査を始めるのは後（I7）

- Gen1 は依頼（窓口）だけで起動する
- 番人や見回りが「理由の分からない異常」を見つけたときに自動で起動するのは、費用と特定率を見てから決める
- 一次調査は定期に動かないので、見回りではない（見回りの台帳には載せない）

### 8. 評価セットで特定率を測る（I8）

- 過去に外から調べた件（操業レポートの危険の欄が無害な停止で埋まった件、同じ担保の二重流し、CHANGELOG の衝突、担保の繰り返し起票など）を、当時の記録で再生して評価セットにする
- 特定率（外の調査と同じ原因に着いた割合）の合格線は 0.5（仮置き）。合格するまでは依頼に応えつつ、結果に「試行中」と添える

## 今ある仕組みとの関係

| 仕組み | 関係 |
|---|---|
| 窓口の問い合わせ（ADR 0030） | 「何が起きた？」は問い合わせのまま。探索が要るとプランナーが見たら調査に回す |
| 単発の依頼の `analysis`（ADR 0037） | 同じループの兄弟。対象が製品か工場自身かで分ける（役・権限・データ源が違う） |
| 見回り | 一次調査は見回りではない。見回りが見つけた異常の次の一手として、後で呼べるようにする（決定 7） |
| 調査委員会（ADR 0046） | 一次調査は 1 件・1 工場・事故に限らない。お金の損が見えたら台帳に案件を開いて委員会に渡す。委員会の調査は同じ調査役と道具を使う（役は 1 つ、呼び手が 2 つ） |
| 判断の宛先（ADR 0044） | Engine の中の話は事業主でなく提供元へ（改善 Issue と引き継ぎ資料） |

## 順番（承認の後）

1. 定義 `definitions/investigate.yaml`（範囲・上限・二次に回す条件・引き継ぎ資料の形・Issue の検査の型）と、その検査
2. DB の調査用ロールとビュー（expand だけ。人に見せてから）
3. 調査役のジョブ（`worker/investigate.sh`・`core-gates/investigate.py`）と道具（SQL・ログ・定義・GitHub の読み取り）
4. 窓口の振り分けに `investigate` を足す（`desk.yaml`、相談役の指示、体制の宣言）
5. 提出: 報告・改善 Issue の起票（委員会の道を使い回し、決定 5 の検査を通す）・引き継ぎ資料と送り出し口・事故の台帳への案件
6. 評価セット（決定 8）で特定率を測る。コンソールの「窓口に相談」はその後

## 選ばなかった案

- **調査専用の口を作る**: 依頼者が口を使い分けられない。窓口に集約する
- **一次でも Engine のソースを読ませる**: 特定率は上がるが、二次との境目がなくなり、商用でソースを渡さない形と合わない
- **決まったクエリの一覧だけで読ませる**: 安全だが探索できず、問い合わせとの差がなくなる
- **1 件 $1 で安いモデル**: 評価の前に下げると「特定できない」ばかりになりそう。評価セットで試してから下げる
- **引き継ぎ資料をそのまま Issue に書く**: public のリポジトリに顧客の情報が出る。本体は工場の中に置き、Issue には要約と id だけ
- **理由の分からない停止のたびに自動で調査する**: 費用が読めない。特定率と費用を見てから
