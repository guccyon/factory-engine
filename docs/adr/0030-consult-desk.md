# ADR 0030: 事業部の窓口（外からの依頼の壁打ちと、各ファンクションへの問い合わせ）

- 状態: 承認（2026-11-05 オーナー。決めどころ W1〜W6 は推奨どおり）
- 関係: ADR 0009（操業コンソールと工場側のチケット。操業 API・優先度・`tickets` の入口の抽象化）、ADR 0025・0026（プランナーの責務と着手判定）、ADR 0028（P5b の Answer ライン）、ADR 0029（ラインの流量の宣言）、`definitions/stages.yaml` の intake / clarify / triage、`definitions/planner.yaml`

## 文脈

今、ラインに何を流すかは 2 つの経路でしか決まらない。P3 のタスクの補充が積むものと、建設者が GitHub の Issue にラベルを付けて入れるもの。
後者は「どのチケットを」と明確に言える人（建設者）しか使えず、工場の外の人が「先にこれをやってほしい」と言える窓口がない。

オーナーの要望（2026-11-05）:

- 何を流すかの選択は、工場が持つべき知見ではない。建設側の都合や顧客の事情で外が決め、任意のタスクを流せるようにしたい。商用の運用でも「先にどうしてもこれを」はある（データのエクスポートの依頼、アプリの開発ロードマップの特定の項目から進めて、など）
- 依頼はいつも「チケットのどれを」と明確とは限らない。「どの辺りのどんな機能を進めて」という曖昧な依頼を、プランナーと壁打ちしてチケットに落とし、流してもらえる窓口が事業部に要る
- 現場で経営層から各ファンクションの担当者に質問が来るように、仮想事業部にも各ファンクションに聞ける口が要る
- 顧客は、担当者が使っている Claude Desktop などに代理で聞いてもらう形になる。Claude が工場の API を叩く構造

すでにある部品:

- intake / clarify（T20）: Issue に `factory:request` を付けると、問い手が Issue のコメントで要求者と最大 3 往復し、確定した `Request` を残す。往復の場は GitHub の Issue に限られ、確定した後のタスクへの切り出しはない（triage は未着手）
- プランナー（ADR 0025・0026）: チケット 1 件ごとの着手判定と経路の決定。テーマからタスクのまとまり（依存つき）を切るのは「最小のプランナーの後に足す」とされ、まだない。優先順位の付け方は持たない
- 操業 API（ADR 0009）: 優先度・保留・停止の操作の正本。Gen1 は Mac の中だけで開き、ログインがない。外に出すときはログインと役割の分け（運用主・要求者）を先に入れるとしていた
- P5b の Answer ライン（曖昧な問いに精緻化を経て回答）: 項目だけで、形は決まっていない

## 決定

### 1. 事業部の窓口を、工場の外向きの口として 1 つ置く

「窓口」は、工場の外の人（とその代理の Claude）が事業部に話しかける唯一の口。相談は 2 種類だけ受ける。

| 種類 | 例 | 結果 | 工場への作用 |
|---|---|---|---|
| 依頼（request） | 「予約まわりの通知を先に進めて」「生徒の利用状況を CSV で出して」「#812 を先に」 | 確定した `Request` と、タスクのまとまりの下書き → 依頼者の確認でチケットになり、指定の優先度でラインに入る | チケットを作る・優先度を変える |
| 問い合わせ（inquiry） | 「今週どこまで進んだ？」「なぜこの画面はこの形？」「障害の件はどうなった？」「この機能はいつ頃？」 | 根拠（どの記録・文書を見たか）つきの回答 | なし（読むだけ） |

窓口は操業コンソール（ADR 0009）とは別のプロセスにする。コンソールは工場を操作する人（運用主・建設者）の道具で、止める・承認する・流量を変えるまでできる。窓口はそれより狭く、上の 2 種類だけを、外に開いてよい認証つきで受ける。どちらも制御プレーンの同じ関数（`ops.py` など）を通るので、振る舞いは変えない。

### 2. 何を流すかは外が決める。工場は影響を見せるだけ

- 依頼で決まった優先度は依頼者の指定として記録する（`tickets.priority_set_by` に依頼者）。プランナーは優先順位を付けない（ADR 0025 のプランナーの責務のまま）
- プランナーが返すのは判断の材料だけ: どのタスクに分かれるか、見込みの費用と時間、今の流量（ADR 0029）でいつ頃着手できるか、押し出されるチケット、既存のチケットとの重なり
- 明確な指示（「#812 を先に」）は壁打ちを通さず、操業 API の優先度の操作と同じ関数で即時に通す
- 依頼者が複数いて指定がぶつかったら、運用主に回す（Gen1 は依頼者＝運用主の 1 人なので起きない）

### 3. 依頼の壁打ちは、工場の側のプランナーが相手をする

壁打ちの相手は依頼者の手元の Claude ではなく、工場の中のプランナーにする。製品の `specs/`・ロードマップ・ADR・流れているチケット・過去の Plan を読めるのは工場の中だけで、そこを知らないと「どの辺りのどんな機能」を既存のチケットや要件に結び付けられないため。依頼者の手元の Claude は、依頼者の言葉を窓口に渡し、プランナーの問いと下書きを依頼者に見せる代理に徹する。

流れ:

```
依頼者（と手元の Claude）
  → 窓口: 相談を開く（依頼の本文、対象の製品、希望の優先度・期限があれば）
  → プランナー（相談役）: clarify と同じ問いの型（理由と選択肢つき）で往復。既存のチケット・要件・ロードマップの項目と結び付ける
  → 確定: Request（何を・何のために・いつまでに・どの精度で）と、タスクのまとまりの下書き（依存つき、要件 → 画面 → 契約 → 実装の順）、見込み
  → 依頼者の確認 1 回（ADR 0025 の E3「1 タップで投入」と同じ）
  → チケットになる（tickets の source は desk）。以後は今のラインと同じ: 1 件ごとの着手判定（ADR 0026）→ 経路どおりに配る
```

- 往復の仕組みは T20 の clarify を使い回し、往復の場を GitHub の Issue のコメントから窓口の会話に広げる。上限は 3 往復のまま。使い切ったら、決まったところまでを下書きにし、残りを「未確定」と書いて返す（止めない）
- データのエクスポートのような「成果物を返す依頼」も依頼として受け、タスクは Answer ライン（P5b）の仕事になる。Gen1 は実装のタスクとして流す（スクリプトを書いて結果を添える）
- 依頼の本文と回答はデータとして扱い、プランナーにもシェルにも命令として渡さない。プランナーは今どおり製品のリポジトリも Issue も書き換えない（読むだけ）。作用は dispatcher が結果を見て行う

### 4. 問い合わせは、1 つの回答役がファンクションの立場を選んで答える

ファンクションごとに別の役を作らない。回答役（`answer`）が問いを受け、どのファンクションの立場で答えるかを選び、そのファンクションの定義と記録を根拠に答える。

| ファンクション | 見るもの |
|---|---|
| 計画（プランナー） | ロードマップ、チケットと Plan、流量と見込み |
| デザイン | `specs/design/`、UXSpec、デザインの判断の記録 |
| 開発 | PR・検査の記録、内部品質の診断、ADR |
| 品質（QA） | Verdict・Defect（P5a 以降） |
| 運用 | 出荷と Release、停止の記録、Incident（P5b 以降） |
| 工場長 | 日報、費用、停止、判断の記録 |

- 答えには必ず根拠（見た記録・文書の参照）と、分からないことを分からないと書く欄を付ける。推測で埋めない
- 回答役は読むだけで、工場を変える操作は持たない。問い合わせの途中で「では先にやって」となったら、依頼の相談に切り替える（同じ会話の中で）
- これを P5b の Answer ラインの最初の形とする

### 5. HTTP の API が正本、MCP はその薄い包み

- 窓口の API（JSON）が正本。相談はジョブで数分かかるので非同期にする: 相談を開くと会話の id が返り、相手の返事（問い・下書き・回答）は会話を読めば取れる。待つ側が長く待てるよう、読むときに最大の待ち時間を渡せる
- 顧客の Claude Desktop・Claude Code からは MCP のサーバーとして使う。道具は少数に絞る（相談を開く・返事をする・会話を読む・下書きを確認して投入する・チケットの状態を見る・相談の一覧）。MCP のサーバーは API を呼ぶだけで、判断も状態も持たない
- 認証: 依頼者ごとの API トークン（Gen1）。トークンには役割（運用主・依頼者）と対象の製品を持たせる。依頼者ができるのは、自分の相談と、自分の依頼から作ったチケットの優先度・保留まで。運用主はすべての相談を見て、ぶつかった指定を裁ける。パイロット（工場を外のマシンで動かす）では、リモートの MCP と OAuth に移す
- 開く範囲: Gen1 は Mac の中（`127.0.0.1`）と、手元の Claude Code からの stdio の MCP。外のマシンで動かすときは TLS と、開いてよいホスト名を設定に入れる（ADR 0009 の守りと同じ）

### 6. 窓口の費用は専用の枠で数える

- 相談のジョブ（プランナーの相談役・回答役）は、ラインの枠でも委員会の枠でもない、窓口の枠で動かす。ラインを止めていても相談には答えられるようにし、相談がラインのワーカーを奪わないようにするため。枠の数は ADR 0029 の宣言に `desk` として足す（既定 1）
- 相談 1 件の費用の上限を置き（仮置き $2）、超えたら決まったところまでで返す。相談の費用は依頼者と製品ごとに集計し、日報に出す（先方のアカウントを足すかの判断の材料。パイロットの積み残し）

### 7. すべてを記録する

events に `desk.opened` / `desk.message` / `desk.request_confirmed` / `desk.tickets_created` / `desk.answered` / `desk.priority_changed` を足す。誰が・どの製品に・何を・なぜ（依頼者の言葉）と、費用・往復回数・根拠を残す。
窓口から入ったチケットは、後で「依頼 → 確定 → チケット → PR → 出荷」と追えるよう、`Request` の id を持つ。

## 決めどころ（オーナーの承認が要る）

| # | 問い | 推奨 |
|---|---|---|
| W1 | 依頼の壁打ちの相手 | 工場の中のプランナー（製品と流れの知識がある）。依頼者の手元の Claude は代理 |
| W2 | 下書きからチケットへの投入 | 依頼者の確認 1 回で投入。運用主の承認は、依頼者が複数になってから「指定がぶつかったとき」だけ |
| W3 | 優先度を誰が決めるか | 依頼者が指定する。プランナーは影響（見込み・押し出されるもの・重なり）を見せるだけ |
| W4 | 問い合わせの答え方 | 1 つの回答役がファンクションの立場を選ぶ。役はファンクションごとに分けない（分けるのは問いの量と質のデータが溜まってから） |
| W5 | 外への出し方 | API を正本に、MCP は薄い包み。Gen1 はトークン＋stdio、パイロットでリモートの MCP＋OAuth |
| W6 | 窓口の費用 | 専用の枠（ADR 0029 に `desk`）と、相談 1 件の上限。ラインの一時停止中も相談は受ける |

## 順番

1. 窓口の API と会話の記録（events・artifacts）、トークンと役割。明確な指示（優先度の変更・チケットの状態）だけ先に通す
2. 依頼の壁打ち: clarify の往復を窓口の会話に広げ、確定した Request からタスクのまとまりの下書きを出す（ADR 0025 の「テーマからタスクのまとまり」をここで作る。P4 の `opportunity_to_ticket` と同じ仕事）
3. MCP のサーバー（stdio）。手元の Claude Code・Claude Desktop から 1 本通す
4. 問い合わせの回答役（計画と工場長の立場から。ほかは P5a・P5b の記録ができてから足す）
5. パイロットの前に: リモートの MCP と OAuth、外のマシンでの開き方

1〜3 は P4 に、4 は P5b の Answer ラインに入れる（`definitions/roadmap.yaml`）。

## 選ばなかった案

- **操業コンソールの API をそのまま外に開く**: 止める・承認する・流量を変えるまでできてしまう。外の人に要るのは依頼と問い合わせだけなので、狭い口を別に作る
- **依頼者の手元の Claude が壁打ちし、確定したチケットだけを API で入れる**: 早く作れるが、製品の要件・流れているチケット・ロードマップを知らないまま切ることになり、重なりや依存を見落とす。工場側の知識を使う意味がなくなる
- **工場が優先順位を決める（依頼を受けて工場が並べ替える）**: 何を先にするかは事業の都合で、工場の知見ではない（オーナー）。工場は影響を見せるところまで
- **ファンクションごとに別の回答役を置く**: 問いの量も種類もまだ分からない。記録が溜まってから分ける
- **GitHub の Issue を相談の場にし続ける**: 顧客の担当者は GitHub を使うとは限らず、Claude Desktop から話す形に合わない。Issue は入口の 1 つとして残す（ADR 0009）

## 結果

- 工場の外の人が、曖昧な言葉のままでも依頼でき、何を先に流すかを外から決められる。建設者の手作業のチケットの差し込みも、この窓口に寄せられる
- 「テーマからタスクのまとまり」（P4）が、窓口の依頼という入口を持つ
- 外に開く口が増えるので、認証と役割、費用の上限、依頼の本文をデータとして扱う守りが前提になる
- 相談の費用と往復回数、確定までの時間、下書きが投入された率、投入後に覆った率が測れる。プランナーの壁打ちの質を Learn に入れる材料になる
