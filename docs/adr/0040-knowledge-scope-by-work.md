# ADR 0040: 知見を業務と背景で効かせる（業務のツリー・軸・適応度）

- 状態: 承認（2026-11-07 オーナー。決めどころ S1〜S8 は推奨どおり、「Gen2 で決めること」は Gen2 で。第 1 版の「入口（ステップ × 道）で分ける」案は、同日のオーナーの指摘で業務のツリーに改め、さらに背景は別の軸で持って適応度で選ぶ形にした）
- 関係: ADR 0013・0023（Learn ループ・学習の体系）、ADR 0024（知見の蓄積と委員会。本 ADR は決定 2 の scope と決定 7 の渡し方を広げる）、ADR 0030（事業部の窓口）、ADR 0037（単発の依頼の道）、ADR 0038（プランナーのワークフローの宣言）、ADR 0039 案（単発の依頼のループ。L6 からの切り出し）、`definitions/knowledge.yaml`・`workflow.yaml`・`artifacts.yaml`、`core-gates/knowledge_context.py`・`knowledge_check.py`

## 文脈

ADR 0039 の L6（外側のループ）の検討で、オーナーが指摘した（2026-11-07）:

- 学びの作用先は、各種作業の入口ごとに違う。今の知見はフラットに持っているのか、作用先が構造化されていて各作業が適切な知見を参照できるのか
- scope を多段構成にしないといけない。同じ役割でも作業の種類によって違う。デザインが要る依頼でも、designer という役割の知見は、ラインでバックログを進めるときの design 作業と、単発の依頼とでは違う
- 知見の構造の見直しは大きな話なので、別に切り出して Learn ループの精度を上げたい

第 1 版の案（作用先を「入口 ＝ ステップ × 道」で表す）に対して、オーナーがさらに指摘した（同日）:

- ケイパビリティと呼んでいるものは、おそらく「業務を実行する能力」と「その成果物を出す能力」を含み、それがカテゴリごとに構造化されている
- 業務を実行するのは各ロールで、知見の作用先は業務とロールで決まるのではないか
- 業務はほとんど入口と同義だが、入口が異なっても同じ業務ということがあるのではないか

確かめると、入口が違っても同じ業務になる例がすでにある。

| 業務 | 入る入口 |
|---|---|
| PR 本文を書く | 実装（`implement`）、続きのジョブ（continue）、本文の直し（`body_fix`）。rally の K-0001・K-0005・K-0006・K-0009 はこの業務の知見 |
| 数字を集めて報告書にまとめる | 単発の分析の依頼（`analysis`）、日次・週次の報告 |
| 画面の案を出す | ラインのチケットの `ui_design`、単発の依頼 |

あわせて、振り分け（プランナー）と単発の依頼の実行役にも知見を渡すこと、依頼者ごとの好みは git ではなく制御プレーンの DB に持つことも論点に入れる。
もう 1 つ、Learn ループの入り口の側の課題として、人の違和感の印（`taste_flag`）が印の文面ごとに別の束になり、同じテーマでもまとまらないことも扱う（factory-engine#264 の補足。11-06 の 8 件の印が 7 個の束になった）。

### 今の形（2026-11-07 時点、main 1569a40 と rally の `.factory-config/knowledge/`）

| 項目 | 今 |
|---|---|
| 置き場 | 製品リポの `.factory-config/knowledge/K-NNNN.yaml` にフラットに 1 件 1 ファイル（rally は 10 件）。テーマ（1〜8）と種類は中に持つ |
| scope | `roles`・`contexts`・`paths` の 3 つ。どれも自由な文字列で、語彙の検査はキーの名前だけ |
| 選び手 | `core-gates/knowledge_context.py`。絞り込みに使うのは `roles` だけ。`contexts`・`paths` は表示するだけで、選ぶのには使っていない。テーマ・作業の種類（道）・変更種別は見ない |
| つないでいる入口 | 実装役（`implement`）の 1 つだけ（`worker/entrypoint.sh` が `--role implement` 固定で呼ぶ）。プランナー・単発の依頼の実行役・デザイナー・検査役・judge・QA・窓口には渡っていない |
| 実際に渡っている知見 | **0 件**。rally の 10 件はすべて `confidence: hypothesis` で、渡す条件（confirmed 以上）に届かない。K-0001 は根拠の事例が 4 件あるが、まだ仮説のまま |
| `roles` に書かれている値 | `implement`・`inspect`・`judge`・`body_fix`・`supervisor`。`supervisor` はエージェントではなく dispatcher のコードなので、文脈として渡す先がない（K-0003・K-0004・K-0008 は誰にも届かない） |
| 教師信号の束ね方 | 違和感の印の signature は `taste:<一言の先頭 40 字>`（`dispatcher/choice.py` の `signature`）。言語化の候補に寄せる段がまだなく、文面が違えば別の束になる。どの業務（ラインの画面か、単発の案か）への印かも鍵に入っていない |
| 依頼者ごとの好み | 置き場がない。種類 `preference` はあるが、製品リポ（git）に置く形しかない |

つまり、知見は役割の名前でしか引けず、その役割も実装役しかつながっていない。同じ役割の中で作業の種類が違う（ラインのデザインと単発のデザイン）ことを表す軸も、作用先がエージェントでない（Engine のコードを直すべき）ことを表す印もない。

つまり、知見は役割の名前でしか引けず、その役割も実装役しかつながっていない。どの業務についての知見かを表す軸も、作用先がエージェントでない（Engine のコードを直すべき）ことを表す印もない。

## 決定

### 1. 作用先の主軸は業務。業務はツリーにする

知見の作用先を、入口ではなく**業務**で表す。業務は、ケイパビリティの「業務を実行する能力」の側で、カテゴリごとのツリーにする（Gen2 のケイパビリティのモデル、2026-11-04 の「ツリー（持ち主は 1 つ）＋使う辺」に揃える）。

- 「多段」はツリーの深さで表す。知見は、ツリーのどの深さのノードにも付けられる。親に付けた知見は子のすべてに効き、子に付けた知見はその業務だけに効く
- ラインのデザインと単発のデザインの違いは、例えば「デザイン」の下に「バックログの画面を仕上げる」と「依頼に応じて案を出す」を子として置いて書き分ける。デザイン全般の知見は親の「デザイン」に付ける
- 業務のノードは「動詞＋対象」くらいの粒度にとどめる。背景（新規か取り込みか、運用中か、など）はツリーに入れず、決定 2 の軸で持つ
- 成果物（ケイパビリティの「成果物を出す能力」の側）とロールも、決定 2 の軸として持つ
- 業務のツリーは工場の定義に持つ（`definitions/work.yaml`、新設）。Gen2 でケイパビリティのモデルを詰めるまでは第 0 版として、今のワークフローのステップ（ADR 0038）、単発の依頼の対応の種類（ADR 0037）、成果物の型（`artifacts.yaml`）から作る。ツリーの葉の側の下書きとして育て、Gen2 のモデルに引き継ぐ

第 0 版のツリーの例（形の例で、中身は第 0 版の PR で決める）:

```
開発（dev）
  要件とストーリー（dev.requirements）
  デザイン（dev.design）
    デザインシステム（dev.design.system）
    バックログの画面を仕上げる（dev.design.screen）
    依頼に応じて案を出す（dev.design.proposal）
  実装（dev.build）
  変更の説明を書く（dev.describe）        … PR 本文。実装・続き・本文の直しから入る
  検査と裁き（dev.review）
計画（plan）
  チケットの進め方を宣言する（plan.workflow）
  依頼を振り分ける（plan.route）
運用（ops）
  QA（ops.qa）
  決定論の操作を動かす（ops.operate）
分析と報告（analyze）
  集計して報告書にまとめる（analyze.report）  … 単発の分析と、日次・週次の報告から入る
  小さな問いに答える（analyze.quick）
窓口（desk）
  依頼者とやりとりする（desk.converse）
```

### 2. 業務のほかの軸は、知見にタグのように付ける。軸は後から足せる

業務を実行する背景（文脈）で知見の効き方は変わる（オーナー 2026-11-07: バックログから新機能を足す実装と、既存のアプリを工場に載せてリファクタする実装とでは効き方が違うかもしれない。業務の抽象度は文脈に応じて異なる）。ただし背景を業務のツリーに入れると、「実装 × 新規 × 運用中 × 単発」のような組み合わせの数だけノードが増える。そこで、業務は主軸のツリーにしたまま、背景は**別の軸**として持ち、知見にタグのように付ける。

- 軸は工場の定義に一覧で持つ（`knowledge.yaml` の `axes`）。軸ごとに、語彙（どこの定義の値を使うか）、階層があるか、作業の側の値をどこから取るか、重み、食い違ったときの扱いを書く
- 知見は、効くと分かっている軸にだけ値を書く。書いていない軸は「その軸では選ばない（どの値でも効く）」
- 軸を足しても、今ある知見は書き直さなくてよい（新しい軸では「書いていない」扱いになる）。後から軸を足していける

最初の軸（例。中身は定義の PR で決める）:

| 軸 | 語彙 | 作業の側の値の出どころ |
|---|---|---|
| 業務（主軸） | 業務のツリー（決定 1） | プランナーの宣言・振り分けの結果・続きの理由（決定 4） |
| 成果物 | `artifacts.yaml` の型（`PR`・`KPIReport`・`DesignConcept` など。足りないものは足す） | 業務から |
| ロール | `agents.yaml`・`workflow.yaml` の役 | ジョブ |
| 作業の目的 | 新機能を足す・既存を直す・不具合を直す・リファクタ・既存のアプリを工場に載せる・移行 | プランナーの宣言 |
| 製品の段階 | `product_stages.yaml`（開発中・出す前後・運用中） | 製品の manifest |
| 依頼の形 | ラインのチケット・単発の依頼（ADR 0037 の道） | 入口 |
| コードの出どころ | 工場が作った・既存のものを引き取った | Blueprint |
| コンテキスト・変更種別・ファイル | 製品の `context-map.yaml`・`change_type_rules.yaml`・glob | プランナーの見込み・差分 |
| 依頼者 | 依頼者の id（依頼者の好みだけ。決定 6） | 窓口 |

抽象度の違いは、知見に付いた軸の数で表す。「実装する」だけに付いた知見はどの実装にも効き（抽象的）、「実装する × 既存のアプリを工場に載せる」に付いた知見は取り込みのときだけ効く（具体的）。

### 3. 選び手は、業務軸から候補を引き、ほかの軸を突き合わせて適応度を出す

1. **業務軸で候補を引く**: 作業の業務のノード自身か祖先に付いた知見と、成果物の型が合う知見を候補にする（どちらか 1 つは知見に必ず書く）
2. **ほかの軸を 1 本ずつ突き合わせる**: 軸ごとに、知見の値と作業の値を比べて点を付ける

| 突き合わせの結果 | 点（仮置き） |
|---|---|
| 一致した（階層のある軸は、作業の値が知見の値の子でもよい） | ＋その軸の重み |
| 知見に値がない | 0 |
| 作業の側の値が分からない（振り分けにとってのファイルなど） | 重みの −1/4 |
| 食い違った | 軸の扱いが `exclude` なら候補から外す、`penalize` なら −その軸の重み |

3. **適応度を出して並べる**: 適応度 ＝ 突き合わせの点の合計 ＋ 業務のノードの深さ ＋ 確かさ（確定 ＞ 確認済み）＋ 鮮度。下限より低いものは渡さず、高い順に件数と文字数の上限（12 件・12000 字、仮置き）まで渡す

- 計算は決定論（LLM を使わない）。何が渡ったかを再現でき、効き目を測れる
- 渡した知見ごとに、適応度とその内訳（どの軸で一致し、どれが分からなかったか）を `knowledge.used` に残す
- 重み・食い違いの扱い・下限は工場の定義の値で、変えるのは定義の PR（学ぶ側が自分で動かさない。ADR 0013 の 8）。最初は、目的・段階・依頼の形は `exclude`、ファイル・コンテキストは `penalize` を仮置きにする
- 値は語彙で検査する（`knowledge_check.py`）。語彙にない値は CI で落ちる。移し替えまでは今の `roles`・`contexts`・`paths` を受け付ける

### 4. 入口は「この回の業務と状況」を渡すだけ

入口（ワーカーのジョブ、窓口の会話、プランナーの判定）は、知見の作用先ではなく、その回の業務と、各軸の値（状況）を選び手に渡す場所にする。

- ラインのチケット: プランナーのワークフローの宣言（ADR 0038）のステップから業務を引く（`ui_design` は `dev.design.screen`、`implement` は `dev.build` と `dev.describe` など）。対応は `work.yaml` に 1 か所で持つ。作業の目的もプランナーが宣言する
- 単発の依頼: 振り分けの結果（ADR 0037 の道と対応の種類）から業務を引く（`analysis` は `analyze.report`、デザインの案なら `dev.design.proposal`）
- 続きのジョブ・本文の直し: 続きの理由から業務を引く（本文の更新は `dev.describe`）
- 製品の段階は manifest、コードの出どころは Blueprint から、どの入口でも同じに取る
- 1 つの回が複数の業務をしてよい（実装のジョブは実装と変更の説明を書く）

これで、入口が違っても同じ業務なら同じ知見が届き、同じ業務でも背景が違えば違う知見が届く。

### 5. エージェントの文脈に入れない作用先を分ける

知見の中には、エージェントに読ませても直らず、Engine のコードや工場の設定を直すべきものがある（`supervisor` 宛ての K-0003・K-0004・K-0008）。知見に `acts_on` を持たせ、作用の仕方を分ける。

| `acts_on` | 作用の仕方 |
|---|---|
| `context`（既定） | 決定 4 の業務の文脈に渡す |
| `engine` | 文脈には渡さない。週 1 の委員会の定例が、担保（`enforcement`）のない `engine` 宛ての知見を Engine の改善 Issue の候補に出す（工場は起票まで。直すのは建設者） |
| `process` | 文脈には渡さない。役割への指示・ラインの設定の変更の提案として人に回す（ADR 0023 の承認の線） |

### 6. 依頼者ごとの好みは制御プレーンの DB に持つ

特定の依頼者（事業主の担当者）についての好み（「表より箇条書きがよい」「数字は税抜きで」「返事は朝にまとめて」など）は、git に置かない。人に紐づく情報で、リポジトリが public の場合もあるため（ADR 0024 の決定 8 の考え方）。

- 置き場は制御プレーンの DB の `requester_preferences`（依頼者の id・主張・決定 2 の軸の値・確かさ・根拠の events の id・確認日・状態）。製品の事業主全体の好みや Blueprint にあたるものは、今までどおり git の知見か Blueprint に置く
- 確かさは出どころで分ける。依頼者が自分で言ったこと（窓口の会話・受け取りの答え）はそのまま確認済み。工場が推し量ったこと（受け取りで直しを求められた傾向など）は仮説で、2 回目に当たるか依頼者が認めたら確認済み
- 委員会には通さない（個人の好みで、作用先はその依頼者の作業だけ）。代わりに、依頼者が窓口（コンソール・MCP）で自分の好みの一覧を見て、直し・消すことができるようにする
- 選び手は、依頼者が分かる回（窓口の会話・振り分け・単発の依頼の実行）に、git の知見と依頼者の好みを合わせて渡す。好みは知見と別の見出しにし、依頼の文面と食い違えば依頼の文面を優先する
- 渡した記録は `knowledge.used` と同じく events に残す（id は `P-NNNN` のような不透明な id。中身は events に書かない）

### 7. 選び手をつなぐ順番

選び手をつなぐのはワーカーのプロンプトの変更なので、ADR 0024 の決定 7 のとおりオーナーの承認を得てマージする。順番は、学びの材料が先に溜まっていて効き目が見えやすいところから。

1. 業務のツリーの第 0 版（`work.yaml`）と、選び手を業務・成果物で選ぶ形にする。実装のジョブは `dev.build`・`dev.describe` を渡す（今の知見の多くは `dev.describe` の知見）
2. 続きのジョブと本文の直し（`dev.describe`）。PR 本文の知見が入口によらず同じに届く
3. プランナーと振り分け（`plan.workflow`・`plan.route`。ADR 0038 の決定 8 の「プランナーの知見に戻す」の受け皿にもなる）
4. 単発の依頼の実行役（`analyze.*`・`ops.operate`・`dev.design.proposal`）と、依頼者の好み（決定 6）
5. デザイン（`dev.design.*`）、検査と裁き（`dev.review`）、QA（`ops.qa`）、窓口（`desk.converse`）

### 8. 効き目を業務ごとに測り、scope の当たり外れを Learn ループに戻す

Learn ループの精度は「正しい知見が、正しい業務に、正しいときだけ届くか」で決まる。今は渡したかどうか（`knowledge.used`）しか残らないので、当たり外れを信号にする（数えるのは測る側。決定論）。

| 信号 | 決め方 | Learn ループでの扱い |
|---|---|---|
| 届いたのに食い違った | 渡した知見の id が、そのジョブの「## 補足」の食い違いに書かれた | 再確認の候補（今の失効のきっかけ「反証」） |
| 届いたのに差し戻された | 渡した知見に従った作業が、同じ真因で差し戻された | 再確認の候補 |
| 届かなかった | 事例の分析で真因が既存の知見と同じだったのに、その回には渡っていなかった（ノードが深すぎる・成果物が抜けている・入口がつながっていない） | 委員会に scope を広げる（親のノードに上げる、軸の条件を外す）変更セットを出す |
| 届きすぎ | ある業務で渡し続けているのに、効き目が見えない状態が続く | 委員会に scope を狭める（子のノードに下げる、軸の条件を足す）候補を出す |

- `knowledge.used` に、その回の業務・成果物と、渡した入口を足す（入口は作用先ではなく、どこから入ったかの記録として残す）
- 知見は**狭く生まれて、再現したら広がる**。事例型の分析役（`case.py`）が下書きを書くときは、業務のツリーと軸の語彙を見せ、業務か成果物を必ず書かせ、その事例の状況の軸の値も全部付けさせる。別の状況で同じことが起きたら、委員会がその軸の条件を外して広げる。別の状況で外れたら条件を足して狭める。確かさを根拠で上げるのと同じく、効く範囲の広さも根拠で決める

### 9. 教師信号は「業務 × 観点」で束ねる。文面は材料に残す

知見を業務で引けても、その手前の束ね方が文面ごとだと、同じテーマの信号が 1 件ずつの束に割れ、回数で固める段（反復型）にも事例型の分析にも届かない。束の鍵を文面から切り離す。

- 束の鍵は `<信号の種類>:<業務>:<観点>`。業務は決定 1 のツリーのノード（例 `dev.design.screen`）。観点は信号の種類ごとに決まった語彙から選ぶ。違和感の印なら `design_guideline.yaml` の節（原則・トーン＆マナー・基礎・部品・画面の型・文言など）とその中の規則の id、検査の指摘なら今までどおり rubric の id
- 観点を付けるのは束ねる段（`learn.py`）。LLM が語彙の中から候補を出してよいが、語彙の外の値は決定論の検査で「未分類」に落とす。人が印を付けるときに言語化の候補から選んだ観点があれば、それを優先する（ADR 0025 の 4、2026-10-31 の内部品質の決定 Q-C の「工場が言語化の候補を出し人が選ぶ」）
- 一言の文面・画面・PR は束の材料として残し、事例型の分析役と委員会が読む。文面での寄せ（似た言い方を同じ束にする）はしない
- 「未分類」が溜まったら、週 1 の委員会の定例が観点の語彙を足す候補を出す。観点（rubric の観点やデザインの基準）を足すのは人の承認（2026-10-31 の内部品質の決定 Q-A）
- 束から作った知見の `work` は、束の鍵の業務をそのまま使う

### 10. 置き場のディレクトリはフラットのまま

知見を業務ごとのディレクトリに分けると、複数の業務や成果物に効く知見の置き場が決まらない。引き方は scope で持ち、ディレクトリはフラットのままにする（構造は今までどおり委員会がオーナー）。`INDEX.md` に業務のツリーの順の一覧を足し、人が「この業務に何が効くか」を読めるようにする。

## 決めどころ

| # | 問い | 推奨 |
|---|---|---|
| S1 | 知見の作用先の主軸 | 業務のツリー（決定 1）。入口では表さない。入口が違っても同じ業務がある。多段はツリーの深さ。第 0 版を今の定義から作り、Gen2 のケイパビリティのモデルに引き継ぐ |
| S2 | 業務を実行する背景（文脈）の持ち方 | 業務のツリーに入れず、別の軸として知見にタグのように付ける。軸は定義の一覧に持ち、後から足せる（決定 2） |
| S3 | 知見の選び方 | 業務軸で候補を引き、ほかの軸を突き合わせて適応度を出し、高い順に渡す。計算は決定論、重みと扱いは定義の値で、変えるのは PR（決定 3） |
| S4 | Engine 宛て・工程宛ての知見を文脈から外すか | 外し、委員会の定例が改善 Issue の候補にする（決定 5） |
| S5 | 依頼者ごとの好みの置き場と通し方 | 制御プレーンの DB。委員会を通さず、依頼者が見て直せる形（決定 6） |
| S6 | 選び手をつなぐ承認の取り方 | この ADR の承認で決定 7 の 1〜5 の順番をまとめて承認とし、各 PR は CI 緑で工場がマージする。業務のツリーの第 0 版の中身だけは PR で見てもらう |
| S7 | 効き目の 4 つの信号を Learn ループに足すか | 足す（決定 8）。「届かなかった」から先に入れる |
| S8 | 教師信号の束ね方 | 文面ではなく「業務 × 観点（決まった語彙）」で束ね、文面は材料に残す。語彙の外は「未分類」にし、語彙を足すのは人の承認（決定 9） |

あわせて、今は渡せる知見が 0 件なので、仮説から確認済みへの上げ方（週 1 の定例の `promote`）が動いていない理由を別に確かめる（K-0001 は事例 4 件で仮説のまま）。これは本 ADR の外の不具合として扱う。

## Gen2 で決めること

本 ADR では決めず、Gen2（ケイパビリティのモデルと、工場のオンボーディングの手順を作るとき）に決める。

1. **ケイパビリティのツリーの切り方**: 領域とカテゴリ、分析と報告や窓口の置き場所、業務と成果物を別のツリーにするか、「使う」の線を知見の届き方にも使うか、性質の軸（a11y・言葉など）に付く知見をどの業務に届けるか、ロールに付く知見をどこまで残すか。資源（実行環境など、2026-11-04 のメタモデルの工程・資源・性質のうちの資源）にも知見を付けるか。語を 2026-11-04 の「工程」と本 ADR の「業務」のどちらに揃えるか
2. **内部品質と外部品質の知見**: 2026-10-31 の決定（判断の材料・知見の置き場・基準を最初から分ける）を、置き場は 1 つのまま業務のノード（検査と QA）や軸で引き分ける形に読み替えてよいか
3. **軸の重みと食い違いの扱いの初期値**の決め方。効き目の信号を見て人が PR で直す形でよいか
4. **人の指示で知見を足す道**（オーナー 2026-11-07）。今は Learn ループの中で委員会を経て足す道しかない。「この知見を加えておいて」と人が指示する道を、ナレッジマネジメントのケイパビリティとして持つ。委員会の審査（整合・根拠・担保・反対）を通すか、人の指示そのものを根拠にして確かさをどこから始めるか
5. **既存の組織の知見の取り込み**（同）。すでに運用中のアプリを工場に載せるとき、その運用の中で溜まった知見を取り込む。工場のオンボーディングの手順の中で、既存の組織の知見を分析の対象にし、工場の知見に反映する
6. **知見の持ち方を「内容を持つ」と「参照を持つ」に分ける**（同）。既存の組織のナレッジマネジメントの中身をコピーすると、原本が更新されたときにコピーと食い違う。工場は参照を持てるようにする。考えられる形の例:
   - 内容を持つ: 今の `K-NNNN.yaml`。工場が学んだ知見
   - 参照を持つ: 原本の場所と版（いつの版を見たか）だけを持ち、使うときに原本を読む
   - 参照＋工場側の付け足し: 原本は参照し、工場が付ける軸のタグや適用の条件だけを持つ（原本には軸がないので、選び手が引けるように）
   - 派生: 外部の知見から工場が作った知見。原本を根拠として指し、原本が変わったら再確認に回す

   原本の更新をどう検知して追従するか、原本を読めないとき（権限・停止）にどうするか、参照先の機密区分をどう扱うかも決める
7. **既存の組織で後から生まれる知見の受け口**（同）。既存の組織でも知見は増え続ける。人が「こういう知見が足されたよ」と工場に共有する形になる見込み（会社で、A 開発部の知見を全社の会や勉強会で B 開発部に届けるのと同じ）。共有を受ける窓口、取り込むときの審査、工場の既存の知見との矛盾の解き方を決める

## 順番

1. 定義: `work.yaml`（業務のツリーの第 0 版と、ステップ・道・続きの理由から業務への対応）、`knowledge.yaml` の `axes`（軸の一覧・語彙・重み・食い違いの扱い）と `acts_on`。`knowledge_check.py` の語彙の検査
2. 選び手: `knowledge_context.py` を業務軸の候補と適応度で選ぶ形に。実装のジョブをつなぎ替え、`knowledge.used` に業務・軸の値・入口・適応度の内訳を足す
3. rally の既存の 10 件の移し替え（業務・成果物と、根拠の事例の状況の軸を付ける、`supervisor` 宛ては `acts_on: engine`）を変更セットの PR で
4. 決定 7 の 2〜5 の順に選び手をつなぐ。依頼者の好みの DB は 4 と一緒に
5. 効き目の信号（決定 8）

束ね方（決定 9）は 1 と並行で入れてよい（業務のツリーができれば、違和感の印の鍵から始められる）。

## 選ばなかった案

- **入口（ステップ × 道）で作用先を表す**（この案の第 1 版）: 入口が違っても同じ業務がある（PR 本文を書く、報告書をまとめる）。入口ごとに知見を書き分けると同じ知見が割れ、片方の入口にだけ届く
- **役割の名前に作業の種類を混ぜる（`designer_line`・`designer_oneoff` のような値）**: 役割と作業の組み合わせの数だけ値が増え、「デザイン全般」を書く方法がなくなる
- **軸を並べるだけで主軸を置かない**: 「デザイン全般」と「単発のデザイン」の親子が表せず、どの軸から引くかが毎回ぶれる。業務を主軸のツリーにし、ほかの軸は突き合わせに使う
- **背景も業務のツリーに入れる（「新機能の実装」「取り込みの実装」をノードにする）**: 目的・段階・依頼の形の組み合わせの数だけノードが増える。軸を足すたびにツリーを組み直すことになる
- **適応度を LLM に付けさせる**: 何が渡ったかが再現できず、重みを学ぶ側が動かすことになる
- **業務ごとにディレクトリを分ける**: 複数の業務に効く知見を複製するか、どこかに寄せるかを毎回決めることになり、矛盾の元になる（ADR 0024 の変更セットの考え方に反する）
- **LLM に関係のある知見を選ばせる**: 何が渡ったかが決定論で再現できず、効き目を測れない。選ぶのは決定論のまま（ADR 0024 の決定 7）
- **依頼者の好みも git の知見に置く**: 人に紐づく情報が git の履歴に残り、消せない。依頼者が自分で直せない
- **違和感の印を文面の近さで寄せる（埋め込みの類似度など）**: 何が同じ束かが再現できず、閾値の調整が学習器の自己採点になる。観点の語彙で束ね、語彙は人が足す
- **すべての作業に全部の知見を渡す**: 文脈が太り、関係のない知見が同じ重みで効く（ADR 0024 の選ばなかった案と同じ）

## 結果

- 入口が違っても同じ業務なら同じ知見が届き、同じ業務でも背景（目的・段階・依頼の形など）が違えば違う知見が届く。軸は後から足せる。プランナーと振り分け、単発の依頼の実行役にも知見が届く
- 業務のツリーという定義が 1 つ増える。ステップ・道・成果物の型を足したときに、業務への対応も直す必要がある（食い違いはテストで見る）。Gen2 のケイパビリティのモデルの下書きにもなる
- Engine を直すべき知見が文脈に紛れず、改善 Issue に回る
- 依頼者ごとの好みが git に残らず、依頼者が自分で見て直せる
- 同じテーマの違和感の印が 1 つの束にまとまり、回数で固める段と事例の分析に届く
- 当たり外れが信号になり、Learn ループが scope そのもの（ツリーのどの深さに付けるか、どの軸の条件を付けるか）を直せるようになる
