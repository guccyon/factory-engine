# ADR 0044: 判断を事業主・依頼者・工場のメンテナーに振り分け、同じ目的の仕事を同時に流さない

- 状態: 承認（2026-11-08 オーナー。決めどころ R1 はオーナーの指示どおり、R2〜R6 は推奨どおり）
- 関係: ADR 0006（仮決めと出口の judge）、ADR 0024（知見と委員会）、ADR 0026 決定 6・7（誰の出番か・受信トレイ）、ADR 0027（衝突の回避と工程の学び）、ADR 0032（通知のルーティング。建設は自社）、ADR 0034（受信トレイで答える）、ADR 0036（プランナーの品質）、ADR 0038（ワークフローの宣言と着手のしかた）、ADR 0040（業務のツリーと `acts_on`）、ADR 0042（振る舞いが変わらない実装は judge に任せる）、`orchestrator/dispatcher/inbox.py`・`judgment.py`・`committee.py`・`planner.py`、`definitions/judgments.yaml`・`knowledge.yaml`・`planner.yaml`

## 文脈

### 起きたこと（2026-11-08）

受信トレイに rally #1192 の判断（judgment 11993）が回ってきた。問いは「PR 本文の直し（body_fix）が終わり、直した本文の再検査が通るまでマージを待たせる仕組みを、Engine のどこで・何を見て判断するか」。選択肢は supervisor の `merge_step` で待つ／必須チェックだけに任せる／`inspector_approved` の中に足す／supervisor が自分で検査を走らせる、の 4 つ。

オーナーの受け止め:

> この内容だと事業化後に提供先の顧客が判断するのは不可能。工場が判断できるように提供までにプロセスを磨き込まないといけない。顧客が判断できないものは、工場のメンテナンス側（事業として工場を提供する我々）に判断を求めるのが正解。受信トレイではない。
> 本質的には、競合が発生するような内容を同時に進めてしまったことにも問題がある。プランナー向けの学びとしてフィードバックが必要。

### 今の作りで人に回る道

- judge が人に回した判断（停止 `judge:`）は、中身にかかわらずすべて `who=owner`（オーナー＝事業主）の件になる（`inbox.py` の `STOPPAGE_WHO` に `judge` がなく、既定の `owner` に落ちる）。「この問いを誰なら決められるか」を見る処理はない
- 人の役割（`WHO`）には `builder`（建設者）があり、更新の再開・差し戻し・ほかの PR を待つ保留はここに回っている。ただし、これは停止の種類で決まるだけで、判断の中身では決まらない。また builder の件も同じ受信トレイに並ぶ
- ADR 0042 で、`implementation`・`user_visible=none`・`reversible=true` の判断は judge が決めるようになった。今回の件は類型が `implementation` だったが、judge は「境目を誤ると直していない本文がマージされる（重さはメジャー）」として自分では決めず、`user_visible`・`reversible` も空だったので、工場の守り（`forced_delegation`）にも当たらなかった

### 事業主には読めない問いが、ほかにも回っている

ADR 0042 の「効果の見込み」の表の 4 件のうち 3 件は、製品ではなく工場の仕組みの問いだった。

| PR | 問い | 何についての問いか |
|---|---|---|
| rally #1192 | body_fix の後のマージの待ちを Engine のどこに置くか | Engine の supervisor |
| rally #1095 | `check.mjs --events` の見張りに TAP を求めるか | 工場の検査の内部 |
| rally #931 | PR 本文の見出しの正をどこに置くか | 工場が使う開発の道具 |

どれも、事業主が利用者や事業の言葉で判断できる材料を持たない。商用で顧客の事業主に届けば、答えようがない問いが受信トレイにたまり、その間 PR はマージで止まる。

### なぜ工場の問いが製品のラインに乗ったか

rally #1192 の元の Issue #1122 は、知見の委員会の週 1 の定例が起票した「担保: K-0012 を ci_check で決定論にする」。K-0012 は `acts_on: engine`（Engine のコードや工場の設定を直すべき知見）で、`definitions/knowledge.yaml` には「週 1 の定例が Engine の改善 Issue の候補に出す（起票まで。直すのは建設者）」とある。ところが委員会の担保の起票（`committee.py` の `enforce_issue`・`weekly_issues`）は `acts_on` を見ずに、どれも製品のリポジトリに `factory:planned` で起票している。そのため、工場の仕組みの変更が製品の PR として作られ（Engine への差分は `tools/pr-body-check/engine/pr-body-recheck.patch` として製品のリポジトリに置かれた）、その仮決めが製品の判断として事業主に回った。

これは「製品リポは工場に依存させず、単体で別の開発組織に移管できる形にする。製品の生産に関する固有知見は工場側が持つ」という方針（2026-11-08 オーナー）にも合わない。

### 同じ目的の仕事を 2 本同時に流した

同じ「担保: K-0012 を ci_check で決定論にする」が 2 本流れていた。

| | 起票 | 起票した道 | PR | 中身 |
|---|---|---|---|---|
| 1 本目 | rally #1052（11-07 04:13 UTC） | 委員会の議決 D-0033（PR #1051）の担保 | #1116（11-07 11:09、開いたまま） | `tools/pr-body-check/merge-gate.mjs` と `ci/pr-body-check.yml` を足す |
| 2 本目 | rally #1122（11-08 02:16 UTC） | 委員会の週 1 の定例（2026-W45）の担保 | #1192（11-08 08:19） | Engine の `merge_step` への差分と、同じ `ci/pr-body-check.yml` を足す |

2 本は同じ新規ファイル（`ci/pr-body-check.yml`）と同じ知見のファイル（`K-0012.yaml`）を作り、片方がマージされればもう片方は衝突する。結局 #1116 を閉じて #1192 に一本化した（11-08）。#1116 の 3 つのジョブ（$3.25）と、2 本分の検査・judge・人の判断が無駄になった。

重なりを止める段は 3 つあったが、どれも働かなかった。

1. **委員会の起票:** 重複を防ぐ鍵が、議決の担保は `議決 × 知見 × 解決策の種類`、週の定例は `週 × 知見 × 解決策の種類` で、どちらも「同じ知見 × 同じ解決策の種類の Issue・PR が開いているか」を見ない。#1122 の本文には「担保の Issue #1052 と #1053 は起票されていますが、K-0012 にはまだ記録がありません」とあり、委員会は 1 本目に気づいていながら、知見のファイルに記録がない（PR がまだマージされていない）ことを理由に 2 本目を起票した
2. **プランナー:** 委員会の Issue は `factory:planned` で起票され、プランナー（`factory:plan`）を通らない。プランナーには流れているタスクとその見込みのファイル（`inflight.md`）とよく衝突するファイル（`hot_files`）を渡す作り（ADR 0027 の 2、ADR 0038）があるが、そもそも呼ばれなかった
3. **投入の並べ方（supervisor）:** 同時に流さないのは「よく衝突するファイル」（工場の記録から作る一覧）に触るタスクだけ。新規ファイルの重なりや、題・知見 id が同じことは見ない

## 決定

### 1. 判断ごとに「誰なら決められるか」（`decider`）を持つ

仮決め・指摘の判断の各件（judge が人に回すもの）に `decider` を持たせる。まず「製品自体の仕様か、工場自体の仕様か」で分け、製品の仕様のうち明確な依頼者がいるものは依頼者に回す（オーナー 2026-11-08）。

| 値 | 決める人 | 中身 |
|---|---|---|
| `business` | 事業主 | 製品自体の仕様。利用者・事業に何が起きるか。画面・文言・見た目、製品の範囲と優先度、公開する契約の形、製品のデータ |
| `requester` | 依頼者 | 製品自体の仕様のうち、明確な依頼者がいる仕事（単発の依頼、窓口から入った依頼など。ADR 0030・0037・0039）。依頼者が分かる仕事は依頼者に聞く |
| `maintainer` | 工場のメンテナー | 工場自体の仕様。工場の工程・仕組み・判断の基準。Engine のコード、検査・judge・CI の道具、ワーカーの指示、工場の知見の担保 |

- 問いの目印は「製品の利用者と事業の言葉だけで選べるか」。選べないなら工場自体の仕様（`maintainer`）
- `requester` になるのは、仕事の由来に依頼者が記録されているとき（窓口の会話・単発の依頼の起票者）。依頼者がいても、工場自体の仕様の問いは `maintainer`

### 2. 決め方は、決定論の印を先に、judge の見立てを後に

1. **由来の印（決定論）:** 次のどれかに当たれば `maintainer`
   - チケットの起こりが `acts_on: engine` か `process` の知見（委員会の担保・Learn の改善案）
   - 差分のすべてが、製品の manifest（`.factory-config/manifest.yaml`）に宣言した「工場の持ち物」の道（`factory_owned_paths`。例: `.factory-config/**`、`tools/pr-body-check/**` のような工場の検査の道具）の中にある
   - 判断の対象が Engine のファイル・イベントの名前・工場の定義（`definitions/`）を名指ししている
2. **judge の見立て:** 印に当たらないものは、judge が製品の仕様か工場の仕様かを書く（ADR 0042 の `user_visible`・`reversible` と同じく必須の欄）。根拠を `precedent` と同じ形で残す
3. **製品の仕様なら依頼者を引く（決定論）:** 製品の仕様で、仕事の由来に依頼者があれば `requester`、なければ `business`
4. **迷ったら `maintainer`:** 製品の仕様か工場の仕様か迷ったら、事業主に読めない問いを送らないほうを既定にする。メンテナーが製品の判断だと見たら付け替える（付け替えは記録に残し、judge の見立ての外れとして数える）

### 3. 工場のメンテナーとは誰か（事業者で変わる）

- 「工場のメンテナー」は役割で、誰が担うかは事業者ごとの設定（Blueprint の人の一覧）で決める
  - 工場を提供元が保守する事業者（今の形）: メンテナー＝提供元（我々）
  - 工場自体も自走させる事業者: メンテナー＝事業主の側の担当。工場の仕様の問いも事業主の側に回る
- 役割に `maintainer` を足す。今の `builder`（建設者）の件（更新の再開・差し戻し・保留）も、同じメンテナーの入口に寄せる

### 4. 宛先と通知

| decider | 出す場所 | Slack の通知 |
|---|---|---|
| `business` | 事業主の受信トレイ（今どおり） | 事業主の Slack（今どおり、ADR 0032） |
| `requester` | 依頼者の件（窓口 MCP の `inbox_list` で依頼者に見える。ADR 0039 の順番 4・5 と同じ） | 依頼者への知らせ（窓口の会話の知らせの口） |
| `maintainer`（メンテナー＝提供元） | 事業主の受信トレイには出さない。提供元の入口（Gen1 は工場のリポジトリの Issue、ラベル `factory:provider-judgment`） | **送らない**（オーナー 2026-11-08）。将来は工場のメンテナーの Slack に送る |
| `maintainer`（メンテナー＝事業主の側） | 事業主の側のメンテナーの件 | 事業主の側の Slack |

- 提供元の Issue は 1 つの PR の問いを 1 本にまとめ、問い・今の案・他の案・judge の見立てと推奨・答えたら何が起きるかを書く
- 答えは Issue のコメント（`/factory answer <件> keep|replace|change: 一言`）か、メンテナーのトークンでの窓口 MCP の `inbox_answer` で受け、今と同じ `inbox.answer` の 1 か所を通す。判断の状態の正本は制御プレーンの記録のまま（ADR 0034 の A1 を保つ。変えるのは、誰に見せてどこで聞くか）
- 通知の宛先は `notifications.yaml`（ADR 0032）に `maintainer` の行として持ち、Gen1 は空（送らない）にする。メンテナーの Slack ができたら、そこに足すだけで送り始める

### 5. 工場のメンテナーを待つ間、製品の PR はどうするか

- judge の推奨があり、`reversible=true` で、`user_visible=none` のものは、推奨で進めて PR を止めない。メンテナーには「事後の確認」として回し、答えが推奨と違えば直しのチケットを積む（ADR 0006 の「仮決めで続行し出口で確定」と同じ考え方）
- それ以外は、PR を保留にしてメンテナーを待つ。保留は `who=maintainer` で、事業主のマージ待ちには数えない
- 確信度の下限や「事後の確認」にする条件は運用パラメータ（工場が調整し、変えた前後を記録する）

### 6. 工場の持ち物の仕事は、製品のラインに流さない

- 委員会の担保の起票と、Learn の改善案の起票は、知見の `acts_on` を見る
  - `context`（製品の作業に渡す知見）: 今どおり製品のリポジトリに起票する
  - `engine`・`process`: 工場のリポジトリに Engine の改善 Issue（`factory:process-proposal`、ADR 0027 の実施の記録と同じ口）として起票する。製品の Issue にはしない。実装とマージは今の承認の線（建設者が直し、アーキ・プロセスの変更はオーナーの承認）
- 製品のリポジトリに置かれた Engine への差分（`tools/pr-body-check/engine/*.patch`）と、工場の検査の道具の置き場は、工場の持ち物として工場のリポジトリに移すかを別に決める（下の「後で決めること」）

### 7. 工場のメンテナーに回った判断を、工場が磨き込むべきところとして数える

- 工程の信号（ADR 0027 の 3）に `maintainer_judgment` を足す。束ねる鍵は `類型 × 由来（担保・Learn・製品のチケット）× 判断の対象（Engine のどの部分か）`
- 束が閾値を超えたら、事例型の分析役に回し、「工場が自分で決められるようにするには、どの判断の基準・既定・前例が足りないか」を掘る。改善案は Engine の改善 Issue に起票する
- 日報（`report.factory_health`）に、事業主に回った判断の数（`business`）、依頼者に回った数（`requester`）、メンテナーに回った数（`maintainer`）、付け替えた数を出す
- 商品化の条件に「事業主・依頼者に回る問いはすべて製品の仕様（付け替え 0）」「`maintainer` の数が下がり続けている」を足す

### 8. 同じ目的の仕事を同時に流さない（プランナーへの学び）

1. **起票の前に確かめる（委員会・Learn）:** 担保の重複を防ぐ鍵を `知見 × 解決策の種類` にし、開いている Issue・PR があれば新しく起票せず、その Issue に議決と案をコメントで足す。知見のファイルに記録がなくても、開いている担保の PR があれば「進行中」と読む
2. **工場が起こした仕事もプランナーを通す:** 委員会・Learn・デザインの線が起票する実装の Issue を `factory:planned` に直行させず、プランナー（`factory:plan`）の着手判定を通す。少なくとも、流れているタスクとの重なりの判定は必ず通す
3. **プランナーが同じ目的を見分ける:** `inflight.md` に開いている PR（チケットの状態が `planned`・`active` でなくても、PR が開いているもの）と、その PR が実際に触ったファイル・新規に足したファイルを載せる。プランナーの決まり（`planner.yaml` の `rules`）に次を足す
   - 流れているタスクと、題・知見 id・`Closes` する目的が同じか、新規に足すファイルが重なるなら、同時に着手しない。後に並べる（`start: after`）か、重複として起票元に返す（どちらにしたかと根拠をプランのログに残す）
   - 片方が進んでいる仕事の続き・作り直しなら、新しい PR を作らず、進んでいる PR の続きのジョブにする
4. **投入の並べ方（supervisor）:** 同時に流さない条件に「新規に足すファイルの重なり」と「同じ知見 id の担保」を足す（ADR 0027 の 2 の「よく衝突するファイル」に加えて）
5. **信号として数える:** 工程の信号に `duplicate_work`（同じ目的の PR が 2 本以上開いた、またはどちらかを閉じて一本化した）を足す。今回の #1116 と #1192 を最初の教材にし、過去 7 日の記録で `process:duplicate_work:K-0012` の束ができ、分析役が上の 1〜3 にあたる改善案を返すことを、受け入れの条件にする

|---|---|---|---|
| R1 | 判断の持ち主の分け方 | 製品の仕様は事業主（`business`）、そのうち依頼者がいれば依頼者（`requester`）、工場の仕様はメンテナー（`maintainer`）（決定 1。2026-11-08 オーナーの指示どおり） | 類型（`implementation` など）で決め打ちする（類型と持ち主は別の軸で、`implementation` にも製品の問いがある） |
| R2 | 製品の仕様か工場の仕様か迷ったときの既定 | `maintainer`（事業主に読めない問いを送らない。メンテナーが付け替える） | `business`（今までどおり事業主に回し、事業主が「分からない」と返したら提供元へ） |
| R3 | 提供元の入口（Gen1） | 工場のリポジトリの Issue（`factory:provider-judgment`）。Slack には送らない（オーナーの指示どおり）。答えは同じ `inbox.answer` を通す | 受信トレイの中に提供元だけが見る欄を作る（オーナーの「受信トレイではない」に合わない） |
| R4 | 提供元を待つ間の製品の PR | 選び直せて利用者に見えないものは推奨で進め、事後の確認にする。ほかは保留 | すべて保留にして提供元を待つ |
| R5 | `acts_on: engine`・`process` の担保の起票先 | 工場のリポジトリの改善 Issue（製品のラインに流さない） | 今どおり製品のリポジトリに起票し、判断の宛先だけ提供元にする |
| R6 | 工場が起こした実装の Issue | プランナーを通す（`factory:plan`） | `factory:planned` のまま、supervisor の投入の前に重なりの判定だけ足す |

## 順番

1. 同じ目的を同時に流さない（決定 8 の 1・3・4）。委員会の起票の鍵、`inflight.md` に開いている PR、プランナーの決まり、投入の重なりの判定。小さく、今日の無駄を直接止める
2. `decider` の欄と由来の印（決定 1・2）。judge のプロンプトと `judgment.py`、manifest の `factory_owned_paths`
3. 宛先（決定 3・4）。`WHO` に `maintainer`、依頼者の件、事業主の受信トレイと通知から除く、factory-engine の Issue、コメントからの答え、`notifications.yaml` の `maintainer` の行（Gen1 は空）
4. `acts_on` で起票先を分ける（決定 6）と、工場が起こした Issue をプランナーに通す（決定 8 の 2）
5. 工程の信号 `maintainer_judgment`・`duplicate_work` と日報の数（決定 7・8 の 5）

## 選ばなかった案

- **受信トレイの件に「提供元向け」の印を付けて同じ一覧に並べる**: 事業主の画面に読めない問いが残り、件数・通知にも混ざる。商用では事業主と提供元は別の組織なので、入口を分ける
- **工場の仕組みの判断をすべて judge に任せる**: 工場の判断の基準そのものを変える問い（今回の「どこで待つか」も、誤ると直していない本文がマージされる）は、今の段階では提供元が決める（工場のプロセス・アーキの変更はオーナーの承認という方針）。決められなかった問いを信号として数え、判断の基準を磨くことで、提供元に回る数を減らしていく
- **重複は人が気づいて閉じる**: 今回はそうしたが、気づくまでにジョブ 3 つ分と判断 2 本分を使った。工場の仕組みで止める

## 結果

- 事業主の受信トレイには、利用者と事業の言葉で選べる問いだけが残る
- 工場の仕組みの問いは提供元に集まり、その数が「提供までに工場を磨き込むべきところ」の物差しになる
- 判断の持ち主の読み違い（製品の仕様を工場の仕様と読むなど）が新しい外れ方になる。付け替えの数で見る
- 提供元の入口（工場のリポジトリの Issue）が 1 つ増える。Slack に来ないので、提供元は Issue を見に行く必要がある。Gen1 は提供元＝オーナーなので、見る場所が受信トレイと工場のリポジトリの 2 つになる
- 委員会・Learn が起こした仕事は、プランナーを通る分だけ着手が遅れる

## 後で決めること

- 製品のリポジトリにある工場の検査の道具（`tools/pr-body-check/` など）と Engine への差分の置き場。製品を単体で移管できる形にする方針に沿って、工場のリポジトリに移すか（Gen1.5 の取り込みの設計と合わせる）
- 今開いている rally #1192 の扱い。本 ADR の決定 6 に従えば Engine の改善 Issue として作り直す対象だが、判断 11993 はオーナーの選択待ちなので、ここでは変えない
