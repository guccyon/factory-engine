# ADR 0037: 単発の依頼に応える（決まった操作の 1 回実行と、集計・分析の報告）

- 状態: 提案（2026-11-06。決めどころ O1〜O7 はオーナーの承認待ち）
- 関係: ADR 0030（事業部の窓口。依頼と問い合わせ、`task_kinds` の `answer`）、ADR 0025・0026（プランナーの着手判定と経路）、ADR 0032（通知の系統。`done.task`）、ADR 0034（受信トレイの答え方。取り返しのつかない作用は自由文で確定しない）、ADR 0024（制限付きの保管先）、ADR 0028（P5b の Answer ライン）、`definitions/desk.yaml`・`definitions/planner.yaml`・`definitions/notifications.yaml`

## 文脈

今の窓口（ADR 0030）とプランナー（ADR 0026）は、依頼をすべて「コードを変える仕事」として扱う。依頼は Issue になり、着手判定 → 経路（デザイン → 実装）→ PR → マージで終わる。
データの書き出しのような成果物を返す依頼も、Gen1 は実装のタスクとして流す（スクリプトを書いて結果を PR に添える。`desk.yaml` の `answer`）。

2026-11-06、定期レポートの再送（`factoryctl report send`）を工場に頼もうとしたところ、頼む道がなかった。窓口から頼んでも Issue → plan → 実装になり、ワーカーは Docker のソケットも制御プレーンの操作も持たないので、決まった操作を 1 回動かすことができない。結局オーナーがコマンドを打った。

オーナーの要望（2026-11-06）:

- 工場への依頼として、レポートを送ってもらうことはできないのか。窓口からの依頼でも、Issue を p0 で作って実行してもらうのでもよい。プランナーは「実行してもらうだけ」の経路を判断できないのか
- 商用化後の実運用では、こういった要望は顧客から普通に来る
- 単発のタスク実行は必ず必要。「XXXX のデータを集計して分析結果を添えて報告して」のような要望に応えるのは、開発事業部としての大きな価値の一つ。ただのソフトウェア開発の自動化工場ではない

依頼には、コードを変えずに済むものが 2 種類ある。

| 種類 | 例 | 今の扱い | 本来の形 |
|---|---|---|---|
| 決まった操作の 1 回実行 | 定期レポートを今すぐ送り直す、報告書を書き出す、使用量の要約を出す | 道がない（人がコマンドを打つ） | 工場がすでに持つ操作を、引数を決めて 1 回動かす |
| 集計・分析の報告 | 「先月の予約のキャンセル率を集計して、理由を添えて報告して」「この 2 週間の停止の傾向をまとめて」 | 実装のタスク（スクリプトの PR） | データを読み、数を出し、解釈を添えた報告書を返す。コードは残さなくてよい |

どちらも、PR を作ってマージするのは筋が違う。製品のリポジトリに使い捨てのスクリプトが溜まり、マージの承認という関係のない人の出番が増え、返す物（報告書）が PR の添付に埋もれる。

## 決定

### 1. 依頼は 3 つの型に分ける。窓口とプランナーのどちらからも同じ型に行き着く

| 型 | 何をするか | 終わり方 |
|---|---|---|
| 変更（change） | コード・契約・文書を変える。今のライン | PR のマージ |
| 操作（operation） | 工場の操作の一覧（決定 2）にある操作を、引数を決めて 1 回動かす | 操作の結果を依頼者に返す |
| 報告（analysis） | データを集計・分析し、解釈を添えた報告書を作る（決定 5） | 報告書を依頼者に届ける |

- 窓口（ADR 0030）: 相談役が下書きを作るとき、タスクごとに型を付ける。`desk.yaml` の `task_kinds` に `operation` と `analysis` を足し、今の `answer`（実装のタスクとして流す成果物）は `analysis` に置き換える。1 つの依頼に型が混ざってよい（「通知の文面を直して、直したら今週のレポートを送り直して」は 変更 → 操作 の依存）
- Issue（ADR 0026）: プランナーの判定に `operate` と、経路の役に `analyst` を足す。`factory:plan` の付いた Issue が操作の一覧のどれかに当たるなら、プランナーは `operate`（操作の id と引数）を返す。集計・分析なら経路を `[analyst]` にする。「Issue を p0 で作って実行してもらう」はこれで通る
- 型を決めるのはプランナー（相談役）だが、決めるのは対応付けまで。実行するのは dispatcher（決定 3）で、プランナーは今どおり読むだけ
- 型の判断の根拠（なぜ変更でなく操作か）は、今の着手判定と同じく 3 層（根拠・解釈・確信度）で残す。確信が低ければ依頼者に問う（往復の上限は今のまま）

### 2. 実行できる操作は、工場の定義に一覧で持つ。一覧にない操作はその場で作らない

`definitions/operations.yaml` に、依頼で動かしてよい操作を宣言する。操作は工場（Engine）がすでに持つ関数で、`factoryctl` と同じ実装を呼ぶ（操作の中身を 2 つ書かない）。

```yaml
operations:
  report.send:
    ja: 定期レポートを今すぐ送る（試し送り）
    does: "指定の種類と日付で組み立て直し、notifications.yaml の宛先に送る。毎朝の送信には数えない"
    params:
      kind: { enum: [report.factory_health, report.product, all] }
      date: { type: date, default: today }
      to:   { type: destination, optional: true }   # notifications.yaml の宛先の名前に限る
    tier: send          # 決定 4
    allowed: [owner, requester]
    impl: report.send_now          # dispatcher の関数。factoryctl report send と同じ
  report.render:
    ja: 報告書を書き出して依頼者に返す（送らない）
    tier: read
    ...
```

- 最初の一覧は、今 `factoryctl` にあって外に出してよいものと、データの書き出しにする（仮置き）: `report.send`・`report.render`（報告書の書き出し）・`data.export`（宣言したデータ源のビューを CSV で書き出す。データ源と守りは決定 5 と同じ）・使用量の要約・停止の一覧・チケットの状態。流量・一時停止・入れ替え・承認など、工場の運用そのものを変える操作は入れない（操業コンソールの仕事。ADR 0030 の決定 1）
- 引数は型つきで宣言し、dispatcher が検査してから動かす。依頼の本文から引数を組むのはプランナーだが、宣言にない引数・範囲の外の値は拒む。宛先は `notifications.yaml` にある名前だけ（依頼の本文に書かれた URL やチャンネルに送らない）
- 一覧にない操作を頼まれたら、操作をその場で作らない。製品の側の仕事（製品に機能を足せば済む）なら変更の型にする。工場の側の仕事（工場に操作を足すべき）なら、工場への改善の Issue を起票して建設者に回し（工場は工場を直さない。2026-11-05 オーナー）、依頼者には「今はできない、改善として起票した」と返す
- 操作を足すのは建設者が `operations.yaml` と実装の関数を足す PR で行う。足す操作の段（決定 4）はその PR で決める

### 3. 操作は dispatcher が動かす。ワーカーに権限を渡さない

- 経路は 2 段に分かれる: 定型の操作は dispatcher が決まった関数を動かすだけで LLM を通さない。調査・分析は新しい役（分析役、決定 5）のジョブ。プランナー（相談役）は依頼を一覧の操作か分析に対応付けるだけで、自分では実行しない
- 操作の実行は dispatcher（制御プレーン）だけが行う。ワーカーのジョブに Docker のソケット・制御プレーンの DB・Slack の credential を渡さない（今の守りのまま）
- 流れ: プランナー（相談役）が `operation`（id・引数・判断の根拠）を返す → dispatcher が宣言と照らして検査する → 段（決定 4）に応じて確認を取る → 実行する → 結果を会話（窓口）か Issue のコメントに書き、依頼者に知らせる（決定 6）
- 操作 1 回はチケットを作らない（窓口から来たもの）か、Issue を結果のコメントとともに閉じる（Issue から来たもの）。PR は作らない
- 同じ操作を同じ引数で短い間に繰り返さないよう、操作ごとに重ねて動かさない間隔を持てる（仮置き。`report.send` は 10 分）

### 4. 操作ごとに確認の段を持つ

| 段 | 意味 | 確認 | 例 |
|---|---|---|---|
| `read` | 読むだけ。工場の外に何も出さない、何も変えない | 要らない。すぐ動かして結果を返す | 報告書の書き出し、使用量の要約、停止の一覧、利用者の情報を含まないデータの書き出し |
| `send` | 工場の外（Slack・メール・GitHub）に出す | 依頼者の確認 1 回（送り先と中身の見本を見せる） | レポートの送り直し |
| `change` | 工場・製品の状態を変える | 受信トレイの承認ボタン（ADR 0034 の `approve`）。自由文の解釈では確定しない（ADR 0034 の決定 4）。依頼者に許された対象だけ（ADR 0030 の決定 5） | （最初の一覧にはない） |
| `destroy` | 取り返しがつかない（消す・本番に出す・外部に課金する） | 依頼では受けない。一覧に載せず、運用主が操業コンソールで行う | ― |

- 確認は受信トレイの件として出し、ADR 0034 のどの入口（受信トレイ・Slack・GitHub・Claude のスレッド）からも答えられる。`send` の確認は `approve`（`effect` に「何をどこに送るか」と中身の見本）で、一言の返事でも確定してよい。`change` はボタン（またはそれと同じ明示の承認）だけで確定する
- 依頼の本文に「確認は要らない」とあっても段は下げない。段は操作の宣言だけで決まる

### 5. 集計・分析の報告は、分析役のジョブで報告書を作る

報告（analysis）は、決まった操作でなく、データを読んで考える仕事。新しい役「分析役（`analyst`）」がジョブで行う。ADR 0030 の回答役（問い合わせ。記録を読んで答えるだけ）とは分ける。回答役は既にある記録から答え、分析役は新しく数を出す（集計の問いを書いて動かす）。

報告の依頼の型（`AnalysisRequest`）:

| 欄 | 中身 |
|---|---|
| 問い | 何を知りたいか（依頼者の言葉）と、それで何を決めたいか |
| データ源 | 使ってよいデータ源の id（下の表から）。プランナーが依頼から選び、依頼者の確認で決まる |
| 期間・対象 | 集計の期間、製品、絞り込み |
| 精度 | ざっくり（傾向だけ）/ ふつう / きっちり（数を突き合わせる） |
| 成果物 | 報告書（HTML。所見・トレンドのチャート・異常値の強調・対応の案）。必要なら表（CSV）を添える |
| 期限・費用の上限 | 1 件の上限（仮置き $5）。超えたら決まったところまでで返す |

データ源は定義に一覧で持ち（`definitions/data_sources.yaml`）、分析役はそこにあるものだけを、読むだけの権限で読む。

| データ源 | 中身 | 読み方 | 利用者の情報 |
|---|---|---|---|
| `factory` | 工場の制御プレーン（jobs・events・費用・停止・チケット） | 分析用の読むだけの利用者と、そのためのビュー（中身の本文・秘密を含む列を出さない） | 含まない |
| `github` | 製品の Issue・PR・コミット・検査の記録 | 工場の GitHub トークン（読むだけの範囲） | 含まない |
| `specs` | 製品の `specs/`（イベントの定義・契約・用語） | 製品のリポジトリを読む | 含まない |
| `product_analytics` | 製品の行動イベント・集計用の DB（staging、または製品が用意した読むだけの写し） | 製品が渡す読むだけの接続。製品ごとに `.factory-config/` で宣言する | 含みうる（下の守り） |

- 利用者の情報を含みうるデータ源は、製品の側で読むだけの写しか、個人を特定できる列を落としたビューを用意してもらい、それだけを読む。本番の生の DB に分析役を繋がない。報告書には個人を特定できる値を載せない（集計した数と、個人を指さない例だけ）
- Gen1 で使うのは `factory`・`github`・`specs` と、rally の staging（本番は止めてある）。`product_analytics` の宣言と、製品の側の写しの用意はパイロットの前に決める（O5）
- 分析役は集計の問い（SQL・GitHub の検索）と、その結果を成果物と一緒に返す。dispatcher は報告書に載った数のうち「きっちり」の精度のものを、同じ問いを読むだけの接続で動かし直して突き合わせる（ずれたら報告書に印を付けて差し戻す）。数の作り話を報告書に載せないため
- 報告書は 1 枚で完結する HTML（ADR 0032 の追記と同じ作り。外部の CSS・JS を読まない）。章立ては「所見 → 数（表・トレンドのチャート、それぞれに出した問いの参照）→ 解釈 → 打てる手 → 分からないこと・限界 → 次に調べるとよいこと」。推測は推測と書く
- 報告書の書き方（オーナー 2026-11-06。定期レポートへのフィードバックを単発の報告にも当てる）:
  - **項目は多めに出して、後から削る**。依頼者はどんな数が取れるかを知らないので、初回は問いに関わりそうな数を広めに載せ（使ったデータ源で取れるものの一覧も末尾に添える）、依頼者が要らないものを省く。省いた結果は会話に残し、同じ依頼の続きや定期レポートへの昇格のときに使う
  - **冒頭とひとことの要約は所見を書く**。何をしたかの要約ではなく、問題なく進んでいるか、計画が崩れそうな兆しはないか、早めに打てる手はないか、を依頼者の事業の目線で書く
  - **異常値を強調する**。前の期間・基準値・目安から外れた数は、報告書の中で色と印で目立たせ、なぜ異常とみたか（比べた相手と幅）を添える
  - **問題があるときは対応の案を添える**。案ごとに、効き目の見込み・手間・誰がやるか（工場で引き受けられるなら、その依頼の形）を書く。工場で引き受けられる案は、そのまま窓口の依頼にできる形で出す
- 報告書は制御プレーンに成果物として残す（後で同じ依頼の続きができるように）。製品のリポジトリには残さない（使い捨てのスクリプトを溜めない）。依頼者が「これを毎週」と言ったら、そのときは定期レポートの種類を足す変更の型にする（決定 7）

### 5a. 論点: 本番のデータの渡し方（分析役の一番の論点。O5 で決める）

分析役の価値の大半は製品の本番のデータ（予約・利用・売上）にあるが、そこには利用者の個人情報が入っている。渡し方の候補と、推奨の組み合わせ:

| 論点 | 候補 | 推奨（仮） |
|---|---|---|
| どこを読むか | (a) 本番の DB に直接 (b) 本番の読み取り専用の複製（リードレプリカ）(c) 定期に作る分析用の写し（個人を特定できる列を落とす・仮名化する） | (c) を正。(b) は製品の側がビューで列を絞れるときだけ。(a) はしない |
| 誰が用意するか | 工場が製品の DB に入って作る / 製品（事業主）の側が用意して接続を渡す | 製品の側。工場は `.factory-config/data_sources.yaml` で宣言された接続だけを使う。宣言にない表は読まない |
| 権限の絞り方 | DB の利用者を分析専用にし、許したビューだけ `select`。接続はジョブごとに期限つきで渡し、ワーカーには渡さず分析役のジョブにだけ | 分析専用の利用者＋ビュー＋ジョブごとの期限つきの接続。問いの実行は dispatcher を通して記録する（誰が・どの問いを・何行読んだか） |
| 個人情報の扱い | 列を落とす・仮名化（ハッシュ）・少ない件数の集計を出さない（k 匿名の下限） | 写しの側で落とす・仮名化。報告書と会話には集計した数だけを載せ、件数が下限（仮置き 5）未満のマスは伏せる。個人の行を成果物に出す依頼（「この人の利用履歴」）は分析では受けず、運用主の判断に回す |
| 記録の残し方 | 問いの結果をそのまま events に残す / 残さない | events には問いと行数・集計の結果だけ。行そのものは残さない。どうしても残す根拠は制限付きの保管先（ADR 0024）へ |
| 誰が許すか | 事業主の同意（データ源を宣言する PR のマージ）＋データ源ごとに使ってよい依頼者 | 事業主の同意を正とする。宣言のないデータ源を頼まれたら、宣言を足す提案として事業主に返す |

Gen1 は rally の本番を止めているので、staging と工場のデータで形を作る。パイロット（既存のモバイルアプリの事業主）の前に、この表を事業主と決める。

### 6. 結果は依頼者に、依頼の来た口で返す

- 窓口から来た依頼: 結果（操作の結果、報告書）を窓口の会話に書く。MCP の「会話を読む」で取れる
- Issue から来た依頼: Issue のコメントに結果（報告書は添付か、制御プレーンの成果物へのリンク）を書いて閉じる
- どちらも、ADR 0032 の `done.task`（作業の完了報告。今は `status: later`）を `ready` にして、依頼者の宛先に知らせる。Slack アプリの宛先なら報告書を添付し、本文は 3 行の要約（ADR 0032 の追記と同じ）
- 事業主の宛先に工場の内部の情報（費用・停止の中身）を混ぜない守り（ADR 0032 の決定 3）は、報告書にも当てる。`factory` のデータ源を使った報告を事業主に出すときは、`report.factory_health` と同じ組織の判定を通す

### 7. すべてを記録し、型の判断を後で見返す

- events に `op.requested`（id・引数・どの口から・判断の根拠）/ `op.confirmed`（誰が・どの入口から）/ `op.executed`（結果・所要時間）/ `op.rejected`（宣言の外・段の拒否）、`analysis.requested` / `analysis.delivered`（データ源・問いの数・突き合わせの結果・費用）を足す
- 型の判断（変更・操作・報告）は着手判定と同じく後で結果と突き合わせる（ADR 0026）。「操作にしたが実は変更が要った」「変更にしたが操作で済んだ」を数え、プランナーの評価セット（ADR 0036）に入れる
- 同じ報告の依頼が繰り返されたら（同じ問い・同じデータ源が期間を替えて 3 回など）、定期レポートか操作の一覧に足す候補として、工場への改善の Issue にする（P3 の学習の材料）

## 決めどころ（オーナーの承認が要る）

| # | 問い | 推奨 |
|---|---|---|
| O1 | 依頼の型 | 変更・操作・報告の 3 つ。窓口とプランナーの両方で同じ型に行き着く（決定 1） |
| O2 | 操作をどこまで許すか | 工場の定義に一覧で持つものだけ。一覧にないものはその場で作らず、製品の仕事なら変更に、工場の仕事なら改善の Issue に（決定 2） |
| O3 | 確認の段 | 読むだけは即時、外に送るものは依頼者の確認 1 回、状態を変えるものは受信トレイの承認ボタン。取り返しのつかないものは依頼では受けない（決定 4） |
| O4 | 報告の作り手 | 新しい分析役。問い合わせの回答役（読むだけで答える）とは分ける。数は問いとともに返し、dispatcher が動かし直して突き合わせる（決定 5） |
| O5 | 本番のデータの渡し方 | 決定 5a の推奨: 製品の側が用意する分析用の写し（個人を特定できる列を落とす・仮名化）を正に、分析専用の利用者とビュー、ジョブごとの期限つきの接続。報告には集計だけを載せ、少ない件数は伏せる。Gen1 は工場のデータ・GitHub・specs・rally の staging だけで作り、パイロットの前に事業主と決める |
| O6 | 成果物の置き場 | 制御プレーンに残し、製品のリポジトリには残さない。繰り返す依頼は定期レポートや操作に昇格させる（決定 5・7） |
| O7 | どのフェーズで作るか | 操作（順番 1〜3）は P4 の窓口の続きとして今作る（窓口から 1 本通す `consult_desk` の検証にも使える）。報告（順番 4〜5）は P5b の Answer ラインの最初の形として前倒しし、P5a と並べて作る |

## 順番

1. `definitions/operations.yaml` と、dispatcher の実行の口（宣言の検査・段・記録）。最初の操作は `report.send`・`report.render`。`factoryctl op run <id> --param ...` で人も同じ口を通せるようにする
2. 窓口の相談役と、プランナーの判定に型を足す（`operation`・`operate`）。`send` の確認を受信トレイの件にする（ADR 0034 の `approve`）
3. 結果の返し方（窓口の会話・Issue のコメント）と `done.task` を `ready` に
4. 分析役と `data_sources.yaml`。最初のデータ源は `factory`（分析用の読むだけの利用者とビュー）・`github`・`specs`。報告書の HTML と、数の突き合わせ
5. 製品のデータ源（`product_analytics`）。rally の staging から。パイロットの前に、製品の側の写しの宣言の形を決める
6. 後で: 定期の実行（「毎週これを」）、繰り返す依頼の昇格の候補出し、操作の一覧を増やす（データの書き出しなど）

## 選ばなかった案

- **すべてを変更の型で流し続ける（スクリプトの PR にする）**: 今の形。製品のリポジトリに使い捨てのスクリプトが溜まり、マージの承認という関係のない出番が増え、報告書が PR に埋もれる。操作は PR にすると実行の権限がなく、そもそも動かせない
- **ワーカーに工場の操作の権限を渡し、何でも実行させる**: 早いが、依頼の本文が命令としてシェルに届く道ができる。外に出す・壊す操作の確認も入れられない。操作は一覧と段で縛り、dispatcher が動かす
- **操作の一覧を持たず、プランナーが factoryctl のコマンドを組み立てる**: 一覧がないと、何を頼めるかを依頼者に見せられず、確認の段も決められない。宣言にない引数を止める場所もない
- **報告を問い合わせの回答役に任せる**: 回答役は既にある記録を読んで答える。新しく数を出す仕事は費用も時間も重く、数の突き合わせも要るので、別の役とジョブにする
- **分析役を製品の本番の DB に直接繋ぐ**: 利用者の情報が報告書と会話の記録に流れ込む。読むだけの写しかマスクしたビューに限る

## 結果

- 「レポートを送り直して」のような依頼が、窓口からも Issue からも、コマンドを打つ人なしに通る。外に出すものは依頼者が 1 回確かめてから出る
- 「XXXX を集計して分析結果を添えて報告して」に、根拠の問いと突き合わせた数を載せた報告書で応えられる。工場が開発だけでなく、事業部として調べて報告する仕事を受けられるようになる
- 何を頼めるか（操作の一覧・データ源の一覧）が定義に見える。依頼者の手元の Claude は、窓口からこの一覧を読んで頼み方を選べる
- 外に開く口が広がるので、操作の段・引数の検査・利用者の情報の守り・費用の上限が前提になる。型の判断の誤りは評価セットで測る
