# ADR 0037: 単発の依頼に応える（オンデマンドの依頼の型と、その場で応える道）

- 状態: 提案（2026-11-06。決めどころ D1〜D5 はオーナーの返答で決まり、D6・D7 が承認待ち）
- 関係: ADR 0030（事業部の窓口。依頼と問い合わせ、`task_kinds` の `answer`）、ADR 0025・0026（プランナーの着手判定と経路）、ADR 0032（通知の系統。`done.task`、報告書の添付）、ADR 0034（受信トレイの答え方。取り返しのつかない作用は自由文で確定しない）、ADR 0024（制限付きの保管先）、ADR 0028（P5a・P5b）、`definitions/desk.yaml`・`definitions/planner.yaml`・`definitions/notifications.yaml`

## 文脈

今の窓口（ADR 0030）とプランナー（ADR 0026）は、依頼をすべて「コードを変える仕事」として扱う。依頼は Issue になり、着手判定 → 経路（デザイン → 実装）→ PR → マージで終わる。
データの書き出しのような成果物を返す依頼も、Gen1 は実装のタスクとして流す（スクリプトを書いて結果を PR に添える。`desk.yaml` の `answer`）。

2026-11-06、定期レポートの再送（`factoryctl report send`）を工場に頼もうとしたところ、頼む道がなかった。窓口から頼んでも Issue → plan → 実装になり、ワーカーは Docker のソケットも制御プレーンの操作も持たないので、決まった操作を 1 回動かすことができない。結局オーナーがコマンドを打った。

オーナーの要望（2026-11-06）:

- 工場への依頼として、レポートを送ってもらうことはできないのか。窓口からの依頼でも、Issue を p0 で作って実行してもらうのでもよい。プランナーは「実行してもらうだけ」の経路を判断できないのか
- 単発のタスク実行は必ず必要。「XXXX のデータを集計して分析結果を添えて報告して」のような要望に応えるのは、開発事業部としての大きな価値の一つ。ただのソフトウェア開発の自動化工場ではない。商用化後の実運用では、こういった要望は顧客から普通に来る
- レポートは主に運用の段（P5b）以降の仕事なので、今の時点で完全な定義を作るのは難しい。Gen2 でパイロットに入れて運用に乗せると、現場の実際の要求が届く。追加の実装でケイパビリティを得ながら、型を更新していく。今の時点では「オンデマンドの要求に即時で応えるケースがある」「そこにはいくつかの型がある」と認識できていればよい

## 決定

### 1. 今決めるのは最小の形まで。型は運用で更新する

- 単発の依頼（オンデマンドで、即時の対応を求めるもの）があることと、それにいくつかの型があることを、窓口とプランナーの前提に入れる
- 型の一覧・操作の一覧・データ源の一覧は、どれも定義に宣言で持ち、足していく前提にする。今の一覧は叩き台で、完全な定義にしない
- 型を足すきっかけは、実際に届いた依頼（Gen2 のパイロット以降）。どの道にも乗らなかった依頼は記録し（決定 8）、型を足す改善の候補にする

### 2. プランナーが、依頼ごとに適切なワークフローを選んで実行させる

プランナー（窓口の相談役と、Issue の着手判定）は、依頼を見て次の道から選ぶ。チケットの経路（どの役を通すか）を選ぶのと同じ判断で、型から機械的に決めない（ADR 0026）。

| 道 | 何をするか | 例 | 終わり方 |
|---|---|---|---|
| チケット化（今のライン） | 要件・画面・契約・実装に切って流す | 機能を足す、画面を直す | PR のマージ |
| ラインに直接流す | 既存のチケットを指定の優先度でラインに入れる（ADR 0030 の決定 2 の即時の道） | 「#812 を先に」「この Issue を p0 で」 | チケットがラインに入る |
| 決定論の操作を実行 | 工場の操作の一覧（決定 3）にある操作を、引数を決めて 1 回動かす。LLM を通さない | レポートの送り直し、報告書の書き出し、データの書き出し | 操作の結果を返す |
| 小さな LLM の仕事 | 少ない往復で済む規模なら、その場で LLM のジョブを 1 回呼んで答える（決定 5） | 「先週の停止を 3 行でまとめて」「この Issue の要点と関係する PR を出して」 | 回答か短い報告書を返す |
| 分析役の報告 | 集計・分析を分析役のジョブで行い、報告書を作る（決定 5・6） | 「先月の予約のキャンセル率を集計して、理由を添えて報告して」 | 報告書を届ける |

- 1 つの依頼に道が混ざってよい（「通知の文面を直して、直したら今週のレポートを送り直して」は チケット化 → 操作 の依存）
- 窓口: `desk.yaml` の `task_kinds` に `operation`・`quick`・`analysis` を足し、今の `answer`（実装のタスクとして流す成果物）は `analysis` に置き換える
- Issue: プランナーの判定に `operate`（操作の id と引数）・`quick` を足し、経路の役に `analyst` を足す。「Issue を p0 で作って実行してもらう」はこれで通る
- 道を選ぶのはプランナーだが、決めるのは対応付けまで。外に出す・状態を変える作用は dispatcher が確認の段（決定 4）を通して行う
- 道の判断の根拠（なぜチケットでなく操作か）は、今の着手判定と同じく 3 層（根拠・解釈・確信度）で残す。確信が低ければ依頼者に問う（往復の上限は今のまま）

### 3. 決定論の操作は、工場の定義に一覧で持ち、dispatcher が動かす

`definitions/operations.yaml` に、依頼で動かしてよい操作を宣言する。操作は工場（Engine）がすでに持つ関数で、`factoryctl` と同じ実装を呼ぶ（操作の中身を 2 つ書かない）。

```yaml
operations:
  report.send:
    ja: 定期レポートを今すぐ送る（試し送り）
    does: "指定の種類と日付で組み立て直し、notifications.yaml の宛先に送る。毎朝の送信には数えない"
    params:
      kind: { enum: [report.factory_health, report.product, all] }
      date: { type: date, default: today }
      to:   { type: destination, optional: true }   # notifications.yaml の宛先の名前に限る
    tier: send          # 決定 4
    allowed: [owner, requester]
    impl: report.send_now          # dispatcher の関数。factoryctl report send と同じ
```

- 最初の一覧（叩き台）: `report.send`・`report.render`（報告書の書き出し）・`data.export`（宣言したデータ源のビューを CSV で書き出す）・使用量の要約・停止の一覧・チケットの状態。流量・一時停止・入れ替え・承認など、工場の運用そのものを変える操作は入れない（操業コンソールの仕事。ADR 0030 の決定 1）
- 引数は型つきで宣言し、dispatcher が検査してから動かす。宣言にない引数・範囲の外の値は拒む。宛先は `notifications.yaml` にある名前だけ（依頼の本文に書かれた URL やチャンネルに送らない）
- 実行は dispatcher（制御プレーン）だけが行う。ワーカーのジョブに Docker のソケット・制御プレーンの DB・Slack の credential を渡さない（今の守りのまま）
- 一覧にない操作はその場で作らない。製品の側の仕事ならチケット化に、工場の側に操作を足すべきなら工場への改善の Issue を起票して建設者に回し（工場は工場を直さない。2026-11-05 オーナー）、依頼者には「今はできない、改善として起票した」と返す
- 操作は PR を作らない。窓口から来たものはチケットを作らず、Issue から来たものは結果のコメントとともに閉じる

### 4. 操作ごとに確認の段を持つ

| 段 | 意味 | 確認 | 例 |
|---|---|---|---|
| `read` | 読むだけ。工場の外に何も出さない、何も変えない | 要らない。すぐ動かして結果を返す | 報告書の書き出し、使用量の要約、停止の一覧 |
| `send` | 工場の外（Slack・メール・GitHub）に出す | 依頼者の確認 1 回（送り先と中身の見本を見せる） | レポートの送り直し |
| `change` | 工場・製品の状態を変える | 受信トレイの承認ボタン（ADR 0034 の `approve`）。自由文の解釈では確定しない（ADR 0034 の決定 4） | （最初の一覧にはない） |
| `destroy` | 取り返しがつかない（消す・本番に出す・外部に課金する） | 依頼では受けない。運用主が操業コンソールで行う | ― |

- 確認は受信トレイの件として出し、ADR 0034 のどの入口からも答えられる
- 依頼の本文に「確認は要らない」とあっても段は下げない。段は操作の宣言だけで決まる
- 小さな LLM の仕事と分析役の報告は `read` の段で動く（読むだけの接続で、結果は依頼者にだけ返す）。結果を依頼者以外の宛先に送るときは `send` の確認を通す

### 5. LLM で答える仕事は、規模で 2 つに分ける

| | 小さな LLM の仕事（`quick`） | 分析役の報告（`analysis`） |
|---|---|---|
| 規模の目安（仮置き） | 依頼者との往復 1 回まで、エージェントのターン 8 まで、費用 $0.5 まで | それより大きい。1 件の上限 $5 |
| 動く枠 | 窓口の枠（ADR 0030 の決定 6）。ラインを止めていても答える | 窓口の枠。重ければラインの枠を 1 つ借りる（流量の宣言に従う） |
| 成果物 | 会話の返事、または短い報告書 | 報告書（決定 6）、必要なら表（CSV） |
| 数の扱い | 既にある記録を読んで答える。新しい集計はしない | 集計の問い（SQL・検索）を書いて動かす。問いは結果とともに返す |

- プランナーが `quick` と見積もったが目安を超えたら、決まったところまでで返し、続きを `analysis` に切り替える提案を添える（止めない）
- ADR 0030 の問い合わせの回答役（記録を読んで答える）は `quick` の一種として扱う。役を増やさない
- どちらの LLM の仕事も、読むだけの接続しか持たない。依頼の本文はデータとして渡し、命令として扱わない

### 6. 報告書の型と書き方

報告の依頼の型（`AnalysisRequest`）:

| 欄 | 中身 |
|---|---|
| 問い | 何を知りたいか（依頼者の言葉）と、それで何を決めたいか |
| データ源 | 使ってよいデータ源の id（決定 7）。プランナーが依頼から選び、依頼者の確認で決まる |
| 期間・対象 | 集計の期間、製品、絞り込み |
| 精度 | ざっくり（傾向だけ）/ ふつう / きっちり（数を突き合わせる） |
| 成果物 | 報告書（HTML。所見・トレンドのチャート・異常値の強調・対応の案）。必要なら表（CSV）を添える |

- 報告書は 1 枚で完結する HTML（ADR 0032 の追記と同じ作り。外部の CSS・JS を読まない）。章立ては「所見 → 数（表・トレンドのチャート、それぞれに出した問いの参照）→ 解釈 → 打てる手 → 分からないこと・限界 → 次に調べるとよいこと」。推測は推測と書く
- 書き方（オーナー 2026-11-06。定期レポートへのフィードバックを単発の報告にも当てる）:
  - **項目は多めに出して、後から削る**。依頼者はどんな数が取れるかを知らないので、初回は問いに関わりそうな数を広めに載せ（使ったデータ源で取れるものの一覧も末尾に添える）、依頼者が要らないものを省く。省いた結果は会話に残し、同じ依頼の続きや定期レポートへの昇格のときに使う
  - **冒頭とひとことの要約は所見を書く**。何をしたかの要約ではなく、問題なく進んでいるか、計画が崩れそうな兆しはないか、早めに打てる手はないか、を依頼者の事業の目線で書く
  - **異常値を強調する**。前の期間・基準値・目安から外れた数は、報告書の中で色と印で目立たせ、なぜ異常とみたか（比べた相手と幅）を添える
  - **問題があるときは対応の案を添える**。案ごとに、効き目の見込み・手間・誰がやるか（工場で引き受けられるなら、その依頼の形）を書く。工場で引き受けられる案は、そのまま窓口の依頼にできる形で出す
- 「きっちり」の精度の数は、dispatcher が同じ問いを読むだけの接続で動かし直して突き合わせる（ずれたら報告書に印を付けて差し戻す）。数の作り話を報告書に載せないため
- 報告書は制御プレーンに成果物として残す（同じ依頼の続きができるように）。製品のリポジトリには残さない（使い捨てのスクリプトを溜めない）。依頼者が「これを毎週」と言ったら、定期レポートの種類を足すチケット化の道にする

### 7. データ源は工場の DB に限らない。宣言で持ち、増やしていく

集計の対象は工場の Postgres だけではない。P5b で運用（Ops）の部分を作ると、外部への接続（監視・エラーの追跡・アプリのログ・課金）も入り、それらも集計の対象にする（オーナー 2026-11-06）。データ源は `definitions/data_sources.yaml`（共通の種類）と製品の `.factory-config/data_sources.yaml`（その製品の接続）で宣言し、LLM の仕事はそこにあるものだけを、読むだけの権限で読む。

今の時点で思いつく集計の依頼（オーナー 2026-11-06 の列挙。叩き台）:

| 依頼 | 系統 | 主なデータの出どころ | 今使えるか |
|---|---|---|---|
| 工場の稼働状況 | 開発 | 工場の操業の記録（jobs・events・費用・停止） | 使える |
| 生産性の低下状況 | 開発 | 工場の操業の記録、GitHub（PR・リードタイム） | 使える |
| 品質の低下状況 | 開発 | 検査・Verdict・Defect（P5a 以降）、GitHub | 一部 |
| バグトラッキングに届いたエラーの分析 | 開発・CS | エラーの追跡（外部。P5b 以降） | まだ |
| アプリケーションの利用状況 | マーケティング | アプリの行動イベント・ログ | まだ（製品のデータ。決定 8） |
| ユーザーの登録・増加状況 | マーケティング | アプリの DB・行動イベント | まだ（同上） |
| 契約・課金の状況 | CS・事業 | 課金の基盤（外部） | まだ（同上） |
| 売り上げの集計 | 事業 | 課金・決済の基盤（外部） | まだ（同上） |

- 系統は 3 つに分かれる: 開発（主に工場の操業の記録から取れる）、マーケティング（主にアプリの側のログから取れる）、カスタマーサクセス・事業（課金・問い合わせ）。どちらも合わせたクロス集計（例: リリースの前後で利用とエラーがどう変わったか）も要る
- データ源には「系統」と「利用者の情報を含むか」を宣言に持たせる。依頼の型（決定 1）を足すときに、どの系統のどのデータ源が要るかで見積もれるようにする
- 今使えるのは `factory`（工場の制御プレーン。分析用の読むだけの利用者とビュー、本文・秘密を含む列を出さない）・`github`（読むだけの範囲）・`specs`（製品の `specs/`）。外部の接続は、P5b の Ops で接続を作るときにデータ源として足す

### 8. 本番のデータの扱いは、後のフェーズで決める

本番のデータには利用者の個人情報が入っていて、扱いが難しい。Gen1 では本番のデータを LLM の仕事に読ませない（rally は本番を止めてあり、staging だけで形を作る）。

後で決めるときの候補（オーナー 2026-11-06）: レポートを作るための専用の基盤を作る。本番のデータを、日時などで適切にマスキングした上で写しにし、写しの側で集計・分析する。決めるときの論点:

- どこを読むか（本番の DB には直接繋がない前提で、マスキングした写しか、列を絞った読み取り専用の複製か）
- 誰が写しを用意し、誰が許すか（事業主の同意の形）
- 権限の絞り方（分析専用の利用者・ビュー・ジョブごとの期限つきの接続）
- 個人情報の扱い（列を落とす・仮名化・少ない件数の集計を伏せる・個人の行を成果物に出さない）
- 記録の残し方（events には問いと行数・集計の結果だけ。行そのものは残さない。どうしても残す根拠は制限付きの保管先（ADR 0024））

### 9. 結果の返し方と記録

- 窓口から来た依頼は窓口の会話に、Issue から来た依頼は Issue のコメントに結果を書く。ADR 0032 の `done.task`（作業の完了報告）を `ready` にして依頼者の宛先に知らせ、Slack アプリの宛先なら報告書を添付し、本文は所見の要約にする
- 事業主の宛先に工場の内部の情報（費用・停止の中身）を混ぜない守り（ADR 0032 の決定 3）は報告書にも当てる
- events に `op.requested` / `op.confirmed` / `op.executed` / `op.rejected`、`quick.answered`、`analysis.requested` / `analysis.delivered`（データ源・問いの数・突き合わせの結果・費用）を足す
- 道の判断は着手判定と同じく後で結果と突き合わせ（ADR 0026）、プランナーの評価セット（ADR 0036）に入れる。どの道にも乗らなかった依頼、同じ報告の繰り返し（同じ問いが期間を替えて 3 回など）は、型・操作・定期レポートを足す改善の候補にする

## 順番

1. `definitions/operations.yaml` と、dispatcher の実行の口（宣言の検査・段・記録）。最初の操作は `report.send`・`report.render`。`factoryctl op run <id> --param ...` で人も同じ口を通せるようにする
2. 窓口の相談役と、プランナーの判定に道を足す（`operate`・`quick`）。`send` の確認を受信トレイの件にする。結果の返し方と `done.task` を `ready` に
3. `quick`（窓口の枠の小さな LLM のジョブ。工場の記録・GitHub・specs を読むだけ）
4. 分析役と `data_sources.yaml`、報告書の HTML と数の突き合わせ。P5b の Ops で外部の接続を作るときに、そのデータ源を足す
5. 後のフェーズ: 本番のデータを扱うレポートの基盤（決定 8）、定期の実行（「毎週これを」）、型・操作の一覧を実際の依頼から足す

## 選ばなかった案

- **すべてをチケット化の道で流し続ける（スクリプトの PR にする）**: 今の形。製品のリポジトリに使い捨てのスクリプトが溜まり、マージの承認という関係のない出番が増え、報告書が PR に埋もれる。操作は PR にしても実行の権限がなく、そもそも動かせない
- **ワーカーに工場の操作の権限を渡し、何でも実行させる**: 早いが、依頼の本文が命令としてシェルに届く道ができる。外に出す・状態を変える操作の確認も入れられない。決定論の操作は一覧と段で縛り、dispatcher が動かす
- **操作の一覧を持たず、プランナーが factoryctl のコマンドを組み立てる**: 何を頼めるかを依頼者に見せられず、確認の段も決められない。宣言にない引数を止める場所もない
- **今の時点で型を完全に定義する**: 単発の依頼の多くは運用の段以降に来るもので、今は想像で書くしかない（オーナー 2026-11-06）。形の骨組みと一覧の器だけを作り、実際の依頼で埋める
- **分析役を製品の本番の DB に直接繋ぐ**: 利用者の情報が報告書と会話の記録に流れ込む。本番のデータは決定 8 の基盤を作ってから

## 結果

- 「レポートを送り直して」のような依頼が、窓口からも Issue からも、コマンドを打つ人なしに通る。外に出すものは依頼者が 1 回確かめてから出る
- 小さな問いにはその場で、大きな集計・分析には所見と対応の案を添えた報告書で応えられる。工場が開発だけでなく、事業部として調べて報告する仕事を受けられるようになる
- 何を頼めるか（道・操作・データ源の一覧）が定義に見え、実際の依頼に合わせて増やせる。依頼者の手元の Claude は、窓口からこの一覧を読んで頼み方を選べる
- 外に開く口が広がるので、操作の段・引数の検査・費用の上限・本番のデータを読ませない守りが前提になる。道の判断の誤りは評価セットで測る
