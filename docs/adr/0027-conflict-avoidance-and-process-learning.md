# ADR 0027: 衝突の回避と、工程の進め方を工場が自分で学ぶ仕組み

- 状態: 承認（2026-11-03 オーナー。方向はカードで「3 つとも ADR にして進める」を選択、本文は #150 で承認）
- 関係: ADR 0013（Learn ループ）、ADR 0023（学習の体系。テーマ 6「工程の進め方」）、ADR 0024（知見と委員会）、ADR 0025（上流の工程。プランナー）、ADR 0017（続きのジョブ）、ADR 0012（出荷）、factory-engine #148（衝突の解消の費用を抑える）

## 文脈

2026-11-02 の 1 日の費用は、枠の上限 $700 に対して $1,772 だった。そのうち $1,420（345 回）は、PR が main と衝突したときの解消に使われていた。

工場の記録を 48 時間分まとめると、衝突の解消は 587 回あった。CHANGELOG.md を含むものが 578 回（98%）、CHANGELOG.md だけのものが 523 回（89%）だった。残りの内訳は headquarters.ts 14 回、README 類 20 回、openapi.yaml 7 回、screens.ts 6 回などで、数は少ない。

原因は 3 つある。

1. 製品の規約で、利用者に見える変更は CHANGELOG.md の `[Unreleased]` に 1 行足すことになっている。同時に流したすべての PR が同じ箇所を書き換えるので、1 件マージされるたびにほかの PR が衝突する
2. プランナーは、ルート（経路）と着手の可否を決めるときに、並行で流れている PR やタスクが触るファイルを見ていない
3. Learn ループ（ADR 0013）は、製品の欠陥（検査の指摘の採用・judge の差し替え・人の不同意）だけを教師信号にしている。費用・衝突・やり直しのような工程の無駄は扱わず、停止は「Engine の改善に回す」として束ねていない（`learning.yaml` の `ignore_signatures: ["stoppage:*"]`）。ADR 0023 のテーマ 6「工程の進め方」は、`status: first` のまま入力が流れていない

#148 で 1 回あたりの費用は下がった（実測で $11〜17 → $0.31）。ただし衝突そのものは減っていない。

この無駄に気づいて直したのは建設者だった。オーナーの方針は、工場がタスクの実行を振り返り、自分で気づいて改善すること。

## 決定

### 1. CHANGELOG は PR ごとの断片にし、取りまとめは別の工程にする

- 製品の PR は、CHANGELOG.md を直接書き換えない。代わりに `changelog.d/<Issue 番号>.md` に、`[Unreleased]` に入れる行を書く（1 PR 1 ファイル）。ファイル名が PR ごとに違うので、衝突は起きない
- 取りまとめは決定的（LLM を使わない）に行う。`core-gates/changelog_compile.py` が断片を種類ごとに CHANGELOG.md の `[Unreleased]` に移し、移した断片を消す
- 取りまとめは出荷の前に必ず 1 回、加えて断片が `CHANGELOG_COMPILE_EVERY`（仮置き 10）件たまったときに、supervisor が取りまとめのジョブを積む。このジョブは PR を 1 本作り、CI が通れば通常どおり自動でマージする。取りまとめの PR は検査と judge の対象外とする（中身は断片の移動だけ）
- 製品の CLAUDE.md、ワーカーの指示、検査のルーブリック（PROC 系）を「CHANGELOG.md ではなく `changelog.d/` に書く」に揃える。これは製品の書き方の変更なので、rally の PR で行う
- #148 の、CHANGELOG.md だけの衝突を機械的に解く処理は残す（移行の間、断片を使わない古い PR があるため）

### 2. プランナーが衝突を避ける並べ方を決める

- プランナーは、ルートを決めるときに「変わる見込みのファイル」を挙げる。根拠はチケットの本文と、コードベースの構造（契約・生成した型・画面の一覧のような登録の箇所）
- 投入の前に、supervisor が「よく衝突するファイル」の一覧（下の 3 で工場の記録から作る）と、開いている PR・待っているタスクが触るファイルを突き合わせる。同じ「よく衝突するファイル」に触るタスクは、同時に流さず順番に並べる。並べた根拠はプランのログ（`factoryctl plan show`）に残す
- 毎回の追記が同じ箇所に集まる作り（例: 機能ごとに 1 か所の登録ファイルに足す）は、プランナーが分割の改善チケットを提案する。これは製品のアーキテクチャの変更なので、改善チケットとして積み、人の判断の扱いは既存の規則（ADR 0019 の改善チケットの上限）に従う

### 3. Learn ループに工程の信号を足す（ADR 0023 のテーマ 6）

- **信号:** 次を教師信号に足す（`learning.yaml` の `teacher_signals`）。どれも制御プレーンの events から一次ソースで取れる
  - `conflict_fix`：衝突の解消のジョブ（`continue.enqueued` の reason=conflict）。衝突したファイル（ワーカーのログの `conflicts=[...]`）と費用を持つ
  - `rework`：同じチケットのやり直し（rerun・積み直し・途中終了の続き）が窓の中で `REWORK_MIN`（仮置き 3）回以上
  - `cost_outlier`：1 マージあたりの費用が、同じ種類のタスクの中央値の `COST_OUTLIER_X`（仮置き 3）倍以上
  - `wait`：人を待たない理由（衝突・CI・同時の上限）で、チケットが `WAIT_MIN_H`（仮置き 3）時間以上止まった
  - 停止（`stoppage:*`）は束ねる対象に戻す。作用先は Engine と工程で、製品の overlay のルールにはしない
- **束ね方:** 夜の Retrospective（LLM を使わない）が、工程の信号を `process:<信号>:<鍵>` で束ねる。鍵は衝突ならファイル、やり直しと費用ならタスクの種類と工程。束ごとに件数・チケット数・費用の合計を出す
- **気づき:** 束が閾値（仮置き: 7 日で 10 件以上、または費用の合計が $50 以上）を超えたら、事例型の分析役（ADR 0023、`case.py`）に回す。分析役は、仕様・伝達・検査・工程の観点からなぜなぜで真因を掘り、作用先ごとの改善案を返す
- **改善の行き先と承認の線**（ADR 0023 の表に従う）
  - 運用パラメータ（同時に流す数、並べ方の閾値、取りまとめの間隔など）：工場が変えて試してよい。変える前と後を記録し、次の 7 日で効き目を測る。効かなければ戻す
  - プランナーへの知見（例: 「このファイルに触るタスクは並べて流す」）：知見の候補として委員会（ADR 0024）に回し、通ればプランナーの入力に入れる
  - 製品の構造の改善（例: 断片化、登録ファイルの分割）：製品の改善チケットとして積む
  - 工場のプロセスとアーキテクチャの変更（例: 本 ADR の 1 のような仕組み）：Engine の改善案を書き、オーナーの承認を得る（今の段階の方針どおり）
- **効き目:** 束の件数と費用を、改善の前の 7 日と後の 7 日で比べる。結果は委員会の週次の報告と日報に出す。学習器に自分を採点させない（ADR 0013 の 8）ので、数えるのは govern 側（`factoryctl report learning`）
- **入口の確認:** 今回の CHANGELOG の衝突を最初の教材にする。過去 7 日の記録を流したときに、`process:conflict_fix:CHANGELOG.md` の束ができ、分析役が 1 と 2 にあたる改善案を返すことを、受け入れの条件にする

## 順番

1. CHANGELOG の断片と取りまとめ（Engine の `changelog_compile.py`・supervisor・ワーカーの指示、rally の CLAUDE.md・ルーブリック）
2. 工程の信号・束ね方・分析役への回し方（`learning.yaml`・`learn.py`・`case.py`）。ここで「よく衝突するファイル」の一覧ができる
3. プランナーの並べ方（`planner.py`・supervisor の投入）。2 の一覧を入力にする

1 は効き目が最も大きく、小さい。2 と 3 の順は、3 が 2 の一覧を使うため。

## 選ばなかった案

- **CHANGELOG を PR の本文から出荷のときに作る**：書き手（ワーカー）と読み手（利用者向けの変更履歴）の間に PR の本文という別の形が挟まり、検査で確かめにくい。断片なら CI と検査がファイルとして見られる
- **CHANGELOG の追記をやめる**：利用者や API の利用者に見える変更の記録は製品の規約として残す
- **衝突の解消を全部機械的にする**：コードの衝突は意味を見て解く必要がある。機械的にするのは CHANGELOG.md だけ（#148）
- **工程の信号を LLM に束ねさせる**：同じ記録に同じ束を返さず、効き目を比べられない。ADR 0013 と同じく、束ねるのは決定的に、言葉にするのだけを LLM に任せる
- **建設者が気づいて直すのを続ける**：工場の仮想化のゴール（自律改善）に届かない。商品化の条件の「運用シグナルからの自律改善提案」にもあたる

## 結果

- 衝突の解消のほぼ全部（CHANGELOG.md が関わる 98%）がなくなる見込み
- 工程の無駄が教師信号として数えられ、気づき・真因・改善案・効き目の確認までを工場自身が回せる。建設者は承認の線の上の判断だけを受け取る
- 製品の規約（CHANGELOG の書き方）が変わる。移行の間は、断片を使う PR と使わない PR が混ざる
- 夜の Retrospective と分析役のジョブが増える。分析役は 1 日の件数の上限（`case_review` の既存の上限）の中で回す

## 実施の記録（2026-11-04）

- 入口の確認を満たした。2026-11-03 15:00 UTC に `process:conflict_fix:CHANGELOG.md` の束（689 件・$2,919.79）が分析役に回り、改善案を 5 つ返した。そのうち「変更ごとの断片にして出荷のときにまとめる」と「同じ共有ファイルに触る PR の同時数を絞る」が、本 ADR の 1 と 2 にあたる
- 効き目: CHANGELOG.md の衝突の解消は、11-02 の 403 件・$1,972.69 から、11-03 の 38 件・$1.53（どれも断片方式の前に開いた PR）、11-04 の 0 件になった。1 日の消費は $1,772 から $296 になった
- 足りなかったこと: 工程の束の改善案が記録（`case.analyzed`・`CaseAnalysis`）で止まり、どこにも起票されていなかった。オーナーの承認（2026-11-04）で、supervisor が工場のリポジトリに改善案の Issue（`factory:process-proposal`）を起票するようにした（`process_issue_step`、1 日 1 件、同じ signature が開いていれば足さない、events の `process.proposal_filed`）。実装とマージは今までどおり承認の線に従う
