# ADR 0006: judge と判断の記録

- 状態: 承認（2026-10-27 戦略会議 第 1 回の決定 D5・D6。前半＝仮決め続行と記録を本 ADR と同時に入れ、後半＝judge 本体・モード・差し戻しは別の PR で入れる。閾値は委任の範囲で仮置き）
- 関係: 戦略会議の議事録（建設者の手元の 50_build-work/strategy/minutes/2026-10-27_strategy-meeting.md の 4 節・9 節・10 節）、ADR 0004（supervisor は判断しない）、ADR 0005（番人）、`definitions/judgments.yaml`

## 文脈

ラインの途中で判断が要ると、工場は止まって人に聞くか、最初からやり直すしかなかった。
P1 入口では T14 が設計判断を ADR の Question として建設者に返し、回答まで SSOT を据え置いた。正しい振る舞いだったが、人が不在なら止まったままになる。
最初に戻すと、そこまでの作業がすべて手戻りになる（無駄なトークン）。中断して再開するのは HITL と変わらない。
戦略会議の方針は、判断が要るものをラインの最初か最後に寄せ、途中はバイパスしながら磨き上げることにある。
また、昼に人が並走しているときと夜に全面委任するときで判断の仕方を変えられ、その品質の差を後から見えるようにしたい。

## 決定

### 前半（本 ADR と同時に入れる）

1. **ワーカーは途中の判断を仮決めして続ける**。止まって問い返すための ADR や Question だけを作らない。例外は秘密情報・権限設定・破壊的スキーマ・決済ロジックで、これは承認の関所なので従来どおり止まる
2. **仮決めは PR 本文の「## 仮決め」に構造化して書く**（類型 id・問い・選んだ・他の案・根拠・解釈・確信度・影響）。dispatcher が分解して artifacts の `Judgment`（stage=provisional）と events の `judgment.provisional` に残し、PR に `factory:provisional` を付ける。分解は文字列の処理だけで、シェルにもプロンプトにも渡さない
3. **記録は 3 層**: 根拠（参照した SSOT・ADR・Issue の箇所、過去の判断の id、manifest の制約）／解釈（根拠をどう読んで決定に至ったか）／スコア（自己申告の確信度 0〜1 と、使えた実績＝同じ類型での人の採点との一致率と件数、どちらで決めたか）。加えて決定・他の案・影響・モード・決めた者・後の人の採点
4. **類型は 6 つ**（`definitions/judgments.yaml` v1）: 用語と境界、インターフェースの定義、設計の選択、受け入れ条件の解釈、スコープの変更、検査の採用（judge だけが使う）。記録は類型 id と版の両方を持つ。見直しは時間ではなくデータ量で起こし（1 類型が 30 件超で分割候補、3 か月で 5 件未満で統合候補、一致率の二極化）、提案は週次の振り返りに出し、分け直しは人が行う
   - 追記（2026-10-28、v2。オーナー 了承）: v1 は対象・理由・雑多な残りが混ざり、設計の選択に半分近くが集まった。全件 115 件を「何について決めたか」の 1 軸で振り直し、7 つにした: ユーザーインターフェース（ui）、システムインターフェース（system_interface）、内部実装（implementation）、エラー処理（error_handling）、データ（data）、スコープ（scope）、検査結果（inspection）。受け入れ条件の解釈は理由なので類型から外し、印 ticket_interpretation にした。見直しは 1 類型を割らず全件を振り直し、総数を増やしすぎない。振り直しは definitions/judgment-remap-v1-v2.yaml と factoryctl judgment recategorize

### 後半（承認付きの別 PR。実装は orchestrator/README の「judge と差し戻し」）

5. **出口で judge が裁く**。入力は仮決めの Judgment・SSOT・過去の判断・manifest、出力は決定（採用・差し替え・人へ）・確信度・根拠・解釈・影響。ツールは持たせない（読むものはこちらで渡す）。差し替えになった仮決めは修正 Issue として起票する
6. **確信度は自己申告から実績へ**。人の採点が溜まると類型ごとの一致率が出るので judge の入力に渡す。実績が 10 件未満の類型は自己申告だけ、10 件以上は実績を優先、一致率が 80% を下回る類型は unattended でも人へ回す（仮置き）
7. **モードは attended / unattended**。Blueprint 側（製品の manifest）の設定で、factoryctl と時間帯で切り替える。attended は人の 1 タップで流し、unattended は上限の範囲で自動で流す。品質と生産量のトレードオフは事業者ごとに違うので、Engine は決めない
8. **印は events とラベル**。PR には `factory:judged:unattended`、`factory:confidence:low` などのラベル。Release の手前で止める強い印は作らない
9. **差し戻し制御は judge の類型「検査の採用」として扱う**（D5）。検査器の指摘を judge が裁き、採用された Defect と nit を同じ修正 Issue に入れて自動で起票する（指摘本文はデータとして引用し、ワーカーへの指示にしない）。差し戻しは 1 PR につき 1 回（仮置き。差し戻しが 20 件溜まったら最初の見直し。「再検査で指摘が残った件数」と「2 回目を流していたら直ったと推定される割合」を集計に入れる）。上限（1 PR の回数、1 日の件数、1 件の予算）は Blueprint 側。差し戻しの PR も autonomy の表どおりに supervisor が扱い、モードは変わらない
10. **レポートは events から集計し、期間は引数**。週次は Routine で自動、`factoryctl report --from --to` でオンデマンド。採点の待ち行列も同じ

## 選ばなかった案

- **判断が出たら最初からやり直す**: そこまでの作業がすべて手戻りになり、トークンを焼く
- **中断して人の回答を待って再開する**: HITL と変わらず、夜間に止まる。待機中のジョブの状態機械も要る（ADR 0003 の Temporal の採否基準に触れる）
- **確信度を judge の自己申告だけにする**: 主観のままで、運用期間が延びても精度が上がらない。人の採点との一致率を実績として足す
- **印を強くする（unattended で決めたものは Release の手前で止める）**: ラインを止めない方針（D7）に反する。印は記録とラベルにとどめ、統計で品質の差を見る
- **類型を固定する**: 最適な分け方は蓄積で変わる。版を持たせ、分け直し後に再集計できるようにする

## 結果

- T14 のような設計判断は、止まらずに仮決めで進み、記録が残る。差し替えになったときの手戻りは修正 Issue 1 本に限られる
- 類型ごとの件数・確信度・後の採点との一致率が events と artifacts から出せる。judge を入れる前でも、仮決めの頻度と自己申告の分布が分かる
- ワーカーのプロンプトを変えるので、本 ADR の前半はマージ基準の「外部入力がエージェントのプロンプトにつながる経路の変更」に当たり、承認付きで入れる
