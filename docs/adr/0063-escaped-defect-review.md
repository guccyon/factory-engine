# ADR 0063: 本番に流出した不具合を振り返り、混入を防ぐ打ち手を仕組みにする（流出の振り返り）

- 状態: 提案
- 関係: ADR 0061（チケットの振り返り。観点が違うので分ける。0061 の決定 3 の「運用の材料」と決定 5 の「運用と障害」は本 ADR に移す）、ADR 0053（メジャー不具合の自律修正と緊急便）、ADR 0049・0060（出荷の QA の関門）、ADR 0057（本番の見張り）、ADR 0046（事故調査委員会）、ADR 0023（学習の体系・事例型・承認の線）、ADR 0024（知見）、ADR 0040（知見の作用先）、ADR 0044（判断の宛先）、ADR 0013（Learn ループ・学ぶ側に自分を採点させない）
- 仕様: 05_specs の `20_learn-loop.md`（Learn ループの正本）、`07_onboarding.md`、`04_glossary.yaml`

## 文脈

2026-11-16、rally で S1 の不具合が 2 件、本番に出たあとで見つかった。

- **rally#1785**（なりすまし）: 生徒が、画面に出るコーチの ID から署名なしのトークンを自分で作り、コーチとしてほかの生徒の予約・動画・チャットを見られた。トークンの署名鍵がないと、黙って署名なしのモックで動く作り（fail-open）だった。本番も 0.53.0 で鍵を入れるまでは鍵なしで動いていた見込み
- **rally#1798**（体験予約のキャンセルで今月の通話回数が減る）: S1 の直しの緊急便 0.53.0 が、QA を待たずに本番に出た（ADR 0053 の追記: S1 の緊急便は工場が本番まで承認する）。その後 staging の同じ 0.53.0 を QA が探索して見つけた。原因は同じ日の別の不具合の直し（rally#1605 → PR #1768）で、キャンセルが回数を使うかを「キャンセルした時点の受講権」で判定するように変えたこと。緊急便はその時点の main をまるごと載せるので、この変更も関門を通らずに本番に出た見込み（前の本番の版に入っていたかは、実装したら記録で確かめる）

オーナーの方針（2026-11-16）:

- そもそも、本番に不具合が流出しないようにするべき
- 今後の世代で、障害報を発行する仕組みと障害対応のフローを作る。そのフローの中で、障害の発生原因を振り返り、混入を防ぐための学びと仕組み化をする
- Gen1 では、そのうち**振り返り以降だけ**を先に作る。これは Learn の責務

いまある仕組みで、この役を受け持つものはない。

| いまあるもの | 足りないところ |
|---|---|
| ADR 0053（メジャー不具合の自律修正） | 直して出し直すまで。なぜ入ったか・なぜ止められなかったかは問わない |
| ADR 0061（チケットの振り返り） | 障害を議題の材料に入れるが、N 件（初期 12）たまるまで開かない。12 件の中の 1 件として扱われ、「どの関門をすり抜けたか」を必ず問う決まりがない。打ち手は知見が中心 |
| ADR 0023 の事例の分析（`case_review`） | 生産の中の差し戻し・停止を掘る。本番に出た不具合は対象にしない |
| ADR 0046（事故調査委員会） | 工場の振る舞いで事業主に**お金の損**が出たもの。製品の不具合の流出は対象外（分担はそのまま） |

## 決定

### 0. 工場が決めるのは重要度ごとの動き、基準は製品のドメインのもの

2026-11-16 オーナー: 障害の重要度の判定の基準は、製品のドメインに強く依存する。工場の仕組みが決めるのは S1〜S4 の**重要度ごとの動き**（差し止め・自律修正・緊急便・振り返りの深さ）までで、**どの不具合がどの重要度か**の基準は製品ごとに持つ。

- 基準の正本は製品の `.factory-config/quality_policy.yaml`（S1 の条件と S2〜S4 の基準。今の形のまま）。Engine の `definitions/quality_policy.yaml` は、製品が書いていないときの既定の雛形にとどめる
- 基準は障害が起きるたびに育つ。流出の振り返りは、関門の表とは別に「**重要度の付け方は合っていたか**」を問う（もっと重く扱うべきだった・基準にない種類だった）。基準を直す案は、打ち手の 1 つとして事業主に回す（製品の基準なので事業主の判断。決定 5 の表の「重要度の基準」）

### 1. 言葉

- **流出**: 利用者に届く本番の版に、不具合が入っていたこと。本番で見つかったものと、staging で見つかったが同じ不具合を含む版がすでに本番に出ていたものの両方
- **混入**: 不具合の原因になった変更が main に入ったこと。混入したが本番に出る前に止められたものは流出ではない（関門が効いた例として、ADR 0061 の振り返りで扱う）
- **流出の振り返り**: 流出した不具合 1 件について、どこで混入し、なぜ関門で止められなかったかを調べ、混入を防ぐ打ち手を起票すること。業務のツリーでは `learn.escape`
- 呼び名は仮。用語集（05_specs/04_glossary.yaml）の未決の語に入れる

### 2. 対象と、いつ開くか

- **本番に流出したものは、どの重要度も 1 件ずつ**開く（2026-11-16 オーナー）。演習（drill）は除く
- まとめてよいのは**同じ原因のもの**だけ（同じ原因で束ねた `factory:bundled`、ADR 0053 の 6。同じ直しの PR で閉じたもの）。日数でまとめない
- 深さは重要度で変える

| 重要度 | 振り返りの形 |
|---|---|
| S1・S2 | **深い振り返り**: 委員会（決定 7）で、決定 4 の (1)〜(3) をすべて埋め、なぜなぜ分析で真因まで掘って確実に再発を防ぐ |
| S3・S4 | **簡易な振り返り**: 分析役 1 体で、(1) 混入と (2) 関門の表を埋め、なぜなぜは 1〜2 段まで。真因の型（下）を付ける |

- **簡易から深いへ上げる**: 簡易な振り返りで付けた真因の型・すり抜けた関門と理由が、同じ製品でほかの流出と重なり、その数が 3 件（仮置き。日数では区切らない）に届いたら、重なった流出をまとめて 1 回の深い振り返りを開く（同様の問題の多発）。深い振り返りは、それまでの簡易な振り返りを材料にする
- 開くのは**直しの PR がマージされた後**（Incident が閉じた、または Defect の Issue が閉じた）。直しを先にし、振り返りで直しを遅らせない。直しの差分は原因をたどる材料にもなる
- supervisor の `escape_review_step` がジョブ `escape_review` を積む。委員会と知見の専用の枠（`GOVERNANCE_PARALLEL`）で動き、ラインの差し止め・一時停止の間も動く

### 3. 流出かどうかの判定（決定論）

- Incident の `env` が prod なら流出
- staging で見つかったものは、見つけた時点で本番に出ていた版が、見つけた版と同じか新しければ流出の候補（`release.deployed` の env=prod の記録で見る）
- 振り返りが原因の変更を特定したら、その変更を含む版が本番に出ていたかで確定する。出ていなければ「流出ではなかった」と記録して終える（`escape.reviewed` の `escaped: false`。関門が効いた例として記録に残る）
- 判定の記録は events の `escape.detected`（Incident の id・版・判定の理由）

### 4. 必ず問うこと: どこで混入し、なぜ関門で止められなかったか

振り返りの結果は、次の 3 つを必ず埋める（空欄で終えられない形にする）。

**(1) 混入**: 原因の変更（PR・チケット）と、どの工程で入ったか（要件・設計・実装・既存の潜在。既存の潜在は、いつから本番にあったか）。

**(2) 関門の表**: 原因の変更が本番に出るまでに通った関門を 1 行ずつ。関門の一覧は `definitions/learning.yaml` の `escape.gates` に置く（Gen1 は下の 8 つ）。

| 関門 | 書くこと |
|---|---|
| 要件（プランナーの受け入れ条件・守るストーリー） | 動いた・飛ばされた・なかった。止められたはずか。止められなかった理由 |
| 実装の試験（CI） | 同上 |
| 検査（inspect） | 同上 |
| 裁き（judge） | 同上 |
| チケットの QA（確かめ直し） | 同上 |
| 出荷の QA の関門（判定と探索。ADR 0049・0060。流したシナリオ・飛ばしたシナリオ） | 同上 |
| 本番の承認（承認者、緊急便の自動の承認） | 同上 |
| 本番の見張り（ADR 0057） | 同上（流出したあと、どれだけ早く気づけたか） |

止められなかった理由は、次の型から選び、説明を添える: **観点がない**（その関門がそもそも見ない種類のもの）・**見たが見逃した**・**飛ばす決まりだった**（緊急便・シナリオの選び方など）・**材料が渡っていない**（仕様・ストーリー・既存の決めごとが関門に届いていない）・**試験がない**・**その他**。

**(3) なぜなぜ分析で真因まで掘る**（2026-11-16 オーナー: 当該事象だけでなく真因を突き止めて再発防止策を考える）

- 起点は 2 つ置く: 「なぜ混入したか」と「なぜ関門で止められなかったか」（関門ごと）。それぞれ枝分かれを許すなぜなぜの木にする（1 本の鎖にしない）
- 各段は前の段の答えに対して問い、根拠（記録・差分・ADR・プロンプト）を添える。根拠のない段は仮説と印を付ける
- 「ワーカーが見落とした」「注意が足りなかった」「確認不足」で止めない。そこからもう 1 段、なぜ仕組みが見落としを許したかを問う
- 止めてよいのは、工場の仕組み（役割への指示・関門の観点・決まり・定義・渡す材料）か製品の設計の決めごとに行き着き、そこを変えれば同じ型の不具合が別の場所でも入らなくなると言えたとき。これを**真因**として印を付ける
- **水平展開**: 真因が同じで、まだ見つかっていない不具合が製品のほかの場所にないかを探す（例: 「受講権を今の時点で判定している」箇所がほかにないか）。見つかれば Defect として起票する
- 再発防止策は、当該事象の直し（済み）ではなく真因に対して立てる。1 つの真因に、混入を防ぐ策と、関門で止める策の両方を考える

### 5. 打ち手（仕組み化）と行き先

打ち手は種類ごとに行き先を決める。承認の線は変えない（ADR 0023・0044）。

| 種類 | 例 | 行き先 | 誰が決めるか |
|---|---|---|---|
| 重要度の基準（製品） | `quality_policy.yaml` の S1 の条件・S2〜S4 の基準の追加・見直し | 製品リポの Issue（文面は工場が書く） | 事業主 |
| 試験（製品） | 回帰の試験、ストーリーと must_not の追加 | 製品リポの Issue（工場のラインで作る） | 工場。既存の仕様を確かめるものに限る。振る舞いの決めごとを新しく定めるものは事業主 |
| 検査のルール（製品） | 製品の検査ルール（overlay）の追加 | 今の検査ルールの流れ（ADR 0013。shadow を経て採用） | 工場 |
| 関門（Engine） | 検査・QA の観点、シナリオの選び方、出荷・緊急便の決まり | factory-engine の改善 Issue | 提供元（人の承認） |
| プロセス | 役割への指示、ワークフローの宣言、ラインの設定 | 提案として人に回す（ADR 0023 の承認の線） | 人 |
| 再発防止の知見 | 「受講権の判定は、予約を取った時点か今かを要件に書く」のような普遍的な学び | 知見の変更セットの PR（決定 5 の 2） | 知見のレビュー（ADR 0024 の 4 観点）。展開は ADR 0040 のまま |

- **生産の振り返り（ADR 0061）とは分ける**（2026-11-16 オーナー）。障害の振り返りは**再発防止**の観点、生産の振り返りは**開発の効率・持続性・スケーラビリティ**の観点で、問いも材料も違う。流出の振り返りは自分で再発防止の知見を抽出し、1 回の振り返りで 1 本の知見の変更セットの PR にする（作法は ADR 0024 の決定 4 のまま。主題に `prevention` の印を付ける）
- レビューは今の知見のレビュー（整合・根拠・担保・反対の 4 観点）を使い、根拠の役は「真因まで掘れているか・水平展開をしたか」も見る。振り返りに出た委員はレビューに入らない
- 確かさは、1 件の流出に根拠がある知見は hypothesis。ただし決定論の担保（試験・検査ルール）を同時に起票したものは、担保がマージされたら settled に上げられる（ADR 0024 の基準のまま）
- 生産の振り返りは、流出の振り返りの結果を読んでよいが、障害の原因は掘らない（ADR 0061 の決定 3 の「運用の材料」と決定 5 の「運用と障害」の取っ掛かりはこちらに移す）
- 直しの PR に回帰の試験がすでに入っていれば、試験の打ち手は「済」として記録だけ残す
- 同じ関門・同じ理由の打ち手の Issue がすでに開いていれば、新しく起票せず、根拠としてコメントを足す
- 製品リポの Issue には工場の語・知見の id を書かない（ADR 0061 の決定 7 と同じ書き方）

### 6. 材料（決定論で組み立てる）

- Defect の Issue（再現・期待・実際）と Incident（重要度・見つけた環境・版）
- 直しの PR の差分と、足した試験
- 原因の候補: 直しの PR が変えた行を、その前に最後に触った PR（git の履歴で引く）。あくまで候補で、確定は振り返りが行う
- 原因の候補のチケットの記録: 要件とストーリー・プラン・ワークフローの宣言・CI・検査の指摘・judge・チケットの QA の結果
- その版の出荷の経路: 定期便か緊急便か、`release.approved` の承認者と `qa_skipped`、QA の関門で流したシナリオと飛ばしたシナリオ（ADR 0060）とその結果
- 本番の見張りの記録（ADR 0057）と、流出してから見つかるまでの時間
- 同じ製品の過去の流出の振り返り（同じ関門・同じ理由の再発を見るため）

### 7. 誰が振り返るか

多角的に振り返る（2026-11-16 オーナー）。ADR 0061 の委員会の形（ロールの委員と議長）を、障害の振り返り用の顔ぶれで使う。

- **原因に関わったロールの委員**: 原因のチケットのジョブに出てきたロール（プランナー・実装・検査・judge・QA など）。そのロールの立場から「自分の工程で、なぜ入れた・なぜ通したか」を話す
- **関門の委員**: 原因のチケットに出てこなくても、すり抜けた関門の持ち主（出荷の QA の関門の QA・本番の承認をした supervisor の決まりの持ち主など）は必ず入れる
- **品質の立場の委員**: 製品の品質方針（`quality_policy.yaml`）と重要度の基準を持ち、「利用者にとって何が起きたか」と水平展開を受け持つ
- **議長（事業部のリーダー）**: 意見を突き合わせ、なぜなぜの木をまとめて真因を決め、再発防止策と知見を決める。どの立場の意見を採ったか・採らなかったかを残す
- 委員は並列に意見を出し、議長がなぜなぜの木を組んだあと、委員に 1 回だけ見せて反論を受ける（2 周目）。真因の決め打ちを避けるため
- ロールの委員は 6 つまで（仮置き）。深い振り返りは 1 件 $15、簡易な振り返りは 1 件 $2 まで（仮置き。どちらも tier-judge）。見回りの費用の集計（05_specs/10）に足す
- 打ち手の起票（Issue の作成）と知見の変更セットの Issue は dispatcher が決定論で行う。委員会は文面と行き先を返すだけ

### 8. 記録と見える化

- 正本は制御プレーンの artifacts（型 `EscapeReview`）と events（`escape.detected`・`escape.reviewed`・`escape.filed`）。`escape.reviewed` に、混入の工程・すり抜けた関門と理由の型・打ち手の Issue を残す
- 操業コンソールの委員会のページ（`/committees`）に「流出の振り返り」を足し、混入・関門の表・なぜなぜ・打ち手を出す
- 建設日報に、流出の件数と、すり抜けた関門と理由の内訳の推移を出す
- **同じ関門を同じ理由で 2 回すり抜けたら**、その関門の打ち手の Issue を受信トレイに提供元宛てのお知らせとして出す（打ち手が効いていない、または手が付いていない合図）

### 9. 効き目の確認

打ち手の Issue が閉じたあと、同じ真因・同じ関門・同じ理由の流出が起きていないかを決定論で数える（学ぶ側に自分を採点させない。ADR 0013 の 8）。次の流出の振り返りの材料に「同じ製品の過去の流出の振り返りと、その打ち手の状態」を入れ、効いていなければ議題にする。月に 1 回、製品ごとに流出の件数・真因の型・打ち手の消化を建設日報にまとめる。

### 10. 後の世代の障害報・障害対応とのつなぎ

- 入口は Incident（`incident.opened`・`incident.closed`）と Defect の Issue。今は QA と本番の見張りが Incident を開く
- 障害報と障害対応のフローができたら、障害報が閉じたところから本 ADR の振り返りを呼ぶ。障害報の「原因と再発防止」の欄は、流出の振り返りの記録を指す。振り返り以降の中身は本 ADR のまま使う

### 11. 事故調査委員会との分担

事故調査委員会（ADR 0046）は「工場の振る舞いで事業主にお金の損が出たもの」を横断で見る。流出の振り返りは「製品の不具合が本番に出たこと」を見る。流出が事業主のお金の損（返金など）を伴ったときは、事故の台帳に残すかを事故調査委員会が判断する（本 ADR は台帳に書かない）。

| 要件 | 「本番では鍵が要る」が要件・ストーリーになかった（材料が渡っていない） | 直しの受け入れ条件に、月額契約の前に取った体験予約の扱いがなかった（材料が渡っていない） |
| 試験・検査 | 鍵なしで起動できることを、試験も検査も問題にしなかった（観点がない） | 試験は「受講権のない生徒」だけ。予約の後に契約した場合がない（試験がない）。検査も通した（指摘の記録は実装したら確かめる） |
| 出荷の QA の関門 | 権限の探索で初めて見つけた。それまでの関門の探索は、なりすましを試していなかった（観点がない） | 0.53.0 は S1 の緊急便で、関門を待たずに本番へ（飛ばす決まりだった）。関門は本番の後に staging で見つけた |
| 本番の承認 | — | S1 の緊急便を工場が自動で承認。便には main がまるごと載り、S1 の直しと関係のない #1768 も一緒に出た（飛ばす決まりだった） |
| 打ち手の候補 | 製品: 鍵なしでは起動しない（済、#1786）。Engine: 検査・QA の観点に「既定で開く（fail-open）設定」を足す | Engine: S1 の緊急便は、本番の版に直しだけを足して作る（main をまるごと載せない）か、載る変更を関門に通す。製品: 予約を取った時点と今で受講権が違う場合の回帰の試験 |

緊急便が main をまるごと載せることは、ADR 0053 の追記（2026-11-14）で S2 については対処したが、S1 では残っていた。どう直すかは出荷の決まりの変更なので、本 ADR では決めず、ADR 0064（S1 の緊急便は直しだけを載せる）に分けた。

## 選ばなかった案

- **ADR 0061 の振り返りで扱う／知見の流れだけ 0061 に乗せる**: 障害の振り返りは再発防止、生産の振り返りは効率・持続性・スケーラビリティで、観点が違う（オーナー）。12 件たまるまで開かず、S1 の流出が他のチケットに埋もれる
- **分析役 1 体で振り返る**: 安いが、1 つの立場の見方に寄り、真因の決め打ちになりやすい（オーナー: 多角的にしっかり振り返る）
- **事故調査委員会（ADR 0046）で扱う**: あちらは「お金の損」を横断で見る組。製品の不具合の流出とは見る物も材料も違う
- **流出のたびに専用のチェックを足す**: ADR 0046 の文脈と同じく、工場が太る。打ち手は関門の観点・試験・決まりの見直しとして起票し、必要かは関門ごとに判断する
- **S3・S4 を日数でまとめて振り返る**: 違う原因のものが混ざり、1 件ごとの混入の経路が薄まる。まとめるのは同じ原因のものだけにする（オーナー）
- **S3・S4 も S1・S2 と同じ深さで振り返る**: 件数が多く費用に見合わない。簡易に振り返り、重なったら深くする
- **障害報・障害対応のフローを先に作る**: オーナーの方針で後の世代。振り返り以降を先に作り、入口は Incident にしておく
