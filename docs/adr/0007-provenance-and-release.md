# ADR 0007: 来歴とロット（Release）

- 状態: 承認（2026-10-27 戦略会議 第 1 回の決定 D7。付ける属性の細部は委任の範囲で決め、運用で調整する）
- 関係: 戦略会議の議事録（建設者の手元の 50_build-work/strategy/minutes/2026-10-27_strategy-meeting.md の 5 節・8 節）、ADR 0006（判断の記録とモード）、`definitions/events.yaml` の `provenance_fields`

## 文脈

有形のものづくりでは、製品のロット番号で市場に出た後の問題と製造工程を結び、リコールの範囲を決める。
アプリ開発で問題と製造工程を厳密に結ぶことはできないが、「ロードマップのうち全面委任のモードで作った割合」「それで市場に出た不具合の数」「利用者の声がどの版に対するものか」を、後で傾向が掴める程度の統計にしたい。
カスタマーサクセスなどの報告で紐付けの情報が欠けていれば、その分は統計から落ちる。

## 決定

1. **ロット＝Release**。release_id は `<repo>@<app_version>`。Gen1 は `factoryctl release create` で後付けし、前の Release 以降にマージされた工場の PR（`pr.merged`）をまとめて含める。1 つの PR が入る Release は最初の 1 つ（`release.included`）
2. **来歴は製造・出荷・利用・報告の全部に付ける**。製造の来歴は Engine の版、ワーカーのイメージ（ID）、製品の既定ブランチの先頭（base / overlay の版）、モード、モデルの tier で、`job.started` と PR の成果物の `payload.provenance` に入れる。決め手と確信度は判断の記録（ADR 0006）が持ち、PR の URL で結ぶ
3. **属性はすべて optional で、eager に付ける**。取れなければ `unknown` で記録し、検査や投入の条件にしない。記録の失敗でワーカーは止めない
4. **統計には紐付けできた割合を必ず併記する**（`factoryctl report provenance --from --to`）。付ければ付けるほど統計は精緻になるが、製造を来歴の仕組みにロックインしない
5. **製品側は行動イベントの共通属性に `release_id` と `app_version`（optional）を持つ**。利用者の声や不具合の報告を版に結ぶ入口になる。intake（clarify）で報告を受けるときに版を問う項目は、プロンプトの変更なので承認付きの別 PR にする

## 選ばなかった案

- **来歴が揃わない PR は Release に入れない**: ラインが来歴の仕組みにロックインされる（D7 の前提に反する）
- **Release をマージ時に自動で切る**: Gen1 には出荷の経路がまだなく、版の付け方も決まっていない。後付けで足りる
- **来歴を git のタグやコミットメッセージに書く**: 正本が 2 つになる。制御プレーンの events だけに置き、PR からは URL でたどる

## 結果

- 版から PR、PR から製造の来歴（モード・判断の記録）をたどれる。モードごとの不具合率を出す材料が揃う
- 2026-10-27 時点では、モード（ADR 0006 の後半で入る）と Engine の版（上げ直すときに `ENGINE_VERSION` を入れる）が `unknown` になる。紐付け率で欠けが見える
- 出荷の経路（P2 以降）ができたら、environment と rollback_target を Release に足す
