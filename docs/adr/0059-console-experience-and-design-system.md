# ADR 0059: 操業コンソールを開発事業部の窓口として作り直す（体験・構造・デザインシステム）

- 状態: 提案（2026-11-14。体験と構造、デザインシステムの初版はオーナーが確認済み）
- 関係: ADR 0009（操業コンソール・操業 API）、ADR 0030・0039（窓口の API）、ADR 0032（通知の出し分け）、ADR 0034（受信トレイの判断）、ADR 0044（判断の宛先）、ADR 0058（繰り返すエラーのお知らせ）。仕様は建設者の手元の 05_specs/16_console.md（体験と構造）と 17_console-design-system.md（見た目の決まり）

## 文脈

操業コンソールは ADR 0009 の「工場の状況を見て操作する画面」として始まり、ホーム・ライン・受信トレイ・製品・出荷・使用量・設定・ヘルプと機能が増えた。

- 画面は `console_page.py` の 1 つの Python の文字列に CSS と JS が全部入っている。部品の決まりがなく、同じ札やボタンがページごとに書かれている
- 工場を回す人（提供元）の目線で作られていて、製品にしか関心のない事業主には「工場の管理画面」に見える。同じ件（不調・判断待ち）がホーム・ライン・受信トレイの 3 か所に出る
- スマホでは横にはみ出す画面があり、判断に答えるボタンが画面の外に出る
- 運用が始まると、マーケティング（利用状況）とカスタマーサクセス・サポート（障害の調べもの）も見る。事業主の側の複数の人が、同じ依頼を重ねて出すおそれがある

## 決定

1. **位置づけ**。操業コンソールは開発事業部が他部門（経営・企画、事業主のプロダクトオーナー、マーケティング、カスタマーサクセス・サポート）と向き合う窓口とする。API が正本で、画面はその利用者の 1 つ（ADR 0009 の 5）。外部の CDN は使わない（ADR 0009 の 4）
2. **3 つの軸を分ける**
   - ワークベンチ（見え方）：メニューの並び・ホームに出すもの・受信トレイの既定の絞り込みだけを変える。画面はどのワークベンチからでも全部たどれる。本人が選ぶ（商用化では最初のログインの短いアンケートで既定を選ぶ）。今は「工場」と「製品」の 2 つ
   - 権限：画面ではなく操作に掛ける。役は IAM の 4 つ（運用者・責任者・依頼者・見る人 × 製品）。押せない操作は消さずに、だれなら押せるかを添えて薄く出す。マーケティング・サポートの人には新しい役を作らず、依頼者か見る人を付ける
   - プラン：使える機能。運用の機能（障害報の管理・利用状況）は上位のプランとし、プランにない機能は例の画面と期間限定の利用の入口を出す
3. **サイトの構造**。ホーム、受信トレイ（事業部から人へ）、問い合わせ（人から事業部へ。似た依頼を送る前に出し、依頼ごとに見える人を選ぶ。既定は全員）、製品（概要・見通し・障害と問題・利用状況・リリースと環境・準備度）、事業部の様子（レーンの上を流れるジョブとリアルタイムのチャート）とライン、費用、工場の保守、設定・ヘルプ。1 つの件は 1 か所で片付け、ほかのページは件数とリンクだけ。移したページの URL は転送する（`/ship` → 製品のページ、`/usage` → `/cost`）
4. **端末**。PC は FHD を基準、幅の区分はスマホ 600 未満・タブレット 600〜1199・PC 1200〜1599・広い PC 1600 以上。スマホでするのは、すぐ答える判断・単発の依頼・承認・製品の進みと障害の対応状況の参照だけ。Safari と Chrome は必須、Firefox はあれば良い
5. **運用の情報の正本は事業部**。障害報・利用状況は工場が正本を持つのが基本。既に外部のサービスで管理していて移せない事業主だけ外部を正本のままにし、工場は入口・要約・索引を持つ。外部につなぐ鍵は鍵番が持ち、画面に値を出さない
6. **デザインシステムは 3 つの層**
   - ブランドの層（主の色・灰・信号の原色・字の族）、意味の層（地・字・主な操作・状態の名前、明るい・暗いの 2 テーマ）、部品の層（`c-` の部品）
   - 部品は意味の層の名前だけを使う。ブランドの刷新はブランドの層の値を差し替えるだけにする
   - 状態は色と字の両方で出す。本文の字のコントラストは 4.5 以上、操作の枠と焦点の輪は 3 以上
7. **作り方**。ビルドなしの静的ファイルにする。`console_page.py` を `brand.css`・`tokens.css`・`components.css` とページごとの JS に分け、`console.py` が配る。部品はブラウザ標準の Web Components か小さな関数。部品のカタログのページをコンソールの中に置き、PR の画面のキャプチャもそこから撮る。事業部の様子のリアルタイムは 10 秒ごとの読み直しをサーバーからの知らせ（SSE）に変えて作る
8. **作る順**。(1) 静的ファイルへの分割と決まり・部品の土台（見た目は大きく変えない）、(2) 骨組み（メニュー・下のタブ・工場の状態・ワークベンチの切り替え）とホーム、(3) 受信トレイの詳細と問い合わせ、(4) 製品のページ・事業部の様子・ライン、(5) 工場の保守・費用・設定・ヘルプ。PR ごとにオーナーの承認を得てマージする。ログイン・アンケート・役による絞り込み・プランは商用化のとき

## 採らなかったもの

- **画面の枠組み（React など）とビルド**: Node と依存の更新が工場の保守に増える。コンソールの規模では部品の数が少なく、標準の Web Components で足りる。商用の顧客向けアプリを別に作るときに、API の上で改めて検討する
- **サーバーで HTML を組む**: 事業部の様子のように動き続ける図が作りにくい
- **役で見える画面を絞る**: 事業パートナーのように工場を回す人と製品のオーナーを兼ねる人がいて、画面で絞ると行き来ができなくなる。見え方は本人のワークベンチ、安全は操作の権限で守る
- **運用の情報の正本を外部のサービスに置くのを既定にする**: 外部のサービスを使っていない事業主は工場の中で済むほうがうれしく、工場の自律改善にも使う

## 残り（この ADR の外）

- 製品の「見通し」のデータ。Gen1 はチケットの順番と投入待ちから「次に来るもの」を出す。ロードマップを工場に持たせるかはあとで決める
- プランの区分と期間限定の利用の日数（事業化のとき）
- オンボーディングの仕様に、運用の情報の置き場の聞き取りと「運用を引き受ける」の準備度の項目を足す（運用の機能を作り始めるときに同じ変更で）
