# ADR 0036: プランナーが大きさを見積もって切り、結果と突き合わせて育つ（パイロット前の最低限の品質）

- 状態: 提案（決めどころ Q1〜Q6 はオーナーの承認待ち）
- 関係: ADR 0025・0026（プランナーの責務と着手判定）、ADR 0027（工程の信号。テーマ 6「工程の進め方」）、ADR 0030（窓口。順番 2 のタスクのまとまりの下書き）、ADR 0017（続きのジョブ）、ADR 0013・0023・0024（Learn ループ・学習の体系・知見と委員会）、`definitions/planner.yaml`、`definitions/desk.yaml`、`definitions/learning.yaml`

## 文脈

rally #455（本部がコーチのお休みをまとめて片づける）で、プランナーは「着手できるか」と「どの役をどの順で通すか」（プロダクトデザイナー → 実装役）は正しく決めた。
しかし、実装のチケットは backend（新しい API 2 本と DB）・契約（admin-web と student-app の OpenAPI、境界間イベント）・画面（admin-web の新しい画面と既存の画面の変更）を 1 枚のまま実装役に回した。

| | ターン | 費用（API 換算） | 中身 |
|---|---|---|---|
| 1 回目（ジョブ 4945） | 121（上限 120 で途中終了） | $11.33 | backend と境界間イベントだけ（55 ファイル） |
| 続き（ジョブ 4950） | 60 | $8.14 | 契約・画面・UXSpec・README |
| 合計（PR #984） | 181 | $19.47（約 27M tokens） | 84 ファイル、+6,799 行 |

今のプランナーの欠けているところ:

1. **大きさを見ない。** Plan に `expected_files` と役ごとの `effort` はあるが、「1 回の実装で終わる大きさか」を見積もる欄も、超えたら切る決まりもない。切れるのはデザインシステムの仕事を別のチケットにすることだけ（`planner.split_design_system`）
2. **結果と突き合わせていない。** ADR 0026 は「判断の根拠を残し、経路ごとの結果と突き合わせて後で見返す」としたが、突き合わせる仕組みがない。プランナーの品質を測っているのは、問い手の clarify の一巡（`scripts/clarify-bench.sh`、10 件中の一致）だけ
3. **育つ道がない。** 見積もりの外れは、工程の信号（ADR 0027 の 3）の `rework`（やり直しが 3 回以上）や `cost_outlier` に紛れて入るだけで、プランナーの入力（製品の知見）に戻らない

タスクのまとまりへの切り方は、窓口の相談役（ADR 0030 の順番 2、`core-gates/desk_consult.py`・`desk_line.py`）がすでに持っている。依頼から要件・画面・契約・実装のタスクを依存つきで切り、確認 1 回で Issue に起票し、依存が閉じたものから `factory:plan` に回す。足りないのは、窓口を通らずに入ってきた 1 枚のチケット（Issue に `factory:plan`、P3 のタスクの補充、建設者の手書き）を、プランナーが同じように切ること。

オーナーの方針（2026-11-05）: パイロット導入（12 月）までに、最低限のプランナーの品質を確保する。導入後は、製品の特性と事業のドメインに合わせて、工場の中の Learn ループで進化していく。

## 決定

### 1. プランナーは大きさを見積もり、Plan に残す

Plan の答えに `size` を足す。経路の役ごとではなく、実装役に回す仕事 1 件について書く。

| 欄 | 中身 |
|---|---|
| `layers` | 触る層。`contract`（specs/contracts/）・`db`（マイグレーション）・`backend`・`web`・`mobile`・`docs`（specs/ と README だけ）から。製品の層の名前は `.factory-config/manifest.yaml` の構成から読む |
| `expected_files` | 今の欄のまま（変わる見込みのファイル）。数も大きさの材料にする |
| `turns` | 見込みのターンの帯: `S`（〜30）・`M`（〜60）・`L`（〜90）・`XL`（90〜） |
| `basis` | 見積もりの根拠（似た過去のチケットと、その実績） |

見積もりの材料として、dispatcher が製品ごとの**実績の表**を決定論で作ってプランナーに渡す（下の 4）。プランナーが勘で帯を選ぶのではなく、「この製品で backend に新しい API を 1 本足したチケットは、中央値 25 ファイル・45 ターン」のような表を見て選ぶ。

### 2. 切る基準を超えたら、タスクのまとまりに切る

実装役に回す仕事が、次の**どれか 1 つ**に当たれば、プランナーは `ready` の代わりに `split` を返す（切る基準。`planner.yaml` の `sizing`）。

| 基準 | 仮の値 | #455 |
|---|---|---|
| 触る層（`docs` を除く） | 3 以上 | contract・db・backend・web の 4 |
| 変わる見込みのファイル | 30 を超える | 84（実績） |
| 見込みのターンの帯 | `L` 以上（ターン上限の半分の 60 を超える） | 181（実績） |

- 1 件の目安は「1 つの層とその契約、30 ファイル・60 ターンまで」。ターン上限（実装役の `MAX_TURNS`）に余裕を残し、続きのジョブなしで終わる大きさにする
- 切り方は窓口の相談役と同じ型を使う（`desk.yaml` の `task_kinds`・依存つき・`要件 → 画面 → 契約 → 実装` の順）。実装はさらに層で分け、たとえば #455 なら「契約（OpenAPI と境界間イベント）→ backend → admin-web の画面」の 3 枚になる
- 起票は `desk_line` の起票と依存の進め方を共通にして使う（依存のないタスクは `factory:plan`、あるタスクは待ちのラベル、閉じたら `factory:plan` に替える）。もとのチケットは親として残し、子がすべて閉じたら閉じる
- 子のチケットは、もとのチケットの UXSpec・受け入れ条件のうち、その子の範囲を本文に持つ（UXSpec は全体を参照し、範囲だけを書く）。子もプランナーの着手判定を通る（ふつうは実装役だけの経路になる）
- 決定論の守り（guards）に `oversized` を足す: プランナーが `ready` を返しても、`size` が基準を超えていれば `split` に替える。見積もりが空（`size` がない）の実装は `ready` のまま通し、見返すための印（advisory `no_size`）だけ付ける

### 3. 切るのは、実装の手前で画面が決まってから

画面の設計（プロダクトデザイナー）は機能全体で 1 回にする。画面を層ごとに分けて考えると、要素と振る舞いの一貫性が崩れるため。

- 最初の判定で経路にプロダクトデザイナーが入るときは、最初の判定では切らない（`size` は今の見立てとして残す）
- デザインの線が終わり（UXSpec が本文に入り）、経路が実装役に進むとき（`advance_steps`・`design_line.choose` の後）に、プランナーの**実装の手前の判定**を 1 回積む。UXSpec の `contract_needs`・`screens`・`changes` が材料になり、見積もりの精度が上がる
- デザインの役が入らない経路は、最初の判定で切る

### 4. 結果と突き合わせる: 実績の記録、評価セット、合格線

#### 4a. 実績の記録（`plan.outcome`）

チケット（子を含む）が閉じたら（PR のマージか、閉じた）、dispatcher が決定論で `plan.outcome` を残す。最新の Plan と突き合わせる。

- 実装のジョブの数、ターンの合計と最大、費用の合計、途中終了の回数、続きのジョブの理由ごとの数（`continue.enqueued`）
- 実際に変わったファイルと層（PR の差分から）、見込みのファイルの再現率と適合率
- 差し戻し: 人が経路を変えた（`factory:plan-human` の後に別の経路）、judge が範囲を問うて人に回した（`factory:needs-judgment`）、違和感の印（`taste.flagged`）
- 判定: `ok`／`undersized`（切るべきだった: 途中終了、またはターンか費用が基準を超えた）／`oversized`（切りすぎ: 子が 10 ターン未満で終わった）／`misrouted`（経路が覆った）

これを集めた実績の表（製品ごと・層の組ごとのファイル数とターンの中央値と分布）を、プランナーの入力（決定 1 の材料）にする。最初の版は過去の記録（jobs・events・PR）から作り直して入れる。

#### 4b. 固定の評価セット（プランナーのベンチ）

`eval-corpus/planner/` に、過去のチケットの本文と、人が付けた正解（切るべきか、触る層、大きさの帯、経路）を置く。最初は 12 件: rally の実績から、切るべきだったもの（#455 ほか）、1 枚で足りたもの（#886 など）、デザインシステムの仕事、画面のない小さな改修を混ぜる。正解はオーナーの代理で建設者が付け、オーナーが確かめる。

プランナーのプロンプト・基準・モデルを変えるときは、このベンチ（`scripts/planner-bench.sh`。clarify のベンチと同じ形）を回し、前の版と比べてから入れる。

#### 4c. 合格線（パイロット導入の前に満たす最低限）

| 測るもの | 合格線（仮） | 測り方 |
|---|---|---|
| 切る／切らないの一致 | ベンチで 10/12 以上 | 4b |
| 大きさの帯 | ベンチで ±1 帯の内が 10/12 以上 | 4b |
| 実装の途中終了 | 直近 2 週のチケットの 10% 以下 | 4a の `undersized` のうち途中終了 |
| 1 チケットのターン | 中央値 60 以下、90 パーセンタイルが上限（120）以下 | 4a |
| 見込みのファイルの再現率 | 中央値 0.6 以上 | 4a（衝突を避ける並べ方の材料。ADR 0027 の 2） |
| 経路の覆り | 10% 以下 | 4a の `misrouted` |

ベンチの 2 つはパイロット前に満たす。実績の 4 つは、直近 2 週に実装のチケットが 10 件以上あるときに測り、満たさなければ日報で知らせる（ラインは止めない）。合格線は、ロードマップの P4 に項目 `planner_quality` として足す。

### 5. その差を Learn に入れ、製品ごとにプランナーの知見が育つ

工程の信号（ADR 0027 の 3）に `plan_miss` を足す。

- 信号: `plan.outcome` が `ok` でないもの。signature は `process:plan_miss:<判定>:<層の組>`（例: `process:plan_miss:undersized:backend+contract+web`）
- 束が閾値（今の工程の信号と同じ: 7 日で 10 件以上か費用 $50 以上。加えて `undersized` は 3 件以上）を超えたら、事例型の分析役（`case.py`）に回す
- 作用先は 2 つに分ける

| 作用先 | 例 | 承認の線 |
|---|---|---|
| 製品の知見（`.factory-config/knowledge/` の planner 向けの項目） | 「rally の admin-web の新しい画面は、fixtures と screens.ts と README の追記で 1 画面あたり 8 ファイル増える」「通知の種類を足すと student-app の設定画面まで広がる」 | 知見の委員会（ADR 0024）。製品ごとの癖なので、製品の中で育つ |
| Engine の基準（`planner.yaml` の `sizing` の値、プロンプト） | 「30 ファイルの基準は rally では緩い」 | 値の調整は運用パラメータとして工場が試してよい（前後を測り、効かなければ戻す）。基準の種類やプロンプトの変更はオーナーの承認 |

実績の表（4a）は毎日作り直すので、知見にしなくても、製品の実績はそのまま次の見積もりに効く。知見は表で表せない「なぜ大きくなったか」を残す。

### 6. 途中終了したら、続きの前にプランナーに戻す

途中終了（ターン上限）の続きは、今は同じ大きさのまま何度でも積める。これを 1 回までにし、2 回目の途中終了では、続きを積まずにプランナーの判定（残りの作業を見て切る）に回す。1 回目の続きも、残りの見込みが `L` 以上なら切る。

## 決めどころ（オーナーの承認が要る）

| # | 問い | 推奨 |
|---|---|---|
| Q1 | 切る基準 | 層 3 以上・ファイル 30 超・ターンの帯 L 以上のどれか 1 つ（決定 2）。値は運用パラメータとして工場が調整してよい |
| Q2 | 切る時点 | デザインの役が入る経路は、画面が決まった後、実装の手前で切る（決定 3）。画面は機能全体で 1 回 |
| Q3 | 切り方の型 | 窓口の相談役と同じタスクの型と起票の仕組みを共通に使う（決定 2）。プランナーが 2 つの切り方を持たない |
| Q4 | 合格線 | ベンチ 2 つはパイロット前に必須、実績 4 つは日報で見張る（決定 4c） |
| Q5 | Learn の作用先 | 製品ごとの癖は製品の知見（委員会）、基準の値は工場が試してよい、基準の種類とプロンプトはオーナー（決定 5） |
| Q6 | 途中終了の続き | 続きは 1 回まで。2 回目はプランナーに戻して切る（決定 6） |

## 順番

1. 実績の記録（`plan.outcome`）と実績の表、過去の記録からの作り直し。今の合格線の実績 4 つをまず測り、出発点を日報に出す
2. `size` の見積もりと切る基準（`planner.yaml` の `sizing`、guards の `oversized`、`split` の判定）。起票は `desk_line` と共通にする
3. 実装の手前の判定（決定 3）と、途中終了の戻し（決定 6）
4. 評価セット 12 件とベンチ、合格線のロードマップの項目
5. 工程の信号 `plan_miss` と、製品の知見への作用

1〜4 をパイロット導入の前に入れる。5 は 1 の記録がたまってから（2 週間）。

## 選ばなかった案

- **実装役のターン上限を上げる**: 1 回で終わるようにはなるが、文脈が長くなるほど費用が膨らみ、検査も judge も大きな差分を見ることになる。人の確認も重い。大きさは切って抑える
- **決定論だけで切る（ファイル数や層の数を機械的に数える）**: チケットの本文からはファイル数が読めず、UXSpec がないと層も分からない。見積もりはプランナーに任せ、決定論は基準を当てる守りと、実績の表を作ることに使う
- **窓口とは別の切り方をプランナーに持たせる**: 型が 2 つになり、起票と依存の進め方が分かれる。窓口の型を使い回す
- **画面の設計の前に切る**: 画面が層ごとに分かれて設計され、一貫性が崩れる。#455 の UXSpec のように、契約の要る点（`contract_needs`）は画面を決めて初めて分かる
- **切りすぎを気にしない**: 子が小さすぎると、ジョブごとの立ち上げ（読む・検査・judge・CI）の費用が勝つ。`oversized` も外れとして数える

## 結果

- 大きなチケットが 1 回の実装で上限に当たることが減り、途中終了の続きと大きな差分の検査の費用が減る
- プランナーの品質を、ベンチと実績の 2 つで測れる。パイロットの前に満たすかを数字で言える
- 製品ごとの実績の表と知見が、そのままプランナーの入力になり、導入後は製品の特性に合わせて見積もりが育つ
- 窓口の依頼と、1 枚で入ってきたチケットが、同じタスクの型と起票の仕組みを通る
- 切るとチケットとジョブの数は増える。1 件ごとのプランナーの判定と、検査・judge の立ち上げが増える分は、合格線の実績で見張る
