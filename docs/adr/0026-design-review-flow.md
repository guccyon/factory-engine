# ADR 0026: デザインの判断の流れ（着手判定・2 つのデザイナー役・レビューページ・プッシュ通知）

- 状態: 提案（2026-11-01 戦略会議。オーナーが方針を決め、P4 で設計・実装に落とすよう指示。レビュー依頼の型は 2026-11-01 にオーナーと見直し）
- 関係: ADR 0025（上流の工程と人との協業。E1・E2・E4 の運用をこの ADR で改める）、ADR 0014（検査役の承認）、ADR 0013（Learn ループ）、ADR 0009（操業コンソール）、ADR 0020（状態は制御プレーン）

## 文脈

ADR 0025 に沿って、デザイナー役とデザイン検査役（#105）、人の選択の画面（#106）を作り、製品の管理画面のタスク 1 件でデザインの線が端から端まで通った。
デザイナー役が 2 案を作り、検査役が「新しい画面なので人へ」と回し、操業コンソールの上部に案の画像が出た。

実物を見たオーナーの判断は「この流れでは判断できない」だった。聞き取りで出た問題は 4 つ。

1. **判断の材料がない**。断片的な画面だけでは、利用者がそこで何を達成したいのか、体験をどう設計したのか、なぜこのデザインなのかがわからない。要求仕様（PRD）と、実物大の画面・前後の遷移・押したときの挙動・マイクロインタラクションを書いた画面定義書がセットでないと、個人の好み以上の判断にならない
2. **判断する人と場所が合わない**。判断するのはプロダクトオーナーやデザインのチーフで、工場の操業画面は見ない。業務の標準ツール（Slack など）の上でやり取りしないと判断が滞る
3. **工程の間で待ちが出る**。前の工程の完了時に次の担当へプッシュで依頼が届かないと、工程の間の分断がボトルネックになる
4. **デザインと実装の粒度が違う**。複数画面の機能ではデザインが 1〜2 回で実装のタスクは数十になる。一方で、開発の進め方（マイルストーンの有無）や、求められるデザインの水準は製品と組織で大きく違う

良い点として、見える形で 2〜3 案が出ることは残す。

工場で作りたいのは製作の外注先ではなく、業務を素早く円滑に回す仮想の開発事業部である。判断の流れは、判断する人の業務の流れに合わせる。

## 決定

### 0. 工場はどのパターンにも備え、パターンはチケットごとの着手判定で決める

どの製品・組織にどのデザインの進め方が合うかは、事業として先に決めない。工場はすべてのパターン（下の 1 と 2 の組み合わせ）を持ち、チケットが入ってきた時点で着手判定（プランナーが持つ。0b）で決める。

- 入力: チケット（GitHub Issue など外部のチケット管理）と、そのプロダクトの工場の知見（デザインシステムの有無と成熟度、ガイドライン、似た画面、過去の回答）
- ready: デザインの依頼の要否と範囲を決めてラインへ流す。デザインシステムが確立していれば、チケットはシンプルなままで ready
- まだ着手できない: 理由と選択肢つきの問いをチケットのコメントで起票者に返す（例：デザインシステムがない製品で画面を含むチケットに指定がなければ「既存の画面に倣って任せる／先にデザイン案を出す／デザインシステムを作るところから」）。返信のイベントで判定し直す
- 答えはプロダクトの既定として知見（ADR 0024）に溜め、同じ問いを繰り返さない。下の「デザインの型」はこの既定として運用の中で決まる
- 問いの仕組みは clarify（要求者との往復）を使い回す。実装のチケットには今は着手の判定がない
- Gen1 では、チケットへの要求・要件（デザインを含む）の記載と問いへの回答は、オーナーの代理で建設者が行う。デモ製品の見た目にはこだわらず、商用と同じ経路（問い→回答→判定し直し→知見）を通すことを優先する

### 0b. デザイナー役を 2 つに分け、プランナーが振り分け、指示役がディスパッチする

デザインの仕事は性質の違う 2 つに分かれる（2026-11-01 オーナー）。

| 役割 | 仕事 | 入力 | 頻度・重さ |
|---|---|---|---|
| デザインシステムのデザイナー役（`design_system`、新設） | コンセプト・デザインの原則・トーン＆マナー・ガイドライン・トークン・部品の一覧・画面の型を考える。足りない部品を足す | PRD／Blueprint、ブランドの方向、既存のアプリ | まれで重い。オンボーディングと、部品の追加 |
| プロダクトデザイナー役（今の `ui_design`。旧称「画面のデザイナー役」） | 既存のデザインシステムから、画面や機能に固有のデザイン（デザインのパッケージ）に落とす | チケット、PRD、`specs/design/`、対象の画面 | よくあって軽い。新しい画面・作り直し |

業界ではデザインシステムやブランドの担当と、プロダクト（機能）のデザイナーを別の職種として置くことが多い。経験の差というより、扱う範囲と成果物が違う。

- プランナーが着手判定（決定 0）と合わせて経路を決める。経路は決まった型から選ぶのではなく、タスクごとに「どの役割をどの順で通すか」の並びとして組む（2026-11-01 オーナー: パターンを固定化せず、タスクに合わせて最適な判断を柔軟に行う）。よくある形は `design_system → ui_design → implement`／`ui_design → implement`／`implement`（デザイナーを通さない）だが例にすぎず、契約のタスクを先に挟む、デザインシステムの部品の追加だけを先に流す、などもプランナーが判断する
- 判断の根拠はログとして残し、後で改善のために見返せるようにする。judge と同じ 3 層（根拠＝読んだもの、解釈＝なぜこの経路か・検討してとらなかった経路とその理由、確信度）に、入力の版（チケット本文・知見・デザインシステムの有無）を添えて、チケットの成果物（Plan）と events に残す。経路ごとの結果（費用・所要時間・承認率・手戻り）と突き合わせ、振り分けの見直しと Learn の入力にする
- 指示役（supervisor）は Plan の経路の並びどおりに次の役割を起動するだけ（判断は持たない。ADR 0011 の D2）
- 「大は小を兼ねる」（全部をデザインシステムのデザイナー役に回す）はとらない。プロダクトデザイナー役は読む範囲を `specs/design/` と対象の画面に絞り、ターン数とモデルの重さを小さくできる。デザインシステムのデザイナー役は重いモデル・多いターンで、まれにだけ動かす
- 役割・経路ごとに 1 件あたりの費用・所要時間・デザイン検査役の承認率・人の選択との一致率を記録し、振り分けの良し悪しを数字で見直す（タスクあたりの所要時間が伸び始める見込みへの備えでもある）
- これに伴い、プランナーは P4 で必須にする。ADR 0025 で仮置きしたプランナーの責務に「着手判定」と「経路の決定」を足す

### 1. デザインの依頼の範囲は、変更の大きさで入口で決める（D1）

開発の進め方（マイルストーンの有無）に依らず、同じ仕組みで流す。依頼の大きさはプランナー（いなければ intake）が仮決めし、理由をレビューページに書く。

| 変更の大きさ | デザインの依頼 | 人の判断 |
|---|---|---|
| 既存画面の小さな改修（項目 1 つ、文言） | なし。実装役が既存の画面定義書と部品で仮決めし、画面定義書も更新する | 出口のキャプチャで違和感の印 |
| 新しい画面 1 枚、既存画面の作り直し | タスク 1 件に依頼 1 件（ライン上） | PO が体験を承認。見た目はデザインシステムで決まり、ブランドに効く画面だけデザインのチーフへ |
| 複数画面にまたがる新機能 | まとめて依頼 1 件。体験の承認後に実装のタスクに切る | PO が体験を承認、デザインのチーフが見た目の 2〜3 案から選ぶ |
| プロダクトの開始時 | オンボーディングのタスクとしてデザインシステムを作る（ADR 0025 E2） | コンセプトとトーン＆マナーを選ぶ |

### 2. プロダクトごとの「デザインの型」

どこまでデザインの工程を厚くするかは、製品に求められる水準と組織の体制で決まる。オンボーディングで最初に選ぶこともできるが、決めなくてよい。決めなければ着手判定の問いへの答えから既定として溜まる（0）。

| デザインの型 | オンボーディング | 以後の依頼 |
|---|---|---|
| `business`（業務システム型。デザイン性はあまり要らない） | 既成の部品集をそのまま採用。コンセプトとトーン＆マナーは最小限 | 見た目の判断は出さない。PO が体験だけ承認 |
| `existing`（デザインシステムあり） | 組織の既存のデザインシステムを取り込む | タスク単位でデザインを実装と同時に進める |
| `from_scratch`（デザインの知見がない） | 工場がコンセプトから一緒に考え、デザインシステムを作る | できた後は `existing` と同じ |

### 3. 人に渡す材料は UI のレビュー依頼（D2。2026-11-01 見直し）

デザイナー役の成果物を、コードの PR の説明と同じ型の「UI のレビュー依頼」にする。上から読めば判断できる順に並べ、画像 1 枚だけを出さない。
日本の受託でよく使う画面定義書の様式にはこだわらない（オーナー: サービス企業ではカンプ＋項目定義＋UI プロトタイプを渡すのがふつう。要はレビューに要る情報へ素早く届くこと）。

本文（レビューページの並び）:

| 見出し | 中身 |
|---|---|
| 概要 | 何の画面を、どうするか（1〜2 文） |
| 背景 | PRD の要約: 誰が何を達成したいか、達成した状態、範囲（PRD 本体へのリンク） |
| 変更点 | 画面ごとに新しい画面か変える画面か、今と変えた後 |
| 判断してほしいこと | 体験の案（PO）と見た目の案（デザインのチーフ）、推す案と理由、PRD の要求との対応、とらなかった案 |
| 画面の流れ | ユーザーフローと、推す案のコマ（続く画面・主な状態のカンプ）。プロトタイプの画像版 |
| 項目定義と振る舞い | 画面ごとの項目定義の表（項目・部品・中身・データの出どころ・必須・備考）と振る舞いの表（どこを・操作・条件・結果）、画面遷移、そのほか（マイクロインタラクション・文言・アクセシビリティ・計測・契約への要求。あるものだけ） |
| 迷った点と未決 | 決めきれなかった点と仮の値、特に見てほしいこと |
| デザイン検査役が確かめたこと | 検査役の判断と指摘 |

正本は製品リポジトリの `specs/ux/` に YAML で置き（ADR 0025 E5）、レビューページはそこから生成する。項目の形は `definitions/ui_design.yaml` の `package`。
小さな改修では変わる行だけを書く。

動くプロトタイプ（デザイナー役の HTML を操作できる形）は画像版のあとに足す。どちらも費用（コマの数・プロトタイプの有無と、その回の費用・ターン・トークン）を `ui_design.drafted` に残し、トークン効率を見て続けるか外すかをオーナーが決める。

### 4. 実装は体験の承認で始め、見た目は並行で追従する（D3）

PO がワイヤーフレームと画面定義書（要素と振る舞い）を承認した時点で、実装のタスクに切って投入する。画面定義書が各タスクの受け入れ条件になる。
見た目はデザインのチーフが並行して選び、デザインシステムのトークンと部品の差し替えで画面が追従する。ADR 0025 E1（要素と振る舞いは実装の前、見た目の細部は後追い）を、承認を 2 つに分ける形で具体化する。

### 5. 判断の場所は工場のレビューページ（D4）

- 工場がデザインのパッケージごとにレビューページを作り、正本にする。承認・直し（コメントつき）・案の選択・違和感の印はページから戻せる
- 連絡ツールにはページのリンクを担当のメンションつきで流し、連絡ツール側からも承認・直しを戻せるようにする（ツールが対応していれば）
- Figma などの外部サービスへの共有は将来のオプション（レビューページを正本のまま書き出す）
- 操業コンソールの選択カード（#106）は、判断待ちの件数と滞留時間の表示に縮め、選ぶ操作はレビューページに移す

### 6. 判断する人は役割で分ける（D5）

- プロダクトオーナー: 体験（PRD・ユーザーフロー・ワイヤーフレーム・画面定義書）
- デザインのチーフ: 見た目（案の選択、ブランドに効く画面）
- 担当者と連絡先は Blueprint に書く。Gen1 は両方オーナー

### 7. 工程のつなぎはイベント駆動のプッシュ（D6）

- 工程の完了イベントで、次の担当（人でも工場の役割でも）に依頼をプッシュする。PRD ができた→デザイナー役、デザイン検査役が通した→PO とチーフ、PO が承認した→実装のタスクに切って投入、直しが付いた→デザイナー役が作り直して同じページを更新し再通知
- 待ち時間を記録し、一定時間で再通知、さらに経過で代理へ切り替える。判断待ちの滞留を SLI にする
- プッシュを受ける環境がまだない場合のため、操業コンソールに受信トレイを置く（トップに通知アイコンとバッジ、人が対応するタスクの一覧）
- 通知先は工場の建設時のオプションにする（受信トレイは常にある）。Gen1 は Claude アプリで回し、Slack はオーナーの個人のワークスペースで早めに検証する。Gen2 までに Slack 通知に対応する

### 8. #105・#106 は残して作り替える（D7）

デザイナー役とデザイン検査役は出力をデザインのパッケージに広げる。検査役はパッケージを観点に加える（PRD との対応、画面定義書の節の揃い）。#106 の選択カードは上の 5 のとおり縮める。新しい流れができるまでの間も、今の `factory:design` はそのまま使える。

## ADR 0025 への影響

- プランナーの責務（仮置き）に、着手判定と経路の決定を足す。P4 の必須にする

- E1: 承認を体験（PO）と見た目（デザインのチーフ）に分ける。人に回す条件は、依頼の大きさとデザインの型で決まる
- E4: 類型「見た目と印象」はそのまま。判断する人をデザインのチーフとして記録する
- 「人の選択の画面」は操業コンソールではなくレビューページに置く

## 進め方

0. プランナー（最小）: 着手判定と経路の決定。clarify の問いの仕組みを使い回し、経路を Plan に残す。指示役は経路どおりにディスパッチ
0b. デザインシステムのデザイナー役（`design_system`）。経路ごとの費用・時間の記録
1. レビューページと受信トレイ（Engine）。まず Claude アプリへの通知で回す
2. デザイナー役の出力をデザインのパッケージに広げる（画面定義書の型を `definitions/` に置く）
3. Blueprint にデザインの型と判断する人を足す
4. Slack 通知の検証（オーナーの個人のワークスペース。秘密情報はリポジトリに置かない）
5. 製品のタスク 1 件でパッケージ → レビューページ → 承認 → 実装を一巡する

## 結果

- 判断する人は、背景と振る舞いを含めた材料を、普段使う連絡ツールから開いて判断できる
- 体験の承認で実装が始まるので、見た目の判断が実装の待ちにならない
- 製品と組織ごとにデザインの工程の厚さを選べる。業務システムでは見た目の判断が出ない
- 工程の状態（判断待ち・通知済み・再通知）が増える。状態は制御プレーンに置く（ADR 0020）
