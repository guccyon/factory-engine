# ADR 0009: 操業コンソールと、工場側のチケット（優先度・割り込み・操業 API）

- 状態: 承認（2026-10-28 オーナー。スレッド「工場の使い方と仕様を確かめる」で 5 点を選択）
- 関係: ADR 0003（制御プレーン）、ADR 0004（supervisor の依存順の投入）、ADR 0005（停止の記録）、ADR 0006（モード）。仕様の検討資料は建設者の手元の 50_build-work/strategy/2026-10-28_factory-console-spec.html、ケイパビリティ台帳の節 O

## 文脈

工場に入れたチケットが、いまどこで何を待っているかを見る方法がなかった。順番待ちは GitHub のラベル（`factory:planned`）と制御プレーンの `jobs` の 2 か所に分かれ、並びは「Issue を作った順」と「受け付けた順」で固定だった。
急ぎのチケットを先に流すには `factory:implement` を直付けして同時実行の上限を迂回するしかなく、障害の調査や hotfix のために作業中のものを止めて割り込む手段もなかった。
停止・やり直し・モードの切り替えは Mac 上の `factoryctl` からしかできず、Mac に入れる建設者しか操作できない。
事業化して顧客に工場を提供するときは、工場の状況を見て操作するアプリ（モバイルか Web）が要る（オーナー）。

## 決定

1. **チケットを工場側で抽象化し、制御プレーンに持つ**（オーナー: 案 A）。表 `tickets`（入口のサービス・その中の識別子・対象の製品・題名・優先度・保留・依存）を足す。GitHub Issue は入口の 1 つにすぎず、Jira・Redmine・Backlog などもフォームの代わりに受けられるようにする。優先度・保留・順番の正本は `tickets` で、入口のラベルは最初の値を渡すだけ。人がコンソールや factoryctl で変えた値は入口のラベルで上書きしない
2. **割り込みを許す**（オーナー: 案 B。障害の調査や hotfix では作業中のものを止めてでも先にやりたい）。最上位の段（p0）のジョブが待っていて枠が空いていなければ、dispatcher が優先度の低い作業中のジョブ（実装と要求の確認だけ。検査・判定は短いので止めない）を止め、順番待ちに戻す。`claude -p` は途中から再開できないので、止めた時点までの作業は捨てて最初からやり直す。捨てた時間と費用は `job.preempted` に残し、割り込みが本当に要る頻度を測る
3. **優先度は内部では 0〜100 の数で持ち、ラベルは 4 段から始める**（オーナー）。p0 緊急（100。割り込む）／ p1 急ぎ（75）／ p2 通常（50。既定）／ p3 後回し（25）。キューは優先度の高い順、同じなら受け付けた順に取り出す。依存順の投入（supervisor）も優先度の高い順にし、p0 は同時に流す上限を待たない。保留中のチケットは取り出さない
4. **操業コンソールは工場のほかのプロセスと同じく独立したコンテナで動かす**（オーナー: 案 A）。制御プレーンだけを読み書きし、GitHub にも外部の CDN にも触らない。閉じた網・オンプレミスでも動かせるようにするため。Gen1 の既定は Mac の中だけで開く（`127.0.0.1:8790`）。外から見るときは閉じた網を足し、開いてよいホスト名を設定に入れる
5. **API を先に固め、画面は簡易に作る**（オーナー: 案 A。商用ではちゃんと体験設計から作る）。操業 API（JSON）が見る・操作するの正本で、Gen1 の画面はその利用者の 1 つ。将来の顧客向けアプリも同じ API の上に載せる。操作（優先度・保留・停止・割り込み）は `ops.py` の同じ関数を通り、コンソール・factoryctl・入口のラベル・dispatcher で振る舞いを変えない。すべての操作は events に「誰が・何を・なぜ」で残し、介入件数（健康指標）に入る

## 段階

1. 見る: ライン（依存待ち・投入待ち・順番待ち・作業中・検査と判定・人の出番・今日の済み）と工場の状態（工場長の生存、モード、作業中の数、今日の費用、開いている停止）。**この ADR で実装**
2. 順番の操作: 優先度・保留・再開。**実装**
3. 止める操作: 停止・割り込み（p0）。**実装**。ラインそのものの停止とモードの切り替えは次
4. 人の出番に答える: 差し戻しの提案を流す、判断待ちに答える、承認する（いまは GitHub のラベルの付け替え）
5. 作業中の途中報告: ワーカーから経過（ターン数・費用・最後の動き）を送る
6. 入口の抽象化の仕上げ: ワーカーが GitHub の Issue ではなく `tickets` から本文を受け取る。Jira などの入口を足すのはこのあと

## 守り

- コンソールは開いてよいホスト名だけを受ける（DNS rebinding）。操作は、起動ごとに作って画面に埋めた合言葉のヘッダーがあるときだけ受ける（ほかのサイトからの CSRF）
- Gen1 はログインがない。外に出すときはログインと、役割ごとの見えるもの・できる操作の分け（運用主・要求者）を API 側に先に入れる
- 入口のラベルは数を決めるだけで、シェルにもプロンプトにも渡さない

## 選ばなかった案

- **GitHub を正本にする（優先度もラベルで表す）**: 早く作れるが、GitHub を知らない利用者や GitHub 以外の入口に広げられない。順位の入れ替えや保留はラベルでは表しにくい
- **割り込みは「次の枠を取る」だけにする**: 障害の調査や hotfix を待たせることになる。止めて捨てる費用は記録して見える化する
- **最初からインターネットに出してログインを付ける**: Gen1 の利用者は建設者と オーナー だけ。操作で工場を止めたり費用を使ったりできるので、外に出すなら権限の分けまで要る
- **画面を rally の管理画面と同じ技術で作り込む**: Gen1 の目的はどの情報と操作が要るかを見極めること。Gen2 に残るのは API の形

## 結果

- 順番待ちと作業中が 1 画面で見え、ブラウザから優先度・保留・停止を操作できる。factoryctl にも同じ操作（`tickets` / `priority` / `hold` / `resume`）を足す
- 既存の DB には `postgres/init/003_tickets.sql` を `psql -f` で当てる（冪等）。それまでに積まれたジョブは優先度 50（通常）として扱う
- 割り込みの頻度・捨てた時間と費用、人の操作の回数を events から集計できる。割り込みが多すぎれば、段の数か割り込む条件を見直す
- 入口のラベルの変化は、ジョブに受け付けた後には拾わない（実装の Issue はラベルが外れるため）。受け付けた後の優先度の変更はコンソールか factoryctl で行う
