# ADR 0046: 工場の事故を記録として貯め、調査委員会が横断で見回る

- 状態: 提案
- 関係: ADR 0005（停止の記録）、ADR 0011（工場が止まったときに起こす）、ADR 0023（学習の体系と事例型の分析役）、ADR 0024（知見と委員会）、ADR 0027（工程の信号）、ADR 0028（夜間の探索）、ADR 0038（チケットごとの上限）、ADR 0040（知見の作用先）、factory-engine #308（工場の中のエラーに気づけない）
- 検討の記録: 事業部の仕様の置き場（05_specs）の 09（事故の記録と調査委員会、叩き台 0.1）

## 文脈

工場の大きな事故は、これまで事故ごとに直してきた。直すときに、その事故専用の検出や自動の処理を足すこともあった（例: CHANGELOG だけの衝突を機械で解く処理 #148、同じ担保を起票しない判定 #337）。

オーナーの指摘（2026-11-10）:

- 事故のたびに専用のチェック処理を足していくと、工場は太り続ける。原因を直したので再発しにくいのに、チェックだけが残り続ける
- それより、大事故を記録として貯め、調査委員会が定期的に・探索的に、事業所を横断して見回るほうがよい。貯まった事故の事実で見回りの観点が増え、探索の力が上がる。工場は太らない
- 記録は運用データだが、製品ごとの情報を取り除いて抽象化し、商用化した後はすべての提供先の工場に配れるようにしたい。脆弱性の CVE のような扱いで、工場の共有財産にする

これまでの大きな事故を並べると、型が少数に集まる。静かな停止（止まったことに気づかない）が 3 件、自己帰還（工程の出力が同じ工程の入力に戻る）が 2 件、取り合い（同じファイル・番号を並列で奪い合う）が 2 件、ほかに循環待ち・土台・取りこぼし・過剰な人回しが 1 件ずつ（下の「最初の記録」）。型で見れば、事故ごとの専用のチェックより、型ごとの見回りの観点のほうが少ない数で広く効く。

## 決定（案）

### 1. 言葉

- **事故**: 工場そのものの振る舞いが原因で、費用・時間・成果物に大きな損が出た出来事。製品の利用者に起きる「障害（Incident、S1〜S4、ADR 0043 の O5）」とは分ける
- **事故の台帳**: その工場の中だけに置く、事故の生の事実
- **事故記録（FIR、Factory Incident Record）**: 台帳から製品の情報を抜いて抽象化した記録。配れる。id は `FIR-YYYY-NNNN`
- **事故の型**・**見回りの観点**・**兆し**・**調査委員会**: 下のとおり。ADR 0024 の委員会（製品の知見の審査）とは別の組

### 2. 事故記録の形

`definitions/incident.yaml` に形を置き、`incidents/FIR-YYYY-NNNN.yaml` に 1 件 1 ファイルで置く。作法は ADR 0024 の知見に揃える（消さずに状態を変える。draft → published → revised / withdrawn。id は再利用しない。足すときは同じ型の既存の記録への影響を添えた変更セットにする）。

項目: id、題、状態、公開の月、型（主と副）、影響の帯、影響を受ける Engine の部品と版の範囲と使い方の条件（`affects`）、外から見える症状、仕組み（なぜなぜの要約）、正規化した影響（1 日の予算の枠に対する倍率・消費に占めた割合・止まった時間・誰が気づいたか）、見回りの観点、直し（直した版・原因の直し・一般の歯止め・専用のチェックと見直しの期日・その場の手当て）、関係する ADR、再発、台帳の id（配るときに必ず空にする）。

`affects` の版の範囲と `mitigation.fixed_in` を持たせるのは、記録を受け取った工場が「自分は当たるか」を決定論で判定できるようにするため（CVE の影響を受ける版にあたる）。

### 3. 事故の型と影響の帯

最初の型は 8 つ: 暴走（`unbounded_repeat`）、自己帰還（`self_feedback`）、取り合い（`contention`）、循環待ち（`circular_wait`）、静かな停止（`silent_stall`）、取りこぼし（`lost_work`）、過剰な人回し（`over_escalation`）、土台（`host_env`）。見回りの観点は型ごとに持つ。型を増やすのは調査委員会の議決とオーナーの承認。

影響の帯（仮置き）: critical（秘密・個人情報・権限の漏れ、本番の利用者に工場の失敗が届いた）、high（1 日の予算の枠を超えた、ラインが 12 時間以上止まった）、medium（枠の 50% 以上を事故の処理が使った、6 時間以上止まった、同じ処理が 20 回以上くり返した）、low（届かないが人が手で解いた）。medium 以上を事故として FIR にし、low は台帳だけに残して型の再発として数える。

### 4. 置き場

| もの | 置き場 |
|---|---|
| 事故の台帳 | 工場の制御プレーンの DB（`incident_case`）と events（`fincident.*`）。利用者の情報を含むときは ADR 0024 の制限付きの保管先 |
| 事故記録（FIR） | Gen1 は本リポジトリの `incidents/`（抽象化済みなので public に置いてよい）。Engine の版に乗って配られる |
| 製品の知見（K） | 製品のリポジトリ（ADR 0024 のまま）。事故から製品の学びが出たら、製品の知見として ADR 0024 の流れに渡す |

ADR 0040 の業務のツリーに `govern.patrol`（見回り）と `govern.incident_review`（調査と記録）を足し、事故記録はこの業務にだけ渡す。ラインのワーカー（実装・デザイン・検査）には渡さない。ワーカーを守るのは原因の直しと一般の歯止めで、文脈ではない。

### 5. 太らせない決まり

1. 事故ごとの専用のチェック処理は、原則として足さない。直すのは原因で、増やすのは記録と観点（データ）
2. 足してよい歯止めは、ひとつの型の事故をまとめて止める一般の歯止め（ADR 0038 の上限、ADR 0005 の番人など）だけ。新しい一般の歯止めは ADR でオーナーの承認
3. 専用のチェックがどうしても要るときは、FIR の `dedicated_checks` に名前と見直しの期日（既定 90 日）を書く。期日に調査委員会がまだ要るかを見て、要らなければ外す Issue を起票する。今ある専用のチェック（#148 など）も棚卸しして載せる
4. 観点の数は型の数で増え、事故の件数では増えない。同じ型の事故は既存の記録の再発か、観点の例として足す
5. 見回り 1 回に入れる観点は上限つき（仮置き 8 個）。最近・影響の大きい型を重く、長く再発していない型を軽く回して選ぶ
6. 見回りの予算は固定し、観点が増えても増やさない

### 6. 調査委員会

| 役 | すること |
|---|---|
| 見回り役 | 定期に工場の記録（events・停止・費用・PR とジョブ）を事業所を横断して読み、兆しを挙げる。観点 7 割・自由な探索 3 割（仮置き） |
| 調査役 | 兆しをなぜなぜで掘り、事故かどうか・型・影響・既存の記録との重なりを決める。ADR 0023 の事例型の分析役（`case.py`）を流用 |
| 記録役 | 台帳から FIR の下書きを作り、製品の情報を抜く |
| 査読役 | 書いた役とは別のエージェントで、割り出せないか・ほかの工場でも起きうるか・重複していないかを見る |

- Gen1 は見回り＋調査を 1 つのジョブ、記録＋査読を別の 2 つのエージェントにし、決定論の検査（`core-gates/incident_check.py`）を挟む
- 委員会は自分で直さない。Engine の直しは改善 Issue（建設者が直す）、製品の直しは製品の Issue にする
- 動かす枠は ADR 0024 の追記の専用の枠（`GOVERNANCE_PARALLEL`）。ラインを止めても見回りは動く
- 見回り: 日次の軽い見回り（決定論の集計＋安いモデル、上限 $1、JST 5〜6 時）、週次の深い見回り（上限 $10、週の上限のリセットの後）、出来事ごとの調査（1 件 $5）。合計は週 $25 まで。数値は仮置きの運用パラメータで、工場が調整してよい
- 結果（兆しの数、台帳に載せた事故、起票した Issue、公開待ちの FIR）は建設日報と週の報告に出す

### 7. 今ある見回りとの関係

- 停止の番人（ADR 0005）と builder を起こす仕組み（ADR 0011）は速い警報としてそのまま。記録は見回りの入力
- 建設者の毎時の見回り（工場の外の routine）は、生存の確認と知らせに絞る。工場の中の兆しは調査委員会が見る
- 夜間の探索（ADR 0028）は製品を見る。調査委員会は工場を見る。積み方（夜ごとにチャーターを回す、予算の枠を超えたら積まない、一時停止中も流す）は流用し、見回りのチャーターを観点にする
- 工程の信号（ADR 0027）は見回りの決定論の入力。束が事例型の分析に回り、影響が事故の帯に届けば台帳にも載せる

### 8. 製品の情報を取り除く決まり

- 書かない: 製品・リポジトリ・会社・事業主の名前と事業の固有の言葉（役で言い換える）、人の名前・アカウント・メール・ホスト名・IP・個人のパス、Issue・PR・ジョブの番号と URL・コミットのハッシュ、利用者のデータと秘密情報、生の金額・トークン数・件数（比と帯にする）。日付は月まで
- 残す: Engine の部品の名前と版、ADR の番号、業界で共通の規約の名前（「CHANGELOG.md など」）、仕組み・型・観点・直し方
- 守りは 3 重: 決定論の検査（形の検出と、制御プレーンが知っている製品名・リポジトリ名・事業主名の辞書との照合）、査読役、公開のオーナーの承認

### 9. 公開と配る道

- Gen1: FIR の公開（`published` にして既定ブランチに入れる）は 1 件ずつオーナーが承認する。配ると戻せないため。台帳・下書き・Issue の起票までは工場が自分で行う
- Gen2: 提供元が持つ事故記録の配信に分け、Engine とは別の版を持たせる。工場は記録の版を別に固定し、Engine を上げなくても記録が先に届く。届いた工場の見回り役は、まず `affects` と自分の版で当たるかを判定する。提供先の工場からの投稿は、事業主の同意つきで抽象化済みの FIR の下書きだけを送る形にする（別の ADR）
- Gen3: 新しい工場を建てるときの最初の観点の一式にする

## 順番（承認の後）

1. 定義と検査: `definitions/incident.yaml`、`core-gates/incident_check.py`、`incidents/` に上の記録を draft で置く
2. 台帳: 制御プレーンの `incident_case`、events（`fincident.opened` / `fincident.recorded` / `fincident.published`）、factoryctl の一覧・表示・持ち込み
3. 見回り: supervisor の見回りのステップ（夜間の探索と同じ形で日次と週次を積む）、観点の選び方、兆しを受信トレイと日報に
4. 調査と記録: 兆し → 調査 → 台帳 → Engine の Issue → FIR の下書きの PR → 査読 → オーナーの承認
5. 専用のチェックの棚卸しと見直しの期日
6. Gen2 の配信と投稿の道（別の ADR）

## 選ばなかった案

- **事故ごとに専用のチェックを足し続ける**: 工場が太り、原因を直した後もチェックが残る
- **事故記録を製品の知見（K）に混ぜる**: 製品のリポジトリに工場の失敗が残り、製品を別の組織に移すときに要らないものが付いていく。ほかの工場にも配れない
- **事故記録をラインのワーカーに渡す**: ワーカーの文脈が太る
- **見回りを決定論だけにする**: 既知の型しか見つからない。未知の事故を探す自由な探索の分を残す
- **ADR 0024 の 4 役の委員会をそのまま使う**: 製品の知見の審査と工場の事故の調査は、見るもの・置き場・配り先が違う。役も重い
