# ADR 0038: プランナーがワークフローと上限を宣言し、指示役がガードレールとして守らせる

- 状態: 承認（2026-11-06 オーナー。W1〜W7 は推奨どおり。W4 に、衝突は着手の判断で避け、ほぼすべてのタスクが触るものは Learn ループで仕組みとして解く、を足した（決定 4b））
- 関係: ADR 0004（supervisor は判断を持たない）、ADR 0012（出荷の列車）、ADR 0013・0023（Learn ループ・学習の体系）、ADR 0014（検査役の承認）、ADR 0016・0017（続きのジョブ）、ADR 0025・0026（プランナーの責務と着手判定）、ADR 0027（衝突の回避と工程の信号）、ADR 0028（QA と触れる環境）、ADR 0029（流量の宣言）、ADR 0036（大きさの見積もりと切る基準）、ADR 0037（単発の依頼の道）、factory-engine#241（上流の要件とストーリー）・#242（QA 役）、`definitions/planner.yaml`、`orchestrator/dispatcher/supervisor.py`・`continuation.py`

## 文脈

オーナーの指摘（2026-11-06、#241 のスレッド）:

- プランナーの重要な責務は、タスクをどう進めるか、どの役に回すかのワークフローを決めること。ワークフローを決めるとは、タスクを実行するループの中の各ステップを実行するか飛ばすか、流れの最後まで行ったら後続のループ（Learn・出荷）に回すか、までを含む
- 各ステップの側だけの判断に任せると、無限ループで余分にトークンを使う。過去に、衝突をひたすら直し続けたことがあった
- どこを厚めに動かすか、上限をどこまでにするかもプランに含める。その計画に基づいて、指示役（supervisor）がガードレールを守らせる

今のプランナー（`planner.yaml`）が決めているのは、ループの入口の一部だけである。

| 決めていること | 決めていないこと（今は固定か、各ステップが自分で決める） |
|---|---|
| 着手の可否（`ready`・`ask`・`escalate`・`split`） | 検査役・judge・QA・出荷・Learn を通すか |
| 上流の役の経路（`design_system`・`ui_design`・`implement`） | どこを厚くするか（`effort` は記録だけで、何にも効いていない） |
| 役ごとの手間の見込み（`effort`）と大きさ（`size`） | ステップごとのターン・費用・繰り返しの上限 |
| 切るかどうか（ADR 0036） | 流れの終わりにどのループへ渡すか |

上限は今、工場の全体で 1 つの値を環境変数で持っていて、チケットの中身を見ない。

| 上限 | 今の値 | 問題 |
|---|---|---|
| 実装のターン | `MAX_TURNS`（全ジョブ同じ） | 小さな直しも大きな機能も同じ上限。途中終了は 1 回だけ続ける（ADR 0036 の 6） |
| CI 落ち・検査の指摘の直し | PR ごとに `CONTINUE_MAX`（2）回 | 種類ごとに数えるだけで、チケット全体の合計がない |
| 衝突の解消 | head ごとに 1 回（ADR 0016） | **回数の上限がない**。既定ブランチが進むたびに 1 回ずつ積めるので、同時に流れる PR が多いと何十回でも回る |
| 1 ジョブの費用 | `TOKEN_BUDGET_PER_JOB` を超えたら印だけ | 止めない。チケット全体の費用の上限はない |
| 1 日の費用 | 枠の上限で投入を止める | 止まるのは枠を使い切った後で、どのチケットが使ったかは見ない |

2026-11-02 には、1 日の費用 $1,772 のうち $1,420（345 回）が衝突の解消だった（ADR 0027）。CHANGELOG の断片化で衝突の大半は消えたが、「直し続けることを止める仕組み」がないことは変わっていない。原因を消しても、別の共有ファイル（画面の一覧・契約・生成した型）で同じことが起きうる。

ADR 0037 で、プランナーは依頼ごとに道（チケット化・ラインに直接・決定論の操作・小さな LLM の仕事・分析役の報告）を選ぶようになった。道を選ぶのが「どのループに入れるか」なら、本 ADR は「そのループの中をどう回すか」を決める。

## 決定

### 1. プランナーの出力を、役の経路からワークフローの宣言に広げる

Plan に `workflow` を足す。今の `steps`（上流の役の経路）は `workflow` の一部になる。

```yaml
workflow:
  path: ticket                 # ADR 0037 の道。ticket・direct_line・operate・quick・analysis
  steps:
    - {step: ui_design,  run: true,  effort: standard, why: "新しい画面 1 枚。既存の部品で足りる"}
    - {step: implement,  run: true,  effort: deep,     why: "契約と backend にまたがる。ここを厚く"}
    - {step: checks,     run: true}                      # 飛ばせない（決定 3）
    - {step: inspect,    run: true,  effort: light,    why: "画面の変更が小さい。観点は振る舞いだけ"}
    - {step: judge,      run: auto}                      # 仮決めか指摘があれば動く（決定 3）
    - {step: qa,         run: true,  scope: ["stories/coach-bulk-holiday.yaml"], why: "ストーリーの『増やす』に当たる"}
  caps:                                                    # 決定 4。宣言しない欄は既定値
    implement: {turns: 60, cost_usd: 8}
    retries:   {conflict: 3, ci_fix: 2, review_fix: 2, continue: 1, qa_rerun: 1}
    ticket:    {cost_usd: 15}
  handoff:                                                 # 決定 5
    ship: train                # train・none・expedite
    learn: signals             # signals・case_review
  basis: "似た過去のチケット #886（M、42 ターン、$5.1）。衝突しやすい screens.ts に触る"
```

- ステップの一覧（カタログ）は `definitions/workflow.yaml` に宣言する: 上流の役（`design_system`・`ui_design`、#241 で入る要件とストーリーの役）・`implement`・`checks`（CI と決定論のゲート）・`inspect`（検査役）・`judge`・`qa`（#242）・`merge`・`ship`・`learn`。役を足すときはカタログに足す
- ステップごとに `run`（`true`・`false`・`auto`）と、その理由（`why`）を書く。飛ばしたステップも理由を残す（後で突き合わせるため）
- 道ごとに、ステップのひな形を持つ（決定 6）。プランナーはひな形から、要らないステップを飛ばし、厚みと上限を決める。ひな形にないステップは足せない
- 宣言の根拠は今の着手判定と同じく 3 層（根拠・解釈・確信度）で残す。宣言は `plan.decided` に入り、`factoryctl plan show` で見える

### 2. どこを厚くするかを、ステップごとの `effort` で宣言し、実際に効かせる

今の `effort`（`light`・`standard`・`deep`）は記録だけだった。これを、ステップごとに何が変わるかの表で効かせる（`workflow.yaml` の `efforts`）。

| ステップ | `light` | `standard` | `deep` |
|---|---|---|---|
| 上流の役 | 既存の画面・部品に倣う 1 案 | 2 案 | 3 案、ゼロから考える |
| `implement` | ターン帯 S、tier-small も可 | 帯 M | 帯 L、tier-large |
| `inspect` | 変更種別に当たる観点だけ | 今の観点すべて | 観点すべて＋差分の外の影響（呼び出し元・契約の利用者） |
| `qa` | 宣言したストーリーの主な流れだけ | 宣言したストーリーの全歩 | 関係するストーリー全部と観点すべて（flow・authz・persistence・words） |

- 厚みはモデルの大きさ（tier）とターンの既定値と観点の範囲を変える。費用が増えるので、`deep` を付けたら理由を必ず書く
- 迷ったら `standard`。プランナーは「作業の量とトークンの量が小さい経路を選ぶ」（今の規則）をワークフロー全体に広げて当てる

### 3. 飛ばせないステップは、固定の規則で決める

安全のためのステップは、プランナーの宣言で飛ばせない。dispatcher の決定論の守り（guards）が、飛ばす宣言を見つけたら `run: true` に戻し、印（`mandatory_skip`）を残す。

| ステップ | 規則 | 理由 |
|---|---|---|
| `checks`（CI・決定論のゲート） | 常に動く。飛ばせない、厚みも下げない | 品質の最低線。決定論で安い |
| マージの表（autonomy の matrix・`always_human_approve`・`phase_grants`） | 常に当てる | 破壊的なスキーマ変更・決済・秘密・権限は人の承認（ADR 0004） |
| 出荷の承認（prod） | 常に人の承認ボタン | 取り返しがつかない（ADR 0012） |
| `inspect`（検査役） | コードを変える PR では飛ばせない。厚みは `light` まで下げてよい。差分が `docs` と `changelog.d/` だけなら飛ばせる | マージの前提が検査役の承認（ADR 0014） |
| `judge` | 仮決め（Question 成果物）か検査の指摘があれば必ず動く（`auto`）。なければ動かない | 仮決めを出口で裁く約束（ライン設計の前提） |
| `learn` の信号の記録 | 常に記録する。飛ばせない | 学習器に自分を採点させない（ADR 0013 の 8）。プランナーが「学ばなくてよい」と決められると、自分の外れを隠せる |

- 飛ばしてよいのは、上流の役・`qa`・`ship` の渡し方・`learn` の事例レビューへの追加の回し、の範囲。規則の表は `workflow.yaml` の `mandatory` に持ち、テストで当てる
- 規則の追加・緩めはオーナーの承認（判断基準の変更）

### 4. 上限をステップごとに宣言し、上限には天井を置く

上限は 3 層で持つ。

| 層 | 誰が決める | 例 |
|---|---|---|
| 天井（`ceilings`） | Engine の定義（`workflow.yaml`）。運用パラメータとして工場が調整してよい | 実装のターン 120、衝突の解消 5 回、1 チケット $30 |
| 既定値（`defaults`） | 大きさの帯（ADR 0036）から決まる | 帯 M なら実装 60 ターン・$8 |
| 宣言 | プランナーがチケットごとに | 「衝突しやすいファイルに触るので衝突の解消は 2 回まで」 |

- プランナーは天井の内側でだけ上限を決められる。天井を超える宣言は天井に切り詰め、印（`cap_clamped`）を残す
- 上限の種類: ステップごとのターンと費用、繰り返し（`conflict`・`ci_fix`・`review_fix`・`continue`（途中終了の続き）・`qa_rerun`・`judge_rounds`）、チケット全体の費用
- 既定値（仮置き）:

| | S | M | L |
|---|---|---|---|
| 実装のターン | 30 | 60 | 90 |
| 実装の費用 | $3 | $8 | $15 |
| チケット全体の費用 | $6 | $15 | $25 |
| 衝突の解消 | 3 回（どの帯も。天井 5） | | |
| CI 落ちの直し・検査の指摘の直し | 2 回ずつ（今の `CONTINUE_MAX`） | | |
| 途中終了の続き | 1 回（ADR 0036 の 6） | | |

- **衝突の解消に、初めて回数の上限が入る**。数えるのはチケットごとの合計（head をまたいで）。今の「head ごとに 1 回」は重複を避ける規則として残す

### 4b. 衝突は、まず着手の判断で避ける。上限は避けきれなかったときの守り

オーナーの方針（2026-11-06）: そもそも衝突しないように、実行中のタスクを見て着手するかどうかを決めるのもプランナーの役割。それでも衝突するときはするので、上限（決定 4）はその守りとして置く。

- **着手の判断**: プランナーは、ワークフローを宣言するときに、実行中のジョブ・開いている工場の PR・待っているタスクが触る（見込みの）ファイルと、このチケットの見込みのファイルを突き合わせる。重なりがあれば、宣言に `start` を書く: `now`（すぐ流す）か `after: [#812]`（そのチケットが閉じるかマージされてから流す）。理由と、重なるファイルを残す。ADR 0027 の 2（よく衝突するファイルの並べ方）を、supervisor の投入の機械的な並べ方から、プランナーの着手の判断に広げる。supervisor は `after` を依存と同じように扱って守らせる（判断はしない）
- **仕組みで解くもの**: CHANGELOG のように、ほぼすべてのタスクが触るファイルは、プランナーの並べ方では解かない（並べるとラインが 1 本になる）。ADR 0027 の 1（変更ごとの断片と、決定論の取りまとめ）のように、製品か工場の作りを変えて衝突そのものをなくす
- **それを見つけて対策まで考えるのは Learn ループ**: 夜のレトロスペクティブ（ADR 0027 の 3）が、衝突の解消（`conflict_fix`）と上限に当たったこと（`cap_hit`）を、ファイルごとに束ねる。触ったタスクの割合が高いファイル（仮置き: 直近 7 日に流したチケットの 30% 以上が触る）は「広く触られるファイル」として、並べ方の改善ではなく、構造の改善（断片化・登録の分割・生成への置き換え）の案を事例型の分析役に必ず出させる。改善の行き先と承認の線は ADR 0027 の表のまま（製品の構造は製品の改善チケット、工場の仕組みはオーナーの承認）
- **プランナーは知見の蓄積を読んで計画する**: プランナーの入力に、製品の知見（`.factory-config/knowledge/` の planner 向けの項目。ADR 0024・0036 の 5）、よく衝突するファイルと広く触られるファイルの一覧、実績の表（ADR 0036 の 4a）、上限に当たった過去の事例（`cap_hit`）を必ず入れる。宣言の `basis` には、どの知見と実績を見たかを書く。同じ外れ（同じファイルで同じ上限に当たる）を繰り返したら、`plan_miss` として数える（決定 8）

### 5. 流れの終わりに、どのループへ渡すかを宣言する

| 渡し先 | 宣言 | 意味 |
|---|---|---|
| 出荷 | `train` | 次の出荷の列車に乗せる（今の既定） |
| | `none` | 出荷しない（工場の内部・文書だけ・試験だけ）。列車の差分に数えない |
| | `expedite` | 列車を待たずに staging に出す提案をする（prod は今までどおり承認ボタン）。障害の直しなど |
| QA | `qa` を `run: true` にしたとき、マージ後に触れる環境でそのストーリーを流す | 今は `factoryctl qa run` で人が積む（#242）。宣言があれば supervisor が積む |
| Learn | `signals` | 信号を記録するだけ（既定。決定 3 で飛ばせない） |
| | `case_review` | 結果にかかわらず、事例型の分析役に回す（新しい種類のタスク、初めての製品の層など、学びたいとき） |
| 単発の依頼 | ADR 0037 の `done.task` | 結果を依頼者に返す。道ごとのひな形が持つ |

### 6. ADR 0037 の道ごとに、ワークフローのひな形を持つ

| 道 | ひな形のステップ | 上限の既定 |
|---|---|---|
| `ticket` | 上流の役 → implement → checks → inspect → judge → merge → qa → ship → learn | 決定 4 の帯 |
| `direct_line` | 既存のチケットの宣言のまま（優先度だけ変える） | 既存の宣言 |
| `operate` | 確認のレベル（ADR 0037 の 4。飛ばせない）→ 実行 → 返す | LLM を通さないので回数だけ（実行 1 回） |
| `quick` | 実行 → 返す | ターン 8・$0.5（ADR 0037 の 5 の目安をこの形の上限にする） |
| `analysis` | 実行 → 数の突き合わせ（「きっちり」のとき飛ばせない）→ 報告書 → 返す | $5（ADR 0037 の 5） |

ADR 0037 の「規模の目安」は、この ADR の上限として dispatcher が守らせる。目安を超えたときの動き（決まったところまで返し、`analysis` への切り替えを提案する）は、上限に当たったときの動き（決定 7）の 1 つとして扱う。

### 7. 指示役は宣言を読み、数えて、上限で止めるだけ

supervisor は判断を持たない（ADR 0004）という形を変えない。宣言を読み、数え、比べ、決まった動きをするだけにする。

- **読む**: 最新の Plan の `workflow`。宣言がない Plan（今の Plan、宣言の前に積んだチケット）は、道のひな形と帯の既定値で動かす（今の動きと同じになる）
- **飛ばす**: `run: false` のステップは積まない。積まなかったことを `workflow.step_skipped` に残す
- **数える**: チケットごとの台帳（ステップごとのターン・費用・繰り返しの回数）を events から決定論で作る（`workflow.usage`）。続きのジョブを積む前と、ジョブを積む前に台帳を見る
- **止める**: 上限に当たったら、そのステップの続きを積まず、上限の種類ごとに決まった動きをする

| 当たった上限 | 動き |
|---|---|
| 衝突の解消 | 同じファイルに触る開いている PR がマージか閉じるまで、このチケットを待ちに入れる（並べて流す。ADR 0027 の 2）。待ちの後の 1 回でも衝突したら人へ（停止 `cap:`） |
| CI・検査の指摘の直し | 人へ（今と同じ） |
| 実装のターン・途中終了の続き | プランナーに戻して残りを切る（ADR 0036 の 6） |
| ステップの費用・チケット全体の費用 | そのチケットの投入を止めて人へ。費用の内訳（どのステップが使ったか）を停止の本文に付ける |
| `quick` の上限 | 決まったところまで返し、`analysis` への切り替えを提案する |

- 上限に当たったことは `workflow.cap_hit`（ステップ・上限の種類・宣言の値・実績）に残し、日報に出す
- 人が上限を上げて続けるときは `factoryctl plan cap <repo>#<issue> <種類>=<値>`（天井の内側）。上げたことも記録する

### 8. 宣言と結果を突き合わせ、プランナーの知見に戻す

- `plan.outcome`（ADR 0036 の 4a）に、ステップごとの宣言と実績（動いたか・ターン・費用・繰り返しの回数・上限に当たったか）を足す
- 外れの判定を足す: `cap_hit`（上限に当たった）、`skipped_miss`（飛ばしたステップの後で、そのステップが見つけるはずの問題が出た。例: QA を飛ばしたチケットに、後で Defect が起票された）、`overprovisioned`（`deep` を付けたが `light` 相当の実績で終わった）
- 工程の信号（ADR 0027 の 3）に `process:cap_hit:<ステップ>:<上限の種類>` を足し、束が閾値を超えたら事例型の分析役に回す。改善の行き先と承認の線は ADR 0027 の表のまま（既定値・天井の値は運用パラメータ、規則とプロンプトはオーナー）
- プランナーの評価セット（ADR 0036 の 4b）の正解に、ワークフロー（飛ばすステップ、厚くするステップ）を足す

## 決めどころ（2026-11-06 オーナー承認。W4 以外は推奨どおり）

| # | 問い | 推奨 |
|---|---|---|
| W1 | プランナーが決める範囲 | 上流の役だけでなく、ループの中のステップ（検査・judge・QA・出荷・Learn）の実行と飛ばし、厚み、上限、後続のループへの渡し方まで（決定 1・2・5） |
| W2 | 飛ばせないステップ | `checks`・マージの表・prod の承認・Learn の信号の記録は常に。検査役はコードの PR で飛ばせず `light` まで。judge は仮決めか指摘があれば必ず（決定 3） |
| W3 | 上限の層 | 天井（Engine）・既定値（帯）・宣言（プランナー）の 3 層。プランナーは天井の内側だけ。天井と既定値の値は運用パラメータとして工場が調整してよい（決定 4） |
| W4 | 衝突の解消の上限 | 推奨どおり。チケットごとの合計で 3 回（天井 5）。当たったら並べて待ち、待ちの後の 1 回でも衝突したら人へ（決定 4・7）。加えて（オーナー）: 衝突はまずプランナーが実行中のタスクを見た着手の判断で避ける。ほぼすべてのタスクが触るものは仕組みで解き、Learn ループのレトロスペクティブで分析と対策まで考える。プランナーは知見の蓄積を把握して計画する（決定 4b） |
| W5 | 上限に当たったときの動き | 種類ごとに決まった動き（決定 7）。費用の上限は人へ、ターンはプランナーに戻して切る |
| W6 | `effort` を効かせるか | 効かせる。ステップごとの表でモデルの大きさ・ターン・観点の範囲を変える（決定 2）。`deep` は理由が必須 |
| W7 | 入れ方 | まず記録だけ（宣言を出させて、守らせたらどうなったかを日報に出す）を 1 週。次に上限、最後に飛ばし（順番） |

## 順番

1. `definitions/workflow.yaml`（カタログ・飛ばせない規則・天井・既定値・道のひな形・厚みの表）と、Plan の `workflow` の形、guards（`mandatory_skip`・`cap_clamped`）。プランナーのプロンプトに宣言を出させ、実行中のタスクの見込みのファイルと知見を入力に入れる（決定 4b の `start`）。**守らせず記録だけ**: supervisor は「宣言どおりなら何を飛ばし、どこで止めたか」を `workflow.shadow` に残し、日報に出す
2. チケットごとの台帳（`workflow.usage`）と上限の守り。最初に衝突の解消の回数（効き目が最も大きい）、次に費用とターン。`factoryctl plan cap`。`start: after` の守り
2b. レトロスペクティブの「広く触られるファイル」の束と、構造の改善の案（決定 4b）
3. 飛ばしの守り（上流の役・QA・出荷の渡し方）。QA の自動の積み込みは #242 のマージ後
4. 厚みの表を効かせる（モデルの大きさ・ターン・観点の範囲）
5. 突き合わせ（`plan.outcome` の拡張、`cap_hit` の信号、評価セットの正解）

1 は記録だけなので、今のラインの動きを変えない。2 以降は 1 の記録を 1 週見てから入れる。

## 選ばなかった案

- **各ステップが自分の続け方を決める（今の形）**: ステップは自分の失敗しか見ないので、「直せば通る」と判断して続ける。衝突の解消を繰り返したのはこの形だった。ループの外から、チケット全体の予算で見る役が要る
- **上限を工場の全体で 1 つの値にしたまま、値を絞る**: 大きなチケットが不当に止まり、小さなチケットの無駄は残る。チケットの中身を見て決めるのはプランナーの仕事
- **指示役に判断させる（上限に当たったら続けるかを LLM で決める）**: 指示役は判断を持たない（ADR 0004）。判断はプランナー（入口）と judge（出口）に寄せ、指示役は宣言を数えて守らせるだけにする。数えるのが決定論なので、効き目も比べられる
- **プランナーに安全のステップも飛ばせるようにする**: プランナーの見立てが外れたときに、最後の守りがなくなる。安全のステップは固定の規則で、プランナーの宣言の外に置く
- **天井を置かず、プランナーの宣言だけで縛る**: プランナーが大きすぎる上限を宣言したら、無限ループを止められない

## 結果

- 衝突の解消のような繰り返しが、チケットごとの上限で必ず止まる。止まったときは、並べて待つか人に回るかが決まっている
- 費用がチケットの中身に合わせて配られ、`deep` を付けたところに使われる。どこを厚くしたかと、その結果が記録で見える
- プランナーの責務が、入口の判定から、ループ全体の計画へ広がる。プランナーのプロンプトと出力が大きくなり、1 回の判定の費用は少し増える
- 宣言のない Plan はひな形と既定値で動くので、移行の間も今の動きを保つ
- 飛ばした判断の外れ（`skipped_miss`）を数えられるので、飛ばしすぎをプランナーの知見で直せる

## 追記（2026-11-10 オーナー）: 複数の役を通るタスクは必ずプランナーを通す

11/7〜9 の実績では、実装に回った 130 チケットのうち Plan があったのは 10 件だった。プランナーを通さない判断をした役はなく、工場の内部の起票（知見の担保・分析役・差し戻しの直し・デザインシステムの子・CHANGELOG の取りまとめ）が `factory:planned` を直接付けて、プランナーの入口を通らずに投入されていた。

**決定**: 複数の役のワークフロー（実装 → 検査 → judge → マージ → QA …）を経由して成果を出すタスクは、必ずプランナーを通し、ステップ・厚み・モデル・上限を決める。特定の職能への定型の単発の依頼（実際の会社で、実装中のエンジニアがデザイナーに SVG を 1 枚頼むようなもの）は通さなくてよい。

- 守らせるのは指示役（supervisor）。投入の直前に、`factory:planned` のチケットに Plan がなければ、実装に回さず `factory:plan` に付け替える（`plan.rerouted`）。起票する側を全部直さなくても、この 1 か所で必ず通る
- 通さなくてよいもの（単発の依頼の印）: `factory:changelog`（決定論の取りまとめ）、`factory:direct`（1 つの役への定型の依頼）、プランナー自身が切った子（`plan.split` の child・children。親の Plan の下にある）
- モデルの選択は、プランナーの宣言した厚み（`effort`）からモデルの大きさを引く（順番 4）。それまでは Plan の size からの tier の試行（model.routed）が効く
- 指示役は判断を持たない（ADR 0004）。Plan の有無と印を見るだけで、通すかどうかの中身はプランナーが決める
- `PLAN_GATE=0` で止められる（プランナーの費用が予算を圧迫したときの逃げ道）
