# ADR 0040: 知見を作業の入口ごとに効かせる（scope の多段化）

- 状態: 提案（2026-11-07。決めどころ S1〜S8 はオーナーの承認待ち）
- 関係: ADR 0013・0023（Learn ループ・学習の体系）、ADR 0024（知見の蓄積と委員会。本 ADR は決定 2 の scope と決定 7 の渡し方を広げる）、ADR 0030（事業部の窓口）、ADR 0037（単発の依頼の道）、ADR 0038（プランナーのワークフローの宣言。ステップのカタログ）、ADR 0039 案（単発の依頼のループ。L6 からの切り出し）、`definitions/knowledge.yaml`、`definitions/workflow.yaml`、`core-gates/knowledge_context.py`・`knowledge_check.py`

## 文脈

ADR 0039 の L6（外側のループ）の検討で、オーナーが指摘した（2026-11-07）:

- 学びの作用先は、各種作業の入口ごとに違う。今の知見はフラットに持っているのか、作用先が構造化されていて各作業が適切な知見を参照できるのか
- scope を多段構成にしないといけない。同じ役割でも作業の種類によって違う。デザインが要る依頼でも、designer という役割の知見は、ラインでバックログを進めるときの design 作業と、単発の依頼とでは違う
- 知見の構造の見直しは大きな話なので、別に切り出して Learn ループの精度を上げたい

あわせて、振り分け（プランナー）と単発の依頼の実行役の入口にも知見を渡すこと、依頼者ごとの好みは git ではなく制御プレーンの DB に持つことも論点に入れる。
もう 1 つ、Learn ループの入り口の側の課題として、人の違和感の印（`taste_flag`）が印の文面ごとに別の束になり、同じテーマでもまとまらないことも扱う（factory-engine#264 の補足。11-06 の 8 件の印が 7 個の束になった）。

### 今の形（2026-11-07 時点、main 1569a40 と rally の `.factory-config/knowledge/`）

| 項目 | 今 |
|---|---|
| 置き場 | 製品リポの `.factory-config/knowledge/K-NNNN.yaml` にフラットに 1 件 1 ファイル（rally は 10 件）。テーマ（1〜8）と種類は中に持つ |
| scope | `roles`・`contexts`・`paths` の 3 つ。どれも自由な文字列で、語彙の検査はキーの名前だけ |
| 選び手 | `core-gates/knowledge_context.py`。絞り込みに使うのは `roles` だけ。`contexts`・`paths` は表示するだけで、選ぶのには使っていない。テーマ・作業の種類（道）・変更種別は見ない |
| つないでいる入口 | 実装役（`implement`）の 1 つだけ（`worker/entrypoint.sh` が `--role implement` 固定で呼ぶ）。プランナー・単発の依頼の実行役・デザイナー・検査役・judge・QA・窓口には渡っていない |
| 実際に渡っている知見 | **0 件**。rally の 10 件はすべて `confidence: hypothesis` で、渡す条件（confirmed 以上）に届かない。K-0001 は根拠の事例が 4 件あるが、まだ仮説のまま |
| `roles` に書かれている値 | `implement`・`inspect`・`judge`・`body_fix`・`supervisor`。`supervisor` はエージェントではなく dispatcher のコードなので、文脈として渡す先がない（K-0003・K-0004・K-0008 は誰にも届かない） |
| 教師信号の束ね方 | 違和感の印の signature は `taste:<一言の先頭 40 字>`（`dispatcher/choice.py` の `signature`）。言語化の候補に寄せる段がまだなく、文面が違えば別の束になる。どの入口（ラインの画面か、単発の案か）の印かも鍵に入っていない |
| 依頼者ごとの好み | 置き場がない。種類 `preference` はあるが、製品リポ（git）に置く形しかない |

つまり、知見は役割の名前でしか引けず、その役割も実装役しかつながっていない。同じ役割の中で作業の種類が違う（ラインのデザインと単発のデザイン）ことを表す軸も、作用先がエージェントでない（Engine のコードを直すべき）ことを表す印もない。

## 決定（案）

### 1. 作用先を「入口」として工場の定義に一覧で持つ

知見が効く場所を、役割の名前ではなく**入口**で表す。入口は「どのステップ（役）が」×「どの道（作業の種類）で」の組で、工場の定義（`knowledge.yaml` の `entries`）に一覧で持つ。ステップと道の名前は ADR 0038 の `workflow.yaml` の `steps`・`paths` をそのまま使い、ワークフローの外にいる役（プランナー、窓口、本文を直す役など）を足す。

| 入口の例 | 何をするところか |
|---|---|
| `implement@ticket` | ラインでチケットを実装する（今つながっている唯一の入口） |
| `ui_design@ticket` | ラインでバックログの画面をデザインする |
| `ui_design@quick` | 単発の依頼でデザインの案を出す |
| `plan@ticket` | プランナーがチケットの進め方を宣言する |
| `plan@desk` | 振り分け: 単発の依頼の道・対応の種類を選ぶ（ADR 0039 の受付・振り分け） |
| `execute@analysis`・`execute@quick`・`execute@operate` | 単発の依頼の実行役 |
| `inspect@ticket`・`judge@ticket`・`qa@ticket`・`body_fix@ticket` | 検査・裁き・QA・本文の直し |
| `desk@desk` | 窓口の会話（依頼者とのやりとり） |

入口ごとに、選び手に渡せる手がかり（下の 3 段目のうち、その入口で分かるもの）も宣言する。例えば `implement@ticket` は変更種別・コンテキスト・触る見込みのファイルを渡せるが、`plan@desk` はファイルを知らない。

### 2. scope を 3 段にする（だれが・どの仕事で・何について）

| 段 | キー | 値 | 例 |
|---|---|---|---|
| 1 だれが | `steps` | 入口のステップ（`workflow.yaml` の `steps` と、決定 1 で足す役） | `[ui_design]` |
| 2 どの仕事で | `work` | 道（`ticket`・`operate`・`quick`・`analysis`・`desk`） | `[quick]` |
| 3 何について | `change_types`・`contexts`・`files` | 変更種別（`change_type_rules.yaml`）・コンテキスト（製品の `context-map.yaml` の id）・ファイルの glob | `contexts: [booking]` |

- 当てはめは、段どうしは「かつ」、段の中は「または」、空の段は「すべて」。今の知見は 2 段目が空なので、どの道にも効く（今と同じ）
- 3 段目の手がかりを入口が持っていないとき（`plan@desk` にとっての `files` など）は、その段で落とさず、順位を下げるだけにする（ファイルの知見が振り分けにまったく届かないのを避ける）
- 並べ方は、当たった段の数が多い（具体的な）ものを先に、次に確かさ（settled → confirmed）、次に確認日の新しい順。件数と文字数の上限は今のまま（12 件・12000 字、仮置き）で、入口ごとに上書きできる
- 値は語彙で検査する（`knowledge_check.py`）。語彙にない値は CI で落ちる。今の自由な文字列のせいで `implement` と `implementer` が混ざったようなことを防ぐ
- 今の `roles` は `steps` に、`paths` は `files` に読み替える。移し替えの PR までは両方の名前を受け付ける

ラインのデザインと単発のデザインの違いは、`steps: [ui_design]` に `work: [ticket]` か `work: [quick]` を足して書き分ける。デザイン全般の知見は `work` を空にしておけば両方に効く。

### 3. エージェントの文脈に入れない作用先を分ける

知見の中には、エージェントに読ませても直らず、Engine のコードや工場の設定を直すべきものがある（`supervisor` 宛ての K-0003・K-0004・K-0008）。知見に `acts_on` を持たせ、作用の仕方を分ける。

| `acts_on` | 作用の仕方 |
|---|---|
| `context`（既定） | 決定 2 の入口の文脈に渡す |
| `engine` | 文脈には渡さない。週 1 の委員会の定例が、担保（`enforcement`）のない `engine` 宛ての知見を Engine の改善 Issue の候補に出す（工場は起票まで。直すのは建設者） |
| `process` | 文脈には渡さない。役割への指示・ラインの設定の変更の提案として人に回す（ADR 0023 の承認の線） |

### 4. 依頼者ごとの好みは制御プレーンの DB に持つ

特定の依頼者（事業主の担当者）についての好み（「表より箇条書きがよい」「数字は税抜きで」「返事は朝にまとめて」など）は、git に置かない。人に紐づく情報で、リポジトリが public の場合もあるため（ADR 0024 の決定 8 の考え方）。

- 置き場は制御プレーンの DB の `requester_preferences`（依頼者の id・主張・決定 2 と同じ 3 段の scope・確かさ・根拠の events の id・確認日・状態）。製品の事業主全体の好みや Blueprint にあたるものは、今までどおり git の知見か Blueprint に置く
- 確かさは 2 つの出どころで分ける。依頼者が自分で言ったこと（窓口の会話・受け取りの答え）はそのまま確認済み。工場が推し量ったこと（受け取りで直しを求められた傾向など）は仮説で、2 回目に当たるか依頼者が認めたら確認済み
- 委員会には通さない（個人の好みで、作用先はその依頼者の作業だけ）。代わりに、依頼者が窓口（コンソール・MCP）で自分の好みの一覧を見て、直し・消すことができるようにする
- 選び手は、入口が依頼者を知っているとき（`desk@desk`・`plan@desk`・単発の依頼の `execute@*`）に、git の知見と依頼者の好みを合わせて渡す。好みは知見と別の見出しにし、依頼者の言葉と食い違えば Issue と依頼の文面を優先する
- 渡した記録は今の `knowledge.used` と同じく events に残す（id は `P-NNNN` のような不透明な id。中身は events に書かない）

### 5. 選び手をつなぐ入口の順番

入口をつなぐのはワーカーのプロンプトの変更なので、ADR 0024 の決定 7 のとおりオーナーの承認を得てマージする。順番は、学びの材料が先に溜まっていて効き目が見えやすいところから。

1. 選び手を入口と 3 段の scope で選ぶ形にする（`implement@ticket` はそのまま動く。変更種別・コンテキスト・見込みのファイルを手がかりに足す）
2. `plan@ticket`・`plan@desk`（プランナーと振り分け。ADR 0038 の決定 8 の「プランナーの知見に戻す」の受け皿にもなる）
3. 単発の依頼の実行役（`execute@quick`・`execute@analysis`・`execute@operate`）と、依頼者の好み（決定 4）
4. `ui_design@*`・`design_system@*`、`inspect@ticket`・`judge@ticket`・`body_fix@ticket`・`qa@ticket`、`desk@desk`

### 6. 効き目を入口ごとに測り、scope の当たり外れを Learn ループに戻す

Learn ループの精度は「正しい知見が、正しい入口に、正しいときだけ届くか」で決まる。今は渡したかどうか（`knowledge.used`）しか残らないので、入口ごとの当たり外れを信号にする（数えるのは測る側。決定論）。

| 信号 | 決め方 | Learn ループでの扱い |
|---|---|---|
| 届いたのに食い違った | 渡した知見の id が、そのジョブの「## 補足」の食い違いに書かれた | 再確認の候補（今の失効のきっかけ「反証」） |
| 届いたのに差し戻された | 渡した知見に従った作業が、同じ真因で差し戻された | 再確認の候補 |
| 届かなかった | 事例の分析で真因が既存の知見と同じだったのに、その入口には渡っていなかった（scope が狭い、または入口がつながっていない） | 委員会に scope を広げる変更セットを出す |
| 届きすぎ | ある入口で渡し続けているのに、その入口の作業でその知見の id が一度も参照されない・効き目がない状態が続く | 委員会に scope を狭める候補を出す |

- `knowledge.used` に入口（`entry`）と使った手がかりを足す
- 事例型の分析役（`case.py`）が知見の下書きを書くときは、決定 1 の入口の一覧を見せ、`steps`・`work` を必ず書かせる（空のままにするときは「すべての入口に効く」理由を書く）

### 7. 教師信号は「入口 × 観点」で束ねる。文面は材料に残す

知見を入口で引けても、その手前の束ね方が文面ごとだと、同じテーマの信号が 1 件ずつの束に割れ、回数で固める段（反復型）にも事例型の分析にも届かない。束の鍵を文面から切り離す。

- 束の鍵は `<信号の種類>:<入口>:<観点>`。入口は決定 1 の一覧（例 `ui_design@ticket`）。観点は信号の種類ごとに決まった語彙から選ぶ。違和感の印なら `design_guideline.yaml` の節（原則・トーン＆マナー・基礎・部品・画面の型・文言など）とその中の規則の id、検査の指摘なら今までどおり rubric の id
- 観点を付けるのは束ねる段（`learn.py`）。LLM が語彙の中から候補を出してよいが、語彙の外の値は決定論の検査で「未分類」に落とす。人が印を付けるときに言語化の候補から選んだ観点があれば、それを優先する（ADR 0025 の 4、Q-C の「工場が言語化の候補を出し人が選ぶ」）
- 一言の文面・画面・PR は束の材料として残し、事例型の分析役と委員会が読む。文面での寄せ（似た言い方を同じ束にする）はしない。何が同じかを言葉の近さで決めると、決定論で再現できない
- 「未分類」が溜まったら、週 1 の委員会の定例が観点の語彙を足す候補を出す。観点（rubric の観点やデザインの基準）を足すのは人の承認（2026-10-31 の内部品質の決定 Q-A）
- 束から作った知見の scope の 1・2 段目は、束の鍵の入口をそのまま使う。ラインの画面への印から学んだことは `ui_design@ticket` に、単発の案への印から学んだことは `ui_design@quick` に効く

### 8. 置き場のディレクトリはフラットのまま

知見を入口ごとのディレクトリに分けると、複数の入口に効く知見の置き場が決まらない。引き方は scope で持ち、ディレクトリはフラットのままにする（構造は今までどおり委員会がオーナー）。`INDEX.md` に入口ごとの一覧を足し、人が「この入口に何が効くか」を読めるようにする。

## 決めどころ

| # | 問い | 推奨 |
|---|---|---|
| S1 | 作用先を「ステップ×道」の入口で表すか | 表す（決定 1）。ステップと道は ADR 0038 のカタログをそのまま使う |
| S2 | scope の段の分け方 | だれが（`steps`）・どの仕事で（`work`）・何について（`change_types`・`contexts`・`files`）の 3 段（決定 2）。4 段目（依頼者の業種・画面の種類など）は必要が見えてから足す |
| S3 | 手がかりのない段の扱い | 落とさず順位を下げる（決定 2） |
| S4 | Engine 宛て・工程宛ての知見を文脈から外すか | 外し、委員会の定例が改善 Issue の候補にする（決定 3） |
| S5 | 依頼者ごとの好みの置き場と通し方 | 制御プレーンの DB。委員会を通さず、依頼者が見て直せる形（決定 4） |
| S6 | 入口をつなぐ承認の取り方 | この ADR の承認で 1〜4 の順番をまとめて承認とし、各 PR は CI 緑で工場がマージする。入口ごとに承認を取る案もある |
| S7 | 効き目の 4 つの信号を Learn ループに足すか | 足す（決定 6）。「届かなかった」から先に入れる |
| S8 | 教師信号の束ね方 | 文面ではなく「入口 × 観点（決まった語彙）」で束ね、文面は材料に残す。語彙の外は「未分類」にし、語彙を足すのは人の承認（決定 7） |

あわせて、今は渡せる知見が 0 件なので、仮説から確認済みへの上げ方（週 1 の定例の `promote`）が動いていない理由を別に確かめる（K-0001 は事例 4 件で仮説のまま）。これは本 ADR の外の不具合として扱う。

## 順番

1. 定義: `knowledge.yaml` に `entries`（入口の一覧と手がかり）、scope の 3 段、`acts_on`。`knowledge_check.py` の語彙の検査（`roles`・`paths` も移し替えまでは受け付ける）
2. 選び手: `knowledge_context.py` を `--entry` と手がかりで選ぶ形に。`implement@ticket` をつなぎ替え、`knowledge.used` に `entry` を足す
3. rally の既存の 10 件の移し替え（`roles` → `steps`、`supervisor` 宛ては `acts_on: engine`）を変更セットの PR で
4. `plan@ticket`・`plan@desk` をつなぐ
5. 依頼者の好みの DB と、単発の依頼の実行役の入口
6. 残りの入口と、効き目の信号（決定 6）

束ね方（決定 7）は 1 と並行で入れてよい（入口の一覧ができれば、違和感の印の鍵から始められる）。

## 選ばなかった案

- **入口ごとにディレクトリを分ける**: 複数の入口に効く知見を複製するか、どこかに寄せるかを毎回決めることになり、矛盾の元になる（ADR 0024 の変更セットの考え方に反する）
- **役割の名前に作業の種類を混ぜる（`designer_line`・`designer_oneoff` のような値）**: 役割と道の組み合わせの数だけ値が増え、「デザイン全般」を書く方法がなくなる
- **LLM に関係のある知見を選ばせる**: 何が渡ったかが決定論で再現できず、効き目を測れない。選ぶのは決定論のまま（ADR 0024 の決定 7）
- **依頼者の好みも git の知見に置く**: 人に紐づく情報が git の履歴に残り、消せない。依頼者が自分で直せない
- **違和感の印を文面の近さで寄せる（埋め込みの類似度など）**: 何が同じ束かが再現できず、閾値の調整が学習器の自己採点になる。観点の語彙で束ね、語彙は人が足す
- **すべての入口に全部の知見を渡す**: 文脈が太り、関係のない知見が同じ重みで効く（ADR 0024 の選ばなかった案と同じ）

## 結果

- 同じ役割でも、ラインの作業と単発の依頼とで違う知見が効く。プランナーと振り分け、単発の依頼の実行役にも知見が届く
- Engine を直すべき知見が文脈に紛れず、改善 Issue に回る
- 依頼者ごとの好みが git に残らず、依頼者が自分で見て直せる
- 同じテーマの違和感の印が 1 つの束にまとまり、回数で固める段と事例の分析に届く
- 入口ごとの当たり外れが信号になり、Learn ループが scope そのものを直せるようになる
- 入口の一覧という定義が 1 つ増える。ステップや道を足したときに入口の一覧も直す必要がある（`workflow.yaml` との食い違いはテストで見る）
