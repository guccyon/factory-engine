# ADR 0060: 出荷の QA の関門は、変更に関係するシナリオと、しばらく確かめていないシナリオだけを流す

- 状態: 提案（2026-11-14。方針はオーナーが同日に了承: ADR 0054 の決定 7 の「流すシナリオの選び方」を前倒しする。この文書の細部の承認待ち）
- 関係: ADR 0049（出荷の QA の関門）、ADR 0054（版ごとのチケットとシナリオごとのジョブ。決定 7 をこの ADR で決める）、ADR 0055（時刻をまたぐストーリー）、ADR 0038（プランナーの宣言）

## 文脈

ADR 0054 は、最初は毎便すべてのシナリオを流し、ストーリーが 12 本を超えるか費用が増えたら選び方を決める、とした。実際の便（rally、2026-11-14）で、本数や費用より先に時間が足りなくなった。

- 0.22.0 は 8 本（判定 3・探索 1・時刻をまたぐ判定 4）を流し切るのに約 3 時間半かかった（判定は同時に 1 本。iOS のシミュレーターが 1 台）
- 便は 20 分から 1 時間おきに出た（0.21.0 から 0.28.0 まで 8 便）。どの便も 1〜3 本流したところで次の版が出て、関門は打ち切られた
- その結果、新しい形の関門は 1 回も報告まで届いていない。承認に添える QA の報告が出ない

使える材料はすでにある。

- プランナーは、チケットごとに「増やす・変える・守るストーリー」を宣言している（Plan の `stories`。ADR 0038）。直近 3 日の着手の判定 124 件のうち 63 件に宣言がある
- 製品のストーリーは、触るアプリとコンテキストを `touches` に書いている（`touches.apps`・`touches.contexts`）
- 版（Release）は、載せた PR の一覧を持つ（`release.created` の `prs`）
- ストーリーごとの判定は、いつ・どのジョブで出たかが残っている（QAVerdict）

## 決定

### 1. ストーリーごとに「確かめ直しが要るか」を決める

関門を開いたとき、ストーリー 1 本ずつに次の順で当てはめる。最初に当たったものが理由になる。

| 順 | 条件 | 流すか | 理由の記録 |
|---|---|---|---|
| 1 | まだ 1 回も確かめていない | 流す | `never` |
| 2 | 最後に確かめたあとに出た版の PR が、そのストーリーに関係する | 流す | `changed`（PR の番号） |
| 3 | 最後に確かめてから `stale_hours`（24 時間）を超えた | 流す | `stale` |
| 4 | どれでもない | 流さない | `fresh`（最後に確かめた時刻） |

- 「確かめた」は、そのストーリーの判定が pass か hold で出たこと（blocked は確かめられていないので数えない）。出どころは問わない（出荷の関門・QA だけのチケット・手で流した判定）
- 「最後に確かめたあとに出た版」で見るので、打ち切られた関門で流せなかった分は、次の関門に持ち越される。打ち切られた関門で確かめ終えた分は、次の関門でやり直さない
- 3 があるので、関係の読み違いで漏れたストーリーも、1 日以内に必ず確かめ直される

### 2. PR がストーリーに関係するかの決め方

決定的に決める（LLM を使わない）。PR ごとに次の順で見る。

1. **宣言**: その PR のチケットの最新の Plan に `stories` の宣言があれば、そこに書かれたストーリー（増やす・変える・守る）
2. **ファイル**: 宣言がなければ、PR が変えたファイルのパスで決める
   - 利用者の流れに触らないパス（`docs/`・`changelog.d/`・`CHANGELOG.md`・`.md`）は見ない
   - `specs/stories/<id>.yaml` は、そのストーリー
   - パスにコンテキストの名前が入っていれば（`messaging`・`async_lesson` など。`-` と `_` は同じに見る）、`touches.contexts` にそのコンテキストを持つストーリー
   - コンテキストは分からないがアプリの下（`apps/<app>/`）なら、`touches.apps` にそのアプリを持つストーリー
   - どれにも当たらないファイル（配備・共通の土台・依存の更新など）が 1 つでもあれば、**全部のストーリー**
3. PR のファイルを読めなかったときも、全部のストーリー

迷ったら広く取る。狭く取りすぎた分は決定 1 の 3（24 時間）が拾う。

### 3. 流す順と、変えないもの

- 順番は、変更に関係するもの（`changed`・`never`）→ しばらく確かめていないもの（`stale`）。時刻をまたぐストーリーは、選ばれたものだけを今までどおり最後に 1 本ずつ（ADR 0055）
- 探索は毎便 1 本のまま（ストーリーに書いていない食い違いを探す役目なので、選び方に乗せない）
- 判定で流すものが 1 本もなければ、探索だけで報告を作る
- 版のチケットの費用の上限は、選んだ単位から計算する（ADR 0054 の決定 5 のまま）

### 4. 報告と記録

- 計画（`qa.gate_plan`）に、ストーリーごとの選び方を残す（`selection: {<story>: {run, why, prs?, last?}}`）
- 版の Issue の本文と報告に、流さなかったストーリーと理由を書く（「変更に関係なし。11/14 12:02 に確認済み」）。承認者は、何を確かめて何を確かめていないかを報告で見られる
- 切り替えは `definitions/qa.yaml` の `gate.select`（既定は真）。偽にすると毎便すべて流す（ADR 0054 の最初の形）

### 5. 本番の承認の前

本番を立てる段階の製品では、承認に出す版の報告に、流さなかったストーリーが「最後にいつ・どの版で確かめたか」を必ず載せる。承認の前に全部を流し直すことは、この ADR では決めない（rally は本番を立てない段階。全部を流し直す契機は、製品が launch に進むときに決める）。

## 順番

1. この PR: 本 ADR と実装（`dispatcher/qa_select.py`、`qa_gate.py` の計画、`definitions/qa.yaml`）
2. 済の条件: rally の便で、関係するストーリーだけの関門が報告まで届き、版の Issue が閉じる。流さなかったストーリーと理由が報告に載る

## 選ばなかった案

- **便の間隔を QA が終わる長さに空ける**: 出荷を QA の都合で遅らせる。ストーリーが増えるほど間隔が延びる
- **判定を同時に流す本数を増やす**: iOS のシミュレーターが 1 台なので、増やせるのは Web だけ。端末を増やせば効くが、本数に比例して時間と費用が増える形は変わらない（端末を増やしたら `gate.parallel` を上げる。この ADR と両立する）
- **関係するかを LLM に決めさせる**: 関門を開くたびに費用がかかり、同じ入力で答えが変わる。プランナーの宣言という、すでに払った判断を使う
- **「必ず通すシナリオ」を別に指定する**: 指定の手入れが要る。24 時間の決まり（決定 1 の 3）で、全部が毎日 1 回は通る
- **版ごとに全部を流す日を決める（週 1 回など）**: 便が続くと、全部を流す関門が打ち切られて届かない。ストーリーごとに鮮度を見れば、打ち切られても確かめた分が残る

## 結果

- 関門の長さが、ストーリーの総数ではなく、その便の変更の広さで決まる。小さい変更の便は短く終わり、報告まで届く
- 打ち切られた関門の仕事が無駄にならない（確かめた分は次に持ち越さず、確かめていない分だけ持ち越す）
- 全部のストーリーが、少なくとも 24 時間に 1 回は確かめられる
- 宣言のない PR は、ファイルから広めに取る。配備や共通の土台に触る PR が載った便は、全部を流す
- プランナーの宣言の正しさが、QA の範囲に効くようになる。宣言の漏れは 24 時間の決まりで拾うが、その間は見つからない
