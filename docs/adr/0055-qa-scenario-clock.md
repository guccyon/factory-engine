# ADR 0055: QA が staging の時刻を「指定の時刻」に合わせ、画面の時計もそろえ、合わせている間は環境を 1 人で使う

- 状態: 提案（2026-11-13。オーナーは「時刻をまたぐ流れが確かめられないのは直すべき」と判断済み。この文書の細部の承認待ち）
- 関係: ADR 0028（QA 役。P5a の `scenario_time`）、ADR 0049（出荷の QA の関門）、ADR 0054（提案。QA をシナリオごとのジョブに分ける）

## 文脈

出荷の QA の関門（ADR 0049）で、判定の「確かめられなかった（blocked）」が多い。rally 0.17.0 の判定（ジョブ 7652）では 6 本のうち 3 本が blocked で、3 本とも時刻をまたぐ流れだった。

| ストーリー | またぐ時刻 | QA がしたこと | 結果 |
|---|---|---|---|
| `coach-prejoin-check` | 開始 5 分前・開始時刻 | 15 分後に始まる枠を作り、実際の時間で待った | 5 分前になる前にランが終わった |
| `student-prejoin-check` | 同上 | 同上（Web と iOS） | 同上 |
| `student-books-after-first-lesson` | 前提の「完了したレッスン」は開始時刻を過ぎないと作れない | 20〜40 分後の通話を予約して待った | 開始時刻の前にランが終わった |

時計を進める道具（中継の `env_restart`、ADR 0028 の `scenario_time`）はすでにある。それでも使われなかった理由は 3 つ。

1. **道具が「何時間進める」の形で、「翌日・暦月の境」向けに書いてある。** 「この枠の開始 4 分前にする」には、QA が今のサーバーの時刻と進めている量から秒を逆算しないといけない。プロンプトの例も「翌日なら 24」だけ
2. **進むのはサーバーの時計だけで、画面の時計は進まない。** rally の画面は、応答の `Date` ヘッダーからサーバーとのずれを出して「入室できるか」を決めている（rally #1315）。ところが `Date` はサーバーの OS の時計（実際の時刻）で付き、進めた時計（`CLOCK_OFFSET_SECONDS`）を映さない。サーバーだけ進めると、API は「始まっている」、画面は「まだ」と食い違い、流れとして確かめられない
3. **staging は判定と探索が同時に使っている（ADR 0049）。** 時計を進めると再起動で数十秒止まり、探索のジョブからも時刻が飛んで見える。進めてよいかの決まりがない

## 決定

### 1. 道具は「時刻を指定して合わせる」形にする

中継の `env_restart` に次を足す（今の `advance_hours`・`reset_clock` は残す）。

| 引数 | 意味 |
|---|---|
| `set_to` | サーバーの時計をこの時刻（ISO 8601、タイムゾーン付き）に合わせて再起動する。工場が「この時刻 − 依頼したときの実際の時刻」から進める量を出す（再起動の数十秒のぶん、上がったときのサーバーの時刻は少し先になる） |
| `advance_minutes` | 分で進める（`advance_hours` と同じ働き。5 分前・開始時刻など短い幅のため） |

- 進める量は 0 以上（実際の時刻より前には戻さない）。合計の上限（62 日）は今のまま
- 道具の答えに、再起動のあとのサーバーの時刻（製品の時計で測ったもの）と進めている量を返す。QA は返った時刻を見て次の歩を決める
- 新しい読むだけの道具 `env_clock` を足す。サーバーの今の時刻と進めている量を返す（再起動しない）
- サーバーの時刻は、製品の応答の `Date` ヘッダーで測る（決定 2 で製品が進めた時計を映すため）。読めないときは「実際の時刻＋進めている量」で答え、そう書く

### 2. 時計を進められる製品は、画面の時計もサーバーに合わせる（製品の約束）

`.factory-config/ship.yaml` の `touch.clock_env` を宣言する製品は、次を満たす。満たさない製品は、時刻をまたぐストーリーの「画面の歩」を QA が確かめられない。

- サーバーの応答の `Date` ヘッダーを、進めた時計（製品の時計）で付ける。画面に中継する部品（Web の前段）も、この `Date` を書き換えずに渡す
- 時刻で振る舞いが変わる画面（開ける時刻、締め切り、残り時間など）は、端末の時計でなくサーバーに合わせた時計で決める

本番では時計を進めないので、本番の `Date` は今と変わらない。オンボーディングの準備の項目（`touch.clock_env` の説明）にこの約束を書き足す。

画面の側を製品が合わせられないときの代わりとして、Web の画面に限り QA はブラウザーの時計（Playwright の `page.clock`）をサーバーの時刻に合わせてよい。iOS シミュレーターの時計は Mac の時計なので動かさない。

### 3. 時計を合わせている間は、その環境を 1 つのジョブだけが使う

- 時計を進めてよいのは、その環境で動いている QA のジョブが自分だけのとき。ほかの QA のジョブ（判定・探索・合成の利用者）が同じ環境で動いていれば、道具は進めずに断り、その旨を返す（QA はその歩を skipped、exit がまたぐなら blocked にする）
- 関門（ADR 0049）は、ストーリーの `time` があるもの（時刻をまたぐストーリー）を、ほかの判定・探索と分けて**最後に**流す。ほかのジョブが全部終わってから、時刻のジョブを積む
  - ADR 0054 の前（判定は 1 ジョブで全ストーリー）: 判定を「時刻なし」「時刻あり」の 2 ジョブに分け、時刻ありは判定（時刻なし）と探索の両方が終わってから同じ固定 Issue に積む
  - ADR 0054 の後（ストーリーごとのジョブ）: 時刻ありのストーリーのジョブは、その版のほかのジョブが終わってから 1 本ずつ積む
- 関門の待ちの時間（`gate.hours`）は、時刻のジョブにも同じく効く。時間切れなら、流せなかったストーリーを報告に書く（今のまま）

### 4. 戻し忘れを工場が戻す

- 時計を進めたジョブが終わったら（成功・失敗・時間切れのどれでも）、そのジョブのあとに環境の時計が 0 でなければ、工場が `reset_clock` の再起動を依頼する。記録は `release.restart_requested` の `by` を `qa:<job_id>:cleanup` にする
- QA には今どおり「流し終えたら自分で 0 に戻す」と指示する。工場の戻しは安全網

### 5. QA への指示を「時刻の歩の段取り」に書き直す

プロンプトの「時間をまたぐ手順」を、翌日だけでなく「開始 N 分前・開始時刻・締め切り」も含む形に直す。段取りは次の順。

1. 前提のデータ（予約・枠など）を、時計が 0 のうちに実際の時刻で作る
2. またぐ時刻の少し後（例: 開始 5 分前の 1 分後）を `set_to` で指定して合わせる
3. 画面を開き直し（ブラウザーの文脈を作り直す・アプリを起動し直す）、サーバーの時刻で画面が切り替わったかを見る
4. 次の時刻（例: 開始時刻の 1 分後）にまた `set_to` で合わせる。実際の時間で待つのは 2 分まで
5. 終わったら `reset_clock`。使った回数と時刻を interpretation に書く

1 ジョブで再起動してよい回数の上限は `definitions/qa.yaml` に置く（最初は 8 回。運用パラメータ）。

## 順番

1. この PR: 本 ADR（提案）
2. 承認後の実装 1（factory-engine）: 道具の `set_to`・`advance_minutes`・`env_clock`、同じ環境にほかの QA のジョブがいれば断る、ジョブの終わりの戻し、プロンプトの書き直し、再起動の回数の上限。DB の変更なし
3. 実装 2（rally）: backend の `Date` を製品の時計で付け、admin-web と student-web の前段がそれを渡すことを確かめる（テストつき）
4. 実装 3（factory-engine）: 関門で時刻ありのストーリーを最後に流す（決定 3）。ADR 0054 の実装 3 と同じ場所（`qa_gate.py`）を触るので、0054 の実装 3 より先に入るなら 2 ジョブの形、後なら 1 本ずつの形で入れる
5. 済の条件: rally の定期便 1 便の関門で、`student-prejoin-check`・`coach-prejoin-check`・`student-books-after-first-lesson` の 3 本が blocked でなく pass か hold で返る

## 選ばなかった案

- **実際の時間で待つ（今の QA がしたこと）**: 開始 5 分前の流れでも 15〜40 分待つ。ターンと時間の枠を食い、翌日・暦月の境は流せない
- **前提を作る専用の仕込み（例: 「5 分後に始まる予約」を DB に直接入れる）**: 製品ごと・ストーリーごとに仕込みが要る。予約の確定の流れ自体を通らなくなる。仕込み（`touch.drills`）は別の用途で残す
- **利用者ごと・要求ごとに時計をずらす（ヘッダーで時刻を渡す）**: 環境を分け合えるが、製品のすべての時刻の扱いにジョブの印を通すことになり、悪用の口にもなる
- **QA のジョブごとに使い捨ての環境を立てる（ADR 0043 の O7）**: 時刻を分け合わずに済むが、1 ジョブごとに環境を立てる時間と資源がかかる。並べたいジョブが増えたら選び直す
- **端末の時計も進める（iOS シミュレーターの時計を変える）**: Mac の時計を変えることになり、Mac の上のほかの仕事（工場自身）に響く
