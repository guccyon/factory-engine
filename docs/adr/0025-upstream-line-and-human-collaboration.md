# ADR 0025: 上流の工程（プランナー・デザイナー役）と人との協業の入口・出口

- 状態: 承認（2026-10-31 オーナー。E1・E2 とデザインシステム・デザイン検査役・ガイドラインは個別に決定、E3〜E5 は推奨どおり。プランナーの責務は 2026-11-01 に決定）
- 関係: ADR 0006（判断の類型）、ADR 0013（Learn ループ）、ADR 0014（検査役の承認）、ADR 0023（学習の体系。テーマ 8 人の意図と好み）、`definitions/stages.yaml` の define / design、`definitions/roadmap.yaml` の P4

## 文脈

P0〜P3 で、チケット（タスク）から PR を作って検査しマージするまでは工場の中で回るようになった。
一方で、テーマから要件を起こし、画面を設計し、タスクに切って依存を付けるところは、まだ建設者（人の側の Claude）が手でやっている。
P4 はこの上流を工場に移す。画面の設計が工程に入ると、人の審美眼が要る判断が増え、工程も分岐する。
ライン設計の前提（判断は入口か出口へ、途中の HITL は置かない、仮決めで続行して出口で確定）は変えずに、この 2 つを扱う形を決める。

2026-10-31 に、デザイナー役の成果物の形を手で 1 回試した（題材は製品のタスク「管理画面で本部がお知らせを送る」）。

## 試作で分かったこと

1. **案のモックは静的な HTML と画面のキャプチャで足りる**。アプリを組み立てず、API もなしで、3 案を数分で出せた。ワーカーのコンテナにある Chromium で撮れる
2. **見た目の正本がないと、案が実物とずれる**。製品にはデザイントークンも部品の一覧もなく、各画面が既定の色を直書きしている。モックは今の見た目を手で写すしかなかった。生徒アプリでの見え方を並べる案は、Flutter 側の見た目を知らないと正確に描けない
3. **管理画面の案の違いは、ほとんどが流れ（ui）の判断だった**。「送る前にどう確かめるか」は「取り消せない操作は確認を挟む」という規則があれば judge が決められる。人の審美眼が効くのは、利用者が見る画面とブランドに効く見た目
4. **画面の設計から契約への要求が出る**。「送る前に届く人数を出す」案は、契約にない API を要する。今のタスクの切り方（API のタスク → 画面のタスク）では、画面を設計した時点で契約のタスクがもう流れている。上流では 要件 → 画面 → 契約 → 実装 の順で切る必要がある

## 決定: デザインシステムをプロジェクトの開始時に用意する（2026-10-31 オーナー）

デザイナー役は、タスクごとにゼロから画面を考えない。プロダクトごとに、プロジェクトの開始時にデザインシステムを必ず用意し、以後の画面はそれの組み合わせとして設計する。

- 中身: デザインコンセプト（誰に・どんな印象を与えるか）とトーン＆マナー（言葉づかい・写真やアイコンの扱い・色と余白の性格）、デザイントークン（色・文字・余白・角丸・影）、部品の一覧（ボタン・入力・カード・一覧・空と失敗と読み込み中の表示など、状態つき）、画面の型（一覧・詳細・入力・確認）、文言と書体の決まり。置き場は製品リポジトリの `specs/design/`（正本）と、各アプリのテーマと部品の実装
- 作り方: プロダクトのオンボーディング（Blueprint を渡した直後）で、工場が最初のタスクとしてデザインシステムを作る。コンセプトとトーン＆マナーは複数案（ムードの案と見本の画面）から人が選び、出来上がりを人が確認して定義を終える（入口の判断）。以後のタスクはこの定義の中で動く
- デザイナー役の約束: 案はデザインシステムの部品と型だけで組む。足りない部品が要るときは、画面のタスクとは別に「デザインシステムに部品を足す」タスクを切る（仮決めで画面に直書きしない）
- 検査役の約束: 画面の PR がデザインシステムの外の色・余白・部品を使っていたら指摘する（後で決定論の検査にする）
- すでに走っている製品（rally）には後から入れる。P4 の最初のタスクは rally のデザインシステム（トークン → 部品の一覧 → 既存画面の置き換え）

## 決定: デザインガイドラインを定義して育てる（2026-10-31 オーナー）

個別の機能の実装でばらつきをなくし、一貫したデザインにするため、プロダクトごとにデザインガイドラインを定義し、開発とともに育てる。
何を基準にするかのアウトラインは Engine の標準として `definitions/design_guideline.yaml` に置く（定評のある公開のデザインシステムの構成を参考にした）。
値と本文はプロダクトの `specs/design/` に置き、オンボーディングで必須の節を埋める。デザイン検査役はこのガイドラインを観点にし、指摘と人の違和感の印がガイドラインの変更の入り口になる。

## 決定: デザイン検査役を置く（2026-10-31 オーナー）

PR の承認を検査役に委任しているのと同じ構造で、デザイン案の承認をデザイン検査役に委任する（ADR 0014 の形をデザインの線にも置く）。

- 位置: デザイナー役の後、実装の線の入口の前。デザイナー役とは別の文脈で動かす（自分の案を自分で採点させない）
- 見るもの: 要件の受け入れ条件を画面の要素と振る舞いで満たしているか、状態（読み込み中・空・失敗・確認）が揃っているか、デザインシステムの部品と画面の型だけで組まれているか、文言の決まり、アクセシビリティの基本（コントラスト・押せる大きさ）、案どうしの違いが選ぶ価値のある違いか
- 出すもの: 承認（そのまま実装へ）／直し（デザイナー役に戻す。1 回まで）／人へ（見た目と印象の判断、新しい画面、確信が低いとき）。判断は judge と同じ 3 層（根拠・解釈・確信度）で記録する
- 育て方: 人に回した判断と人の選択の一致を記録し、一致率が溜まった類型から委任を広げる。検査の観点は Learn ループで育てる（PR の検査役と同じ）。最初は PR の検査役と同じ仕組みの別の観点の組として始め、規模に応じて分ける

| E1 | デザインの判断をどこに置くか | **決定（2026-10-31 オーナー）**: 基本は実装の手前で決める。どの画面も、最低限「画面の中の要素」と「振る舞い（操作・状態・遷移）」が決まった状態で実装に流す。見た目の細部は後追いでよい（出口のキャプチャで直しのタスクにする）。案の承認はデザイン検査役が持ち、新しい画面とブランドに効く画面、検査役の確信が低い案は人の選択に回す（デザインの線の出口＝実装の線の入口。待つ間も他のタスクは流れる） |
| E2 | 審美眼の渡し方 | **決定（2026-10-31 オーナー）**: プロダクトのオンボーディングの段階でデザインシステムを用意し、そのときにデザインコンセプトとトーン＆マナーまで、ある程度定義を終える。以後の人の審美眼は、デザイン検査役から回ってきた案の選択と、出口の違和感の印で渡す |
| E3 | プランナーが切ったタスクの投入 | 最初はテーマ単位のまとまりを人が 1 タップで承認して投入。judge との一致が溜まったら委任 |
| E4 | 判断の類型 | 類型に「見た目と印象（aesthetic）」を足す（版 v3）。この類型は judge に委任せず人が決め、選択を記録して一致率を後で見る。流れの判断は今の ui のまま judge に委任できる |
| E5 | 成果物の置き場 | Requirements と UXSpec は製品リポジトリの `specs/` にファイルで置く（差分で追える）。案のモックとキャプチャはオブジェクトストアに置き、PR と選択の画面からリンクする |

## 工程の形（E1〜E5 を推奨どおりに取った場合）

```
オンボーディング（1 回）: コンセプトとトーン＆マナーの案から人が選ぶ → デザインシステム（工場が作り、人が確認）
入口（人）: テーマ
  → プランナー: Requirements とタスクの下書きのまとまり（依存つき）→ 人の 1 タップで投入（E3）
  → デザイナー役: UXSpec（画面の要素・振る舞い・状態）と案（デザインシステムの部品で組んだ 2〜3 案のモックとキャプチャ。小さな追加は 1 案）
  → デザイン検査役: 承認／直し／人へ（新しい画面・ブランドに効く画面・確信が低い案は人が選ぶ）
  → 契約のタスク → 実装役 → 検査役 → マージ
出口（人）: 実装後の画面のキャプチャを見て違和感の印（taste_flag）、出荷の判断。見た目の細部の直しはここからタスクにする
```

## P4 の完了条件（roadmap.yaml）

0. 製品にデザインシステム（トークン・状態つきの部品の一覧・画面の型）があり、新しいプロダクトでは開始時のタスクとして工場が作る
1. テーマ 1 つから、人が触らずに Requirements とタスクのまとまり（依存つき）が出る
2. 画面を含むタスクは、画面の要素と振る舞いが決まった UXSpec を持って実装に流れる。案はデザイン検査役が承認し、新しい画面・ブランドに効く画面・確信の低い案だけが人の選択を経る
3. 人の判断は入口と出口にだけあり、ラインの途中で待たない
4. 実装後の画面のキャプチャが PR に付き、人の違和感の印が教師信号として Learn に入る
5. clarify が往復 3 回以内で収束する

## プランナーの責務（2026-11-01 オーナー。ADR 0026 と合わせて改める）

デザイナー役を 2 つに分け、どちらに回すか（あるいはデザイナーを通さずに実装役へ直行させるか）をプランナーが決める。そのためプランナーは必須とし、仮置きを解く。

- デザイナー役は 2 つ。**デザインシステムのデザイナー**はコンセプト・原則・ガイドラインからトークン・部品・画面の型まで考える（オンボーディング、部品・基準の追加、作り直し）。**画面のデザイナー**は既存のデザインシステムから、ページや機能に固有のデザインに落とす（今の `ui_design`）
- プランナーの責務: チケット 1 件ごとの着手判定（ADR 0026 の 0。足りなければ起票者に問う）と、経路の決定。経路は型から選ばず、タスクに合わせてどの役をどの順で通すか（デザイナーを飛ばして実装役へ直行も含む）を柔軟に組む。結果は制御プレーンの `Plan` に置き、指示役は最初の役のラベルどおりに配る（ADR 0020）
- 判断の根拠（根拠・解釈・確信度、役ごとの理由、とらなかった経路と理由、入力の版）を `Plan` と events に残し、後で経路ごとの結果と突き合わせて見返し、改善に使う（2026-11-01 オーナー）
- テーマから Requirements とタスクのまとまり（依存つき、要件 → 画面 → 契約 → 実装の順）を切るのも、引き続きプランナーが持つ（最小のプランナーの後に足す）
- 優先順位の付け方、テーマそのものの提案、Opportunity の発見（observe・triage）は持たない
- 効率: 振り分けごとの費用・時間・往復の回数を記録し（`plan.decided`）、すべてを上位の役に回す案と質と費用を比べてから割り当てを直す

## 進め方

承認を待たずに進めるもの（製品側、または工場の外）:

- 製品の CI で画面のキャプチャを撮り PR から見られるようにする
- 製品のデザインシステムの最初のタスク: デザイントークンの正本と両アプリのテーマ化（値は今の見た目のまま）。続けて部品の一覧
- デザイナー役の試作をもう 1 回、利用者が見る画面（生徒アプリ）で行う

承認のあとに Engine に入れるもの: デザイナー役のジョブ、デザイン検査役（検査役の仕組みにデザインの観点の組を足す）、案の選択と違和感の印の画面（P3 の抜き取りの画面と同じ部品）、プランナー（最小）、`judgments.yaml` の v3。

## 結果

- 建設者が手でやっているタスクの切り出しが、工場の工程になる。人の負担は、テーマとブランドの入口、重い画面の案の選択、出口の違和感の印に寄る
- 工程が 2 本の線（デザイン・実装）に分かれ、状態の管理が増える。状態は制御プレーンに置く（ADR 0020）
- 見た目の正本がない製品では、デザイナー役の質が上がらない。デザインシステムを開始時の必須のタスクにし、画面はその組み合わせにする。タスクごとのゼロからの設計をなくす
