# ADR 0025: 上流の工程（プランナー・デザイナー役）と人との協業の入口・出口

- 状態: 提案（2026-10-31。E1 と「デザインシステムを先に用意する」はオーナーが決定。E2〜E5 は承認待ち）
- 関係: ADR 0006（判断の類型）、ADR 0013（Learn ループ）、ADR 0014（検査役の承認）、ADR 0023（学習の体系。テーマ 8 人の意図と好み）、`definitions/stages.yaml` の define / design、`definitions/roadmap.yaml` の P4

## 文脈

P0〜P3 で、チケット（段）から PR を作って検査しマージするまでは工場の中で回るようになった。
一方で、テーマから要件を起こし、画面を設計し、段に切って依存を付けるところは、まだ建設者（人の側の Claude）が手でやっている。
P4 はこの上流を工場に移す。画面の設計が工程に入ると、人の審美眼が要る判断が増え、工程も分岐する。
ライン設計の前提（判断は入口か出口へ、途中の HITL は置かない、仮決めで続行して出口で確定）は変えずに、この 2 つを扱う形を決める。

2026-10-31 に、デザイナー役の成果物の形を手で 1 回試した（題材は製品の段「管理画面で本部がお知らせを送る」）。

## 試作で分かったこと

1. **案のモックは静的な HTML と画面のキャプチャで足りる**。アプリを組み立てず、API もなしで、3 案を数分で出せた。ワーカーのコンテナにある Chromium で撮れる
2. **見た目の正本がないと、案が実物とずれる**。製品にはデザイントークンも部品の一覧もなく、各画面が既定の色を直書きしている。モックは今の見た目を手で写すしかなかった。生徒アプリでの見え方を並べる案は、Flutter 側の見た目を知らないと正確に描けない
3. **管理画面の案の違いは、ほとんどが流れ（ui）の判断だった**。「送る前にどう確かめるか」は「取り消せない操作は確認を挟む」という規則があれば judge が決められる。人の審美眼が効くのは、利用者が見る画面とブランドに効く見た目
4. **画面の設計から契約への要求が出る**。「送る前に届く人数を出す」案は、契約にない API を要する。今の段の切り方（API の段 → 画面の段）では、画面を設計した時点で契約の段がもう流れている。上流では 要件 → 画面 → 契約 → 実装 の順で切る必要がある

## 決定: デザインシステムをプロジェクトの開始時に用意する（2026-10-31 オーナー）

デザイナー役は、段ごとにゼロから画面を考えない。プロダクトごとに、プロジェクトの開始時にデザインシステムを必ず用意し、以後の画面はそれの組み合わせとして設計する。

- 中身: デザイントークン（色・文字・余白・角丸・影）、部品の一覧（ボタン・入力・カード・一覧・空と失敗と読み込み中の表示など、状態つき）、画面の型（一覧・詳細・入力・確認）、文言と書体の決まり。置き場は製品リポジトリの `specs/design/`（正本）と、各アプリのテーマと部品の実装
- 作り方: 入口でブランドの方向（E2）を受けて、工場が最初の段としてデザインシステムを作る。人はムードの選択と出来上がりの確認をする（入口の判断）
- デザイナー役の約束: 案はデザインシステムの部品と型だけで組む。足りない部品が要るときは、画面の段とは別に「デザインシステムに部品を足す」段を切る（仮決めで画面に直書きしない）
- 検査役の約束: 画面の PR がデザインシステムの外の色・余白・部品を使っていたら指摘する（後で決定論の検査にする）
- すでに走っている製品（rally）には後から入れる。P4 の最初の段は rally のデザインシステム（トークン → 部品の一覧 → 既存画面の置き換え）

## 決めどころ（オーナーの承認が要る）

| # | 問い | 推奨 |
|---|---|---|
| E1 | デザインの判断をどこに置くか | **決定（2026-10-31 オーナー）**: 画面の重さで分ける。新しい画面とブランドに効く画面は「案の選択」を実装の入口に置く（デザインの線の出口＝実装の線の入口。待つ間も他の段は流れる）。既存画面への小さな追加は、デザイナー役が仮決めで 1 案にして流し、出口のキャプチャで人が見る |
| E2 | 審美眼の渡し方 | 最初に 1 回、ブランドの方向（ムードの 3 案から選ぶ＋言葉で一言）。以後は案の選択と違和感の印だけ。選んだ理由の一言は任意 |
| E3 | プランナーが切った段の投入 | 最初はテーマ単位の束を人が 1 タップで承認して投入。judge との一致が溜まったら委任 |
| E4 | 判断の類型 | 類型に「見た目と印象（aesthetic）」を足す（版 v3）。この類型は judge に委任せず人が決め、選択を記録して一致率を後で見る。流れの判断は今の ui のまま judge に委任できる |
| E5 | 成果物の置き場 | Requirements と UXSpec は製品リポジトリの `specs/` にファイルで置く（差分で追える）。案のモックとキャプチャはオブジェクトストアに置き、PR と選択の画面からリンクする |

## 工程の形（E1〜E5 を推奨どおりに取った場合）

```
開始時（1 回）: ブランドの方向（人）→ デザインシステム（工場が作り、人が確認）
入口（人）: テーマ
  → プランナー: Requirements と段の下書きの束（依存つき）→ 人の 1 タップで投入（E3）
  → デザイナー役: UXSpec と案（デザインシステムの部品で組んだ 2〜3 案のモックとキャプチャ）
      ├ 重い画面: 人が案を選ぶ（実装の入口）
      └ 軽い画面: 仮決めで 1 案
  → 契約の段 → 実装役 → 検査役 → マージ
出口（人）: 実装後の画面のキャプチャを見て違和感の印（taste_flag）、出荷の判断
```

## P4 の完了条件（roadmap.yaml）

0. 製品にデザインシステム（トークン・状態つきの部品の一覧・画面の型）があり、新しいプロダクトでは開始時の段として工場が作る
1. テーマ 1 つから、人が触らずに Requirements と段の束（依存つき）が出る
2. 画面を含む段では、デザイナー役がデザインシステムの部品で組んだ案（キャプチャつき）を出し、重い画面は人の選択を経て実装に流れる
3. 人の判断は入口と出口にだけあり、ラインの途中で待たない
4. 実装後の画面のキャプチャが PR に付き、人の違和感の印が教師信号として Learn に入る
5. clarify が往復 3 回以内で収束する

## 進め方

承認を待たずに進めるもの（製品側、または工場の外）:

- 製品の CI で画面のキャプチャを撮り PR から見られるようにする
- 製品のデザインシステムの最初の段: デザイントークンの正本と両アプリのテーマ化（値は今の見た目のまま）。続けて部品の一覧
- デザイナー役の試作をもう 1 回、利用者が見る画面（生徒アプリ）で行う

承認のあとに Engine に入れるもの: デザイナー役のジョブ、案の選択と違和感の印の画面（P3 の抜き取りの画面と同じ部品）、プランナー（最小）、`judgments.yaml` の v3。

## 結果

- 建設者が手でやっている段の切り出しが、工場の工程になる。人の負担は、テーマとブランドの入口、重い画面の案の選択、出口の違和感の印に寄る
- 工程が 2 本の線（デザイン・実装）に分かれ、状態の管理が増える。状態は制御プレーンに置く（ADR 0020）
- 見た目の正本がない製品では、デザイナー役の質が上がらない。デザインシステムを開始時の必須の段にし、画面はその組み合わせにする。段ごとのゼロからの設計をなくす
