# ADR 0045: 既存の製品を工場に載せる（オンボーディング）を Gen1.5 で予行演習する

- 状態: 承認（2026-11-09 オーナー。A・B・C・F、リポジトリを SSOT にすること、関心事モデルの D1〜D12 はオーナーが決定）
- 関係: ADR 0001（Engine と製品の分離）、ADR 0012（出荷）、ADR 0028（QA と実行環境）、ADR 0036（プランナーの見込み）、ADR 0038（着手のしかた）、ADR 0040（知見の範囲）、ADR 0041（ロールごとの権限）、ADR 0043（P5b の最小の形と持ち越し）
- 検討の記録: 事業部の仕様の置き場（05_specs）の Q9・Q15・Q16、オンボーディングの叩き台と関心事モデルの図（Gen1.5 の検討資料）

## 文脈

Gen1 の工場は、工場が一から作った、リポジトリ 1 本の製品（1 号機）を前提に作った。製品とリポジトリが 1 対 1 で、仕様の正本・ルール・CI・出荷の形を工場が最初から決め、工場の外に作り手はいない。

Gen2 では、サービスイン済みで数年たった製品を引き受ける。その製品は複数のリポジトリ（API、モバイル、インフラのコード）に分かれ、本番が動いていて、仕様は散らばっているか無い。先方には社内の開発者がいて、工場と並行して同じリポジトリを触る。工場がこれを解析して取り込めないと Gen2 に入れない。そこで Gen2 の前に Gen1.5 を挟み、オンボーディングを作る（2026-11-08 オーナー）。

今の工場で、この前提に合わない所（洗い出し）:

| # | Gen1 の前提 | 既存・複数リポジトリの製品で困ること |
|---|---|---|
| G1 | 製品＝リポジトリ 1 本。ジョブは `REPO` を 1 つ持ち、ワーカーは製品リポジトリを 1 本だけ取ってくる | 「製品」という束が無い |
| G2 | 変更は 1 PR で完結（1 号機は monorepo） | API の追加が API とクライアントの 2 本の PR になる。順番と互換が要る |
| G3 | 仕様の正本が最初からある | 既存のコードから仕様を起こす工程が無い |
| G4 | 製品リポジトリのルールは工場が決めた | 先方の慣習（言語・ブランチ・レビュー・リリース）がある |
| G5 | 工場のゲートの一部は製品の CI で動く | 先方の CI は先方のもの。変更は人の作業 |
| G6 | 出荷は工場の手元の Docker（ADR 0012） | 先方の出荷の仕組み・ストア配信・IaC がある。本番は最初から動いている |
| G7 | 触れる環境はリポジトリ 1 本で立つ | 複数のリポジトリの版の組み合わせで立てる必要がある。合成シードが無いかもしれない |
| G8 | ワーカーの道具は 1 号機の技術向け | 先方の技術に合う道具が要る |
| G9 | 規模が小さい | 触るファイルの見込み（ADR 0036、再現率の中央値 0.125）はさらに外れる。どこに何があるかの地図が要る |
| G10 | 工場の外に作り手がいない | 社内の開発者や別の工場が並行して触る。仕様とコードのずれが外から生まれる |
| G11 | 生産の知見は製品リポジトリの `.factory-config/` | 先方のリポジトリに工場の知見を置けない |
| G12 | 知見は工場の中で育てたものだけ | 先方の組織にある知見を参照したい |

## 決定

### 1. Gen1.5 は本物のリポジトリでの予行演習。Gen2.0 で作り直す

- Gen1.5 では、Gen2 で実際に引き受けるリポジトリを参照して、オンボーディング（下の 3 の S0〜S4）だけを行う。製品の開発（S5 以降）は Gen2
- Gen1.5 で作る置き場・宣言・工程・道具は予行演習のためのもので、Gen2.0 で改めて作り直す。作り込みすぎない。Gen1.5 の成果は「オンボーディングのやり方」の記録（手順、出口の条件、解析の道具、つまずいた所）で、Gen2.0 の設計の入力にする
- 先方のリポジトリは非公開。名前・解析の結果・コードの断片は public のリポジトリ（factory-engine・1 号機）に書かない。予行演習の記録は非公開の置き場に置く

### 2. 製品のリポジトリが SSOT。開発のノウハウは工場が持つ

- 製品のドメイン知識・仕様・設計は製品のリポジトリに置き、それを正とする。開発のノウハウ（生産の知見、任せる範囲、評価のデータ、判断の記録）は工場が持つ
- 製品のリポジトリは、社内の開発者も複数の工場も触る前提で、特定の工場に依存しない形で書く。工場固有の設定や知見は製品のリポジトリに置かない（1 号機の `.factory-config/` は、05_specs の Q15 の決定どおり Gen2 で工場の側に移す）
- 宣言を 2 つに分ける
  - **製品の構成**（どのリポジトリがこの製品か、役割、契約の持ち主と使う側）: 製品のリポジトリの横断の仕様に置く。人もどの工場も同じものを読む
  - **工場の引き受け**（この工場が担当するリポジトリ、製品の段階、リポジトリごとの任せる範囲、担当の印）: 工場の置き場に置く
- ジョブとチケットは製品に付き、ジョブはその中の対象のリポジトリを持つ（G1）。形は Gen1.5 の予行演習で確かめ、Gen2.0 で実装する

### 3. オンボーディングの工程

| 工程 | やること | 出口の条件 |
|---|---|---|
| S0 受け入れ | 範囲・権限・接続を決める | 全リポジトリを読めて、工場の置き場ができた |
| S1 棚卸し | リポジトリごとの技術・ビルド・テスト・CI・出荷・環境・ドキュメント・Issue の使い方・チームの慣習を集める | 全リポジトリで「ビルドの仕方・テストの仕方・出し方」が埋まった（不明は不明と書く） |
| S2 解析 | 構成の地図、API の契約（コードから起こす）、DB のスキーマ、画面と流れの一覧、リポジトリ間の依存（どの画面がどの API を呼ぶか）、用語と境界の候補、テストの現状 | 契約と画面の一覧が実物と突き合わさった（照合が通る割合を出す） |
| S3 仕様の起こし | 解析から製品の仕様の下書きを起こし、問いを並べず「こう読んだ」を見せて直してもらう | 事業主が読みを確かめた |
| S4 動かす | 工場の中で全リポジトリをビルド・テストし、組み合わせて触れる環境を立てる。今の品質を基準点として測る | 工場だけで環境が立ち、既存のテストの結果が記録された |
| S5 試運転 | 小さい変更を人のレビュー付きで通す（Gen2） | — |
| S6 引き受け | 任せる範囲を指標で段階的に広げる（Gen2） | — |

- S1・S2 は読むだけで、先方のリポジトリに書かない。権限は読み取りだけで始める（ADR 0041 のロールに読み取り専用の区分を足す）
- S3 の下書きを先方のリポジトリに PR で出すかは事業主と相談して決める。それまでは工場の側に持つ
- S4 は工場の中で閉じる。先方の本番と本番データに触れない

### 4. ほかの作り手（社内の開発者・別の工場）と同じリポジトリを並行して触る

Gen2 で実装する。方向だけここで決める。

- バックログは 1 つで、チケットごとに担当（人か、どの工場か）を明示する。工場は自分の担当だけに着手する
- プランナーの着手判断（ADR 0038）は、工場の実行中のタスクに加えて、ほかの作り手の開いている PR とブランチも進行中の仕事として見る
- ほかの作り手の変更がマージされるたびに、工場の地図・契約・仕様とのずれを確かめる。ずれは仕様の更新の PR か人への確認にする。仕様を書くことを人に強いない
- 工場の PR は先方のレビューの決まりに従う。ほかの作り手の PR に工場の型を求めない。製品リポジトリの中は先方の慣習が勝つ

### 5. リポジトリをまたぐ変更と、本番の扱い（Gen2 で実装する方向）

- 1 つのチケットが複数のリポジトリに触るときは、リポジトリごとの PR の組（変更の束）にする。順番は契約で決まる（互換を保って足す → 使う → 古いものを消す）。古いものを消す工程は人の承認
- 触れる環境は、束の各 PR の版の組み合わせで立てる。P5b から持ち越した PR ごとの使い捨て環境・定期便・TestFlight（ADR 0043）はこの形で作り直す
- 工場は当面、先方の本番に触れない。出荷は先方の既存の仕組みに乗せ、工場は出せる状態の PR と手順までを作る。インフラのコードは差分の確認（plan）まで、適用は人

### 6. 先方の組織の知見と外部の資料は参照で持つ

- 写しは作らず、参照（場所）と工場の側の要約・タグを持つ。取り込み元は S1 で一覧にし、人が足せる
- Figma や Confluence などの外部の資料は、パスワードや API キーを受け取らない。事業主が OAuth のコネクタで工場に読み取りだけを許可し、いつでも取り消せる。コネクタの無いサービスは書き出したファイルを受け取り、原本とずれることを記録する（D8）
- コンソールの設定画面で、コネクタごとの認証の状態を見てつなぎ直せるようにする。コンソールに入る個人の権限とトークンの管理は別に設計する

### 7. 関心事・成果物・置き場をモデルとして持つ

- オンボーディングで扱う関心事を 10 に分ける: 引き受けの範囲、製品の構成、技術スタックと外部サービス、体制と共存、組織の知見、構造とコードのルール、契約とデータ、ドメインと機能、作り方と出し方、品質と基準点。関心事ごとに入力・成果物・そろったと言える条件を持つ
- 成果物の置き場は 3 つ。製品のリポジトリ（別の開発組織に移しても要るもの）、工場の置き場（この工場だけが使うもの、コードから作り直せるもの）、提供元（どの製品にも効くやり方）。この順に問いを当てて決める
- 製品のリポジトリに置くものは、工場の置き場で下書きを作り、事業主が確かめてから PR で入れる
- 個別に決めた置き場: コードの索引は工場（人が読む要約はアーキテクチャの説明として製品のリポジトリ）（D1）、品質方針は製品のリポジトリ（D2）、出荷は人が読む説明を製品のリポジトリ・自動化の手順を工場（D3）、技術スタックと外部サービスの地図は製品のリポジトリ（新規の製品でも作る）（D10）

### 8. 仕事ごとの必須の提供ラインと、準備度メーター

- 事業主から最低限もらうものを、有効にする仕事ごとに分ける。仕事の単位は新しく作らず、工場のレーンに合わせる: 開発を始める（Dev のビルド）、本番に出す・ストアに出す（Ops の出荷の出し先）、運用を引き受ける（Ops）（D6）
- 開発を始めるのに必須: 担当リポジトリに PR を出せる権限、バックログ管理システム、通知の宛先と承認者、工場の中で動く環境、一部でも動くテスト
- 項目ごとに粒度を 4 つの値で持ち、仕事ごとに最低と目標を決める。必須が欠けたら始めない。粒度が足りなければ「品質が出にくい」と理由つきで警告し、事業主へのお願いを並べる。始めるかは事業主が決める（D7）
- 稼働 ready（L3 動かせる と L4 変えられる の間）は、L1〜L3 の条件と「開発を始める」の必須を機械で確かめたうえで、事業主が承認して越える（D4）。L3 では主な画面のキャプチャを数点撮って、動くことを確かめる（D5）

### 9. 取り込みと同期は、オンボーディングの後も回し続ける

- **取り込みのループ**: 人（事業主、社内の開発者、別の部隊）が資料・知見・接続をいつでも窓口から足す。工場は効く関心事だけを解析し直し、準備度を更新する。誰が・いつ・何を足したかを工場の置き場に記録する
- **同期のループ**: 誰の変更でも main に入ったら工場が差分を読む。コードの索引と基準点は作ったときのコミットを持ち、差分の分だけ自動で作り直す（使う前にも古さを確かめる）。人が読む説明（アーキテクチャの要約・契約・画面の一覧）は、構造が変わる差分のときだけ直す PR を出す（D1）
- オンボーディングは、この 2 つのループの最初の 1 周とする

### 10. 既存のテストは、壊れたものを無効化して全部緑から始める

- 管理する情報を「通る・通らない」の 2 値にそろえる（D9）。L3 で工場の中で流して分類し（緑・先方でも赤・揺れる・外部サービスが要る・工場の環境で動かない）、環境で直るものは環境の側で直す
- 残った赤は、テストの道具の機能で理由とチケット番号を目印に書いて無効化する（消さない）。無効化 1 本（またはまとまり）ごとに「直して有効に戻す」技術的負債のチケットを作る
- Lint の違反と、将来の脆弱性の診断の指摘も同じ形で扱う（今ある分は抑えて 0 から始め、解消をチケットにする）
- 壊れたテストが多いときの線: 環境で直らない赤がテスト全体の 1 割未満なら、無効化して緑で始める。1 割以上なら、無効化した上で準備度メーターで警告し、始めるかは事業主が決める。線の値は運用で調整する（D11）
- 無効化の PR は、稼働 ready の承認の後に最初のチケットとして出し、社内の開発者のレビューを通す。テストが長く放置されたコードでは、実コードとテストのどちらが正しいかを工場だけでは決められないため（D12）
- 稼働 ready のときに最初に積むチケット: 壊れたテストの無効化、無効化したテストを直して戻す、テストの追加と拡充（主な流れの今の振る舞いを写すテストと画面の E2E）、Lint の基準をそろえる、シードと環境の補強。工場が書き、事業主が順番を決める

## 決めていないこと

- **B. 横断の仕様の置き場（方針は決定 2026-11-09 オーナー）**: 製品のリポジトリに置く。事業主が乗れるなら ① 履歴を残して 1 本のモノレポにまとめる。無理なら ③ まとめのリポジトリ＋リポジトリと版の一覧（submodule を使わない）。② まとめのリポジトリ＋submodule は、変更が「各リポジトリの PR＋指す版を上げる PR」になり、各リポジトリで直接作業する人がいると指す版が古いまま残るので、開発の場としては使わない（版の組み合わせの記録には使える）。事業主との相談は、① にしたときに先方の CI・出荷・権限で何が変わるかが分かる S1 の後に行い、どれにするかはその製品ごとに決める
- Gen1.5 の置き場の形（非公開のリポジトリか、工場の端末の中か）。予行演習なので、置き場の選び方そのものを記録して Gen2.0 で決める

## 選ばなかった案

- **既存のテストの赤を基準点として記録し、新しく増えた赤だけで判定する**: 先方のリポジトリに書かずに済むが、どのテストが信じられるかという 3 値以上の情報を工場がずっと持つことになる。無効化して 2 値にそろえ、直すのをチケットにする方が扱いやすい（D9 でオーナーが変更）
- **公開されている OSS で演習する**: Gen1.5 の時点で本物のリポジトリを参照できるので不要。OSS では先方の慣習・本番・社内の開発者という肝心の条件が再現しない
- **工場の側の置き場を Gen1.5 で前倒しで本実装する**: Gen1.5 は予行演習で、やり方が分かってから Gen2.0 で作り直す方が手戻りが少ない
- **リポジトリごとに別の製品として扱う**: 今の工場のまま動くが、またぐ変更の順番と互換を誰も持たない
- **横断の仕様を工場の側に置く**: リポジトリを SSOT にする原則と、製品を工場から切り離して移管できる原則に反する

## 結果

- Gen1.5 の出口の条件: 本物のリポジトリで S0〜S4 を工場だけで通し（先方のリポジトリには書かない）、解析の結果（契約・画面の一覧・リポジトリ間の依存）を人が見て「Web 版の開発を始められる」と言い、やり方の記録が Gen2.0 の設計の入力として残る
- Gen1.5 の道具（棚卸し・解析）は使い捨てでよいが、どの手順が決定論で済み、どこに LLM が要ったかを記録する
- 準備度・オンボーディングのレベル・外部コネクタの認証状態などの一部は操業コンソールにも出す。コンソールは表示だけで、正本は製品のリポジトリと工場の置き場のまま。何をいつ出すかは下の追記で決めた
- Gen2.0 の設計（05_specs）に、2・4・5・6 の方向と、Gen1.5 の記録を入れる

## 追記（2026-11-09、承認）: 操業コンソールに出すもの

オーナー「これらの情報のいくつかは操業コンソールから見えるようにしたい」。置き場所は、上のタブに「製品」を足す案をオーナーが選び、ほかの決めどころも推奨どおりで承認した（2026-11-09）。画面ごとの仕様は事業部の仕様の置き場（05_specs）に置く。

- **Gen1.5 で出すのは 4 つ**: 準備度メーター（8）、オンボーディングのレベル L1〜L5 と次のレベルに足りないもの、技術スタックと外部サービスの地図（D10）、外部コネクタの認証の状態（6）。取り込みと同期の状態とテスト負債の推移は、稼働 ready を越えてから意味が出るので Gen2 で出す
- **外部サービスは 2 つに分けて出す**（オーナー）
  - 製品に組み込まれ、製品が動くのに要る直接のサービス（決済・エラー収集・認可・モバイルの基盤など）: 製品のページの「技術スタックと外部サービス」に、リポジトリごとの言語と枠組みと並べて出す。サービスごとに、使っているリポジトリ、役割、検証用の環境の有無、工場の環境での扱い（検証用の環境につなぐ・模擬で置き換える・使えない）を持つ。検証用の鍵は値を出さず、あるかどうかだけ
  - 工場の生産に使う間接のサービス（バックログ管理・デザインの資料・社内の文書など）: 設定の「サービスとの連携」に、コネクタとして出す
  - 地図の正本は製品のリポジトリ（D10）。Gen1.5 は先方のリポジトリに書かないので、工場の置き場の下書きを出し、「下書き」と示す
- **置き場所**: 上のタブに「製品」を足し、`/products/<製品>` にレベル・メーター・事業主へのお願いを並べる。ホームには「判断待ち」の側に要約のカードを 1 枚。稼働 ready を越えた製品はカードから外す。ページの構成（受信トレイの 2 ペイン、設定は歯車から）は変えない
- **受信トレイ**: 2 種類を足す
  - 準備のお願い: 製品と仕事の組ごとに 1 件。項目ごとには分けない。「渡した」と答えても済にはせず、工場が測り直して粒度が上がった項目から消え、全部消えたら閉じる
  - 稼働 ready の承認: L1〜L3 の条件と「開発を始める」の必須を機械で確かめたあとにだけ出す。警告が残っていれば、承知のうえで始めるかを問う（D4・D7）
- **コネクタの状態**: 設定の「サービスとの連携」に、サービス・製品・許可した人・範囲・状態・期限・最後に使った日時を出す。鍵そのものはコンソールに出さない。鍵の持ち方は個人の権限とトークンの管理の設計で決め、それまでは取り込み元の一覧（OAuth か、書き出したファイルか）だけを出す
- **データの持ち方**: 項目の定義（何を測るか、粒度の 4 つの値、仕事ごとの最低と目標、必須か、レベルの条件）はどの製品にも効くやり方なので Engine の `definitions/` に置く。その製品の値（今の粒度と根拠）は工場の置き場。コンソールは、オンボーディングの道具が記録する判定の記録（製品・時刻・コミット・項目ごとの粒度と根拠・仕事ごとの判定）を読むだけ。履歴を持つので推移も出せる
- **製品の束ね方**: ジョブとチケットを製品に付けるのは Gen2.0（2）。Gen1.5 のコンソールの「製品」は、判定の記録に書かれた製品の名前で束ねるだけにする
- **公開のリポジトリ**: PR の画面のキャプチャ・テストの例のデータは 1 号機の判定から作る。先方の情報は載せない
- **作る順**: 定義と判定の関数（DB と画面に触れない）→ 判定の記録の受け口（表を足す expand）→ 製品のページ（レベル・メーター・技術スタックと外部サービス）とホームのカード → 受信トレイの 2 種類 → 設定の「サービスとの連携」
