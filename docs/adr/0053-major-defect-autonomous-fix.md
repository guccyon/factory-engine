# ADR 0053: メジャー不具合は工場が自分の判断で直し、出し直す（本番で見つかった独立のものは revert も）

- 状態: 承認（2026-11-13 オーナー。方針を承認し、判断基準への組み込みを指示）
- 関係: ADR 0012（出荷）、ADR 0028（QA 役）、ADR 0043（O5 の重要度と差し止め、O6 の定期便と緊急便）、ADR 0049（QA の関門）

## 文脈

QA 役が staging で S1 の Defect を見つけると、ラインを差し止めて Issue に p0 を付ける（ADR 0043 の O5）。しかし Issue は他の Defect と同じく `factory:fix-proposed` で起票され、人が `factory:planned` に替えるまで流れなかった。差し止めの間に流してよいのは「S1 の修正」なのに、その修正が人の 1 タップを待って止まる。

2026-11-12 の rally #1423（受講者が添削待ちの画面を一度離れると、添削が返ってもレッスンを完了にできない）は、これで差し止めから半日以上だれも直さず、ほかのチケットも止まった。修正の後の出し直し（緊急便）も、人か QA 役が `factoryctl release train --emergency` を打つ形で、自動では出ていなかった。

オーナーの方針（2026-11-13）: 先に進めない・業務が止まるレベルの不具合はメジャー不具合として、工場が自律判断で即時に修正・再リリースまで行う。リリース後の本番で見つかり、他の変更と依存がないものは revert も行う。

## 決定

### 1. メジャー不具合の定義

利用者が先に進めない、または業務が止まる不具合。Gen1 では QA 役の重要度 S1（`definitions/quality_policy.yaml` で hold: true のもの）をそのまま使う。重要度の付け方は QA 役のまま変えない。演習（drill）の S1 は対象にしない（直すコードがない）。

### 2. 直す: 人の承認を待たずに流す

- S1 の Defect の Issue は、起票と同時に `factory:fix-proposed` を外して `factory:planned` にし、p0 を付ける（`incident.from_qa` → `major_defect.plan_fix`）
- 修正の PR のマージは、製品のマージ基準のまま（rally は CI 通過で自動マージ）。メジャー不具合だから基準をゆるめることはしない

### 3. 出し直す: 修正がマージされたら緊急便

- S1 の Incident の Defect の Issue が閉じ（修正の PR がマージされ）、まだ Release に入っていないマージ済みの PR があれば、supervisor が緊急便（`train.emergency`、by: supervisor）を出す。Incident ごとに 1 回（`major.rereleased`）。出荷が処理中なら次の周回で出す
- 本番を立てる段階（launch・operating）の製品なら、緊急便の版が staging に出たところで supervisor が本番への承認をする。QA の関門（ADR 0049）の報告は待たない（`release.approved` の `qa_skipped` に理由を残す）。関門そのものは staging の配備で今までどおり開き、結果は記録に残る
- 本番を立てない段階（development。rally がいま）の製品は、緊急便で staging に出るところまで

### 4. 本番で見つかったものは revert も

本番に出た後に見つかったメジャー不具合で、原因の変更が特定でき、その変更に後から依存する変更がないものは、修正を待たずにその変更を revert して出し直す。依存があるもの・原因が特定できないものは 2 と 3（直して出し直す）で扱う。

- 依存がないとは: 原因の PR より後にマージされた PR が、その PR で変えたファイルに触れていない、かつ contract のマイグレーションを含まない（含むものは戻せない。ADR 0012 の 6）
- revert の PR も製品のマージ基準で入れ、3 の緊急便で出す
- 実装は本番を立てる製品が出てから（いまは本番のある製品がない）。それまでは本番のロールバック（`factoryctl release rollback`）を人が使う

### 5. 差し止めの解除

差し止め（ADR 0043 の O5）の解除は今までどおり人が行う。工場が直して出し直した後、人が staging で確かめて解除する。自動で解除するかは、この形で何件か回してから別に決める。

## 順番

1. この PR: 本 ADR と、2・3 の実装（`dispatcher/major_defect.py`、`incident.from_qa`、supervisor の `major_defect_step`）
2. 4 の revert: 本番を立てる製品が出たときに実装する

## 選ばなかった案

- ADR 0049（QA の関門）の改訂として書く: 関門は出荷のレーンの検証の話で、メジャー不具合の扱いは関門の外（夜間の探索や本番の監視）で見つかったものにもかかる。別の ADR にした
- 重要度に新しい段（「メジャー」）を足す: S1 の定義（止める）とほぼ同じで、QA 役の付け方を変えることになる。S1 をそのまま使う
- 緊急便の本番の承認も人に残す: 方針は「再リリースまで工場が行う」。待つ間、利用者は先に進めないまま
- 差し止めも自動で解除する: 方針の範囲の外。直ったかの確かめ方（QA の確かめ直しで足りるか）が決まっていない

## 結果

- S1 が見つかってから修正・出し直しまで人の操作が要らなくなる。人が見るのは差し止めの解除だけ
- 自動で本番に出る経路が増える。本番を立てる製品が出たら、緊急便の本番の承認を supervisor がした件数と、その後に戻した件数を日報で見る
- S1 の付け方が甘いと、承認を通らずに本番に出る変更が増える。QA 役の重要度の当たり具合（ADR 0049 の結果の節）と合わせて見る
