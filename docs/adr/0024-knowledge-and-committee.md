# ADR 0024: 知見の蓄積と委員会

- 状態: 承認（2026-10-31 オーナー。知見の蓄積と委員会への回答）
- 関係: ADR 0023（学習の体系）、ADR 0013（Learn ループ）、ADR 0021（後片付け）、`definitions/knowledge.yaml`、`core-gates/knowledge_check.py`

## 文脈

ADR 0023 で、学習の対象を 8 テーマに分け、事例型の分析役を作った。分析の結果をどんな形で、どこに置き、古さと確かさをどう見分けるかは決めていなかった。
2026-10-31 オーナーの指摘:

- 知見を都度足すだけだと、先に足した知見と後から足した知見が矛盾する。追加するときに、過去の知見の更新と形骸化の防止もセットで行える体制が望ましい
- すべての知見を LLM の文脈として使うのではなく、蓋然性が高く繰り返す事象や、明確な線引きで基準を作れるものは、決定論で担保できるようにしたい。その判断をする committee と組にして運用する。学習ループのイベントの完了時に、committee に持ち込んでチェックする構造にする

叩き台（知見の蓄積と委員会、2026-10-31）を作り、決めどころ 5 点をオーナーに出した。

## 決定

1. **置き場は製品のリポジトリ（git）に 1 件 1 ファイル**。`.factory-config/knowledge/K-NNNN.yaml`（1 件 1 主張）、事例記録は `cases/C-NNNN.md`、委員会の議決は `committee/D-NNNN.yaml`、一覧 `INDEX.md` は自動生成。
   最初はフラットに置く。量が増えるので、ディレクトリ構造は委員会がオーナーとして定期的に見直す。知見の使用の記録（エージェントに渡した、その後どうなったか）は git ではなく制御プレーンの events に残す
2. **知見の形は `definitions/knowledge.yaml`**。テーマ・種類・主張・scope・確かさ・根拠・状態・確認日・期限・失効のきっかけ・担保・議決・機密区分。ファイルは消さず状態（draft → active → stale → superseded / retired）だけを変える。id は再利用しない
3. **確かさと期限**: hypothesis（仮説、30 日）、confirmed（確認済み、90 日）、settled（確定、期限なし。決定論で担保されたか規範に取り込まれた）。数値は仮置き
4. **足すときは変更セット**: 新しい知見 1 件には、影響を受ける既存の知見の扱い（直す・置き換える・廃止する・再確認する・そのまま）を必ず添えて 1 本の PR にする。
   CI の決定論の検査（`core-gates/knowledge_check.py`）が緑になってから委員会に持ち込む。検査は、必須項目と値、期限が確かさに合うこと、supersedes と superseded_by の相互参照、置き換えられた知見が active のまま残らないこと、根拠の参照先、個人情報の形、`INDEX.md` が最新であること
5. **委員会は観点別の 4 役**（整合・根拠・担保・反対）。それぞれ別のエージェントで、知見を書いた分析役は入らない（学ぶ側に自分を採点させない）。意見が割れたら人へ。
   開き方は、出来事（事例の分析・束ね・試した結果・棚卸し）ごとの持ち込みと、週 1 の定例。議決は `committee/D-NNNN.yaml` と events に残し、反対意見も消さない
6. **決定論で担保すると決めても知見は残す**。どんな解決策（lint・テスト・型・スキーマ・CI のチェック・設定・overlay のルール）で担保したかを、知見の `enforcement.solutions` に残す。
   委員会は自分で実装しない。担保や改善は Issue にして工場のラインで作る
7. **エージェントに渡す知見は、active かつ confirmed 以上だけ**。確かさと確認日を付けて渡す。settled で決定論の担保が効いているものは渡さない（担保で防げるので、文脈を減らす）。渡した記録は events の `knowledge.used`。
   この経路はワーカーのプロンプトの変更なので、その PR はオーナーの承認を得てからマージする
8. **個人情報は git に一切置かない**。学びの過程の抽象化で切る（「生徒 A さん」ではなく「予約の確定待ちの生徒」）。守りは二重で、変更セットの CI の決定論の検出と、委員会の根拠の担当が見る。
   障害対応などで利用者の情報をどうしても含む知見は、制御プレーンの制限付きの保管先（システムの管理者だけが見られ、読んだ記録を残す）に置く。git 側からは `restricted:R-NNNN` の不透明な id で指すだけにする
9. **承認の線は ADR 0023 のとおり**。委員会の採用で自動でマージしてよいのは、工場が自動で決めてよい作用先のものだけ。新しい用語・業務ルールの定義、役割への指示・ラインの設定・Engine、Blueprint は、委員会の議決を添えて人に回す

## 今あるものとの関係

- ADR 0013 の Lesson は知見（K）に吸収する。overlay のルール（OV）は「担保の実体」の 1 つ（enforcement の checklist / overlay_rule）として残し、`knowledge: K-NNNN` で元の知見を指す。移し替えは別の PR で行う
- ADR 0023 の事例型の分析役の結果（CaseAnalysis）は、事例記録（cases/）と知見の案（hypothesis の draft）の材料になる

## 段取り

1. 定義・検査・本 ADR（#99、済み）
2. 製品に置き場を作り、CI で `knowledge_check.py` を走らせる（製品の CI は Engine の固定した版のこのファイルだけを取る。rally #397、済み）
3. 事例の分析の結果から、知見の変更セットの PR を工場のラインが作る流れ（supervisor の `knowledge_issue_step` が Issue を起票し、implement ジョブが PR を書く。PR は変更種別 `knowledge` で、4 ができるまでは人の承認）
4. 委員会の 4 役の審査と議決の記録、週 1 の定例（出来事ごとの審査は supervisor の `enqueue_committee` とワーカーの `core-gates/committee_review.py`。議決の集め方は `definitions/knowledge.yaml` の `committee.aggregation`。週 1 の定例は続きで）
5. 制限付きの保管先（制御プレーンの DB。管理者だけ）
6. エージェントに知見を渡す経路（オーナーの承認）

## 選ばなかった案

- **制御プレーンの DB に置く**: 変更の差分と履歴を PR で見られない。製品ごとの知識が製品と一緒に動かない
- **知見を都度足すだけ**: 先の知見と後の知見が矛盾し、古い知見が残り続ける
- **委員会を 1 役にする**: 整合・根拠・担保・反対の観点が 1 つの判断に混ざり、反対意見が残らない
- **すべての知見をエージェントの文脈に入れる**: 文脈が太り続け、確かでない知見も同じ重みで効く
